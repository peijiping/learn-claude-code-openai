## 一、需求（原文）

1. 对话界面上**实时显示子智能体的流式输出**（思考、工具调用过程）。
2. **会话切换之后，子智能体的过程能正确回显在历史对话中**。
3. 现状反馈：「子智能体的执行过程并未存储在对话记录中」。

## 二、结论先行

| 判断 | 结论 |
| --- | --- |
| 是否"完全没实现" | **否**。链路上已有代码：后端会写 `role=subagent` 行、`ws_bridge._history_to_ui` 会挂载、前端有 `SubAgentBlock` 卡片可渲染 |
| 是否"能正常工作" | **否**。属于"半成品 + 时有时无 + 存下来也是残缺" |
| 最严重的问题 | **子智能体记录被写入 assistant/tool 块中间，导致下次加载时整轮消息被自愈逻辑删除（已复现，不可逆）** |
| 为什么"反复修补没实现" | 根因是**结构性耦合**：`role=subagent` 行与标准消息混在同一个 jsonl 里，append 顺序成为事实契约；自愈、压缩、孤儿清理任何一处改动都会破坏它。补丁越加越多，耦合面越脆 |

## 三、现状勘查（证据）

### 3.1 已实现的链路（三层都有代码）

- **采集**：`agents/subagent.py` 用 `FilterSink` 把子智能体的 `thinking_delta / tool_call_start / tool_call_delta / tool_call` 打上 `subagent_id` 转发给父 sink，同时用 `CallbackSink` 旁路收集 → `_build_transcript()` 聚合成 `{subagent_id, name, thinking, toolCalls}`。
- **落盘**：`agent_full_v2._run_subagent()` 拿到 `(summary, transcript)` 后按 `tool_call_id` 暂存，并调 `session_manager.append_subagent_to_session()` **立即**追加一行 `role=subagent`；`_persist_pending_subagent_rows()` 在每轮工具回放后兜底补写。加载时 `Agent._strip_subagent_rows()` 把它挡在模型上下文之外。
- **回放**：`ws_bridge._history_to_ui()` 按 `tool_call_id` 把 `role=subagent` 行挂到发起它的 assistant 消息下；前端 `agentStore.historyToMessage()` 映射为 `subagents[]`，`MessageItem.SubAgentBlock` 渲染折叠卡片。

### 3.2 实测数据（`~/.aigent/projects/default/.chathistory/`）

session_2.jsonl  {system:1, user:1, assistant:3, tool:3}   tools: {..., 'sub_agent': 1}   subagent 行: 0   ← 缺
session_3.jsonl  ...                                       tools: {..., 'sub_agent': 1}   subagent 行: 1
session_4.jsonl  ...                                       tools: {..., 'sub_agent': 1}   subagent 行: 1
session_5.jsonl  {system:1, user:5, assistant:5}                                          subagent 行: 0   ← 本次无子智能体
session_6.jsonl  ...                                       tools: {..., 'sub_agent': 1}   subagent 行: 1

**session_1 / session_2 的子智能体确实执行过（tool 结果里是 `[Background task bg_0001 started]`），但对话记录里没有任何执行记录** → 「没存储」的现象成立，且是**间歇性**的。

### 3.4 六个已确诊缺陷

#### D1（致命）写入位置错误 → 整轮消息被自愈逻辑删除

`agent_loop` 的落盘顺序是：`assistant(tool_calls)` → 执行工具 → 回放 `tool` 结果。而**同步**子智能体在"执行工具"阶段就 `append` 了 `role=subagent` 行，于是磁盘上变成：

```
assistant(tool_calls=[sub_agent])
role=subagent          ← 插在中间
role=tool
```

下次加载时 `load_session_history` → `_sanitize_orphan_tool_calls()`：
- 扫描到 `assistant(tool_calls)` 后，`while messages[j].role == "tool"` 立刻被 subagent 行打断 → `found_ids ≠ expected_ids` → **整条 assistant 消息被丢弃**；
- 继续走到 `tool` 行，`prev` 是 subagent 行 → 判定为"孤儿 tool 消息" → **tool 结果也被丢弃**；
- `needs_rewrite = True` → `save_session_history()` **原子重写文件**，删除不可逆。

用真实代码最小复现（临时目录、不触碰任何真实会话）：

```
--- 加载前磁盘行 ---      system / user / assistant / subagent / tool / assistant
[会话修复] 丢弃孤儿 assistant 消息 （缺失 tool 响应: ['call_A']，丢弃错位 tool 消息: 0 条）
[会话修复] 丢弃孤儿 tool 消息 （缺少匹配的 assistant.tool_calls，tool_call_id='call_A'）
[会话修复] 已丢弃 2 条孤儿消息并写回历史文件
--- 加载后内存 ---        system / user / subagent / assistant      ← 一轮对话凭空消失
--- 加载后磁盘 ---        system / user / subagent / assistant      ← 已重写，不可逆
```

> 这条同时解释了另一类困扰：「切会话后消息变少 / 报 400 orphan」——**它和子智能体记录是同一个 bug 的两面**。仓库里那份未提交的 `_sanitize_orphan_tool_calls`「反向清理孤儿 tool」补丁，正是在追这个症状，但没有触到根因，反而扩大了删除面。

#### D2（重要）落盘时机依赖进程存活

- 后台子智能体：`role=subagent` 行由 `BackgroundManager` 的**守护线程**在子智能体跑完后写入。App 关闭、进程被杀、子智能体仍在跑 → **永远不会有记录**（session_1/2 即此类）。
- 同步子智能体：写入发生在中途，位置错误（见 D1）。
- 没有任何"已开始但未完成"的痕迹，用户重开 App 后无法得知"这里曾经跑过子智能体、卡在哪一步"。

#### D3（重要）transcript 的工具状态配对错误

`subagent._build_transcript()` 处理 `tool_call`（完成）事件时，标记的是 `tool_calls[-1]`，**不按 `tool_id` 匹配**：

```python
elif ev.type == "tool_call" and tool_calls:
    t = tool_calls[-1]          # ← 应为本事件 tool_id 对应的那一条
    t["status"] = "done"
```

一次响应里模型并行发起 7 个工具调用时：先来 7 个 `tool_call_start`（追加 7 条），流结束后一次性来 7 个 `tool_call`（每次都标记**最后一条**）→ 前 6 条永久 `running`。**与 session_6 实测的 6/7 running 完全吻合**。

#### D4（重要）transcript 缺内容

`FilterSink(types={"thinking_delta","tool_call","tool_call_start","tool_call_delta"})` 主动丢弃了 `content_delta`，且 `_build_transcript` 不记录：

- 子智能体**自己的答复正文**（用户最想看的东西）→ 回放只剩工具骨架；
- 每个工具调用的**结果/错误**（只看得到参数）；
- `status`（done/error/aborted）、`started_at/ended_at/duration`、`workdir`、`allowed_tools`、`error`。

#### D5（体验）实时挂载点与回放挂载点不一致

| 场景 | 卡片挂在哪 |
| --- | --- |
| 实时（后台子智能体） | `turn_end` 已把上一条 assistant 置为 `streaming=false`，`sub_agent_start` 到达时 `ensureAssistant()` **新建一条空 assistant 气泡**装在末尾 |
| 回放 | 后端按 `tool_call_id` 挂到**发起 sub_agent 的那条 assistant 消息**下 |

实测确认回放挂载正确（session_6 → `ui[2]`，即带 `sub_agent` tool_call 的那条）。两者规则不同 → **切换会话后卡片位置跳变**，看起来像"多出来一块/少了一块"。

#### D6（结构性根因）记录与消息流共用同一个 jsonl

`role=subagent` 行不是标准 OpenAI 消息，却和标准消息共享 `session_N.jsonl` 与 append 顺序，导致它与至少四条既有机制耦合：

1. `load_session_history` 的拼行修复与自愈重写；
2. `_sanitize_orphan_tool_calls` 的块结构扫描（D1）；
3. `compact_messages_if_needed` → `save_session_history` 的"重写 + 回写 subagent 行"（还依赖进程内 `subagent_rows` 缓存，跨进程可失效）；
4. `error_recovery` 的截断/异常重写路径。

**任何一条的改动都会破坏另外几条**——这就是"别的智能体反复修补却没实现"的结构性原因。继续在这个面上打补丁，只会继续输。

### 4.1 目标（验收标准，可测）

| # | 验收项 | 判定方式 |
| --- | --- | --- |
| A1 | 实时：主对话执行期间，子智能体的思考与工具调用在聊天界面增量出现，卡片归属在「发起 sub_agent 的那条 assistant 消息」下 | 目视 + 与回放位置一致 |

- 不做子智能体的「多卡片并列/树形嵌套」等复杂 UI；不引入新的 LLM 调用。
- 不改变 `sub_agent` 工具的对外契约（prompt / allowed_tools / workdir / run_in_background）。
- 不重写会话压缩算法。

## 五、方案选型

| | 方案 A：旁路记录文件（推荐） | 方案 B：就地规范化 in-file 行 |
| --- | --- | --- |
| 数据位置 | 新增 `session_N.subagents.jsonl`（append-only，与主 jsonl 同目录） | 仍写 `session_N.jsonl` 的 `role=subagent` 行 |
| 与压缩/自愈/异常恢复 | **天然隔离**，互不影响 | 需在 4 条既有机制里逐处兼容（D6 未消除） |
| 写入位置错误（D1） | 不再产生 | 需引入"批次写完后再落盘 + 加载时按 anchor 归位"的复杂约束 |
| 崩溃留痕（D2/A4） | 起止两段式 append，天然支持 | 可做，但会进一步复杂化块结构扫描 |
| 改动面 | ws_bridge / session_runtime（桌面层）+ 前端 + session_manage 一处保守加固 | agent_full_v2 / session_manage / subagent / ws_bridge 全动 |
| 旧数据 | 一次性迁移（in-file 行 → 旁路文件） | 原地兼容 |
| 风险 | 需处理迁移与文件生命周期 | **高风险**：继续在耦合面上加约束，回归面大 |

**推荐方案 A**。理由：本需求当前最大的敌人不是"功能没写"，而是"记录与消息流抢同一个文件"。物理隔离是唯一能一次性终结 D1/D6 的选择；同时它把改动压回桌面层（`ws_bridge`/`session_runtime`）与前端，符合仓库的 thin-layer 铁律。

## 六、方案 A 详细设计

### 6.1 数据模型：旁路记录文件

路径：`<chat_history_dir>/session_<N>.subagents.jsonl`（与 `session_<N>.jsonl` 同目录、同前缀，随会话号绑定）。

每行一条 JSON（**append-only**）：

```json
{
  "v": 1,
  "subagent_id": "sub_fd620688",
  "tool_call_id": "call_00_axgKcZATizLVFshauwhQ9317",
  "session_num": 6,
  "name": "读取 DRG_Docs 下全部 PDF",
  "status": "running | done | error | aborted",
  "source": "sync | background",
  "prompt": "……",
  "workdir": null,
  "allowed_tools": null,
  "started_at": "2026-09-11T09:31:02+08:00",
  "ended_at": "2026-09-11T09:33:41+08:00",
  "duration_ms": 159000,
  "thinking": "……完整思考……",
  "text": "子智能体最终答复正文",
  "toolCalls": [
    { "tool_id": "call_1", "name": "run_read_pdf", "args": "{...}",
      "status": "done", "result_preview": "前 200 字…", "error": "" }
  ],
  "error": ""
}
```

**加载规则**：读取全部行 → 按 `subagent_id` 分组 → **取每组最后一条**（后写覆盖先写）。因此"起始占位行 + 结束完整行"天然合并为最终态；进程被强杀时只剩起始行，卡片显示"运行中/已中断"。

### 6.2 写入路径与时序

| 时机 | 动作 | 目的 |
| --- | --- | --- |
| 子智能体启动 | append `status=running` 占位行（`subagent_id / tool_call_id / name / prompt / started_at`） | 崩溃留痕（A4）；实时回放时可立刻看到卡片 |
| 每个工具调用完成（可选，P1） | append 增量行（同 `subagent_id`，仅带新增 toolCall） | 长任务中途也能看到进展 |
| 子智能体结束 | append 完整行（`status=done/error/aborted`，含 thinking / text / toolCalls / 耗时） | 终态覆盖 |
| 会话清空 | 删除旁路文件 | A6 |
| 会话进回收站 / 还原 | 与主 jsonl 同步移动/还原 | A6 |
| 会话彻底删除 | 删除旁路文件 | A6 |

**关键**：主 `session_N.jsonl` 从此只写标准消息，`role=subagent` 行**不再产生**（新数据）。

### 6.3 写入实现接缝（thin-layer 友好）

现有代码已有一个完美的挂载点：`SessionManager.append_subagent_to_session(session_file, transcript)` —— 它收到的是**完整 transcript（含 `tool_call_id`）**。桌面层只需在拿到 Agent 实例后替换这一个方法：

```python
# ws_bridge（示意）
def attach_sidecar(agent, session_num: int) -> None:
    sm = agent.session_manager
    def _write(session_file, transcript) -> None:
        sidecar.append(session_num, transcript)   # 写 session_<N>.subagents.jsonl
    sm.append_subagent_to_session = _write        # 主 jsonl 不再被写入 subagent 行
    agent._subagent_persisted.clear()             # 让 _persist_pending_subagent_rows 仍会调用我们
```

- `agent_full_v2` 内的 `_persist_one_subagent_row` / `_persist_pending_subagent_rows` 逻辑**无需改动**，它们只管调用，落到哪里由桌面层决定。
- 起始占位行需要"子智能体开始"这一时刻。两种取法（按可授权范围二选一）：
  - **P0（零 interior 改动）**：在 `WSSink.send_func` 里拦截 `sub_agent_start` 事件 → 拿到 `subagent_id`，配合"当前正在执行的 `sub_agent` tool_call_id"（由桌面层包装 `Agent._run_subagent` 时用 thread-local 记录）写入占位行；
  - **P1（更稳，1 行签名增量）**：给 `SubAgent.spawn_subagent()` 增加可选参数 `tool_call_id: str = ""`，`_emit_sub_agent("sub_agent_start", subagent_id, ...)` 的 `StreamEvent` 随之带上 `tool_call_id`，并把该字段写入 transcript。桌面层无需猜测，直接落盘。

### 6.4 实时流协议变更

`docs/frontend/03` 的事件线协议需同步（**只增字段，不改既有语义**）：

| 事件 | 变更 |
| --- | --- |
| `sub_agent_start` | 新增 `tool_call_id`（P1）；`name` 直接给已裁剪的任务名，不要前端再截 |
| `thinking_delta`（带 `subagent_id`） | 不变 |
| `tool_call_start/delta`（带 `subagent_id`） | 新增 `tool_id` 的稳定映射（现在已带，前端需按 `tool_id` 归位而非"最后一个 running"） |
| `content_delta`（带 `subagent_id`） | **新增上行**：子智能体的答复正文也开始流式（只进子智能体卡片，不进主正文，避免与主智能体摘要重复） |
| `sub_agent_end` | 新增 `status`（done/error/aborted）、`duration_ms`，可选 `text`（终止时的正文兜底） |

后端改动点：`subagent.py` 的 `FilterSink(types=...)` 加入 `content_delta`；`_build_transcript` 按 `tool_id` 配对（修 D3）并补 `text` / `error` / 耗时（修 D4）。

### 6.5 前端：唯一锚点规则（修 D5）

**规则：子智能体卡片永远挂在「发起它的那条 assistant 消息」下**，实时与回放共用同一条规则。

实时侧的锚点获取（**纯前端，零后端依赖**）：

1. `applyAgentEventBuffer` 收到 `tool_call_start` 且 `tool_name === 'sub_agent'` 时——**不再直接 `return msgs` 丢弃**，而是把 `{tool_id, assistantMsgId}` 记入本会话的 `subCallAnchors`（`assistantMsgId` = 此刻正在流式的那条 assistant）；
2. `sub_agent_start` 到达时，用 `subagent_id` 建立 `subagent_id → assistantMsgId` 映射，卡片直接挂到该 assistant 上（**无论它是否还在 streaming**）；
3. 兜底顺序：`subagent_id → tool_call_id`（P1 后有）→ 该 assistant 下已有 `subagent` tool_call 的消息 → 末尾新建气泡（仅在会话已被回放替换、锚点丢失时）。

回放侧沿用后端 `_history_to_ui` 的 `tool_call_id` 挂载（已实测正确），仅需改为从**旁路文件**读取记录。

同时修掉前端按"最后一个 running"归位的写法（`tool_call_start` 的 `hasRunning` 守卫与 `tool_call` 的 `tool_id` 匹配需一致），否则并行工具调用同样会错位。

### 6.6 加载自愈加固（必修，独立于本需求）

`session_manage._sanitize_orphan_tool_calls` 必须改为**保守策略**：

1. 判定块结构前，先把 `role=subagent` 行从视图中剔除（或直接跳过连续扫描），**绝不允许它打断 tool 块的连续性判定**；
2. 缺失 tool 响应时，**补齐占位 `tool` 消息**（`"Error: missing tool result (recovered)"`）而不是"丢弃 assistant 及其 tool 结果"——避免任何情况下的静默数据删除；
3. 重写改为"仅在确有修复动作时"，且写入前保留 `.bak` 快照。

> 说明：这会触碰 `session_manage.py`（引擎层），但它是**与是否做本需求无关的数据安全 bug**（D1 的复现已证明会删除整轮对话）。若坚持不动引擎，唯一替代是"一次性迁移旧数据后，永不再让 in-file 行进入该函数"——但历史损坏文件仍无解，不推荐。

### 6.7 旧数据兼容与迁移

一次性、幂等（在 `SessionManager` 初始化或首次加载某会话时触发）：

1. 读取 `session_N.jsonl`，抽出所有 `role=subagent` 行 → append 到 `session_N.subagents.jsonl`（按 `subagent_id` 去重）；
2. **主 jsonl 原地重写为纯标准消息**（去掉 subagent 行）；
3. 写 `session_N.subagents.migrated` 标记避免重复执行。

效果：老会话照常回显；同时消除"in-file 行继续引发 D1"的可能。**注意**：已经被 D1 删除的历史轮次无法恢复，这一点需在评审时明确。

### 9.1 自动化（新增 `tests/test_subagent_sidecar.py`，全部离线、不调真实 LLM）

5. 回归：不再出现 `[会话修复] 丢弃孤儿 assistant 消息` 日志；不再出现 400 orphan 报错。

### 12.5 崩溃回归修复：子智能体一跑完就 TypeError（2026-09-11 追加）

**现象**（用户实测 session_1，`title=用子智能体查看PDF内容`）：

```
[session 1] bg followup turn #1
[background done] bg_0001: 请读取目录 …/WorkSpace/… (46 chars)   ← 结果其实是错误串
[subagent] 开始执行任务 (all child tools): 请读取目录 …
[subagent] 结束 (14.2s): 请读取目录 …
[session 1] bg followup crashed: TypeError: 'str' object is not callable
```

**根因**（`agents/subagent.py`，纯变量遮蔽，与旁路存储设计无关）：

```python
def _finish(summary, err=""): ...          # ① 收束闭包（耗时/状态/正文）
...
sub_msg, _finish, _usage = streamed_create(...)   # ② 第二个返回值是 finish_reason（str）
```

`streamed_create`（`streaming_client.py`）的返回契约是 `(message, finish_reason, usage)`。
②把 ①的闭包**覆盖成了字符串**，于是子智能体跑完第一轮工具、进入收束分支时调用
`_finish(...)` 立刻抛 `TypeError: 'str' object is not callable`。

**为什么会连锁成"后台任务报错 + 卡片永久转圈"**：

1. `spawn_subagent` 抛异常 → 异常逃逸出工具层 → 主智能体这一轮 turn 直接崩
   （表现为 `bg followup crashed`）；
2. 异常逃逸意味着**终态 transcript 永远拿不到** → `SubagentStore` 里只剩
   `session_runtime._bind_sink` 在 `sub_agent_start` 时写的 `running` 占位行
   → 卡片永久"执行中"（实测 session_1 两条记录 `status=running`、`ended_at=null`）；
3. 后台路径下 `BackgroundManager.worker` 把异常串当结果收下
   （`Error: TypeError: 'str' object is not callable` = 46 chars），
   主智能体收到 task_notification 后发现"报错"，于是**原样重试一遍**——
   重试必然同样失败，白烧一次 14s 的子智能体调用。

**修复**（`agents/subagent.py`，两处，均属"采集完整性"范围）：

1. 解包改名：`sub_msg, finish_reason, _usage = streamed_create(...)`，不再遮蔽 `_finish`；
2. 给 `spawn_subagent` 加**兜底 except**：任何未预期异常都收束成
   `_finish(error_msg, err=error_msg)` 正常返回（`status=error` + `error` 文本），
   绝不让异常逃逸。这样即便将来再出类似缺陷，症状也降级为
   "卡片显示失败原因、主智能体拿到工具错误继续跑"，而不是
   "整轮 turn 崩溃 + 卡片永久转圈 + 盲目重试"。
   `BaseException`（ESC 中断 / KeyboardInterrupt）不在此兜底，中断语义不变。

**回归测试**（`tests/test_subagent_sidecar.py` 新增 `TestSpawnSubagentContract`，4 例离线用例，
全套 18 → **22 例全绿**）：

| 用例 | 断言 |
| --- | --- |
| `test_plain_answer_returns_summary_and_transcript` | 模型只回正文（无 tool_calls）时返回摘要 + `status=done` 的 transcript，不再抛 TypeError |
| `test_unexpected_exception_becomes_error_transcript` | 内部未预期异常 → 返回 `status=error`、`error` 含异常类型，`text` 留空 |
| `test_api_failure_keeps_error_status` | `streamed_create` 抛异常仍走原 `子智能体 API 调用失败` 分支 |
| `test_end_event_emitted_on_both_paths` | 正常/异常路径都发 `sub_agent_end`（前端收折叠、停转圈） |

**历史数据处置**：session_1 两条卡在 `running` 的旁路记录已按"两段式"设计**追加**终态行
（`status=error` + 真实原因），主会话文件 `session_1.jsonl` **未改动**；
若前端仍显示旧态，切换会话重新回放即可。

## 附录：后台子智能体执行期间"前端状态断连"修复（2026-09-12）

### 现象（用户报告 + E2E 复现）

后台子智能体（`run_in_background=true`）执行过程中，前端卡片完全冻结——
工具行全部显示"完成"、无任何进展；直到主智能体续轮开始输出时，卡片状态
才"回来"（直接跳到终态）。Playwright + DOM MutationObserver 实测（session_4）：
**后台执行窗口内 10.7 秒零 DOM 更新**。

### 根因（两层叠加）

1. **工具执行阶段零事件**：`spawn_subagent` 的事件全部产生于 LLM 流式阶段
   （`thinking_delta` / `tool_call_start` / `tool_call_delta` / `tool_call`）与任务
   生命周期（`sub_agent_start` / `sub_agent_end`）。而工具**真正执行的循环**
   （往往是最耗时的部分，如批量读 PDF ≈ 10s+）一个事件都不发。
2. **工具状态提前标 done**：`consume_stream` 在**流聚合完毕**时发 `tool_call`
   （完成态）事件——此刻参数刚拼完、工具尚未执行。前端据此把工具行标成
   done，于是整个执行窗口内卡片呈现"全部完成但还在转圈"的矛盾冻结态。

### 修复

- **后端 `agents/subagent.py`**：工具执行循环内、handler 调用前后，经
  `_emit_sub_agent` 直达父级 sinks 发 `tool_exec_start` / `tool_exec_end`
  （携带子智能体内部 `tool_id` / `tool_name`，事件自带 `subagent_id`，
  无需 FilterSink 打标）。`_emit_sub_agent` 签名扩展 `tool_name` / `args` 参数。
- **前端 `agentStore.ts`（applySubagentEvent）**：新增两个 case——
  `tool_exec_start` 按 `tool_id` 把工具行拨回 `running`（不存在则补建一行）、
  `tool_exec_end` 置回 `done`；`agentProtocol.ts` 同步扩展 `StreamEventType`
  与 `isKnownAgentEvent`。
- **旁路 transcript 不受影响**：`_build_transcript` 忽略未知事件类型，
  工具行仍按流式事件闭合为 done。

### 验证

| 层级 | 结果 |
| --- | --- |
| 后端离线复现（`scripts/repro_bg_subagent_events.py`） | 后台窗口内事件流含 `tool_exec_start/end` 成对出现 |
| 前端 store 回放（`frontend/scripts/replay_frontend_store.mjs`） | 卡片工具行 running→done 流转正确，终态 done |
| 后端回归（unittest 78 例） | 全绿（新增 `test_tool_execution_emits_exec_lifecycle_events`） |
| 前端 typecheck | 通过 |
| E2E（Playwright + MutationObserver，session_5） | 后台执行窗口内每个工具执行均有 DOM 更新（running→done 逐个可见）；卡片在后台窗口内即达终态，早于续轮 |

**遗留（有意保留）**：子智能体最后一次 LLM 调用（生成返回摘要）期间，
因"不转发 content_delta"的设计，DOM 无逐字更新，卡片仅以转圈指示等待——
语义明确（正在生成），不属于断连。
