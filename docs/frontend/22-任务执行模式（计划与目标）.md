## 一、概念

### 1.1 两条正交的轴

```
权限轴（既有，本次未改一行）    permission_mode ∈ { default, full_access }
    └ 回答：这个操作「允不允许 / 要不要审批」        ← 规则级，逐条命令判

执行模式轴（本期新增）          execution_mode ∈ { normal, plan, goal }
    └ 回答：这一轮任务「以什么方式干」              ← 模式级，整体行为约束
        normal = 什么都不显示（默认，行为与改造前逐字节一致）
        plan   = 先出方案，未经批准不得改动系统
        goal   = 朝一个明确的目标反复推进直到达成
```

两条轴**可以任意组合**，互不遮蔽：

| 组合 | 语义 |
| --- | --- |
| `default + normal` | 常规：写操作走权限链，危险命令弹审批卡片 |
| `full_access + plan` | 免审批，但计划模式下**写操作照样被拦**（模式级限制不被权限档位越过） |
| `full_access + goal` | 免审批地朝目标死磕 |
| `default + goal` | 朝目标推进，写操作仍按规则级逐条判 |

### 1.2 三种模式的语义

**normal**：默认值。`execution_mode` 为 `None`（存量会话）与 `"normal"` 完全等价 —— 读路径
一律 `.get()` + `or "normal"` 兜底，**零迁移**。

**plan（计划模式）**：只读探索 → 产出计划文书 → 等用户批准 → 才能写。核心承诺是
**「批准前零副作用」**（连 `write_memory` 都拦，见 §3.4）。

**goal（目标模式）**：朝用户给定的完成条件反复推进。**完全复用既有目标能力** —— 评估器、
Stop 边界七分支判定、`[Goal still active]` 回注通道**一行不改**，本期只把它接到执行模式轴上
（详见 §8）。

### 1.3 分层关系（三条轴的职责边界）

| 层 | 回答的问题 | 本次改动 |
| --- | --- | --- |
| 权限管控（17 篇） | 这个操作「允不允许 / 要不要审批」 | **不动**（`permission.py` 一行不改） |
| 沙盒（20 篇） | 命令在 OS 层「实际能碰什么」 | 不动 |
| **执行模式（本篇）** | 这一轮任务「以什么方式干」 | 新增 |

三层是**互补的三道闸**，任一道拦下都走同一个 tool_result 回填契约（模型看到一段可行动的
文案、本轮继续）。判定顺序（自严到宽）：**plan 守卫（模式级）→ 权限判定（规则级）→ 沙盒
（执行期）**。plan 模式下被拦下的命令集合**本就是权限链 allow 集合的真子集**，所以先拦模式
不会掩盖任何硬拒绝语义 —— 反而给模型的信息更可行动（「改用 plan_write 提交计划」而不是
「命令不在白名单内」）。不变量写死在 `execution_mode.py` 的模块注释里并有测试守护：

> **plan 的放行集合 ⊂ 权限链的 allow 集合。**

## 二、状态机与切换规则

### 2.1 plan 的完整生命周期

```
点「计划模式」→ mode=plan（守卫生效）
      ↓
只读探索（run_read / run_glob / 只读 bash / ask_user / 技能与任务查询）
      ↓
调 plan_write 写计划文书 → plan_status=ready
   → 落到 <工作空间>/.aiagent/plan/<模型命名的名字>.md
   → 推 execution_mode_changed（带 plan_status="ready" + plan_path）→ 再推 plan_ready
      ↓
前端渲染计划卡片（正文经 plan_read 拉取）+ **自动在右栏打开该文书**
      ├─ 开始执行：plan_approve
      │            → plan_status=approved + mode 回落 normal
      │            → 注入「[计划已批准] …」续跑指令（用户可见的 user 消息）
      │            → 空闲则自动起一轮执行（忙 / 有待答提问 → 只落状态 + toast 提示）
      │            → 撤胶囊 tag、卡片转只读态
      │            → ⚠ 同时注入**撤销提醒**（见 §5）
      ├─ 继续修改 / 其他（就地输入框）：作为一条**用户消息**发出 → plan 保持
      │            → 模型重新产出文书（覆盖本会话那一份）→ 重推两张信封 → 卡片就地更新
      └─ 暂不执行先看方案：只开右栏 + 一句状态说明，**不发任何命令**（plan 保持）
点胶囊 × → 清 plan 状态 + mode=normal → 推信封（卡片壳一并撤销，见 §7.5）
```

**已知边界（刻意不做，写进系统提示词的退出口）**：plan 模式**没有迭代上限**，只能由用户
手动关闭（点胶囊 × 或批准）。为免"模型只回文本、不调 `plan_write`"时双方互等，
`PLAN_ACTIVE_REMINDER` 里给了一句退出口：「若当前任务不适合产出计划（例如只是问答或诊断），
请直接说明原因并请用户关闭计划模式，不要反复尝试写操作。」

### 2.2 goal 的完整生命周期（薄委托）

```
点「目标模式」（2026-09-30 起**不弹框**）→ 记"武装位" → 用户写下第一条指令
      ↓
该条指令随 `chat` 一起到后端（`exec_mode=goal` + `exec_condition=指令正文`）
后端在**派发 turn 之前**落地（此时才有条件、且还没 rt.busy，见 §2.6）：
【既有】GoalController.set_goal(condition, total_tokens)     ← 非法条件抛 GoalError
【新增】追加一条 [Goal set] 消息（与 Stop 边界 block 消息同族，见 §5.3）
【新增】gate 记 mode=goal（**仅作 UI 投影**）→ 落 meta → 推 execution_mode_changed
      ↓
正常干活；每轮无工具调用时由【既有】Stop 边界 evaluate_after_turn 裁决：
   block   → 【既有】[Goal still active] 回注，回环继续            → mode 保持 goal（tag 不撤）
   defer   → 【既有】后台在跑，本轮结束（目标保持激活）             → mode 保持 goal
   limit   → 【既有】连续 block 超上限强制结束（目标保持激活）       → mode 保持 goal
   error   → 【既有】评估器出错（目标保持激活）                     → mode 保持 goal
   achieved → 【既有】控制器内部已清 active
   failed   →   ＋【新增】mode 回落 normal + 落 meta + 推信封（撤 tag）
用户点胶囊 × → 【既有】clear_goal() ＋【新增】mode 回落 normal + 落 meta + 推信封
```

**新增代码总量**：一个薄委托入口 + Stop 边界一个 4 行方法（`achieved`/`failed` 共用）+
meta 读写 + （2026-09-30）`chat` 里"派发前落地"那一段。**不新增状态机、不新增评估器调用、
不新增任何 goal 判定分支。**

> **历史形态（2026-09-25 ~ 09-30）**：点「目标模式」→ 弹 `GoalInputDialog` 填完成条件 →
> 提交后发 `session_exec_mode(mode=goal, condition=…)`。用户反馈"还要先弹框填条件太啰嗦，
> 点了就直接进目标模式、我第一条指令就是目标"，2026-09-30 改为上面的形态（见 §2.6）。
> `session_exec_mode` 命令**保留**，但不再是 goal 的常规入口。

### 2.3 跨模式切换规则（2026-09-27 改：**直接切换**）

- **任一时刻至多一个模式激活**，但 plan ↔ goal 之间**可以直接切换**，不再要求
  "先关闭再切换"。
- **前端**只是分发层：异模式点击**直接进入**（plan 发命令即时生效；goal 只记**武装位**，
  条件由下一条指令给出，见 §2.6），同模式重复点击直接 `return`（幂等短路，少一次往返）。
  **不再**有"请先关闭…"的 toast 预检（`agentStore.switchExecMode` 与 `InputBox.handlePlusPick`
  两处一并删除）。
- **后端 `Agent.set_execution_mode()` 是唯一权威**：
  - 切 `plan`：有激活目标 → 转发**既有** `clear_goal("switched to plan mode")`
  - 切 `goal`：处于 plan / 有文书状态 → `ExecutionGate.clear_plan()`——**只清内存态与
    meta 的 `plan_status` / `plan_name`，工作空间里的文书文件保留**（下次在 plan 模式
    产出即覆盖；见 §4.5 的生命周期表），随后走既有 `set_goal` + `[Goal set]` 消息
  - 切 `normal`：goal → 转发**既有** `clear_goal()`；plan → 清 plan 状态
  - 同模式重复 = **幂等成功**（不改状态、不发广播）—— 尤其不重置 `plan_status`
- **为什么"直接切换"不等于"静默清"**（原设计的顾虑如何被消解）：
  1. 动作由用户**点选显式触发**，不存在"顺手点一下目标就没了"；
  2. 胶囊 tag 随 `execution_mode_changed` 广播**即时熄掉**，UI 无残留；
  3. 模型侧由 `_sync_execution_mode()` 的**两态注入**告知（plan → goal 走
     `PLAN_EXITED_TO_GOAL_REMINDER` 那一版文案，见 §5）；
  4. 文书**文件不删**，只在内存/meta 里失去"待批准"语义。
  > **历史形态（已废弃，2026-09-25 ~ 09-27）**：前端 toast「请先关闭{计划|目标}模式」
  > 且**不**发起切换，后端另在 `Agent.set_execution_mode` 与 `session_exec_mode`
  > 未跑分支各设一道互斥拒绝。原权衡是"可预期优于静默替换"，2026-09-27 被用户否掉：
  > 切模式本身就是明确意图，"先关闭再切换"是多余的两步操作。
- 仍会经 `error` 信封回前端的**只剩两类**：goal 条件非法（空 / 超 `MAX_GOAL_LENGTH`，
  仅"手改 payload"或老客户端还能触发 —— 桌面端点选路径已改走 §2.6 的"派发前落地"，
  那里非法条件是**静默忽略**而不是回 error）、会话不存在。`agentStore` 的 `error` 分支
  本就是无差别全局 toast，与这两类语义相称。
  注意 `permission_config_save` 曾**刻意避开** error 信封（怕误 toast、该页约定是内联
  报错）—— 本场景不属于那一类，用 error 是**对的**。
- 未跑会话（选中的会话还没构造 Agent）**同口径**：`session_exec_mode` 直接把被让位
  那一方的 meta 字段写空（切 plan 时 `goal_condition=None`，切 goal 时
  `plan_status=None`），不再读投影判互斥。

### 2.4 线程模型与 `rt.busy` 约束（评审 P1-5）

| 组件 | 是否有锁 | 结论 |
| --- | --- | --- |
| `ExecutionGate` | **自带 `threading.Lock`**（状态访问全持锁） | plan 切换**可以在 turn 进行中即时生效** —— 守卫是"每次工具调用现场读 gate"，在途轮的后续 tool_call 立即受新模式约束 |
| `GoalController` | **没有任何锁**（对比 `PermissionGate` 自带锁） | goal 的进入/退出**不允许在 `rt.busy` 时进行**（命令走 `asyncio.to_thread`，`agent_loop` 在工作线程读同一对象 → 跨线程竞争） |

`rt.busy` 的守卫**放在 `ws_bridge`**（Agent 不知道 busy 这个概念，`set_execution_mode` 的
docstring 明确记录了这一点）。判定口径：**「当前模式或目标模式涉及 goal」且本会话 turn 在跑
→ 一律拒绝**并提示「该会话正在执行，请先停止或等本轮结束后再切换目标模式」。

> **实施期取舍**：方案文档给的是"排队到本轮结束**或**给控制器加锁"二选一。实现取**拒绝**
> —— 排队需要在本轮结束时找回被挂起的意图（要新加一处收尾钩子），而 `GoalController` 加锁
> 属于改既有引擎层。拒绝是零新增状态、零引擎改动的方案，且用户看到明确提示可自行重试。

`plan_approve` 的续跑也有 busy 守卫（两条，超集关系）：

1. `rt.busy` → 只落状态 + toast「计划已批准。当前回合结束后请再发一条消息开始执行」；
2. `rt.has_pending_interaction()`（有等待作答的 `ask_user`）→ 同样只落状态 + 提示先作答。

⚠ `rt.start_turn` **自身没有 busy 守卫**（既有 `chat` 分支的守卫在调用方），新分支必须自己判 ——
两线程同写会话 jsonl 是项目里的既有禁忌。

### 2.5 无会话态（评审 P1-7 → 2026-09-27 改版）

`+` 菜单**恒渲染**（"新建任务"态也能点），而无会话时没有会话可挂模式。**两项在任何
情况下都必须可点**（用户要求，2026-09-27）—— 原"置灰 + 提示请先发消息"的方案作废：

- **前端**：无会话时点选记为 **`pendingExecMode` 草稿**（store 级，见 §7.5），
  胶囊 tag 立即显示该草稿（零幻觉：它不是"会话态"，是"待落地的意图"）。
  `switchExecMode` 无会话分支只写草稿并 `return`（**不 toast、不发命令**）。
  草稿**不跨新任务继承**（`newSession()` 重置为 `normal`）：执行模式是会话级状态、
  无继承源，带过去等于让用户在下一条任务里"莫名开着计划模式"（对照权限档位 ——
  它有"本空间新会话默认档位"的产品含义，故有继承链；模型选择同理继承，那是第三条轴）。
- **交接点**：草稿随首条消息经 **`chat` 命令的 `exec_mode` / `exec_condition`**
  交给后端，后端在**建会话时**（`if sid is None` 分支内）写进该会话 meta。
  ⚠️ **不能**等 `session` 信封回来再发 `session_exec_mode`：那时 turn 已经派发、
  `rt.busy=True`，goal 会被 §2.4 的守卫直接拒掉（plan 侥幸能过，但会有"首轮工具
  调用已在 normal 下发生"的竞态窗口）。写 meta 即够 —— `SessionRuntime.build_agent()`
  里 `switch_session → _restore_execution_state` 会读回，**本轮开始前就已生效**。
- **goal 还要补一条 `[Goal set]` 消息**（在同一个新建分支里 append 到会话 jsonl）：
  预选路径没走 `Agent.set_execution_mode()`，也就没走它内部的 `_append_goal_set_message`，
  而 `_restore_execution_state` 只重建控制器、不补这条消息（否则每次切会话都会重复注入）。
  消息形状**逐字对齐** `_append_goal_set_message` —— 与"用户中途点胶囊设目标"产生的
  历史一模一样。plan 不需要补：`_sync_execution_mode()` 会在 `switch_session` 时按
  指纹注入 `<system-reminder>`（幂等）。
- **非法值静默忽略**（未知 mode / goal 条件超 4000 字 / 兜底后仍为空）：草稿态**绝不阻断发送**。
  2026-09-30 起条件由首条指令的正文充当（§2.6），前端已经不会产出空条件，后端这道是
  "手改 payload / 老客户端"的兜底；真被忽略时用户看到的是"胶囊没亮"或随即被 `sessions`
  广播纠正。
- **前端交接的本地登记**（2026-09-27）：收到 `session` 信封且本窗口是发起方（`wasFresh`）时，
  把 `pendingExecMode` 的值写进 `executionModeBySession[sid]` 并清空草稿。
  **不是乐观更新** —— 模式是同一条 `chat` 命令带的，登记只为"草稿已清、会话态未到"
  的那几毫秒不闪一下胶囊；真值由紧随其后的 `sessions` 广播校准（后端忽略非法值时
  这里会被纠正回 `normal`）。
- **后端命令侧不变**：`session_exec_mode` 仍是**双路径**（有 rt 且 agent 已构造 →
  薄委托给 Agent；否则只写 meta，待 `_restore_execution_state` 读回）。`session_id`
  为空则回 error —— 该分支前端已经不会走到，留着是"手改 payload / 老前端"的守卫。

> **历史形态（已废弃）**：无会话时两项 `disabledKeys` 置灰 + `title`「请先发送一条消息
> 创建会话，再设置任务执行模式」，`switchExecMode` 无会话时兜底同文案 toast。
> 用户反馈"任何情况下都应可选"，2026-09-27 改为上述草稿方案。

### 2.6 已有会话：点「目标模式」= 武装，**首条指令即目标**（2026-09-30）

**触发**（用户原话）："点击目标模式时，不用弹出对话框输入目标，在目标模式下，用户输入的
第一个指令就默认设为目标。"

一句话：**点选那一刻没有条件可写，而条件恰恰是用户接下来要说的那句话。** 于是把它拆成
"武装（前端）+ 交接（随下一条 `chat`）"两步，落地点选在**后端派发 turn 之前**。

| 阶段 | 位置 | 行为 |
| --- | --- | --- |
| 点选 | `InputBox.handlePlusPick('goalMode')` → `switchExecMode('goal')` | **不发任何后端命令**，只写 `goalArmBySession[sid] = true`；胶囊当场亮（虚线描边 + 提示"下一条指令将作为目标条件"） |
| 发送 | `agentStore.send()` | 条件 = **该条消息的正文**；`chat.exec_mode='goal'` + `exec_condition=<正文>` 一起送走；武装位**交出并清空**，同时把 `executionModeBySession[sid]='goal'` 登记一下（防闪，见 §7.7 例外） |
| 落地 | `ws_bridge` 的 chat 分支（**busy 守卫之后、`start_turn` 之前**） | ① `rt.agent` 已构造 → 薄委托 `Agent.set_execution_mode('goal', cond)`（清场 / `[Goal set]` / 落盘 / 广播全在里面）；② 未构造 → 写 meta + 手工补 `[Goal set]` + 自行广播（同 `session_exec_mode` 未跑分支口径），随后 `build_agent()` → `_restore_execution_state` 读回 |

**为什么落地点只能是"派发前"**（三条路径都验过，写成硬约束）：

1. `session_exec_mode` 命令：那一刻**条件还不存在**（用户还没说话）→ `GoalController`
   拒空条件，必被 `GoalError` 打回；
2. turn 派发**之后**再设：`rt.busy=True` → 撞 §2.4 的守卫（`GoalController` 无锁，
   工作线程正在读同一对象）；这正是 §2.5 里"禁止等 `session` 信封回来再发命令"的同一条约束；
3. **派发前**：busy 守卫已过、turn 未起 → 与"用户中途点胶囊设目标"完全同一时序、
   同一落盘路径，`[Goal set]` 与用户消息的先后也天然正确。

**条件的口径**（唯一实现：`ws_bridge._goal_condition_from_message`）：

```
exec_condition（前端显式给，非空优先）  →  否则本条消息的正文
                                        →  否则 [附件] 文件名 / [引用] 文件名（同默认标题口径）
```

正文为空（纯附件 / 纯引用）也**不留空条件**；兜底后仍为空或超 `MAX_GOAL_LENGTH` →
**整份忽略**（按普通消息发），只记一条 warning 日志，前端胶囊由随后的 `sessions` 广播纠正。

**武装位的边界（五条，都必须有）**：

| 场景 | 行为 | 为什么 |
| --- | --- | --- |
| 再点一次「目标模式」/ 后端已是 goal | **幂等短路**，不动 | 已在目标模式里，重设会重置目标 |
| 点胶囊 `×` | **只清本地位**，不发命令 | 后端此刻还是武装前那个模式（武装从未落地）—— 发 `normal` 会顺手杀掉用户的 plan |
| 武装中点「计划模式」 | 清武装位 **+ 真发** `session_exec_mode(sid,'plan')` | plan 的真源在后端，必须即时生效；后端本来就在 plan 时这条是幂等空操作 |
| 在途提问（ask_user）期间发消息 | **不交棒**，武装位留到真正的下一条指令 | 那是"作答"（后端把正文回填给 `ask_user`、不另起 turn），拿它当目标会当场设错 |
| `execution_mode_changed` 到达 / `clearSession` / 删会话 / 删空间 | 清武装位 | 广播是本会话模式的**唯一权威**；后三者下这条草稿已无意义（`dropExecBuckets` 三桶同清） |

**与"无会话草稿"的关系**：语义等价、**归属不同** —— `pendingExecMode` 属于"还没建出来的
新会话"，`goalArmBySession[sid]` 属于已有会话，两者不合并成一条真值来源（否则切会话会把
A 的武装带到 B）。无会话时点「目标模式」仍是 §2.5 那套（`pendingExecMode='goal'`），
发送时条件同样取首条指令的正文。

**不做的事**：不给后端加"预告目标"的中间状态（`GoalController` 一行不改 —— 空条件的
`set_goal` 依旧是错），不改 `session_exec_mode` 的即时生效语义，不在弹层这条路上留兼容层
（`GoalInputDialog.tsx` 与其 CSS **已删**）。

### 2.7 目标模式**可见化**：指令徽标 + 检查记录 + 常驻目标条（2026-09-30 二次改版）

**触发**（用户原话）："我的目标模式执行和普通的模式没有区别，用户也感知不到每轮执行完的
偏差和结果是什么。……用户被设为目标的指令消息要标出来，已设为执行目标。目标的每一轮执行
完之后的目标检查结果也要输出到对话界面上，历史消息也可以回放。"

改造前的事实：goal 与 normal 在界面上**零差别** —— 目标指令消息无任何标记；Stop 七分支的
裁决结果里**只有 `block` 落盘**（`[Goal still active]`，且那是给模型看的英文指令），
`achieved` / `failed` / `limit` / `error` / `defer` 的理由**只 `_print` 到终端 + 写日志**，
`GoalController.events` 只进内存、零持久化。用户切换会话能看到的，最多是一条长得像自己
说话的 `[Goal set] Condition: …` 气泡。

改造做四件事（**每件事都同时服务"实时"与"回放"两条链路，共用同一份数据结构**）：

| # | 元素 | 回答的问题 | 承载 |
| --- | --- | --- | --- |
| 1 | **指令徽标** `GoalBadge` | "这条就是我设的目标" | 那条 user 消息的 `goal={"kind":"instruction",…}` |
| 2 | **检查卡** `GoalCheckCard` | "这轮偏在哪 / 成没成" | 每轮裁决的 `goal={"kind":"check", action, round, reason, elapsed, tokens}` |
| 3 | **目标设定卡**（`GoalCheckCard` 的 `set` 分支） | "目标是什么、接下来怎么走" | `[Goal set]` 消息的 `goal={"kind":"set", condition}` |
| 4 | **常驻目标条** `GoalBar` | "还开着目标模式吗、目标是啥、跑到第几轮" | `goalBarBySession[sid]`（四条来源，见 §7.6） |

#### 2.7.1 四个关键杠杆（设计地基）

1. **`MODEL_MSG_FIELDS` 白名单**（`agent_full_v2.py`）：
   ```python
   MODEL_MSG_FIELDS = ("role", "content", "reasoning_content", "tool_calls", "tool_call_id")
   ```
   `_model_messages` **逐字段**投影 → **给消息 dict 挂任意新字段（如 `goal`）永不漏进 LLM 请求**。
   于是"给用户看的元数据"与"给模型看的正文"可以**共用同一条消息**，不必为纯展示需求新造一条通道。

2. **消息形态取"复用 `role:"user"` + 旁挂 `goal`"，不新增 role**。原因：`session_manage.load_session_history`
   的 else 兜底会把**未知 role 静默强转成 user**（`{"role":"user","content":str(content)}`）——
   新增 role 需要 5 处接缝（`_message_to_json_row` / `load_session_history` / `save_session_history`
   回写缓存 / `_strip_subagent_rows` / `_history_to_ui`），且**并不免除**下面第 3 条的尾部顺序问题。
   而"指令徽标"本身就挂在 user 消息上，`goal` 字段基建无论如何都要建。

3. **终止态记录必须"同进 `history_messages` + jsonl"**：`save_session_history` **只重写 `messages`**
   （subagent 行之所以迁去旁路文件正是这个原因）—— 只写 jsonl 的记录会在 compact / 自愈重写时被抹掉。
   故记录进 `history_messages`，再在 `_model_messages` 里**整条过滤**掉（见 2.7.3）。

4. **实时通道 = 新信封 `goal_check`**，走既有 `_emit_kind` → `execution_mode_sink`
   （`deliver` 内部 `call_soon_threadsafe` + 广播）——**线程安全**，Stop 边界跑在工作线程也能直接发；
   agent 侧**无 hub**，绝不能直接 `hub.broadcast`。**不**扩展 `execution_mode_changed`：
   那是"模式变更"语义，会被模式状态机误消费。

#### 2.7.2 轮次口径（**唯一**）

`round` = 后端 `GoalController.active.iterations`（**已完成的评估次数**，每完成一次评估 +1；
`begin_query()` 每轮查询清零的是 `consecutive_blocks`，不是它）。

- **检查卡片显示 `round`**（第 N 轮 = 第 N 次检查）；
- **常驻目标条显示 `round + 1`**（当前进行 / 即将进行的那一轮）；
- 这个 `+1` **只在 store 的 `goalBarRoundLabel` 做一次**，组件不得自算（两处口径分会打架）。

`elapsed` / `tokens` 是**目标期间**（而非整个会话）的时长与消耗：`GoalState.snapshot()` 用
`now - set_at` 与 `total_tokens - tokens_at_start` 现算，是这三个指标**唯一**的组装点。

> ⚠️ `iterations` **只在评估成功返回后 +1**。所以「第 1 轮」长时间不动有两种正当来源：
> ① 一轮内还在连续调工具（评估只在 Stop 边界发生）；② 收尾那次评估**错误**（`error` 分支
> 不改轮次）。后者会表现为"条停在原地 + 弹「评估出错」卡"—— 2026-09-30 实测的
> `invalid JSON` 就是这个，根因与修复见 §12.13。

#### 2.7.3 检查记录的落盘与上下文边界

| action | 落盘 | 进模型上下文 | 为什么 |
| --- | --- | --- | --- |
| `block` | **当场** append（`[Goal still active]` 正文**一字不改**） | **是** | 它的正文就是"你没做完，差在哪，继续"的反馈 —— goal 回环的**唯一驱动力**。且它之后必然还有 assistant 消息，当场落盘安全 |
| `achieved` / `failed` / `limit` / `error` / `defer` | 入队 `_pending_goal_checks`，由 `run_turn` / `run_background_followup` 收尾 `_flush_goal_checks()` 统一写（`content=""`） | **否**（整条过滤） | 对模型是噪音：`achieved`/`failed` 之后目标已经是死的，`limit`/`error`/`defer` 的结论也不该被当成新指令 |

**为什么终止态必须排队**（改造中最容易踩的坑）：Stop 边界发生在**最后一条 assistant 消息之后**——
当场 append 会让 `_finalize_turn_usage` 的 `append_usage_to_last_assistant` 找不到末行 assistant
（**本轮 usage / model_info 永久丢失**），也会让 `run_turn` 的返回值（`history_messages[-1]`）
变成检查记录的正文。`_flush_goal_checks()` 因此**必须**排在 `_finalize_turn_usage()` 与算出 `last` **之后**。

**过滤判据**（`_is_display_only_goal_record`）：`goal.kind == "check"` 且 `action != "block"`。
`set`（`[Goal set]`）与 `instruction`（用户原话）一并保留 —— 前者告知模型目标、后者就是用户输入。
判据只看 `kind`/`action`，不看原文。

> ⚠️ 白名单投影只能剔**字段**、剔不了**整条消息** —— 这批记录正文是空串（评估器读到等于没读），
> 但留着仍会占位。故过滤写在 `_model_messages` 的列表推导里，不是靠白名单。

#### 2.7.4 `[Goal set]` 不再是从前那条怪气泡

`_append_goal_set_message` 的**正文一字不改**（模型照读 `[Goal set] Condition: …`），只旁挂
`goal={"kind":"set","condition":…}`；`_history_to_ui` 见到 `kind ∈ {check, set}` 就把整行转成
`role:"goal_check"` 的展示卡 —— 回放里**不再出现** `[Goal set] Condition: …` 的用户气泡。

#### 2.7.5 指令徽标是**唯一一处乐观更新**（及它的收敛）

后端要等 `chat` 到达、算完条件才知道"这条是目标指令"，而前端在 `send()` 那一刻就一清二楚 ——
所以徽标只能乐观打（否则要为纯展示需求新增一条"已确认为目标指令"的信封，不值当）。
代价是：后端若**静默忽略**整份预选（条件为空 / 超长 / 撞 busy 守卫，ws_bridge 两处 `log.warning`），
**不会有任何回执**，那枚徽标就会一直挂着。

收敛点因此是**后端给出的权威模式**（`settleGoalBadges`）：

| 权威模式 | 动作 |
| --- | --- |
| `goal` | 摘掉 `pending`（徽标留下 —— 事实成立） |
| 非 `goal` | **整枚撤掉**（这次预选没被接受） |

两条触发通道：`execution_mode_changed`（已有会话路径）与 `sessions` 列表（**新会话预选路径不推该信封**
—— 它靠 `_restore_execution_state` 生效，只能在这里落地）。

⚠️ **只动 `pending === true` 的那些**：已确认的历史徽标绝不能被顺手清掉 —— 目标达成后 mode 回落
normal，若按 mode 一刀切，用户会看到"我刚才设的目标"徽标凭空消失。

## 三、plan 的窄只读判定（评审 P0-3）

### 3.1 为什么不能复用权限链的白名单

方案文档原想「把 `_bash_category_decision` 的 ⑦-2 白名单段抽成公开函数，白名单仍只有一份」。
逐行对账后三条都不成立：

1. **抽不干净**：⑦-2 只是循环里的一句 `if`，被 **⑥ 会话记忆** 与 **⑦-1 危险模式**前后夹持；
   而 ⑦-1 **必须先于白名单**（项目里 `cat x > /etc/passwd` 曾被白名单掩护静默放行的历史事故）。
   只抽 ⑦-2 = 丢掉 ⑦-1 = **判定变松**。
2. **返回值不是 bool**：整函数返回 `Decision`（`action ∈ {allow, approve}`），方案想要的
   `-> bool` 是**新语义**，不是"抽出既有函数"。
3. **白名单语义错位**：`BUILTIN_SAFE_COMMANDS` 的语义是「够安全、**可免审批**」，不是
   「只读」—— 表内有 `find` / `env` / `git branch` / `du` / `echo`，而匹配是 **token 前缀
   匹配**。于是下面这些**全数命中白名单**：

```
find . -exec rm -rf {} +        env X=1 rm -rf /        git branch -D main
du --files0-from=…              echo "$(rm -rf x)"      （$(...) / 反引号不在任何否决位）
```

**结论**：`permission.py` **一行不改**；plan 专用的窄只读判定在 `execution_mode.py` 内新建
`bash_is_read_only(command, store)`，只复用权限链的**原语**（`split_command_segments` /
`normalize_segment` / `tokenize` / `pattern_matches` / `cross_pattern_matches` /
`deny_tokens_in_command`）与**内置清单**，**不复用那份白名单策略数据**。

### 3.2 判定规则（五步，逐段）

```
① 解析失败 / 空段                          → False（fail-closed，与权限链同款）
② 任一段含否决位（子串）                   → False
     `>`（覆盖 > >> 2>&1 >&） / `<<`（覆盖 << <<<） / `$(` / 反引号
  任一段含否决位（token）                    → False
     --output / -exec / -execdir / -ok / -okdir / -delete / -fprint* / -fls*
     tee / dd / xargs / truncate / sponge / --pre
③ 敏感路径 token（deny_tokens_in_command）  → False
④ 硬拒绝 ∪ deny_patterns、危险模式 ∪ dangerous_patterns（含跨段）→ False
⑤ 逐段命令头白名单（每段都必须过）：
     头 ∈ PLAN_BASH_READONLY_HEADS 且：
       · git  → 子命令 ∈ {status, diff, log, show, branch}；
                git branch 的额外 token 必须 ∈ 安全开关集（拒 `git branch foo` / `-D`）
                允 `-a/-r/-v/-vv/--all/--remotes/--list/--merged/--no-merged/--contains/--sort/--format`
       · env  → **只允许裸 env**（只打印环境）。`env X=1 cmd` 是启动器，
                且 `env PATH=/tmp/evil ls` 会换掉实际执行的二进制 → 一律 False
       · date → 拒 `-s` / `--set`（会改系统时钟）
```

只读头显式枚举（已核对为 `BUILTIN_SAFE_COMMANDS` 的真子集）：

```
ls pwd cat head tail wc grep rg find which file stat du df echo date git
```

**`_deny_token_hit()` 的三种形态**（实施期抓到的两个真实绕过）：早期草案只做
`tok in deny` 精确匹配，于是

- `--output=patch.diff`（等价 `git diff --output patch.diff`）→ token 是 `--output=patch.diff`
  → **漏过 → 静默写文件**；
- `date --set=now`、`date -s2020-01-01`（短选项带值）→ 同样漏过 → **静默改系统时钟**。

修正后的匹配：① 精确；② 长选项带值取 `=` 前的选项名；③ 短选项聚合取头两个字符（仅当该短
选项在否决集里）。

**刻意不拦 `-i` / `-o`**（与早期草案的差异，理由可验证）：它们的"写"语义只对
`sed -i` / `perl -i` / `sort -o` / `curl -o` 成立，而这些头**本身不在只读白名单内**（第 ⑤ 步
已先拦下）；对放行头（`ls -i` / `grep -i` / `grep -o` / `find … -o`）它们是**只读开关**。
全局拦只会误伤最常用的 `grep -i` 探索，零安全收益。

### 3.3 四个反例（测试里必须断言为 **阻断**）

| 命令 | 命中的判定 |
| --- | --- |
| `find . -exec rm -rf {} +` | ② token 否决位 `-exec` |
| `env X=1 rm -rf /` | ⑤ `env` 非裸调用 |
| `git branch -D main` | ⑤ `git branch` 额外 token 不在安全开关集 |
| `echo "$(rm -rf x)"` | ② 子串否决位 `$(` |

另加：`cat x > /etc/passwd`（② 重定向）、`git diff --output=patch.diff`（② 长选项带值）、
`date -s2020-01-01`（② 短选项聚合）也在测试里断言为阻断。

### 3.5 hook 顺序与阻断回填契约

`register_default_hooks()` 的顺序（**次序即语义**）：

```
PreToolUse: ① plan_guard_hook   ← 新增（模式级，最严，先拦模式）
            ② permission_hook   （规则级）
            ③ log_hook          （必须晚于权限 —— 否则被拦的调用会记成一次成功）
```

`plan_guard_hook(tool_call) -> str | None` 与 `permission_hook` **完全同款**：返回非 None
字符串即被 `hook_system.trigger("PreToolUse", …)` 判为阻断，由 `agent_loop` 回填为该
tool_call 的 result 文本。**不进审批流、不产生 approval 记录**（模式级限制与"要不要审批"无关）。

回填文案（模型可见 → 必须可行动）：

```
Error: Plan mode is active — this tool is blocked.
[可选一行细节，如 bash 的"仅允许只读命令"]
Write your implementation plan with plan_write, then wait for user approval.
Blocked tool: run_write
```

**防御姿态（与权限链一致的 fail-closed / fail-open 之分）**：

- 未注入 gate（独立 `HookSystem` / 子智能体兜底构造 / 单测直连）→ 直接放行（normal 路径逐
  字节不变）；
- 非 plan 模式 → 直接放行（**零开销**，且不会因为解析工具参数而误伤 normal / goal 路径）；
- **只有** `plan_blocks_writes()` 为真时才解析工具参数；**参数解析失败 → fail-closed 阻断**
  （与权限链同款：宁可错杀）；
- gate 状态读取本身抛异常 → **放行**（不猜、不阻断 —— 门自己坏了不该打死正常流程）。

`store` 从权限门取（`PermissionGate.store.load()`，有 mtime 热加载缓存）—— 这一点**必须**，
否则 plan 的判定会漏掉用户的 `deny_patterns` / `dangerous_patterns`，破坏 §1.3 的不变量。

## 四、计划文书

### 4.1 落点与命名（**2026-09-29 改版**）

```
<工作空间根>/.aiagent/plan/<name>.md
    ↑ 工作区**内**；<name> 由**模型**取（`plan_write` 的 name 参数）
```

> **历史形态（已废弃，2026-09-25 ~ 09-29）**：`<data_root>/plans/session_<sid>.md`
> —— 落在元数据目录（`~/.aigent/projects/<id>/`），与会话 jsonl 同源、删会话即级联清理。
> 用户否掉了它：**计划文书回答的是"接下来要怎么改这个项目"，跟代码放在一起才看得见、
> 能进版本库、能直接在编辑器里改**；落在 `~/.aigent` 的那一版，用户根本找不到它。

改版带来的三条**连带约束**（改动时一起看）：

| # | 约束 | 落地处 |
| --- | --- | --- |
| 1 | 名字由**模型**给 → 落盘前必须清洗（目录分隔符 / `..` / 保留字符 / 空名回退），**目录仍由后端强制** | `paths.plan_filename` |
| 2 | 路径再也无法由 `sid` 推出 → meta 落 **`plan_name`**（只存文件名，不存绝对路径：工作空间整体搬家后仍有效） | `SessionManager.set_session_execution` |
| 3 | 会话删除 / 清空**不再删文书文件**（它此时是工作区里的项目文件），但 meta 的执行模式字段必须归零 | `session_manage` 两处 |

路径口径**唯一**在 `paths`（五个函数，任何一处自己拼字符串都会造成"写得到、读不到"）：

| 函数 | 作用 |
| --- | --- |
| `plan_dir_for(workdir)` | `<工作空间根>/.aiagent/plan/` |
| `plan_filename(raw)` | 清洗模型给的名字（恒以 `.md` 结尾，空名回落 `plan.md`） |
| `plan_relpath(raw)` | 展示 / 读取用的**相对工作空间**路径 |
| `resolve_plan_path(dir, name, prev)` | 同名不撞车的最终落点（本会话上一版可覆盖，别人的加 `-2`/`-3`） |
| `plan_display_path(status, name, legacy)` | **三个出口共用**的对外路径判据（见 §6.3） |

为什么相对路径而不是绝对路径：① 右栏标签的 path 本来就允许"工作空间相对"这一形态
（`file_read` 两种形态都收，只是**回执**里的 `path` 恒为解析后的绝对路径）；② meta 里存绝对路径
会在工作空间整体搬家后失效。

> ⚠️ **由此产生的一条硬约束（2026-09-29 实测缺陷）**：计划文书的右栏标签 path 是**相对**形态，
> 而 `file_read` 回执里的 path 是**绝对**形态 —— 右栏任何"这是不是同一份文件"的判断都必须走
> `sameWorkspaceFile`（Doc19 §2.1.1），**绝不能用 `===`**。用字面比较的后果是回执被判成慢回执
> 丢弃、`previewLoading` 永远清不掉，右栏一直「正在读取…」。

**存量会话**（升级前产出的文书仍在 `~/.aigent/projects/<id>/plans/session_<sid>.md`）：
`paths.plan_file_for_session` 保留为**回退读取**口径，`plan_read` 在 meta 无 `plan_name`
时走它 —— 升级后老会话的卡片照样能读到正文（只是不进右栏）。

`WorkspacePaths.plan_dir` = `plan_dir_for(workdir)`；`WorkspacePaths.plans_dir` 保留为
**旧的**元数据目录口径，只服务回退读取。目录由 `plan_write` 落盘时按需 `mkdir parents`
（与 `.attachments` 同策略：没用过计划模式的用户永远不会看到这个目录）。

> ⚠️ 与既有 `.aigent/`（`run_read` 栅格化 PDF 页图的缓存目录，在
> `refs.DEFAULT_IGNORE_DIRS` 里被**剪枝**）刻意区分：`.aiagent/` 是**给用户看的产物
> 目录**，不进忽略清单 —— 计划文书要能在右栏文件树里看见。

### 4.2 格式与覆盖语义

- **Markdown**，人可读、可直接编辑（"在 Finder 打开"本期不做）。
- **单份覆盖**：同一会话重复产出计划即覆盖旧文书，**不做版本历史**。这直接决定了前端只能
  用"消息流末尾固定块"的形态（§10.4）。
- 写入是**原子写**（tmp + `os.replace`，与项目其它落盘一致）。

### 4.3 `plan_write` 工具

```python
{
    "type": "function",
    "function": {
        "name": "plan_write",
        "description": (
            "写入/覆盖本会话的计划文书（仅在计划模式下可用）。"
            "在计划模式下完成只读探索后，用本工具提交实施计划：目标、步骤分解、"
            "涉及文件、风险与验证方式。用户批准后才会开始执行。"
            "文书会写到工作空间的 .aiagent/plan/ 下，用户会在右侧面板里看到它。"
            "不要用它保存代码、笔记或任何交付文档。"
        ),
        "parameters": {
            "type": "object",
            "properties": {
                "name": {"type": "string", "description": "计划文书的文件名…"},
                "content": {"type": "string", "description": "计划正文（Markdown 格式）"}
            },
            "required": ["content"],
        },
    },
}
```

两个刻意的取舍：

- **有 `name` 但没有 `path`**：**目录由后端强制**（模型定不了 —— `name` 里的任何目录
  分隔符都会被 `paths.plan_filename` 剥掉），模型只定**文件名**。比"有 `path` 参数但被
  忽略"干净，又保住了用户要的"每份计划有个一眼看得懂的名字"。
  `name` **可选**：缺省 / 非法值一律回落到一个可用名字（`plan.md`），**绝不因为名字问题
  让落盘失败**。
- **工具常驻**在工具列表里，**不做按模式动态裁剪**：裁剪要动 `tools` / `base_tools` /
  `main_agent_tools` / `default_agent_tools` 等多处传参点，收益（省 ~100 prompt token）不抵
  风险。非 plan 模式下调用由守卫拒绝。

**注入方式（评审 P1-10）**：`ToolRegistry.set_plan_sink(cb)`（holder 形状照抄
`set_background_manager`）。**只能传"已经算好路径"的闭包** —— `ToolRegistry.__init__` 只有
`workdir` / `bash_cwd`，**没有 workspace、没有 session_id、也没有工作空间根**。因此
"清洁名字 → 算路径 → 原子写 → 标状态 → 落盘 → 推信封"全部由 **Agent 侧的闭包**
（`_bind_plan_sink`）完成，registry 侧不做任何路径推断。未注入时 `plan_write` 返回可读的
Error 文本（CLI / 单测路径行为不变）。

handler 步骤：`name` 只做**类型兜底**（真清洗在 `paths.plan_filename`，此处不写第二份规则）
→ 闭包：`resolve_plan_path`（同名不撞车，本会话上一版可覆盖）→ `mkdir parents` → 原子写
→ 换名重规划时**清掉上一版**（best-effort）→ `gate.mark_plan_ready(path, name)` →
`_persist_execution()`（落 meta 的 `plan_name`）→ 经 sink 推 `execution_mode_changed`（先）
→ `plan_ready`（后，带 `plan_path` 相对路径）。

### 4.4 `plan_read`：正文链路（评审 P0-1）

**原方案的决策不成立**：`file_read` 内部是 `read_workspace_file(ws_paths.workdir, path)`，
第一步 `resolve_within(workdir, path)` 把根**钉死在工作区**；而 2026-09-25 版的文书落在
**元数据目录**（默认空间更是整体禁用 `file_read`）。

**修正后的决策：新增专用命令 `plan_read`，`plan_ready` 信封仍不带正文。**

2026-09-29 改版后文书已**在**工作空间内，但仍然**不**复用 `file_read`，两条理由：

1. 卡片只知道 `sid`，路径要由后端从 meta 的 `plan_name` 解析（口径唯一）；
2. `read_workspace_file` 会按扩展名分派 `image` / `pdf` / `office` 分支，与
   `plan_content` 的最小字段契约不符。

| 环节 | 做法 |
| --- | --- |
| 路径解析 | `sid → pid → meta.plan_name → plan_relpath → resolve_within(workdir, …)`；meta 无 `plan_name`（存量会话）则回退 `plan_file_for_session(…, ws_paths.plans_dir)` |
| 越界防线 | `plan_filename` 已把名字清洗成纯文件名（`..` / 分隔符全被剥掉），所以 `resolve_within` 是**第二道**兜底 —— 防的是清洗规则将来出现漏洞。联调实测：把 `plan_name` 改成 `../../../../etc/hosts` 会被清洗成 `.aiagent/plan/hosts.md`，"读不到就是读不到"，不越界 |
| 回执形状 | **复用既有降级字段形状**（照 `file_content_disabled`）：`{project_id, session_id, path, name, size, mtime, encoding, binary, too_large, truncated, lines, text, reason}` —— 所有分支都从**同一个构造函数** `plan_content_payload()` 出去，前端不必写第二套解析 |
| 大小上限 | 复用 `refs.file_preview_max_bytes()`（512KB）。超限**一点内容都不读**（"宁可不给，不给半个"），给 `too_large=True` + 人话 reason |
| 健壮性 | 编码 `utf-8` + `errors="replace"`；**绝不抛异常**（`FileNotFoundError` / `OSError` / 连 `stat` 都会抛的 `ValueError`（路径含 NUL）全部分支化成 `reason` 人话） |
| 实时与回放 | **共用同一条链路** —— 实时（`plan_ready` 到达后）与回放（`session_history` 带 `plan_status` 后）**都调 `plan_read`** |
| 落点 | 读取函数放在 `execution_mode.py`（**不是 `ws_bridge.py`**）：① 这是 plan 域的职责；② `ws_bridge` 有**模块级副作用**（import 即构造全局 Agent 并写一行日志），纯文件函数留在那里就没法在不污染 `~/.aigent` 的前提下单测 |

**推送顺序契约**：`plan_write` 成功时后端**先推 `execution_mode_changed`（带
`plan_status="ready"` 与 `plan_path`）再推 `plan_ready`** —— 保证前端处理卡片时 tag 状态已
就位（顺序错也不崩、幂等，但固定顺序便于断言）。

**失败语义**：`reason` 非空（文书被外部删除 / 超限 / 空间目录不可用）→ 前端渲染
「读不到（原因）」占位块 + 保留选项区（但**「开始执行」禁用**，因为批准一份读不到的文书没有
意义；「继续修改」仍可用 —— 模型手上有上下文）。**绝不白屏。**

### 4.5 生命周期（**2026-09-29 改版**）

文书现在落在**工作空间**里 —— 它是**用户的项目文件**（看得见、可编辑、可进版本库），
不再是会话的临时产物。因此：

| 操作 | 是否动文书文件 | 是否归零 meta | 说明 |
| --- | --- | --- | --- |
| `delete_session_permanent` | **不清** | meta 文件整体删除 | 删一个会话顺手删掉工作区里的文档是"越权删用户文件" |
| `clear_session` | **不清** | **清**（`execution_mode` / `plan_status` / **`plan_name`** / `goal_condition`） | 状态必须归零，否则留下"有计划状态、没有上下文"的僵尸壳 |
| `trash_session` | **不清** | 不动 | 软删除（归档）本来就保留文件 |
| 换名重规划（同一会话） | **清上一版** | 覆盖 `plan_name` | 否则工作区里会留下没人认领的旧文书 |

> **历史形态（已废弃，2026-09-25 ~ 09-29）**：`delete_session_permanent` / `clear_session`
> 各清一次 `<data_root>/plans/session_<sid>.md`（"与会话同生共死"）。那一版文书与会话 jsonl
> 同源，清理是必须的；搬到工作区后这条语义反过来了。旧口径的文书**仍在原处**（回退读取需要
> 它们），本次没有做任何搬迁 —— 用户可按需自行删除。

## 五、提示词注入：两态对称（评审 P0-2）

### 5.1 为什么必须有"退出"那一态

**原方案写的是"只处理 plan"、"回落 normal 时不注入任何提示（撤掉 tag 即足够）"—— 这是个会
打死核心流程的错。**

因为该注入是 **append 到历史并落盘**的（不是每轮临时拼接）：plan 期间历史里最后一条提醒是
「禁止任何写操作」；批准后若什么都不注入，模型读到的**最新指令仍是"禁止写操作"** → 表现为
**「用户点了批准执行，模型却拒绝干活」**。

### 5.2 两态文案与指纹

指纹 = **语义状态**（`plan-active` / `plan-exited`），不是哈希：

- 同态重复调用零开销、不刷屏；
- 历史里**从未**注入过本 tag 且当前非 plan → 直接返回（否则每个新会话都会莫名多一条
  「计划模式已结束」）。

**态 ①：plan 激活且未批准**

```
<system-reminder>
当前处于「计划模式」。禁止任何写操作与有副作用的调用：只能做只读探索
（run_read / run_glob / 只读 bash / 向用户提问），然后用 plan_write 提交计划文书，
等用户批准后再开始执行。若当前任务不适合产出计划（例如只是问答或诊断），
请直接说明原因并请用户关闭计划模式，不要反复尝试写操作。
</system-reminder>
```

**态 ②：已退出 plan（前态为 plan 或 `plan_status=approved`）—— 撤销提醒**

正文**按当前模式二选一**（2026-09-27 新增第二版；指纹仍记 `plan-exited`，只换正文）：

②-a 回落到 `normal`（批准执行 / 手动关掉计划模式）：

```
<system-reminder>
计划模式已结束，写操作已恢复，可以正常使用 run_write / run_edit / bash 等工具。
请按已批准的计划文书开始执行。
</system-reminder>
```

②-b **直接切换到 `goal`**（§2.3 改版后新增的路径）：

```
<system-reminder>
计划模式已结束，并直接切换到了「目标模式」。写操作已恢复，可以正常使用
run_write / run_edit / bash 等工具。此前若产出过计划文书且尚未批准，该文书
已作废（文件仍保留在磁盘上，但不要再去执行它）。
请围绕已设定的目标条件继续工作，直到目标达成。
</system-reminder>
```

**为什么必须分两版**：②-a 的落点是"请按**已批准**的计划文书开始执行"，而 plan → goal
这条路径上计划**通常根本没被批准**（状态已作废、文件仍在）。照抄会让模型去找一份它拿不到、
也不该执行的计划。指纹不变是因为它记的是"plan 这个语义态"，不是文案。

机制与 `_sync_environment()` 完全同构：**尾部追加 + 指纹幂等、绝不改历史消息**；注入块会被
`ws_bridge._history_to_ui` 按 `<system-reminder>` 前缀过滤掉，不会漏成聊天气泡。per-turn
在 `agent_loop` 里调用（与 `_sync_environment` 同处）。

**「计划已批准」是另一条东西，两条都要有**：

| 注入 | 形态 | 作用 |
| --- | --- | --- |
| `PLAN_EXITED_REMINDER` / `PLAN_EXITED_TO_GOAL_REMINDER` | `<system-reminder>`（不可见） | **解除**"禁止写"（②-a / ②-b 两版） |
| 「[计划已批准] 用户批准了你的计划文书，现在开始按计划执行。可以正常使用 run_write / run_edit / bash 等写操作。」 | **用户可见的 user 消息**（`rt.start_turn(PLAN_APPROVED_RESUME_TEXT)` 的首条 content） | 告诉模型**执行什么** |

### 5.3 goal 侧刻意**不**注入 system-reminder

既有 Stop 边界在每次 `block` 时已回注 `[Goal still active] / Condition: … / Evaluator: …`
—— 那已是 goal 的成熟反馈通道，再叠一层 system-reminder 就是**第二出处**。

goal 侧只补**一条设置时的消息**（与 block 消息同族同风格，走既有 `append_message_to_session`）：

```
[Goal set]
Condition: {condition}
Work toward this condition; the session will be evaluated when you stop.
```

理由：CLI 的 `/goal` 会在终端打印确认，而桌面端用户是**点胶囊 tag 填条件** —— 未必再发一条
相关消息，模型需要立刻知道目标是什么。复用既有消息族，不引入新的注入机制、不碰
`_sync_execution_mode`。

> **2026-09-30 补充（目标可见化）**：这条"刻意不注入"的取舍**依然成立**，且新加的检查记录
> 也不违反它 —— 检查记录走的是**落盘 user 行 + 旁挂 `goal` 元数据**（§2.7.3 / §6.6），
> **不是** `<system-reminder>`。两者的区别正是这条取舍的关键：注入是"给模型的第二出处"，
> 而检查记录对模型是**透明的**（非 block 的整条不进上下文，block 那条本来就已经存在）。
> 换言之：**"给用户看"这一半被补上了，而"给模型看"这一半一行没多。**

## 六、协议契约

### 6.1 三条新命令（渲染 → 后端）+ `chat` 新增 2 字段

| 命令 | 载荷 | 语义 | 回执 |
| --- | --- | --- | --- |
| `session_exec_mode` | `{session_id, mode, condition?}` | `plan` → 进入计划模式；`goal` → 需带 `condition`（空/超 4000 字由 `GoalError` 拒绝）；`normal` → 退出当前模式（plan 时清 plan 状态，goal 时转发 `clear_goal()`） | 广播 `execution_mode_changed` |
| `plan_approve` | `{session_id}` | `plan_status=approved` + mode 回落 normal + **自动起一轮执行**（忙 / 有在途提问时只落状态 + 提示） | 广播 `execution_mode_changed`，随后正常流式事件 |
| `plan_read` | `{session_id}` | 读本会话计划文书正文（元数据目录直读，**不走 `file_read`**） | **点对点** `plan_content` |

失败一律复用既有 `error` 信封（条件为空或超长 / 会话不存在 / 会话未构造）。
`condition` **仅**在 `mode === 'goal'` 时读取。

> ⚠️ 2026-09-30 起 **goal 的常规入口不再是这条命令**：桌面端点「目标模式」= 武装
> （条件 = 下一条指令的正文），随 `chat.exec_mode / exec_condition` 落地（§2.6）——
> 空条件在本命令里必被拒，而本命令又是"即时生效"语义（`rt.busy` 时更直接拒绝）。
> 本命令保留给"关闭目标模式 / 跨模式切 plan / 非桌面客户端 / 手改 payload"。

`chat` 命令**新增两个可选字段**（2026-09-27 起，2026-09-30 扩展到已有会话）：

| 字段 | 形状 | 语义 |
| --- | --- | --- |
| `exec_mode` | `"plan" \| "goal"` | **新建任务**：预选执行模式，`"normal"` / 缺省 = 不设置（新会话默认档，**零字段**）。**已有会话 + `"goal"`**：目标模式武装位的交接（§2.6），后端在**派发 turn 之前**落地。`"plan"` 仍只对新建生效（已有会话的 plan 走 `session_exec_mode`：plan 必须即时生效）。白名单外的一律忽略并记 `warning` |
| `exec_condition` | `string` | 仅 `exec_mode === "goal"` 时读。**留空 = 用本条消息的正文**（这正是"首条指令即目标"）；正文也为空时用 `[附件] 文件名` / `[引用] 文件名` 兜底。兜底后仍空 / 超 `MAX_GOAL_LENGTH` → **整份忽略**（回落 normal），不阻断发送 |

后端两条落地路径（**互斥**，`fresh_session = sid is None` 分流；顺序即代码顺序）：

```
【新建会话】建会话分支里：
① session_manage.set_session_execution(new_sid, execution_mode=<mode>,
       plan_status=None, goal_condition=<cond|None>)
② 仅 goal：append_message_to_session(new_file, {"role":"user","content":
       "[Goal set]\nCondition: <cond>\nWork toward this condition; ..."})

【已有会话 + goal】busy 守卫之后、start_turn 之前：
① rt.agent 已构造 → Agent.set_execution_mode("goal", cond)
     （跨模式清场 / [Goal set] / 落盘 / 广播全在里面）
② 未构造 → set_session_execution(sid, …) + 手工 append 同一条 [Goal set]
           + hub.broadcast("execution_mode_changed", {…, goal_condition})
```

> **为什么两条都要**：`ws_bridge` 的 `_goal_condition_from_message(raw, text, payload)`
> 是**唯一**的条件口径（显式值 > 消息正文 > 附件/引用兜底），两条路径共用它，
> 不会出现"新会话用正文、老会话用别的"这种分叉。

### 6.2 三个新信封（后端 → 前端）

| 信封 | 字段 | 触发 | 投递 |
| --- | --- | --- | --- |
| `execution_mode_changed` | `{session_id, mode, plan_status, plan_path, goal_condition, goal_round, goal_started_at}` | 任何模式/状态变更（含 goal 达成后自动回落） | **广播**（多窗口一致，同 `permission_changed` 口径） |
| `plan_ready` | `{session_id, plan_status, plan_path, plan_name}` | `plan_write` 成功写入文书后。**不带正文**（正文走 `plan_read`） | **广播** |
| `plan_content` | 见 §4.4 的形状 | `plan_read` 的点对点回执 | **单播**（`safe_send`） |
| `goal_check` | `{session_id, kind:"check", action, round, reason, condition, elapsed, tokens, at}`（**扁平**） | 每次 Stop 裁决（2026-09-30 目标可见化，§2.7） | **广播** |

> `goal_round` / `goal_started_at`（2026-09-30 追加到 `execution_mode_changed`）：常驻目标条
> 要在重连 / 切会话后显示正确的「第 N 轮」与已运行时长。语义与 `goal_condition` 一样是**投影**
> （真相恒为 `GoalController.active`），active 为空时一律 `None`。

> `goal_check` 的**形状与 jsonl 落盘的 `goal` 标记同源同形** —— 都由
> `GoalState.snapshot()`（condition/round/elapsed/tokens/at）+ `decision.action` / `decision.reason`
> 组装。前端把它 append 成一条 `role:"goal_check"` 的 `Message`，与回放通道
> （`_history_to_ui` → `historyToMessage`）产出**同一个消息对象**，共用 `GoalCheckCard` 一套渲染，
> **不存在"实时一套、回放一套"的口径分叉**。
>
> 为什么是**扁平**载荷而不是嵌一个 `goal` 子对象：前端只消费、不转发，扁平省掉一层解构；
> 落盘那边必须是子对象（要挂进 user 行），两者形状由后端各组装一次 —— 但字段名与语义一致，
> 类型定义在 `agentProtocol.ts` 里只有 `GoalMarker` 一个。

> `plan_ready` 的 `plan_path` / `plan_name`（2026-09-29 追加）：前端拿它做两件事 ——
> 写卡片壳的 `path`，以及**自动在右栏打开这枚文书**（见 §7.3）。文书在工作空间里，
> 所以这件事只要复用既有的文件标签机制，不需要新开一条右栏通道。

**唯一投递路径（评审 P1-3）**：`execution_mode_changed` 有**两个触发源**（用户点 tag /
goal 自动回落），但只有**一条投递路径** —— `SessionRuntime._bind_sink` 往 agent 注入
`execution_mode_sink`（实现是 `lambda kind, payload: deliver(kind, payload)`），两个源都经它
走 `deliver()` → `hub.broadcast`。

> 为什么必须这样：agent 侧**没有 `hub`**（全仓 `hub` 只在 `ws_bridge`），而 Stop 边界同步跑在
> **工作线程**。`deliver()` 内部是 `call_soon_threadsafe` + 广播全连接，**线程安全**。
> 若一边 `hub.broadcast`、一边走流式 `event`，就是两套口径 —— 项目里踩过同类漂移。
>
> agent 侧未接线时（CLI / 单测）`execution_mode_sink is None` → **静默跳过**，行为与改造前一致。

### 6.3 `session_history` 新增 6 字段

`session_history`（切会话 / 回放）的 payload 追加（与既有 `permission_mode` 同处，**两处构造点**
共用 `_exec_mode_fields()` 组装，避免口径分叉）：

```
execution_mode  : "normal" | "plan" | "goal"     （读值 `or "normal"` 兜底，零迁移）
plan_status     : null | "ready" | "approved"
plan_path       : string | null                  （**落 meta 的 `plan_name` 派生**，见下）
goal_condition  : string | null
goal_round      : int | null                     （2026-09-30 追加：= active.iterations）
goal_started_at : float | null                   （2026-09-30 追加：= active.set_at，Unix 秒）
```

**`plan_path` 的语义（2026-09-29 改版，判据唯一在 `paths.plan_display_path`）**：
它**不在 meta 里存路径**，而是由 meta 的 **`plan_name`** 现算 —— 但 `plan_name` 必须落盘，
因为文件名由模型给，路径再也无法由 `sid` 推出（不存这一份，切会话后就会"读不到自己刚写的
文书"）。三条出口（`execution_mode_changed` / `session_history` / `sessions` 列表）**共用
同一个函数**，避免某一条通道漏掉回退逻辑：

| `plan_status` | `plan_name` | 返回 |
| --- | --- | --- |
| 空 | 任意 | `null`（没有计划状态就没有路径） |
| 非空 | 有 | `.aiagent/plan/<name>.md`（**相对工作空间**） |
| 非空 | 无 | 存量会话 → 旧的元数据目录绝对路径 |

> **历史形态（已废弃）**：`plan_path` 曾"**派生**给出、不落 meta"，理由是"落哪个文件由 sid
> 唯一决定，再存一份就是第二真相源"。2026-09-29 文件名改成模型给之后这条理由失效 ——
> 现在存的是**名字**（不是路径），路径仍由一处函数现算，第二真相源的问题并没有回来。

### 6.4 `sessions` 列表载荷新增 6 字段（重连的唯一通道，评审 P1-13）

`session_history` **只在收到 `session_switch` 后**才发出；而连接建立时的重放序列
（`projects` / `session_status` / `ask_request` / `approval_request`）**不含它**。前端重连时只做
`resetTransient()` + `listSessions()`。

因此 6 个字段**必须同时**进 `sessions` 列表载荷（`list_sessions` 白名单，与 `permission_mode` /
`unread` 同通道）：

```json
{
  "id": "Kx7mQ2vT8p", "title": "…", "project": "default",
  "execution_mode": "plan",
  "plan_status": "ready",
  "plan_path": ".aiagent/plan/nav-tree 接口实现计划.md",
  "goal_condition": null,
  "goal_round": null,
  "goal_started_at": null
}
```

> `plan_path` 是**相对工作空间**的路径（存量会话例外，见 §6.3 的表）—— 因为右栏标签与
> `file_read` 都用这个口径，前端才能直接拿它去 `openFileTab`。
>
> `goal_round` / `goal_started_at`（2026-09-30）：常驻目标条的重连恢复源。**少了它们，
> 目标条会在重连后带着错误的轮次复活** —— 而 `session_history` 这条通道此时是空的。
>
> 前端两条链路都要消费它：`refreshSessions()` 与 `case 'sessions'` —— 两处都走
> `mergeExecFromSessions()`（无变化时**返回原引用**，避免 zustand 无谓重渲染）。

### 6.5 IPC 通道（渲染 ⇄ 主进程）

| 通道 | 载荷 | 说明 |
| --- | --- | --- |
| `invoke('agent:send')` | `{text, session_id?, project_id?, overrides?, model_id?, attachments?, refs?, **exec_mode?, exec_condition?**}` | 预选执行模式随首条消息带上（2026-09-27）。形状校验：`sessionId === undefined`（新建）才读，且 `exec_mode` 必须在 `['plan','goal']` 白名单内，`exec_condition` 仅 goal 时透传 string |
| `invoke('agent:sessionExecMode')` | `{sessionId, mode, condition?}` | 发 `session_exec_mode`，**fire-and-forget**（回执走广播）。形状校验：`isTrustedSender` + `session_id` 非空 + `mode` 白名单；`condition` **仅** `mode==='goal'` 时读且须是 string |
| `invoke('agent:planApprove')` | `{sessionId}` | 发 `plan_approve`，**fire-and-forget** |
| `invoke('agent:planRead')` | `{sessionId}` | 发 `plan_read`，**有真回执** → `plan_content`（走主进程 `request()` 配对） |

**两条链路，不是"三层"（评审 P2）**：

```
Electron（4 段）：renderer → preload(bridge) → main(IPC handler) → ws.send → ws_bridge
浏览器调试态（2 段）：browserAgent 直连后端 WebSocket（绕过 preload / main）
```

| 文件 | 改动 |
| --- | --- |
| `main/index.ts` | 三个 `ipcMain.handle`（紧接 `agent:sessionPermission` 之后；该文件**无统一注册表**，逐个内联注册）。前两个 `return` 空（fire-and-forget）；`planRead` 走 `request('plan_read','plan_content',{session_id})` |
| `preload/index.ts` + `preload/index.d.ts` | 暴露 `sessionExecMode(sessionId, mode, condition?)` / `approvePlan(sessionId)` / `planRead(sessionId)`。**两文件都改**（`.d.ts` 是渲染层类型来源，漏改则 `typecheck:web` 编译不过） |
| `protocols/agentProtocol.ts` | `ControlKind` 加 3 个 kind；`UiEvent` 加 3 条信封（+ `goal_check`）；`session_history` payload 与 `SessionMeta` 各加 6 字段；新增 `ExecutionMode` / `PlanStatus` / `GoalAction` / `GoalMarker` / `ExecutionModeChangedPayload` / `PlanContentPayload` |
| `lib/browserAgent.ts` | **它不是 mock，是浏览器回退桥**（真连 WS）。实现 3 个方法（不加则 `typecheck:web` 失败）。它**不维护信封清单**（只用泛型 `sendRaw` / `request`），所以"给它加两个信封"这个说法不成立 —— 但它**仍要上行所有收到的信封**给 store |

**点对点信封不设 `handleEvent` 分支**：`plan_content` 与 `file_content` 同款 —— 主进程
`request()` 按 `kind` 全局配对（不带 request id），渲染层只在 `fetchPlanContent` 里从返回值
落库即可。

**`session_exec_mode` 不进主进程 `pending` 表**（fire-and-forget、`ws.send` 直发），与
`session_ui` 同款纪律。

> **2026-09-30 目标可见化：IPC 三件套一行未改。** 本次没有新增"渲染 → 后端"的命令
> （入口仍是既有的 `chat.exec_mode`），`goal_check` 是**后端 → 前端**的广播，
> 经 `main/index.ts` 的 `onEvent` 全量转发、`lib/browserAgent` 的泛型 `sendRaw` / `request`
> 直连 —— 两者都不维护信封白名单。**新增"后端 → 前端"信封时不需要动这三处**，
> 只有新增命令才要（这条值得写下来，省掉下次的无效劳动）。

### 6.6 消息级 `goal` 字段（2026-09-30 目标可见化）

jsonl 的 **user 行**可旁挂一个 `goal` 结构化字段（与既有的 `created_at` / `usage` / `approval`
同族的**纯展示元数据**：加载保留、模型上下文由 `MODEL_MSG_FIELDS` 白名单剔除）：

```json
{
  "role": "user",
  "content": "…",
  "created_at": "2026-09-30T10:00:00",
  "goal": {
    "kind": "instruction | set | check",
    "condition": "把 nav-tree 接口的任务数统计做完",
    "action": "block | achieved | failed | limit | error | defer",
    "round": 3,
    "reason": "评估器原文",
    "elapsed": 95,
    "tokens": 45210,
    "at": "2026-09-30T10:05:00"
  }
}
```

| `kind` | 谁写的 | 写在哪条消息上 | `content` | 前端怎么渲染 |
| --- | --- | --- | --- | --- |
| `instruction` | `run_turn(goal_instruction=…)` | **用户那条目标指令**（正文=用户原话） | 用户原话 | 照常气泡 + 头部挂 `GoalBadge` |
| `set` | `_append_goal_set_message` / ws_bridge 手工补的那条 | `[Goal set]` 消息 | `[Goal set] Condition: …`（**给模型看，一字不改**） | `GoalCheckCard` 的 `set` 分支（「目标已设定」） |
| `check` | `_note_goal_check` → 落盘 | `block`：`[Goal still active]` 那条；其余：**空正文**的独立行 | 见 §2.7.3 | `GoalCheckCard`（「目标检查」+ 结论徽标 + 偏差 + 统计） |

**唯一的字段级约定**：`goal` **不在 `MODEL_MSG_FIELDS` 白名单里**。这是本设计成立的前提
—— 任何"挂进 jsonl 就不会漏进请求体"的保证都来自这一行白名单，改动它等于改动这条契约
（`tests/test_goal_visibility.py::test_goal_field_never_leaks_into_model_request` 钉着）。

**回放端的分流**（`_history_to_ui` 的 user 分支，顺序是硬约束）：

1. `is_tool_images_message` 跳过（既有）；
2. **`goal.kind ∈ {check, set}` → 转成 `role:"goal_check"` 的展示卡并 `continue`**；
3. `content.startswith("<system-reminder>")` 跳过（既有，注入不可见）；
4. 否则按 user 气泡渲染，**仅在确有 `goal` 时**透传该字段（`instruction` 走这条）。

> ⚠️ 第 2 步必须在第 3 步**之前**：判据按 `kind` 走、不依赖正文内容（check 记录正文是空串，
> 本就不命中前缀判断），但顺序写反会让`set` 那条带 `[Goal set]` 正文的记录先被前缀判断放过、
> 漏成用户气泡 —— 这正是要避免的那个形态。

## 七、前端

### 7.1 胶囊 tag（`ExecutionModeTag.tsx`）

- **位置**：输入区工具栏 `.toolbar-left` 的**末位**，即**工作空间 chip（`.ws-select`）右侧**、
  `.toolbar-right` 之前（`.ws-select` 原本就是左组最后一个子节点）。
- **零占位**：`mode === 'normal'` 恒 `return null` —— 工具栏尺寸与 DOM 顺序都不受影响，不需要
  任何"空槽"补偿。
- **形态**：胶囊（`border-radius` 全圆），图标与 `+` 菜单一致（`listTodo` / `target`），文案
  「计划模式」/「目标模式」，`data-exec-mode` 供 CDP 定位。与权限盾牌 chip 刻意**不同形态**
  （那是另一条轴，视觉上不该被误认成同类开关）。
- **关闭**：鼠标悬停时右侧浮出 `×`（`.exec-chip-close` 默认 `display:none`）。样式照
  `.ref-capsule:hover .ref-icon-remove` 写，**不是**照常显 `×` 的 `.att-chip`。
- **`title` 话术三态**（plan 待批准 / plan 已批准 / goal 带条件），并统一带「点 × 关闭」。
  2026-09-30 增第四态：**goal 武装中**（`goalArmed`）→"目标模式：下一条指令将作为目标条件，
  之后朝它反复推进。点 × 关闭"。
- **武装态视觉**（2026-09-30）：`.exec-chip.goal.armed` 加一层**虚线描边**
  （`border:1px dashed rgba(accent,.55)`）+ `data-goal-armed="1"`（供 CDP 定位）。
  虚线语义与 `.md-path-link-unknown` 同族（"尚未落定"），不新增颜色 —— 这一刻后端还是旧
  模式，用实心高亮会让人以为模式已经生效。
- 点 `×` → `switchExecMode('normal')`，**不乐观清态**（§7.7）。武装态下点 `×` 只清本地位
  （§2.6 边界表）。

### 7.2 目标模式：**点选即武装**（原 `GoalInputDialog` 弹层已于 2026-09-30 下线）

- 触发：`+` 菜单点「目标模式」。
- **现在做什么**：只调 `switchExecMode('goal')` → 写 `goalArmBySession[sid]`（或新会话态写
  `pendingExecMode='goal'`），**不弹任何 UI、不发任何命令**。胶囊当场亮起（§7.1 的虚线武装态），
  提示语说明"下一条指令将作为目标条件"。
- **条件从哪来**：`send()` 把该条消息的正文作为 `exec_condition` 一起送走（§2.6）。
  正文为空时由后端用 `[附件] 文件名` / `[引用] 文件名` 兜底 —— 所以**纯附件消息也能进入
  目标模式**，不会出现"点了没反应"。
- **长度校验只剩后端一处**：`MAX_GOAL_LENGTH`（4000）在 `GoalController` 与
  `_goal_condition_from_message` 的调用点判；超长**静默忽略**整个预选（草稿态绝不阻断发送），
  前端不再有"超长就禁用确定"这一步（没有输入框了）。
- **为什么删掉弹层**（用户原话见 §2.6）：条件本来就是用户下一句要说的话，让他在弹框里
  提前抄一遍，等于同一条意图说两遍；而且弹层是**阻塞式**的 —— 点了目标模式却还没进模式，
  必须先填完条件。武装态把这两步合成一步，且胶囊在点选那一刻就有反馈。

### 7.3 计划卡片（`PlanCard.tsx`）—— 对话里的**锚点行**

**位置：消息流末尾**（由 `MessageList` 渲染，与既有 `orphanApprovals` 同款先例）。

为什么不做"锚定产出该计划的 assistant 消息"（原方案写法）：**那条链路不存在** ——
`plan_ready` 不带 `message_id`、`Message` 类型没有 plan 字段、store 里也没有"消息 id → 计划"
的映射。而既有三条锚定先例的锚点都是**消息内部已有键**（`toolCallId` / `contentOffset`），不是
消息 id 级的外部映射。改为"贴消息流末尾"是**零新增锚定机制**，且 `plan_status` + `plan_path`
两个字段就足以还原锚点 → 实时与回放天然一致。

**2026-09-29 二次改版：卡片"变薄"—— 正文与操作都不在这里。** 上一版把**整份 Markdown
正文**渲染在消息流里（限高 420px）并承载行动区，两处问题：

1. **正文不该在这里。** 计划文书写在工作空间内（`.aiagent/plan/<name>.md`），生成完就
   **主动在右栏打开**了 —— 对话里再铺一遍全文等于同一份东西看两遍，还把消息流顶得很长。
2. **操作不该在这里。** 用户拍板的形态是"操作选项**替换输入框的位置**"（§7.3.1）——
   决策就在手边、且与自由输入互斥。动作留在卡片里会让"到底该点哪儿"变成两处。

于是卡片只剩**一个职责**：在消息流里标出"这里产出过一份计划"。形态是一行：


```
┌──────────────────────────────────────────────────────────┐
│ ▎≡ 执行计划   [打开文档] [选择操作]              [待批准] │
│ ▎  计划文书已生成，正文在右侧面板中打开                    │
└──────────────────────────────────────────────────────────┘
```

- **左侧色条**（`border-left:3px`）表示"这是一份文书"，刻意不复用消息气泡样式（它不是一条
  消息）。它**没有 approved 变体** —— 原先"换 `--color-ok` 绿"的规则已随 `.approved` 一并
  删除（四次改版，见下）。
- 下方一行 `.plan-card-line`（二态互斥）：待批准 → "计划文书已生成，正文在右侧面板中打开"；
  `lost` → 换成**原因**并转琥珀色 `--color-warn`。
- **`lost` 的含义变了**：上一版它表示"正文没读到"，现在表示"**文书不存在**"
  （被清理 / 空间目录不可用 / 超 `file_preview_max_bytes` 整份拒绝）。正文因此**仍然照拉**：
  `fetchPlanContent`（`plan_read`）保留下来，用途从"显示"变成"判定能不能批准"（§4.4）——
  操作栏里的「开始执行」据此禁用。
- **「打开文档」**：`openPlanDocInPanel(sid, plan.path)` → 右栏落一枚**常驻**文件标签。
  生成时已经自动开过一次，但用户可能已把标签关掉 —— 这里给一个随时可用的入口。
  仅在 `isPlanDocOpenable(path)` 为真时渲染（存量会话的绝对路径右栏打不开；与其给一枚
  点下去必然失败的死按钮，不如不给）。**判据唯一在 `agentStore`**（卡片与操作栏共用）。
- **「选择操作」**：把操作栏请回输入区位置。**只在操作栏当前被收起时渲染**
  （`ChatPanel` 传 `undefined` 即不渲染）—— 收起态唯一来源是用户在操作栏里选了
  「暂不执行先看方案」（§7.3.1）。**这也是这张卡片存在的第二个理由**：没有它，
  用户收起操作栏后就再也叫不回来了。
  **执行期间（`isSending`）禁用**（2026-09-29 五次改版）：本轮还在跑的时候，用户不该
  再有"做决定"的机会 —— 见 §7.3.1 第 3 条与 §12.10。

**2026-09-29 四次改版：这张卡片只在"等你做决定"期间存在（`ready`）。**

**触发**（用户原话）："执行计划这一栏为什么一直在显示？我们讨论一下，是不是应该点了任意的
选项执行下一步时都应该隐藏掉？只有需要继续操作该计划时才显示……已经批准的计划直接转为普通
的执行模式了，这个也应该隐藏吧。"

上一版让 `approved` 的壳**恒留**，理由是"作为历史"（§12.6 的原始口径）。但壳贴在消息流
**末尾**、不锚定产出它的那条消息（这条链不存在，见上）—— 于是它既不是历史（不跟着历史走），
也不是状态（`approve_plan` 已把 mode 回落 `normal`，卡片上那句"**正在按计划执行**"**当场
就是错的**），只剩一条过期横幅赖在屏幕上，直到会话结束。

现在 **`approved` 的壳根本不会存在**：判据唯一收在 `agentStore.planShellAlive`
（`status === 'ready'`，同时是类型谓词），**三条通道共用** —— 漏改任何一条，壳都会从那个
入口复活（上一版正是只在部分入口实现，"批准后横幅赖着不走"因此不是修一处能好的）：

| 通道 | 位置 | 行为 |
| --- | --- | --- |
| 广播 | `execution_mode_changed` | `planShellAlive(st)` 为真 → 建/更新壳；否则 `mode !== 'plan'` → 撤壳 |
| 回放 | `session_history` | 同判据。覆盖"**批准后切进这个会话**" —— 壳不跟着回放回来 |
| 列表重建 | `mergeExecFromSessions`（断线重连 / 整页重载的唯一恢复源） | 同判据，且**有建也有撤** —— 撤壳支路是四次改版新加的；`resetTransient` 并不清 `planBySession`，少了它内存里的旧壳没有校正面 |

**为什么判据只看 `status`、不看 `mode`**：批准与"清空计划状态"在后端**都**伴随 mode 离开
plan，所以 `approved` 直接判死即可；而 `ready` 恒活 —— 若给 `ready` 也加上 mode 条件，
前一条 `execution_mode_changed` 一旦丢失（断线），壳就永远建不出来。

改完之后"贴消息流末尾"这个位置（见上）才真正自洽：**既然只在待批准期间短暂存在，不锚定
消息位置就不再是缺陷**。撤掉也不丢信息 —— 反馈由操作栏收起 + 执行模式胶囊 + 消息流里那条
`[计划已批准]` 续跑消息承担；文书本身是工作空间里的真实文件（`.aiagent/plan/<name>.md`），
**右栏标签不随壳走**（它是常驻文件标签，`right_panel` 会话级持久化）。

**已知取舍**：会话**忙碌中**批准时后端只落状态 + 回 error 文案、**不起续跑轮**（场景表 #1），
所以那次批准**没有** `[计划已批准]` 消息落进历史 —— 撤壳后消息流里只剩那句 toast。要补
干净需在后端加一条系统消息（**动引擎层，本轮未做**）。

**生成立即自动展示**：`plan_ready` 到达时（`agentStore` 的 case 分支）若该会话是**当前会话**，
自动调同一个 `openPlanDocInPanel` —— 后台会话产出计划**不**抢走用户眼前的视图。
**这是"正文不再进对话"成立的前提：不打开右栏，用户就等于看不到计划。**

**正文（Markdown）由右栏渲染**：`*.md` 在 `FilePreview` 里走**渲染**分支而不是源码视图
（2026-09-29 新增，19 篇 §5.7）—— 渲染纪律与消息正文同源（21 篇 §6.1 事故）：**绝不产出
可导航元素**，外链只放行 `https?:`（`target="_blank" rel="noreferrer noopener"`，交主进程
`setWindowOpenHandler → shell.openExternal`），其余链接降级为纯文本。

**已知限制**：计划文书是**单份覆盖**（每会话一条 plan 状态），换名重规划时上一版文件会被
清掉（§4.5）。

### 7.3.1 计划操作栏（`PlanActionBar.tsx`）—— 占**输入框的位置**

**位置：输入框的位置**（`ChatPanel` 的 `.composer-wrap` 内，与 `InputBox` 同父容器）。
待批准（`plan.status === 'ready'`）**且会话空闲（`!isSending`）**期间由它**顶替输入框**
（后半个条件是 2026-09-29 五次改版补的，理由见下面第 3 条与 §12.10）：

```
┌──────────────────────────────────────────────────────────┐
│ ≡ 执行计划已就绪  正文已在右侧面板打开         [打开文档] │
│ ○ 开始执行                                                │
│ ● 继续修改        ← 选中后就地展开输入框                   │
│ ○ 其他                                                    │
│ ○ 暂不执行先看方案                                         │
│ [ 输入框（仅「继续修改」/「其他」选中时出现） ]             │
│ 选一项后点「确定」                                  [ 确定 ] │
└──────────────────────────────────────────────────────────┘
```

**「确定」= 收起本栏 + 执行动作**（2026-09-29 用户拍板，四个选项一律如此）：
`submit()` 的第一件事就是 `onDismiss()`，然后才 `onApprove()` / `onSendText()`。
上一版只有「继续修改 / 其他」清了选中态，而本栏的渲染条件是 `plan.status === 'ready'`
（要等后端广播才变）—— 于是点了「确定」之后四个选项还原地杵着，看起来像"没生效"
（「开始执行」尤其明显：批准与否由广播校正，中间那段画面完全静止）。
收栏即把输入框还回来，动作在后台照常发生（`plan_approve` / `send` 都已发出，
视觉反馈由消息流与胶囊承担）。

**"操作与自由输入互斥"是布局事实**：`.chat--plan` 下 `.composer` 整块 `display:none`，
选择框占的就是它的位置（左右留白由父级 `.composer-wrap` 统一承担，与消息列严格对齐）。
`InputBox` **不卸载**（`suspended` 只收回焦点，草稿不丢）—— 与 ask 面板的让位同一套手法。

三条连通约束（改动时一起看）：

1. **只隐藏 `.composer`，不是整个 `.composer-wrap`** —— 后者会把操作栏自己一起藏掉。
   （ask 面板的 `.chat--asking` 反过来：它要整块让位，于是隐藏的是 `.composer-wrap`。
   两条让位的选择器层级不同是**刻意**的，合并成一个类会把其中一种场景弄坏。）
2. **收起态有两条入口**（`onDismiss`）：① 「暂不执行先看方案」；② **点了「确定」**（见上）。
   上一版「暂不执行先看方案」是"打开右栏 + 一句说明、留在原地"，但本栏占着输入框位置 ——
   留在原地等于把用户**锁死在四个选项里**（连"退出计划模式"的胶囊 `×`、模型切换、权限盾牌
   都在被隐藏的输入区）。语义是：收起本栏、输入框回来，计划模式照旧生效。
   收起态（`planBarOff`）住在 **`ChatPanel`**（操作栏收起即卸载，组件内 state 会跟着消失）；
   **复位判据是整条 `plan` 对象的身份**（不是 `path|status`）：重新产出的一版是同 path、
   同 status（后端单份覆盖），用那两个字段判不出"新一版来了"，用户每轮修改都得去卡片上
   手动把操作栏请回来。身份变化只发生在 store **替换**该会话的桶时（`plan_ready` / 模式广播 /
   `plan_read` 回填 / 回放），且这些上游都有"无变化则返回原引用"的守卫；切会话即复位。
   另一条随时可用的入口是卡片上的「选择操作」（操作栏被收起时它才渲染）——
   但它**在执行期间同样禁用**（第 3 条）。
3. **执行期间本栏干脆不出现**（2026-09-29 五次改版，`planBarShown` 追加 `!isSending`）。
   触发场景（用户原话）："我点了「继续修改」，模型正在执行'方案再详细些'的时候，
   我却又点开了操作选项、点下「开始执行」—— 操作和执行都乱了。"
   根因是**同一时刻"正在执行"与"有一份 `ready` 计划"会同时成立**：「继续修改」提交后
   模型起新一轮，而新一轮的 `plan_ready` 就在**这一轮之内**（写文书只是本轮的一个工具
   调用，模型随后还要输出收尾文本）。这段时间里若不设防，卡片上的「选择操作」随时能把
   本栏请回来，四个选项照常可点 —— 而 `plan_approve` 在 `rt.busy` 时**照样落盘
   `approved`、只是不起续跑**（`ws_bridge` 只回一句 toast），于是壳被撤掉、用户以为
   已在执行，实际还得再发一条消息。
   现在的纪律：**执行期一律不占输入区**（本栏不渲染，卡片上的入口同时禁用、`title`
   说明"本轮结束后可再选择操作"），等本轮落地（`isSending` 回落）再弹。而"要不要弹"
   （`planBarOff` 收起态）仍由**计划对象身份**复位 —— 新一轮 `plan_ready` 已把它清掉，
   所以**本轮一结束操作栏自动回来**，用户不必再去卡片上手动请（实测见 §12.10）。
   两处判据**必须同源**（都是 `isSending`）：`ChatPanel` 管"不占位"，`PlanCard` 管
   "不给入口"，漏一处就能绕过。
   **本栏因此不再自带「停止」**：上一版有它是因为"占位期间输入区的停止按钮被 `.chat--plan`
   一起藏了"，而现在本栏只在空闲时出现、执行期输入区照常显示（那粒停止按钮也在）——
   那支分支成了死代码，已删。

四个选项**固定**（`CHOICES` 常量，刻意不做可配置 —— 它们是"拿到计划之后能做的全部动作"）：

| 选项 | 行为 | 需要输入 |
| --- | --- | --- |
| 开始执行 | `plan_approve`（fire-and-forget，**不乐观转只读**）+ 收起本栏 | — |
| 继续修改 | 把输入的文字作为**一条用户消息**发进本会话（plan 保持）+ 收起本栏 | ✓ |
| 其他 | 同「继续修改」——**同一条通道**，模型侧不必区分二者 | ✓ |
| 暂不执行先看方案 | **收起本栏**（输入框回来）+ 保证右栏有这份文书（**点选即生效**，不必再点确定） | — |

两条刻意的取舍：

1. **「继续修改」/「其他」走同一条发送通道**：区别只在用户心里，多造一个协议字段没有收益。
2. **`lost` 时只禁用「开始执行」**：批准一份读不到的文书没有意义；但"继续修改"仍可行
   （模型手上有上下文），所以不整块禁用；原因就显示在选项上方（`.plan-bar__lost`）。

**已批准 / 模式退出 / **正在执行** → 本栏消失**：渲染条件是 `status === 'ready'`
（撤壳判据与锚点行**同源** —— `planShellAlive`，§7.3 四次改版）**且 `!isSending`**
（2026-09-29 五次改版，见上第 3 条）；三种情形下输入框都原样回来（分别是"改代码才是
正题"与"本轮还没落地"）。渲染与让位判定都收在 `ChatPanel` **一处**，不散落到卡片里。

**为什么不再聚焦输入框**（旧版行为）：文字现在是在操作栏里**主动写下**的（点选项才出现
输入框、还要再点「确定」），不存在"半截提示被当成用户意图"的风险 —— 当初不自动发的唯一
理由因此消失。`InputBox` 的 `focusSignal` 随之删除（它只服务旧版的「继续修改」）。

- `handlePlusPick` 新增 `planMode` / `goalMode` 两分支（替换原 toast 占位）：

- `activeKey` 从"预留位"变为**真实接线**（映射 `plan` / `goal` / `null`）——
  **无会话时映射的是 `pendingExecMode` 草稿**、**已有会话武装中映射的是武装位**（2026-09-30），

  连带的 `ChatPanel.handleRevisePlan` 也换成了 `handlePlanSendText`（`send(text, [], [])`）。
- 发送消息携带预选模式（`chat.exec_mode`，§6.1）的判据（2026-09-30 更新）：
  `sid === null` → 读 `pendingExecMode`；**已有会话 → 读 `goalArmBySession[sid]`**（武装位）。
  两者都不命中时 payload 形状与改造前逐字节一致（零字段）。
  **例外**：武装中若有在途提问（`interactionBySession[sid]` 非空）→ 本条消息是"作答"，
  不交棒、payload 不带 `exec_mode`，武装位留到下一条真指令（§2.6）。

### 7.5 `agentStore` 的状态与清理规则

```ts
type ExecutionMode = 'normal' | 'plan' | 'goal'
type PlanState = { path: string; status: 'ready' | 'approved'
                   content?: string; reason?: string; tooLarge?: boolean }
// `path`（2026-09-29 改）：**相对工作空间**的 `.aiagent/plan/<name>.md`；
// 存量会话是旧口径的绝对路径。判据在 `paths.plan_display_path`（§6.3）。
// `plan_read` 回执里的绝对路径**不**覆盖它 —— 两种形态混进同一个字段会让
```

`GoalBarState = { condition: string; round: number; startedAt: number | null }`
（`round` = 后端 `active.iterations`，条上显示 `round + 1`，**+1 只在 `goalBarRoundLabel` 做一次**）。

`goalBarBySession` 的 **4 条来源**（判据一律 `goalBarAlive(mode, condition)` =
`mode === 'goal' && !!condition`，**四条共用同一个函数**；任何一条漏改，目标条就在那个入口
复活或消失）：

| 来源 | 行为 |
| --- | --- |
| 广播 `execution_mode_changed` | 判据真 → 建/更新（`round` 缺省沿用本地值，真正推进靠 `goal_check`）；假 → 撤条。同时**顺带**做乐观徽标收敛（§2.7.5） |
| 回放 `session_history` | 同判据；**含"反向"分支** —— 回放一个已结束目标的会话时必须撤掉内存里的旧条（否则它带着上一个目标的条件赖在输入区上方） |
| 列表重建 `mergeExecFromSessions` | **断线重连 / 整页重载的唯一恢复源**（`resetTransient` 并不清这个桶）—— 少了它，重连后目标条消失或带着旧轮次复活 |
| 实时 `goal_check` | **只更新 `round`，不改存亡** —— 目标成没成由 `execution_mode_changed` 决定 |

清理：`dropExecBuckets` **第 4 桶**（`clearSession` / `deleteSessions` / `removeProject` 三处共用）
+ `clearSession` 里显式删。

`goalBarAlive` 与 `planShellAlive` 的**同一条纪律**（§7.5 撤壳那段）：三条恢复通道缺一即静默失效。
两者的差别只有一处 —— 计划壳的存活只看 `status`，目标条的存活看 `mode + condition`（因为
`execution_mode` 只是投影，mode 说 goal 而条件为空是"投影与真相不一致"的中间态）。

`goalArmBySession` 的 read/write 点（**只有 6 处**，改动时六处一起看）：

| 时机 | 行为 |
| --- | --- |
| `InputBox` 的 `goalArmed` / `execMode` selector | **读**：胶囊亮（虚线态）+ `execMode` 派生优先返回 `'goal'`（后端此刻还是旧模式，但用户已表达意图，点选必须有反馈） |
| `switchExecMode('goal')`（有 sid） | **写**：置位（已武装 / 后端已 goal → 幂等短路）；**不发命令** |
| `switchExecMode('normal' \| 'plan')`（有 sid） | **清位**：`normal` 只清本地位（不误杀后端 plan）；`plan` 清位后**真发** `session_exec_mode(sid,'plan')` |
| `send`（有 sid） | **读 + 交出并清空**：交出时同步登记 `executionModeBySession[sid]='goal'`（防闪，见 §7.7 例外表）；在途提问期间**不交棒**（武装位留着） |
| `execution_mode_changed` 广播 | **兜底清位**：后端给出本会话模式的唯一权威，无论值是什么，武装位的使命都结束了 |
| `clearSession` / `deleteSessions` / `removeProject` | **清位**：`dropExecBuckets` 三桶同清（会话都归零/没了，孤儿草稿无意义） |

`pendingExecMode` 的 read/write 点（**只有 4 处**，改动时四处一起看）：

| 时机 | 行为 |
| --- | --- |
| `InputBox` 的 `execMode` selector（`activeSession === null`） | **读**：胶囊/菜单勾选显示草稿 |
| `switchExecMode`（无 sid） | **写**：记草稿（同值短路），**不 toast 不发命令** |
| `send`（`sid === null`） | **读**：`pendingExecMode !== 'normal'` → 随 `chat` 带 `exec_mode`；`goal` 的条件 = 本条消息正文 |
| `session` 信封（`wasFresh`） | **交接并清空**：登记 `executionModeBySession[sid]`，草稿复位 `normal` / `''` |
| `newSession()` | **复位**：不跨新任务继承 |

| 时机 | 行为 |
| --- | --- |
| `execution_mode_changed` | 写 `executionModeBySession[sid]`；`planShellAlive(plan_status)` 为真（⇔ `ready`）→ 建 / 更新卡片壳（保留已拉的正文与 reason）。否则若 `mode !== 'plan'` 且该会话有壳 → **连壳一起撤** —— 覆盖回落 normal、**跨模式直接切到 goal**、以及**批准后回落**（四次改版，见下） |
| `plan_ready` | 只写卡片壳 `{path, status:'ready'}`（保留已拉的 `content`），随后 `void fetchPlanContent(sid)` 拉正文（**副作用必须在 `set()` 之外**）；若该会话是**当前会话**且带 `plan_path` → `openPlanDocInPanel(sid, path, name)` **自动在右栏打开文书**（2026-09-29） |
| `plan_approve` 后 | 由 `execution_mode_changed`（带 `plan_status:'approved'`）校正为只读态 —— **前端不乐观转** |
| `session_history` | 6 字段恢复：`execution_mode` → tag；`plan_status` + `plan_path` → 卡片壳；若 `plan_status` 为空且 `execution_mode !== 'plan'` → **撤掉旧壳**（同下）；`goal_condition` + `goal_round` + `goal_started_at` → **常驻目标条**（走 `goalBarAlive`，含撤条的反向分支）；然后按需 `plan_read` 拉正文 |
| `goal_check`（2026-09-30） | **向 `messagesBySession[sid]` append 一条 `role:'goal_check'` 的 Message**（`goal` 承载 action/round/reason/elapsed/tokens）；`goalBarBySession[sid].round = payload.round`（**只推轮次，不动存亡**） |
| `sessions` 列表载荷 | 走 `mergeExecFromSessions()` —— **断线重连 / 整页重载后恢复 tag、卡片壳与目标条的唯一通道**；同时是**乐观徽标的第二个收敛点**（新会话预选路径不推 `execution_mode_changed`，只能在这里落地，§2.7.5） |
| `switchSession` | 新建/切到无记录的会话 → `execModeOf` 的 fallback 链给 `'normal'` |
| `deleteSessions` / `removeProject` | `dropExecBuckets(mode, plan, arm, **bar**, sids)` **显式清理四桶**（**不**照抄 `permissionModeBySession` —— 那个桶五处都不删，属既有泄漏） |

`execModeOf(s, sid)` 的 fallback 链：**内存桶 → `sessions` 列表条目 → `'normal'`**。
武装位（`goalArmBySession[sid]`）**排在这条链之前**（`InputBox` 的 selector 里先判），
因为它是"用户刚表达、后端还不知道"的那一拍。
**无会话时根本不调用它** —— 直接读 `pendingExecMode`（`InputBox` 的 selector），
这是唯一"没有 sid 也能有非 normal 模式"的入口。

**撤壳判据唯一：`planShellAlive(status) === (status === 'ready')`（2026-09-29 四次改版）。**
它取代了上一版"只在 `plan_status` 为空时撤"的口径 —— 后者让 `approved` 的壳永久留存
（详见 §7.3 四次改版）。新旧口径的对照：

| 信封 / 载荷情形 | 旧口径 | 新口径 |
| --- | --- | --- |
| `plan_status` 为空 + `mode !== 'plan'`（回落 normal / **跨模式直接切到 goal**） | 撤壳 | **撤壳**（判据为假 + 模式已离开 plan） |
| `plan_status='approved'` + `mode='normal'`（批准后回落） | **保留**（当"历史"） | **撤壳** ← 四次改版的改动点 |
| `plan_status='ready'` | 建壳 | **建壳**（判据为真） |

不撤壳会留下什么：`plan_status` 为空的那种是"待批准"**死按钮** —— 后端已无待批准计划，
点下去只会换来一句「当前没有待批准的计划文书。」的 error toast，**死按钮 + 内存与磁盘背离**；
`approved` 那种是一条**过期横幅**（§7.3）。切到 goal 时磁盘上的文书文件**不删**，只是前端
不再有它的卡片壳。

- **三条通道都必须实现**（广播 `execution_mode_changed`、回放 `session_history`、
  列表重建 `mergeExecFromSessions`）—— 前两条是老口径就有的，**第三条是四次改版补的**：
  它此前只"建"不"撤"，而 `resetTransient` 并不清 `planBySession`，断线重连后内存里的旧壳
  因此没有校正面。
- `sessions` 列表载荷的**写入端**（切模式时写回 `plan_status`）**不改**：它忠实镜像后端
  meta（含 `approved`），撤不撤是消费端的判断 —— 写入端若也收窄，重连那边就少了一份
  "该撤壳"的依据。

**zustand v5 硬约束**（项目踩坑）：selector 必须返回**引用稳定值** —— `mode` / `plan` 一律用
`useStore(s => s.executionModeBySession[sid])` 这类直接取值（命中即返回已有对象引用），
**禁止**在 selector 里 `map`/`filter`/`Object.values`/构造字面量；派生状态一律 `useMemo`。
`mergeExecFromSessions` / `dropExecBuckets` 无变化时返回**原引用**，也是同一条纪律。

### 7.7 「不乐观更新」的统一口径

**tag / chip / 卡片的状态只认 `execution_mode_changed` 广播**，与 `permission_changed` 同款：
点菜单 / 点 `×` / 点「开始执行」都只是**发命令**，UI 等广播。理由：传输丢失时乐观 UI 会说谎。
三条链路（实时广播 / `session_history` 回放 / `sessions` 列表）因此天然一致。

> **唯一例外（2026-09-29 明确）**：`plan_ready` 触发的"**自动打开右栏文书**"是纯副作用，
> 不改任何 tag / 卡片的选中态 —— 它只是替用户把产出物摆到眼前（随时可关）。把它归进
> "乐观更新"是范畴错误：右栏本来就是用户可自由开关的视图，没有"真相"需要等广播校准。

> **第二个例外（2026-09-30，目标模式武装态）**：武装位**不是**"等广播的状态"，它是
> **还没交出去的草稿** —— 后端根本不知道它存在，不存在"广播到达前的谎言"。因此：
> ① 胶囊在点选那一刻就亮（`execMode` 派生里武装位优先）；
> ② `send()` 交出武装位时**顺手登记** `executionModeBySession[sid]='goal'`，只为"草稿
> 已清、广播未到"的那几毫秒不闪一下（口径与 §2.5 的 `session` 信封登记完全一致：
> **真值随后由 `execution_mode_changed` / `sessions` 广播校准**，后端忽略非法条件时
> 会被纠正回 `normal`）。两条都**不改**既有的"只认广播"纪律 —— 它约束的是"已交出去的
> 状态"，不是"还在客户端的草稿"。

> **第三个例外（2026-09-30 二次改版，目标指令徽标）—— 唯一一处真正的乐观更新**：
> "这条消息是目标指令"这个事实，后端要等 `chat` 到达、算完条件才知道，而前端 `send()`
> 那一刻就一清二楚。若坚持"只认广播"，就得为纯展示需求新增一条"这条消息已被确认为
> 目标指令"的信封 + 一个 message id 索引 —— **成本远高于收益**（而这条信息真的错了
> 也只是多一枚小徽标，不会误导任何操作）。
>
> 它因此被明确标成乐观态（`goal.pending = true`）并配了**收敛通道**（§2.7.5）：
> `execution_mode_changed` 与 `sessions` 列表两个权威模式入口都会去**认领或撤销**它。
> 判据只认 `pending === true` —— 已确认的历史徽标（早先那次目标指令）绝不能被顺手清掉。
>
> 与第二个例外的区别：武装位是"还没交出去的草稿"（后端不知道），徽标是"**已经交出去、
> 但后端静默忽略时不会回执**"的那一拍 —— 后端可能知道（并接受）也可能完全没理会，
> 所以必须有收敛通道兜底。

### 7.8 目标可见化的三个新组件（2026-09-30）

| 组件 | 位置 | 渲染条件 | 关键约定 |
| --- | --- | --- | --- |
| `GoalBadge.tsx` | 用户气泡**头部**（`.msg-bubble.user` 第一个子节点） | `msg.goal?.kind === 'instruction'` | `title` 里带条件原文（条件通常就等于正文，不重复铺开）；`data-goal-pending` 供交互验证 |

`MessageItem.tsx` 的接线（三处，缺一即静默失效）：

1. **`role === 'goal_check'` 的分支必须放在 user / assistant 两个分支之前** —— 它既不是
   user 也不是 assistant（它是系统对目标状态的播报）；
2. user 分支气泡头部挂 `GoalBadge`；
3. `MessageList` **不用改**（它已经 `messages.map` → `MessageItem`）。

**`GoalBar` 的三条实现约定**：

- **零占位**：桶里没有本会话条目 → `return null`。存亡判据在 store（`goalBarAlive`），组件
  只读桶 —— **不自判**，否则又多一份会漂移的口径。
- **本地 tick**：`startedAt` 存在时每秒 `setNow`，显示"已运行"；`useEffect` 里**必须立刻
  校准一次 `now`** —— `useState` 初值是组件首渲染（无目标时它也在挂载，只 return null）
  那一刻取的，等目标真设上来时已经旧了。
- **执行期禁用 `×`**：后端在 `rt.busy` 时**拒绝** goal 的进入/退出（`GoalController` 无锁，
  §2.4），这里若不设防，用户点 `×` 只会换来一句 error toast。用**禁用 + `title` 说明**
  （"想结束就先停止本轮"）比让他点一个必然失败的按钮好 —— 与 `PlanActionBar` 的
  `!isSending` 同一条纪律。

**与两条让位的关系**：目标条**不占输入框的位置**，因此与 ask 面板（`chat--asking`，隐整个
`.composer-wrap`）和计划操作栏（`chat--plan`，换掉 `.composer`）**互不干扰** —— 目标模式与
ask 同时发生时，目标上下文不会丢。这是把条放在 `.composer-wrap` **之外**的唯一理由。

## 八、与既有 `GoalController` 的复用边界

### 8.1 铁律

> **goal 的唯一真相恒为 `goal_controller.active`。`execution_mode == "goal"` 只是它的投影。**

推论（代码里逐条兑现）：

- `ExecutionGate` **不持有任何 goal 状态**（只有 `mode` 这个字样投影）；
- 读 `execution_mode` 之前/之后都要**用 `active` 校准**（`execution_state()` 与
  `_restore_execution_state()` 各一处）；
- meta 的 `goal_condition` **不是"第二个目标存储"**，而是 `GoalController._record()` 事件的
  **最小落盘投影**：`active` 非空时记 condition，`active` 为 `None`（clear / achieved / failed）
  时置 `None`。**不要拿它当 goal 状态的读源。**

### 8.2 本期新增的只有四条缝

| 位置 | 内容 |
| --- | --- |
| `set_execution_mode("goal", c)` | 转发**既有** `set_goal(condition, total_tokens)`；`GoalError` 原样上抛（空值 / 超 4000 字校验都在里面）；追加一条 `[Goal set]` 消息；`gate.set_mode("goal")` |
| `_restore_execution_state()` | 从 meta 的 `goal_condition` 重建控制器（`GoalController.restore()`，本期**首次**接入，见 §8.3） |
| Stop 边界 `achieved` / `failed` | 各追加一行调用 `_on_goal_terminated()`（`mode=normal` + 落盘 + 推信封），共 4 行 |
| `rt.busy` 守卫 | 在 `ws_bridge`（goal 的进入/退出不在 busy 时进行） |

**`goal.py` 一行不改**；`set_goal` / `clear_goal` / `goal_status` 的签名与实现不变（CLI 的
`/goal` 路径零改动，有回归断言守护）。

`limit` / `error` / `defer` / `block` 四个分支**一行不动** —— 目标仍激活 → mode 保持 goal →
tag 不撤（与既有语义完全一致）。

### 8.3 `restore()` 是本期新建的链路

`GoalController.restore(evaluator, events, block_cap)` 是既有 `@classmethod`（返回**新控制器**），
但**全仓此前零调用** —— 本期首次接上，因此必须自己补齐三处防御 + 一层字段映射：

| 问题 | 处理 |
| --- | --- |
| `restore` **不做非空校验** | 空 / 空白 condition **不得构造事件**（否则会复活一个 `condition=""` 的空目标） |
| `restore` **不恢复 `consecutive_blocks`** | 恢复后显式归 0 |
| `restore` **不重绑 LLM** | 替换后重新 `set_llm(llm_client, evaluator_model)`（热切换接缝） |
| 字段名不一致 | 真实事件字段是 `{type, condition, active, met, failed, reason, iterations, duration}` —— **没有 `goal_condition` 这个键**。meta 名 `goal_condition` → 事件名 `condition`，需**显式一层映射** |
| 会话切换时的陈旧目标（**实施期新增的第 4 处防御**） | `switch_session` **不重建**控制器，于是 A 会话设的目标会被 B 会话继承、B 的胶囊 tag 会莫名亮起。`_restore_execution_state` 里补：meta 无目标而内存里还挂着 `active` → 重建一个空控制器 |

替换策略：用返回值**整体替换** `self.goal_controller`，最后**用 `active` 校准 mode**。

### 8.4 刻意不做的事

- 不给 `GoalController` 加锁（属改引擎层；改用"busy 时拒绝切换"）；
- 不重写评估器、不新增 goal 判定分支、不新增 goal 状态机；
- 不为 goal 加 system-reminder（§5.3）；
- goal 模式下 `plan_write` 仍被拒绝（goal 不是 plan），写操作走正常权限链。

## 十、取舍理由

### 10.1 为什么不做 Spec 模式

第二个"更重的计划模式"需要有独立语义（多轮迭代 / 评审 / 版本），而当前只有"先出方案再执行"
这一个真需求。多一档就要多一套状态机、多一个 UI 入口、多一处互斥矩阵，且与 plan 的差别说不
清楚 —— 明确列为**非目标**。

### 10.2 为什么不与权限合并判定链

两者回答的是**不同问题**（允不允许 vs 以什么方式干），合并会得到一个"说不清优先级"的链：
`full_access + plan` 到底听谁的？现在的答案是**两条独立轴 + 各判一次**，`full_access` 免审批
但**不免模式墙**。而且 plan 的 bash 只读判定**必须**比权限链更严，合并就等于把语义不同的两份
白名单混在一起（§3.1 的三个理由）。

### 10.3 为什么 goal 不重写

既有 `GoalController` / `PromptGoalEvaluator` / Stop 边界七分支是**已经跑通**的成熟链路
（block 回环、limit 上限、后台 defer、`[Goal still active]` 回注）。重写一遍只会引入新 bug，
且会造出**第二出处**。本期只做薄委托 + meta 喂料 + Stop 边界两行回落广播 —— 新增代码合计
不到 20 行，收益却是完整的目标模式 UI。

### 10.4 为什么卡片挂消息流末尾，而操作栏占输入框位置

见 §7.3：锚定 assistant 消息的链路**不存在**（事件无 `message_id`、`Message` 无 plan 字段、
store 无映射），而"单份覆盖"的文书语义本来就决定了"消息流里只该有最新一份"。贴末尾是
零新增机制 + 实时/回放天然一致的唯一自洽形态。

**2026-09-29 二次改版把两件事拆开了**，不再挤在同一张卡里：

- **正文** → 右栏（生成即自动打开）。它是**文档**，该在文档该在的地方，还能进版本库、
  直接在编辑器里改。
- **操作** → 输入框的位置（`PlanActionBar`）。它是**决策**，该在手边，且与自由输入互斥。
- 消息流只留**锚点行**：标出"这里产出过一份计划"，并给「打开文档」/「选择操作」两个入口。

为什么操作**不**留在卡片里：卡片在消息流末尾，而消息流会随对话继续向下滚 —— 把"现在要做的
决定"绑在一个会离开视线的位置，用户真的会找不到它（何况它上面还压着模型产出的长文）。
输入框位置是唯一"永远在视野内、视线自然落点"的位置。

### 10.5 为什么 `plan_write` 不设 `path` 参数

见 §4.3。落点由后端强制，模型没有"我能换地方写"的错觉，也不会出现"传了 path 但被忽略"的
混乱契约。

### 10.6 为什么工具常驻而不动态裁剪

见 §4.3。动态裁剪要改 4 处工具传参点，收益不抵风险。

### 10.7 为什么 `plan_read` 而不是给 `file_read` 开个后门

`resolve_within(workdir, …)` 这道墙是**右栏文件读取的根基**（防越界读任意文件），为了读一份
自己写的文书去开洞，收益远小于风险。新增专用命令：路径由 sid 唯一决定、不接用户输入、
复用既有降级形状 —— 攻击面为零。

### 12.10 增补：执行期不占输入区、也不给操作入口（2026-09-29 五次改版）

### 12.13 增补：评估器稳定性 —— `invalid JSON` 与"轮次卡在第 1 轮"（2026-09-30 三次改版）

**用户报的现象**：目标模式跑完 4 个子任务后弹出「目标检查 · **评估出错**
`GoalError: goal evaluator returned invalid JSON`」，同时输入区上方的常驻目标条
**全程停在「第 1 轮」**，直到本轮报错结束都没动。

#### 根因（实测复现，不是猜测）

评估器（`PromptGoalEvaluator`）此前**开着思考**且 `max_tokens=512`。deepseek-flash 这类
思考模型会把 completion 预算**先烧在 `reasoning_content` 上**，一旦烧满就
`finish_reason=length` / `content=None`，`json.loads("")` 必然抛错。用同一份会话记录连跑 5 次
实测：**1 次命中**（reasoning 2222 字 > 512 token 预算，content 为空），其余 4 次正常 ——
所以这是**随机复现**的坑，不是模型不会写 JSON（同批次关思考后 6/6 稳定）。

两个现象是**同一个根因**：

| 现象 | 因果链 |
| --- | --- |
| 「评估出错」卡片 + 整轮直接结束 | 解析失败 → `GoalError` → `evaluate_after_turn` 走 `error` 分支（**目标保持激活**，但本轮到此为止） |
| 常驻条停在「第 1 轮」 | `round` = `active.iterations`，而它**只在评估成功返回后 +1**；评估从未成功 → 永远是 0 → 条上 `0 + 1 = 第 1 轮`。条本身没坏，是分母没动 |

> 衍生认知：目标模式下**一轮内可以跑几十次工具调用**，期间不会有任何评估（评估只在
> "模型不再调工具"的 Stop 边界发生）。所以「第 1 轮」长时间不动**本身是正常的**——
> 只有当本轮真的收尾（`block` 回环 / `achieved` / `failed` / `limit`）时它才会推进。
> 本次之所以"一直不动 + 报错"，是因为收尾那次评估失败了。
> §2.7.2 的轮次口径**未改**（`iterations` 依旧只数成功的评估）。

#### 修复（全部落在 `agents/goal.py`，协议/前端零改动）

| 层 | 做法 | 为什么 |
| --- | --- | --- |
| ① 关思考 | 评估器调用固定带 `extra_body={"thinking": {"type": "disabled"}}`（`EVALUATOR_EXTRA_BODY`） | 判官只需"读稿 + 吐一小段 JSON"，不需要推理链。关掉后预算只花在 JSON 上，实测单次 100~220 token |
| ② 预算 | 默认 512 → **1024**，可经 `GOAL_EVALUATOR_MAX_TOKENS` 覆盖 | 给中文长 `reason` 留余量；与 ① 配套（见下注） |
| ③ 解析容错 | 新增 `_extract_json_object()`：括号深度扫描（跳过字符串内部与转义）截出**第一个配对完整**的 JSON 对象；整段解析失败时再试它 | 模型常把 JSON 包在围栏里或前后加一句"好的，判定如下：…" |
| ④ 重试 | 首次失败**换更大预算重试一次**（`EVALUATOR_RETRY_TOKEN_FACTOR = 4`），全失败才抛 `GoalError` | 对"关不掉思考"的端点兜底；契约不变，`evaluate_after_turn` 的 error 分支无需改动 |
| ⑤ 可观测 | 每次失败 `log.warning` 带 `finish_reason` + 输出片段 | 上一次这类故障在日志里只留下一句 `invalid JSON`，拿不到任何原始输出，无法定位 |

> ⚠️ **①②必须配套**：只调大预算能降低概率但消不掉（思考长度无上界）；只关思考不调预算也够用
> （实测 216 token 上限），但留余量更稳。**回归判据**：评估器请求里必须出现
> `thinking: disabled`（`tests/test_goal_evaluator.py::test_thinking_is_disabled`）——
> 丢了它就会退回到"约 1/5 概率随机报 invalid JSON"。
>
> 这条 `extra_body` 通道与主循环 / 子智能体**同一条**（`agent_full_v2._advanced_llm_kwargs`
> 总会带上 `thinking`），因此对任何"能用本项目跑主循环"的 OpenAI 兼容端点都成立，
> 不需要按 provider 做能力探测。
