## 一、概念

### 1.1 两条正交的轴

```
权限轴（既有，本次未改一行）    permission_mode ∈ { default, full_access }
    └ 回答：这个操作「允不允许 / 要不要审批」        ← 规则级，逐条命令判

执行模式轴（本期新增）          execution_mode ∈ { normal, plan, goal }
    └ 回答：这一轮任务「以什么方式干」              ← 模式级，整体行为约束
        normal = 什么都不显示（默认，行为与改造前逐字节一致）
        plan   = 先出方案，未经批准不得改动系统
        goal   = 朝一个明确的目标反复推进直到达成
```

两条轴**可以任意组合**，互不遮蔽：

| 组合 | 语义 |
| --- | --- |
| `default + normal` | 常规：写操作走权限链，危险命令弹审批卡片 |
| `full_access + plan` | 免审批，但计划模式下**写操作照样被拦**（模式级限制不被权限档位越过） |
| `full_access + goal` | 免审批地朝目标死磕 |
| `default + goal` | 朝目标推进，写操作仍按规则级逐条判 |

### 1.2 三种模式的语义

**normal**：默认值。`execution_mode` 为 `None`（存量会话）与 `"normal"` 完全等价 —— 读路径
一律 `.get()` + `or "normal"` 兜底，**零迁移**。

**plan（计划模式）**：只读探索 → 产出计划文书 → 等用户批准 → 才能写。核心承诺是
**「批准前零副作用」**（连 `write_memory` 都拦，见 §3.4）。

**goal（目标模式）**：朝用户给定的完成条件反复推进。**完全复用既有目标能力** —— 评估器、
Stop 边界七分支判定、`[Goal still active]` 回注通道**一行不改**，本期只把它接到执行模式轴上
（详见 §8）。

### 1.3 分层关系（三条轴的职责边界）

| 层 | 回答的问题 | 本次改动 |
| --- | --- | --- |
| 权限管控（17 篇） | 这个操作「允不允许 / 要不要审批」 | **不动**（`permission.py` 一行不改） |
| 沙盒（20 篇） | 命令在 OS 层「实际能碰什么」 | 不动 |
| **执行模式（本篇）** | 这一轮任务「以什么方式干」 | 新增 |

三层是**互补的三道闸**，任一道拦下都走同一个 tool_result 回填契约（模型看到一段可行动的
文案、本轮继续）。判定顺序（自严到宽）：**plan 守卫（模式级）→ 权限判定（规则级）→ 沙盒
（执行期）**。plan 模式下被拦下的命令集合**本就是权限链 allow 集合的真子集**，所以先拦模式
不会掩盖任何硬拒绝语义 —— 反而给模型的信息更可行动（「改用 plan_write 提交计划」而不是
「命令不在白名单内」）。不变量写死在 `execution_mode.py` 的模块注释里并有测试守护：

> **plan 的放行集合 ⊂ 权限链的 allow 集合。**

## 二、状态机与切换规则

### 2.1 plan 的完整生命周期

```
点「计划模式」→ mode=plan（守卫生效）
      ↓
只读探索（run_read / run_glob / 只读 bash / ask_user / 技能与任务查询）
      ↓
调 plan_write 写计划文书 → plan_status=ready
   → 推 execution_mode_changed（带 plan_status="ready"）→ 再推 plan_ready
      ↓
前端渲染计划卡片（正文经 plan_read 拉取）+「批准执行 / 继续修改」
      ├─ 继续修改：用户发自然语言 → plan 保持 → 模型重新产出文书（**覆盖**）
      │            → 重推两张信封 → 卡片就地更新
      └─ 批准执行：plan_approve
                   → plan_status=approved + mode 回落 normal
                   → 注入「[计划已批准] …」续跑指令（用户可见的 user 消息）
                   → 空闲则自动起一轮执行（忙 / 有待答提问 → 只落状态 + toast 提示）
                   → 撤胶囊 tag、卡片转只读态
                   → ⚠ 同时注入**撤销提醒**（见 §5）
点胶囊 × → 清 plan 状态 + mode=normal → 推信封（卡片壳一并撤销，见 §7.5）
```

**已知边界（刻意不做，写进系统提示词的退出口）**：plan 模式**没有迭代上限**，只能由用户
手动关闭（点胶囊 × 或批准）。为免"模型只回文本、不调 `plan_write`"时双方互等，
`PLAN_ACTIVE_REMINDER` 里给了一句退出口：「若当前任务不适合产出计划（例如只是问答或诊断），
请直接说明原因并请用户关闭计划模式，不要反复尝试写操作。」

### 2.2 goal 的完整生命周期（薄委托）

```
点「目标模式」→ 弹小输入框填完成条件 → 命令 session_exec_mode(mode=goal, condition=…)
      ↓
【既有】GoalController.set_goal(condition, total_tokens)     ← 非法条件抛 GoalError
【新增】追加一条 [Goal set] 消息（与 Stop 边界 block 消息同族，见 §5.3）
【新增】gate 记 mode=goal（**仅作 UI 投影**）→ 落 meta → 推 execution_mode_changed
      ↓
正常干活；每轮无工具调用时由【既有】Stop 边界 evaluate_after_turn 裁决：
   block   → 【既有】[Goal still active] 回注，回环继续            → mode 保持 goal（tag 不撤）
   defer   → 【既有】后台在跑，本轮结束（目标保持激活）             → mode 保持 goal
   limit   → 【既有】连续 block 超上限强制结束（目标保持激活）       → mode 保持 goal
   error   → 【既有】评估器出错（目标保持激活）                     → mode 保持 goal
   achieved → 【既有】控制器内部已清 active
   failed   →   ＋【新增】mode 回落 normal + 落 meta + 推信封（撤 tag）
用户点胶囊 × → 【既有】clear_goal() ＋【新增】mode 回落 normal + 落 meta + 推信封
```

**新增代码总量**：一个薄委托入口 + Stop 边界一个 4 行方法（`achieved`/`failed` 共用）+
meta 读写。**不新增状态机、不新增评估器调用、不新增任何 goal 判定分支。**

### 2.3 跨模式切换规则（2026-09-27 改：**直接切换**）

- **任一时刻至多一个模式激活**，但 plan ↔ goal 之间**可以直接切换**，不再要求
  "先关闭再切换"。
- **前端**只是分发层：异模式点击**直接发命令**（`goal` 仍需先弹层填完成条件），
  同模式重复点击直接 `return`（幂等短路，少一次往返）。**不再**有"请先关闭…"的
  toast 预检（`agentStore.switchExecMode` 与 `InputBox.handlePlusPick` 两处一并删除）。
- **后端 `Agent.set_execution_mode()` 是唯一权威**：
  - 切 `plan`：有激活目标 → 转发**既有** `clear_goal("switched to plan mode")`
  - 切 `goal`：处于 plan / 有文书状态 → `ExecutionGate.clear_plan()`——**只清内存态与
    meta 的 `plan_status` / `plan_path`，`plans/` 下的文书文件保留**（下次在 plan 模式
    产出即覆盖），随后走既有 `set_goal` + `[Goal set]` 消息
  - 切 `normal`：goal → 转发**既有** `clear_goal()`；plan → 清 plan 状态
  - 同模式重复 = **幂等成功**（不改状态、不发广播）—— 尤其不重置 `plan_status`
- **为什么"直接切换"不等于"静默清"**（原设计的顾虑如何被消解）：
  1. 动作由用户**点选显式触发**，不存在"顺手点一下目标就没了"；
  2. 胶囊 tag 随 `execution_mode_changed` 广播**即时熄掉**，UI 无残留；
  3. 模型侧由 `_sync_execution_mode()` 的**两态注入**告知（plan → goal 走
     `PLAN_EXITED_TO_GOAL_REMINDER` 那一版文案，见 §5）；
  4. 文书**文件不删**，只在内存/meta 里失去"待批准"语义。
  > **历史形态（已废弃，2026-09-25 ~ 09-27）**：前端 toast「请先关闭{计划|目标}模式」
  > 且**不**发起切换，后端另在 `Agent.set_execution_mode` 与 `session_exec_mode`
  > 未跑分支各设一道互斥拒绝。原权衡是"可预期优于静默替换"，2026-09-27 被用户否掉：
  > 切模式本身就是明确意图，"先关闭再切换"是多余的两步操作。
- 仍会经 `error` 信封回前端的**只剩两类**：goal 条件非法（空 / 超 `MAX_GOAL_LENGTH`）、
  会话不存在。`agentStore` 的 `error` 分支本就是无差别全局 toast，与这两类语义相称。
  注意 `permission_config_save` 曾**刻意避开** error 信封（怕误 toast、该页约定是内联
  报错）—— 本场景不属于那一类，用 error 是**对的**。
- 未跑会话（选中的会话还没构造 Agent）**同口径**：`session_exec_mode` 直接把被让位
  那一方的 meta 字段写空（切 plan 时 `goal_condition=None`，切 goal 时
  `plan_status=None`），不再读投影判互斥。

### 2.4 线程模型与 `rt.busy` 约束（评审 P1-5）

| 组件 | 是否有锁 | 结论 |
| --- | --- | --- |
| `ExecutionGate` | **自带 `threading.Lock`**（状态访问全持锁） | plan 切换**可以在 turn 进行中即时生效** —— 守卫是"每次工具调用现场读 gate"，在途轮的后续 tool_call 立即受新模式约束 |
| `GoalController` | **没有任何锁**（对比 `PermissionGate` 自带锁） | goal 的进入/退出**不允许在 `rt.busy` 时进行**（命令走 `asyncio.to_thread`，`agent_loop` 在工作线程读同一对象 → 跨线程竞争） |

`rt.busy` 的守卫**放在 `ws_bridge`**（Agent 不知道 busy 这个概念，`set_execution_mode` 的
docstring 明确记录了这一点）。判定口径：**「当前模式或目标模式涉及 goal」且本会话 turn 在跑
→ 一律拒绝**并提示「该会话正在执行，请先停止或等本轮结束后再切换目标模式」。

> **实施期取舍**：方案文档给的是"排队到本轮结束**或**给控制器加锁"二选一。实现取**拒绝**
> —— 排队需要在本轮结束时找回被挂起的意图（要新加一处收尾钩子），而 `GoalController` 加锁
> 属于改既有引擎层。拒绝是零新增状态、零引擎改动的方案，且用户看到明确提示可自行重试。

`plan_approve` 的续跑也有 busy 守卫（两条，超集关系）：

1. `rt.busy` → 只落状态 + toast「计划已批准。当前回合结束后请再发一条消息开始执行」；
2. `rt.has_pending_interaction()`（有等待作答的 `ask_user`）→ 同样只落状态 + 提示先作答。

⚠ `rt.start_turn` **自身没有 busy 守卫**（既有 `chat` 分支的守卫在调用方），新分支必须自己判 ——
两线程同写会话 jsonl 是项目里的既有禁忌。

### 2.5 无会话态（评审 P1-7 → 2026-09-27 改版）

`+` 菜单**恒渲染**（"新建任务"态也能点），而无会话时没有会话可挂模式。**两项在任何
情况下都必须可点**（用户要求，2026-09-27）—— 原"置灰 + 提示请先发消息"的方案作废：

- **前端**：无会话时点选记为 **`pendingExecMode` 草稿**（store 级，见 §7.5），
  胶囊 tag 立即显示该草稿（零幻觉：它不是"会话态"，是"待落地的意图"）。
  `switchExecMode` 无会话分支只写草稿并 `return`（**不 toast、不发命令**）。
  草稿**不跨新任务继承**（`newSession()` 重置为 `normal`）：执行模式是会话级状态、
  无继承源，带过去等于让用户在下一条任务里"莫名开着计划模式"（对照权限档位 ——
  它有"本空间新会话默认档位"的产品含义，故有继承链；模型选择同理继承，那是第三条轴）。
- **交接点**：草稿随首条消息经 **`chat` 命令的 `exec_mode` / `exec_condition`**
  交给后端，后端在**建会话时**（`if sid is None` 分支内）写进该会话 meta。
  ⚠️ **不能**等 `session` 信封回来再发 `session_exec_mode`：那时 turn 已经派发、
  `rt.busy=True`，goal 会被 §2.4 的守卫直接拒掉（plan 侥幸能过，但会有"首轮工具
  调用已在 normal 下发生"的竞态窗口）。写 meta 即够 —— `SessionRuntime.build_agent()`
  里 `switch_session → _restore_execution_state` 会读回，**本轮开始前就已生效**。
- **goal 还要补一条 `[Goal set]` 消息**（在同一个新建分支里 append 到会话 jsonl）：
  预选路径没走 `Agent.set_execution_mode()`，也就没走它内部的 `_append_goal_set_message`，
  而 `_restore_execution_state` 只重建控制器、不补这条消息（否则每次切会话都会重复注入）。
  消息形状**逐字对齐** `_append_goal_set_message` —— 与"用户中途点胶囊设目标"产生的
  历史一模一样。plan 不需要补：`_sync_execution_mode()` 会在 `switch_session` 时按
  指纹注入 `<system-reminder>`（幂等）。
- **非法值静默忽略**（未知 mode / goal 缺条件 / 条件超 4000 字）：草稿态**绝不阻断发送**。
  前端 `GoalInputDialog` 已挡掉空值与超长（§7.2），后端这道只是"手改 payload"的兜底；
  真被忽略时用户看到的是"胶囊没亮"或随即被 `sessions` 广播纠正。
- **前端交接的本地登记**（2026-09-27）：收到 `session` 信封且本窗口是发起方（`wasFresh`）时，
  把 `pendingExecMode` 的值写进 `executionModeBySession[sid]` 并清空草稿。
  **不是乐观更新** —— 模式是同一条 `chat` 命令带的，登记只为"草稿已清、会话态未到"
  的那几毫秒不闪一下胶囊；真值由紧随其后的 `sessions` 广播校准（后端忽略非法值时
  这里会被纠正回 `normal`）。
- **后端命令侧不变**：`session_exec_mode` 仍是**双路径**（有 rt 且 agent 已构造 →
  薄委托给 Agent；否则只写 meta，待 `_restore_execution_state` 读回）。`session_id`
  为空则回 error —— 该分支前端已经不会走到，留着是"手改 payload / 老前端"的守卫。

> **历史形态（已废弃）**：无会话时两项 `disabledKeys` 置灰 + `title`「请先发送一条消息
> 创建会话，再设置任务执行模式」，`switchExecMode` 无会话时兜底同文案 toast。
> 用户反馈"任何情况下都应可选"，2026-09-27 改为上述草稿方案。

## 三、plan 的窄只读判定（评审 P0-3）

### 3.1 为什么不能复用权限链的白名单

方案文档原想「把 `_bash_category_decision` 的 ⑦-2 白名单段抽成公开函数，白名单仍只有一份」。
逐行对账后三条都不成立：

1. **抽不干净**：⑦-2 只是循环里的一句 `if`，被 **⑥ 会话记忆** 与 **⑦-1 危险模式**前后夹持；
   而 ⑦-1 **必须先于白名单**（项目里 `cat x > /etc/passwd` 曾被白名单掩护静默放行的历史事故）。
   只抽 ⑦-2 = 丢掉 ⑦-1 = **判定变松**。
2. **返回值不是 bool**：整函数返回 `Decision`（`action ∈ {allow, approve}`），方案想要的
   `-> bool` 是**新语义**，不是"抽出既有函数"。
3. **白名单语义错位**：`BUILTIN_SAFE_COMMANDS` 的语义是「够安全、**可免审批**」，不是
   「只读」—— 表内有 `find` / `env` / `git branch` / `du` / `echo`，而匹配是 **token 前缀
   匹配**。于是下面这些**全数命中白名单**：

```
find . -exec rm -rf {} +        env X=1 rm -rf /        git branch -D main
du --files0-from=…              echo "$(rm -rf x)"      （$(...) / 反引号不在任何否决位）
```

**结论**：`permission.py` **一行不改**；plan 专用的窄只读判定在 `execution_mode.py` 内新建
`bash_is_read_only(command, store)`，只复用权限链的**原语**（`split_command_segments` /
`normalize_segment` / `tokenize` / `pattern_matches` / `cross_pattern_matches` /
`deny_tokens_in_command`）与**内置清单**，**不复用那份白名单策略数据**。

### 3.2 判定规则（五步，逐段）

```
① 解析失败 / 空段                          → False（fail-closed，与权限链同款）
② 任一段含否决位（子串）                   → False
     `>`（覆盖 > >> 2>&1 >&） / `<<`（覆盖 << <<<） / `$(` / 反引号
  任一段含否决位（token）                    → False
     --output / -exec / -execdir / -ok / -okdir / -delete / -fprint* / -fls*
     tee / dd / xargs / truncate / sponge / --pre
③ 敏感路径 token（deny_tokens_in_command）  → False
④ 硬拒绝 ∪ deny_patterns、危险模式 ∪ dangerous_patterns（含跨段）→ False
⑤ 逐段命令头白名单（每段都必须过）：
     头 ∈ PLAN_BASH_READONLY_HEADS 且：
       · git  → 子命令 ∈ {status, diff, log, show, branch}；
                git branch 的额外 token 必须 ∈ 安全开关集（拒 `git branch foo` / `-D`）
                允 `-a/-r/-v/-vv/--all/--remotes/--list/--merged/--no-merged/--contains/--sort/--format`
       · env  → **只允许裸 env**（只打印环境）。`env X=1 cmd` 是启动器，
                且 `env PATH=/tmp/evil ls` 会换掉实际执行的二进制 → 一律 False
       · date → 拒 `-s` / `--set`（会改系统时钟）
```

只读头显式枚举（已核对为 `BUILTIN_SAFE_COMMANDS` 的真子集）：

```
ls pwd cat head tail wc grep rg find which file stat du df echo date git
```

**`_deny_token_hit()` 的三种形态**（实施期抓到的两个真实绕过）：早期草案只做
`tok in deny` 精确匹配，于是

- `--output=patch.diff`（等价 `git diff --output patch.diff`）→ token 是 `--output=patch.diff`
  → **漏过 → 静默写文件**；
- `date --set=now`、`date -s2020-01-01`（短选项带值）→ 同样漏过 → **静默改系统时钟**。

修正后的匹配：① 精确；② 长选项带值取 `=` 前的选项名；③ 短选项聚合取头两个字符（仅当该短
选项在否决集里）。

**刻意不拦 `-i` / `-o`**（与早期草案的差异，理由可验证）：它们的"写"语义只对
`sed -i` / `perl -i` / `sort -o` / `curl -o` 成立，而这些头**本身不在只读白名单内**（第 ⑤ 步
已先拦下）；对放行头（`ls -i` / `grep -i` / `grep -o` / `find … -o`）它们是**只读开关**。
全局拦只会误伤最常用的 `grep -i` 探索，零安全收益。

### 3.3 四个反例（测试里必须断言为 **阻断**）

| 命令 | 命中的判定 |
| --- | --- |
| `find . -exec rm -rf {} +` | ② token 否决位 `-exec` |
| `env X=1 rm -rf /` | ⑤ `env` 非裸调用 |
| `git branch -D main` | ⑤ `git branch` 额外 token 不在安全开关集 |
| `echo "$(rm -rf x)"` | ② 子串否决位 `$(` |

另加：`cat x > /etc/passwd`（② 重定向）、`git diff --output=patch.diff`（② 长选项带值）、
`date -s2020-01-01`（② 短选项聚合）也在测试里断言为阻断。

### 3.4 判定矩阵（逐工具，实现与测试共用此表）

plan 激活**且** `plan_status != "approved"` 时：

| 工具 | 判定 | 依据 |

告警。

### 3.5 hook 顺序与阻断回填契约

`register_default_hooks()` 的顺序（**次序即语义**）：

```
PreToolUse: ① plan_guard_hook   ← 新增（模式级，最严，先拦模式）
            ② permission_hook   （规则级）
            ③ log_hook          （必须晚于权限 —— 否则被拦的调用会记成一次成功）
```

`plan_guard_hook(tool_call) -> str | None` 与 `permission_hook` **完全同款**：返回非 None
字符串即被 `hook_system.trigger("PreToolUse", …)` 判为阻断，由 `agent_loop` 回填为该
tool_call 的 result 文本。**不进审批流、不产生 approval 记录**（模式级限制与"要不要审批"无关）。

回填文案（模型可见 → 必须可行动）：

```
Error: Plan mode is active — this tool is blocked.
[可选一行细节，如 bash 的"仅允许只读命令"]
Write your implementation plan with plan_write, then wait for user approval.
Blocked tool: run_write
```

**防御姿态（与权限链一致的 fail-closed / fail-open 之分）**：

- 未注入 gate（独立 `HookSystem` / 子智能体兜底构造 / 单测直连）→ 直接放行（normal 路径逐
  字节不变）；
- 非 plan 模式 → 直接放行（**零开销**，且不会因为解析工具参数而误伤 normal / goal 路径）；
- **只有** `plan_blocks_writes()` 为真时才解析工具参数；**参数解析失败 → fail-closed 阻断**
  （与权限链同款：宁可错杀）；
- gate 状态读取本身抛异常 → **放行**（不猜、不阻断 —— 门自己坏了不该打死正常流程）。

`store` 从权限门取（`PermissionGate.store.load()`，有 mtime 热加载缓存）—— 这一点**必须**，
否则 plan 的判定会漏掉用户的 `deny_patterns` / `dangerous_patterns`，破坏 §1.3 的不变量。

## 四、计划文书

### 4.1 落点与命名

```
<data_root>/plans/session_<sid>.md
    ↑ 元数据目录（~/.aigent/projects/<id>/），**不在工作区内**
```

命名口径与 `.tasks` / `.chathistory` 同源（`session_<sid>`），唯一实现是
`paths.plan_file_for_session(sid, prefix, plans_dir)`；`execution_mode.plan_file_for(paths, sid)`
只是把路径束的 `plans_dir` 喂进去的便捷入口（避免调用方各拼一遍口令、形成第二出处）。

`WorkspacePaths.plans_dir` = `data_root / "plans"`；`ensure_dirs()` 按需补建（与 `.attachments`
同策略：自定义空间也在访问时创建）。

### 4.2 格式与覆盖语义

- **Markdown**，人可读、可直接编辑（"在 Finder 打开"本期不做）。
- **单份覆盖**：同一会话重复产出计划即覆盖旧文书，**不做版本历史**。这直接决定了前端只能
  用"消息流末尾固定块"的形态（§10.4）。
- 写入是**原子写**（tmp + `os.replace`，与项目其它落盘一致）。

### 4.3 `plan_write` 工具

```python
{
    "type": "function",
    "function": {
        "name": "plan_write",
        "description": (
            "写入/覆盖本会话的计划文书（仅在计划模式下可用）。"
            "在计划模式下完成只读探索后，用本工具提交实施计划：目标、步骤分解、"
            "涉及文件、风险与验证方式。用户批准后才会开始执行。"
            "不要用它保存代码、笔记或任何交付文档。"
        ),
        "parameters": {
            "type": "object",
            "properties": {
                "content": {"type": "string", "description": "计划正文（Markdown 格式）"}
            },
            "required": ["content"],
        },
    },
}
```

两个刻意的取舍：

- **schema 只有 `content` 一个参数（不设 `path`）**：落点由后端强制为 `plans/session_<sid>.md`，
  模型无从指定 —— 比"有 `path` 参数但被忽略"干净，也不会给模型"我能换地方写"的错觉。
- **工具常驻**在工具列表里，**不做按模式动态裁剪**：裁剪要动 `tools` / `base_tools` /
  `main_agent_tools` / `default_agent_tools` 等多处传参点，收益（省 ~100 prompt token）不抵
  风险。非 plan 模式下调用由守卫拒绝。

**注入方式（评审 P1-10）**：`ToolRegistry.set_plan_sink(cb)`（holder 形状照抄
`set_background_manager`）。**只能传"已经算好路径"的闭包** —— `ToolRegistry.__init__` 只有
`workdir` / `bash_cwd`，**没有 workspace、没有 session_id、也没有 `data_root`**。因此路径解析
由 **Agent 侧的闭包**完成，registry 侧不做任何路径推断。未注入时 `plan_write` 返回可读的
Error 文本（CLI / 单测路径行为不变）。

handler 步骤：目标路径（由闭包给定）→ `mkdir parents` → 原子写 → `gate.mark_plan_ready(path)`
→ 经 sink 推 `execution_mode_changed`（先）→ `plan_ready`（后）。

### 4.4 `plan_read`：正文链路（评审 P0-1）

**原方案的决策不成立**：`file_read` 内部是 `read_workspace_file(ws_paths.workdir, path)`，
第一步 `resolve_within(workdir, path)` 把根**钉死在工作区**，越界直接回
`reason="路径不在当前工作空间内"`；而计划文书落在**元数据目录**，**天然在工作区之外**。
default 空间更彻底：`file_read` 整体被禁用。

**修正后的决策：新增专用命令 `plan_read`，`plan_ready` 信封仍不带正文。**

| 环节 | 做法 |
| --- | --- |
| 路径解析 | `sid → pid → ws_paths.plans_dir / session_<sid>.md`，**绕开 `resolve_within`**（落点由 sid 唯一决定、内容只由 Agent 写入，没有越界面） |
| 回执形状 | **复用既有降级字段形状**（照 `file_content_disabled`）：`{project_id, session_id, path, name, size, mtime, encoding, binary, too_large, truncated, lines, text, reason}` —— 所有分支都从**同一个构造函数** `plan_content_payload()` 出去，前端不必写第二套解析 |
| 大小上限 | 复用 `refs.file_preview_max_bytes()`（512KB）。超限**一点内容都不读**（"宁可不给，不给半个"），给 `too_large=True` + 人话 reason |
| 健壮性 | 编码 `utf-8` + `errors="replace"`；**绝不抛异常**（`FileNotFoundError` / `OSError` / 连 `stat` 都会抛的 `ValueError`（路径含 NUL）全部分支化成 `reason` 人话） |
| 实时与回放 | **共用同一条链路** —— 实时（`plan_ready` 到达后）与回放（`session_history` 带 `plan_status` 后）**都调 `plan_read`** |
| 落点 | 读取函数放在 `execution_mode.py`（**不是 `ws_bridge.py`**）：① 这是 plan 域的职责（与 `plan_file_for` 同源）；② `ws_bridge` 有**模块级副作用**（import 即构造全局 Agent 并写一行日志），纯文件函数留在那里就没法在不污染 `~/.aigent` 的前提下单测 |

**推送顺序契约**：`plan_write` 成功时后端**先推 `execution_mode_changed`（带
`plan_status="ready"`）再推 `plan_ready`** —— 保证前端处理卡片时 tag 状态已就位（顺序错也不
崩、幂等，但固定顺序便于断言）。

**失败语义**：`reason` 非空（文书被外部删除 / 超限 / 空间目录不可用）→ 前端渲染
「计划文书记录已丢失（路径：…）」占位块 + 保留按钮区（但**批准按钮禁用**，因为批准一份读
不到的文书没有意义）。**绝不白屏。**

### 4.5 级联清理（评审 P1-12）

`plans/session_<sid>.md` 的清理**不止一处**，且三种删除语义不同：

| 操作 | 是否清文书 | 说明 |
| --- | --- | --- |
| `delete_session_permanent` | **清** | 同时把 meta 的三个执行模式字段一并归零 |
| `clear_session` | **清** | 同上（否则会留下"`plan_status=approved` 但文书已不存在"的僵尸状态，前端切回来会渲染一张读不到正文的卡片） |
| `trash_session` | **不清** | 软删除（归档）—— 原样保留文件，还原后卡片照常工作 |

注意清的是**会话 jsonl 文件与文书**，不是整个 `.chathistory` 目录。

## 五、提示词注入：两态对称（评审 P0-2）

### 5.1 为什么必须有"退出"那一态

**原方案写的是"只处理 plan"、"回落 normal 时不注入任何提示（撤掉 tag 即足够）"—— 这是个会
打死核心流程的错。**

因为该注入是 **append 到历史并落盘**的（不是每轮临时拼接）：plan 期间历史里最后一条提醒是
「禁止任何写操作」；批准后若什么都不注入，模型读到的**最新指令仍是"禁止写操作"** → 表现为
**「用户点了批准执行，模型却拒绝干活」**。

### 5.2 两态文案与指纹

指纹 = **语义状态**（`plan-active` / `plan-exited`），不是哈希：

- 同态重复调用零开销、不刷屏；
- 历史里**从未**注入过本 tag 且当前非 plan → 直接返回（否则每个新会话都会莫名多一条
  「计划模式已结束」）。

**态 ①：plan 激活且未批准**

```
<system-reminder>
当前处于「计划模式」。禁止任何写操作与有副作用的调用：只能做只读探索
（run_read / run_glob / 只读 bash / 向用户提问），然后用 plan_write 提交计划文书，
等用户批准后再开始执行。若当前任务不适合产出计划（例如只是问答或诊断），
请直接说明原因并请用户关闭计划模式，不要反复尝试写操作。
</system-reminder>
```

**态 ②：已退出 plan（前态为 plan 或 `plan_status=approved`）—— 撤销提醒**

正文**按当前模式二选一**（2026-09-27 新增第二版；指纹仍记 `plan-exited`，只换正文）：

②-a 回落到 `normal`（批准执行 / 手动关掉计划模式）：

```
<system-reminder>
计划模式已结束，写操作已恢复，可以正常使用 run_write / run_edit / bash 等工具。
请按已批准的计划文书开始执行。
</system-reminder>
```

②-b **直接切换到 `goal`**（§2.3 改版后新增的路径）：

```
<system-reminder>
计划模式已结束，并直接切换到了「目标模式」。写操作已恢复，可以正常使用
run_write / run_edit / bash 等工具。此前若产出过计划文书且尚未批准，该文书
已作废（文件仍保留在磁盘上，但不要再去执行它）。
请围绕已设定的目标条件继续工作，直到目标达成。
</system-reminder>
```

**为什么必须分两版**：②-a 的落点是"请按**已批准**的计划文书开始执行"，而 plan → goal
这条路径上计划**通常根本没被批准**（状态已作废、文件仍在）。照抄会让模型去找一份它拿不到、
也不该执行的计划。指纹不变是因为它记的是"plan 这个语义态"，不是文案。

机制与 `_sync_environment()` 完全同构：**尾部追加 + 指纹幂等、绝不改历史消息**；注入块会被
`ws_bridge._history_to_ui` 按 `<system-reminder>` 前缀过滤掉，不会漏成聊天气泡。per-turn
在 `agent_loop` 里调用（与 `_sync_environment` 同处）。

**「计划已批准」是另一条东西，两条都要有**：

| 注入 | 形态 | 作用 |
| --- | --- | --- |
| `PLAN_EXITED_REMINDER` / `PLAN_EXITED_TO_GOAL_REMINDER` | `<system-reminder>`（不可见） | **解除**"禁止写"（②-a / ②-b 两版） |
| 「[计划已批准] 用户批准了你的计划文书，现在开始按计划执行。可以正常使用 run_write / run_edit / bash 等写操作。」 | **用户可见的 user 消息**（`rt.start_turn(PLAN_APPROVED_RESUME_TEXT)` 的首条 content） | 告诉模型**执行什么** |

### 5.3 goal 侧刻意**不**注入 system-reminder

既有 Stop 边界在每次 `block` 时已回注 `[Goal still active] / Condition: … / Evaluator: …`
—— 那已是 goal 的成熟反馈通道，再叠一层 system-reminder 就是**第二出处**。

goal 侧只补**一条设置时的消息**（与 block 消息同族同风格，走既有 `append_message_to_session`）：

```
[Goal set]
Condition: {condition}
Work toward this condition; the session will be evaluated when you stop.
```

理由：CLI 的 `/goal` 会在终端打印确认，而桌面端用户是**点胶囊 tag 填条件** —— 未必再发一条
相关消息，模型需要立刻知道目标是什么。复用既有消息族，不引入新的注入机制、不碰
`_sync_execution_mode`。

## 六、协议契约

### 6.1 三条新命令（渲染 → 后端）+ `chat` 新增 2 字段

| 命令 | 载荷 | 语义 | 回执 |
| --- | --- | --- | --- |
| `session_exec_mode` | `{session_id, mode, condition?}` | `plan` → 进入计划模式；`goal` → 需带 `condition`（空/超 4000 字由 `GoalError` 拒绝）；`normal` → 退出当前模式（plan 时清 plan 状态，goal 时转发 `clear_goal()`） | 广播 `execution_mode_changed` |
| `plan_approve` | `{session_id}` | `plan_status=approved` + mode 回落 normal + **自动起一轮执行**（忙 / 有在途提问时只落状态 + 提示） | 广播 `execution_mode_changed`，随后正常流式事件 |
| `plan_read` | `{session_id}` | 读本会话计划文书正文（元数据目录直读，**不走 `file_read`**） | **点对点** `plan_content` |

失败一律复用既有 `error` 信封（条件为空或超长 / 会话不存在 / 会话未构造）。
`condition` **仅**在 `mode === 'goal'` 时读取。

`chat` 命令**新增两个可选字段**（2026-09-27，见 §2.5）：**只在新建会话（无
`session_id`）时被读取**，已有会话一律忽略（模式切换走上面的 `session_exec_mode`）：

| 字段 | 形状 | 语义 |
| --- | --- | --- |
| `exec_mode` | `"plan" \| "goal"` | 预选执行模式。`"normal"` / 缺省 = 不设置（新会话默认档，**零字段**）。白名单外的一律忽略并记 `warning` |
| `exec_condition` | `string` | 仅 `exec_mode === "goal"` 时读。空 / 超 `MAX_GOAL_LENGTH` → **整份忽略**（回落 normal），不阻断发送 |

后端在建会话分支里写两样东西（顺序即代码顺序）：

```
① session_manage.set_session_execution(new_sid, execution_mode=<mode>,
       plan_status=None, goal_condition=<cond|None>)
② 仅 goal：append_message_to_session(new_file, {"role":"user","content":
       "[Goal set]\nCondition: <cond>\nWork toward this condition; ..."})
```

### 6.2 三个新信封（后端 → 前端）

| 信封 | 字段 | 触发 | 投递 |
| --- | --- | --- | --- |
| `execution_mode_changed` | `{session_id, mode, plan_status, plan_path, goal_condition}` | 任何模式/状态变更（含 goal 达成后自动回落） | **广播**（多窗口一致，同 `permission_changed` 口径） |
| `plan_ready` | `{session_id, plan_status}` | `plan_write` 成功写入文书后。**不带正文** | **广播** |
| `plan_content` | 见 §4.4 的形状 | `plan_read` 的点对点回执 | **单播**（`safe_send`） |

**唯一投递路径（评审 P1-3）**：`execution_mode_changed` 有**两个触发源**（用户点 tag /
goal 自动回落），但只有**一条投递路径** —— `SessionRuntime._bind_sink` 往 agent 注入
`execution_mode_sink`（实现是 `lambda kind, payload: deliver(kind, payload)`），两个源都经它
走 `deliver()` → `hub.broadcast`。

> 为什么必须这样：agent 侧**没有 `hub`**（全仓 `hub` 只在 `ws_bridge`），而 Stop 边界同步跑在
> **工作线程**。`deliver()` 内部是 `call_soon_threadsafe` + 广播全连接，**线程安全**。
> 若一边 `hub.broadcast`、一边走流式 `event`，就是两套口径 —— 项目里踩过同类漂移。
>
> agent 侧未接线时（CLI / 单测）`execution_mode_sink is None` → **静默跳过**，行为与改造前一致。

### 6.3 `session_history` 新增 4 字段

`session_history`（切会话 / 回放）的 payload 追加（与既有 `permission_mode` 同处，**两处构造点**
共用 `_exec_mode_fields()` 组装，避免口径分叉）：

```
execution_mode  : "normal" | "plan" | "goal"     （读值 `or "normal"` 兜底，零迁移）
plan_status     : null | "ready" | "approved"
plan_path       : string | null                  （**派生**，不落 meta）
goal_condition  : string | null
```

**`plan_path` 刻意不落 meta、改为派生**：落到哪个文件由 `sid` 唯一决定，再存一份就是**第二
真相源**。仅在有 `plan_status` 时给出（`null` 表示"没有计划状态"）。

### 6.4 `sessions` 列表载荷新增 4 字段（重连的唯一通道，评审 P1-13）

`session_history` **只在收到 `session_switch` 后**才发出；而连接建立时的重放序列
（`projects` / `session_status` / `ask_request` / `approval_request`）**不含它**。前端重连时只做
`resetTransient()` + `listSessions()`。

因此 4 个字段**必须同时**进 `sessions` 列表载荷（`list_sessions` 白名单，与 `permission_mode` /
`unread` 同通道）：

```json
{
  "id": "Kx7mQ2vT8p", "title": "…", "project": "default",
  "execution_mode": "plan",
  "plan_status": "ready",
  "plan_path": "/Users/me/.aigent/projects/default/plans/session_Kx7mQ2vT8p.md",
  "goal_condition": null
}
```

> 前端两条链路都要消费它：`refreshSessions()` 与 `case 'sessions'` —— 两处都走
> `mergeExecFromSessions()`（无变化时**返回原引用**，避免 zustand 无谓重渲染）。

### 6.5 IPC 通道（渲染 ⇄ 主进程）

| 通道 | 载荷 | 说明 |
| --- | --- | --- |
| `invoke('agent:send')` | `{text, session_id?, project_id?, overrides?, model_id?, attachments?, refs?, **exec_mode?, exec_condition?**}` | 预选执行模式随首条消息带上（2026-09-27）。形状校验：`sessionId === undefined`（新建）才读，且 `exec_mode` 必须在 `['plan','goal']` 白名单内，`exec_condition` 仅 goal 时透传 string |
| `invoke('agent:sessionExecMode')` | `{sessionId, mode, condition?}` | 发 `session_exec_mode`，**fire-and-forget**（回执走广播）。形状校验：`isTrustedSender` + `session_id` 非空 + `mode` 白名单；`condition` **仅** `mode==='goal'` 时读且须是 string |
| `invoke('agent:planApprove')` | `{sessionId}` | 发 `plan_approve`，**fire-and-forget** |
| `invoke('agent:planRead')` | `{sessionId}` | 发 `plan_read`，**有真回执** → `plan_content`（走主进程 `request()` 配对） |

**两条链路，不是"三层"（评审 P2）**：

```
Electron（4 段）：renderer → preload(bridge) → main(IPC handler) → ws.send → ws_bridge
浏览器调试态（2 段）：browserAgent 直连后端 WebSocket（绕过 preload / main）
```

| 文件 | 改动 |
| --- | --- |
| `main/index.ts` | 三个 `ipcMain.handle`（紧接 `agent:sessionPermission` 之后；该文件**无统一注册表**，逐个内联注册）。前两个 `return` 空（fire-and-forget）；`planRead` 走 `request('plan_read','plan_content',{session_id})` |
| `preload/index.ts` + `preload/index.d.ts` | 暴露 `sessionExecMode(sessionId, mode, condition?)` / `approvePlan(sessionId)` / `planRead(sessionId)`。**两文件都改**（`.d.ts` 是渲染层类型来源，漏改则 `typecheck:web` 编译不过） |
| `protocols/agentProtocol.ts` | `ControlKind` 加 3 个 kind；`UiEvent` 加 3 条信封；`session_history` payload 与 `SessionMeta` 各加 4 字段；新增 `ExecutionMode` / `PlanStatus` / `ExecutionModeChangedPayload` / `PlanContentPayload` |
| `lib/browserAgent.ts` | **它不是 mock，是浏览器回退桥**（真连 WS）。实现 3 个方法（不加则 `typecheck:web` 失败）。它**不维护信封清单**（只用泛型 `sendRaw` / `request`），所以"给它加两个信封"这个说法不成立 —— 但它**仍要上行所有收到的信封**给 store |

**点对点信封不设 `handleEvent` 分支**：`plan_content` 与 `file_content` 同款 —— 主进程
`request()` 按 `kind` 全局配对（不带 request id），渲染层只在 `fetchPlanContent` 里从返回值
落库即可。

**`session_exec_mode` 不进主进程 `pending` 表**（fire-and-forget、`ws.send` 直发），与
`session_ui` 同款纪律。

### 7.2 目标条件弹层（`GoalInputDialog.tsx`）

- 触发：`+` 菜单点「目标模式」（或未来其它入口）。
- 形态：`createPortal` 到 `document.body` 的居中轻量弹层（`.goal-dialog-mask` + `.goal-dialog`，

  （Esc 分层，见 19 篇）。
- 校验：空 / 超长（`MAX_GOAL_LENGTH = 4000`）→ 内联提示 + 禁用确定。**两处都要有**：只留前端
  会被绕过，只留后端体验差（白跑一次往返）。后端 `GoalController.set_goal` 抛的 `GoalError`
  文案经 `error` 信封原样 toast，前端不改一字。

### 7.3 计划卡片（`PlanCard.tsx`）—— 消息流末尾固定块

**位置：消息流末尾**（由 `MessageList` 渲染，与既有 `orphanApprovals` 同款先例）。

为什么不做"锚定产出该计划的 assistant 消息"（原方案写法）：**那条链路不存在** ——
`plan_ready` 不带 `message_id`、`Message` 类型没有 plan 字段、store 里也没有"消息 id → 计划"
的映射。而既有三条锚定先例的锚点都是**消息内部已有键**（`toolCallId` / `contentOffset`），不是
消息 id 级的外部映射。改为"贴消息流末尾"是**零新增锚定机制**，且 `plan_status` + `plan_path`
两个字段就足以还原卡片外壳 → 实时与回放天然一致。

卡片三分支（互斥）：

| 条件 | 渲染 |
| --- | --- |
| `plan.reason` 非空 | `.plan-card-lost` 占位块（图标 + 原因），「批准执行」**禁用** |
| `plan.content === undefined` | `.plan-card-loading`「正在读取计划文书…」（`plan_read` 在途，**不是**加载失败） |
| 有正文 | `.markdown-body.plan-card-body` + `ReactMarkdown`（`remarkGfm`；`table` 包 `.table-scroll`；`urlTransform={safeUrlTransform}`） |

底部 `.plan-card-actions`：`approved` → `.plan-card-note`「已批准，正在按计划执行」；
否则「继续修改」（次）+「批准执行」（主）。

**正文是模型产出的内容 → 绝不产出可导航元素**（21 篇 §6.1 事故的纪律）：正文里的 `a` 只放行
`https?:` 外链（`target="_blank" rel="noreferrer noopener"`，交主进程
`setWindowOpenHandler → shell.openExternal`），其余一律降级为 `<span>`。

**已知限制**：计划文书是**单份覆盖**（每会话一条 plan 状态），多轮 plan 时消息流里只保留"最新
这一份"的正文 —— 这正是"末尾固定块"成为唯一自洽形态的原因。

### 7.5 `agentStore` 的状态与清理规则

```ts
type ExecutionMode = 'normal' | 'plan' | 'goal'
type PlanState = { path: string; status: 'ready' | 'approved'
                   content?: string; reason?: string; tooLarge?: boolean }

executionModeBySession: Record<string, ExecutionMode>   // 缺省视作 'normal'（零占位）
planBySession:         Record<string, PlanState>        // 每会话一条（单份覆盖）
pendingExecMode:        ExecutionMode                   // 无会话态草稿（2026-09-27）
pendingExecGoalCondition: string                        // goal 草稿条件（非 goal 恒 ''）
```

`pendingExecMode` 的 read/write 点（**只有 4 处**，改动时四处一起看）：

| 时机 | 行为 |
| --- | --- |
| `InputBox` 的 `execMode` selector（`activeSession === null`） | **读**：胶囊/菜单勾选显示草稿 |
| `switchExecMode`（无 sid） | **写**：记草稿（同值短路），**不 toast 不发命令** |
| `send`（`sid === null`） | **读**：`pendingExecMode !== 'normal'` → 随 `chat` 带 `exec_mode` / `exec_condition` |
| `session` 信封（`wasFresh`） | **交接并清空**：登记 `executionModeBySession[sid]`，草稿复位 `normal` / `''` |
| `newSession()` | **复位**：不跨新任务继承 |

| 时机 | 行为 |
| --- | --- |
| `execution_mode_changed`（带 `plan_status`） | 写 `executionModeBySession[sid]`；`plan_status` 是 `ready`/`approved` → 更新卡片壳（保留已拉的正文与 reason） |
| `execution_mode_changed`（**`plan_status` 非 `ready`/`approved`**） | 只更新 mode。**例外**：`mode !== 'plan'` 且该会话有卡片壳 → **连壳一起撤**（回落 normal 与**跨模式直接切到 goal** 同款，见下） |
| `plan_ready` | 只写卡片壳 `{path, status:'ready'}`（保留已拉的 `content`），随后 `void fetchPlanContent(sid)` 拉正文（**副作用必须在 `set()` 之外**） |
| `plan_approve` 后 | 由 `execution_mode_changed`（带 `plan_status:'approved'`）校正为只读态 —— **前端不乐观转** |
| `session_history` | 4 字段恢复：`execution_mode` → tag；`plan_status` + `plan_path` → 卡片壳；若 `plan_status` 为空且 `execution_mode !== 'plan'` → **撤掉旧壳**（同下）；然后按需 `plan_read` 拉正文 |
| `sessions` 列表载荷 | 走 `mergeExecFromSessions()` —— **断线重连 / 整页重载后恢复 tag 与卡片壳的唯一通道**，也是**草稿交接的校准源**（§2.5） |
| `switchSession` | 新建/切到无记录的会话 → `execModeOf` 的 fallback 链给 `'normal'` |
| `deleteSessions` / `removeProject` | `dropExecBuckets(sids)` **显式清理**两桶（**不**照抄 `permissionModeBySession` —— 那个桶五处都不删，属既有泄漏） |

`execModeOf(s, sid)` 的 fallback 链：**内存桶 → `sessions` 列表条目 → `'normal'`**。
**无会话时根本不调用它** —— 直接读 `pendingExecMode`（`InputBox` 的 selector），
这是唯一"没有 sid 也能有非 normal 模式"的入口。

**唯一偏离"信封不带 plan_status 就不动卡片"的例外（实施期修正；2026-09-27 扩展到 goal）**：
`mode !== 'plan'` 且 `plan_status` 为空（= 后端已清 plan 状态）→ **连同卡片壳一起撤** ——
既覆盖回落到 normal，也覆盖**跨模式直接切到 goal**（§2.3 改版后的新路径）。
否则卡片会留在消息流里显示"待批准" + 可点的「批准执行」，而后端已无待批准计划 —— 点下去只会
换来一句「当前没有待批准的计划文书。」的 error toast，**死按钮 + 内存与磁盘背离**。
（切到 goal 时磁盘上的文书文件**不删**，只是前端不再有它的卡片壳。）

- 已批准过的卡片**不受影响**：`approve_plan` 只回落 mode、**不清 `plan_status`**，所以它此后
  每条信封都带 `"approved"`（走正常分支），作为**历史**留在消息流里。
- 该纪律在**两个入口**都实现（广播 + `session_history` 回放），保证两条恢复通道口径一致。

**zustand v5 硬约束**（项目踩坑）：selector 必须返回**引用稳定值** —— `mode` / `plan` 一律用
`useStore(s => s.executionModeBySession[sid])` 这类直接取值（命中即返回已有对象引用），
**禁止**在 selector 里 `map`/`filter`/`Object.values`/构造字面量；派生状态一律 `useMemo`。
`mergeExecFromSessions` / `dropExecBuckets` 无变化时返回**原引用**，也是同一条纪律。

## 八、与既有 `GoalController` 的复用边界

### 8.1 铁律

> **goal 的唯一真相恒为 `goal_controller.active`。`execution_mode == "goal"` 只是它的投影。**

推论（代码里逐条兑现）：

- `ExecutionGate` **不持有任何 goal 状态**（只有 `mode` 这个字样投影）；
- 读 `execution_mode` 之前/之后都要**用 `active` 校准**（`execution_state()` 与
  `_restore_execution_state()` 各一处）；
- meta 的 `goal_condition` **不是"第二个目标存储"**，而是 `GoalController._record()` 事件的
  **最小落盘投影**：`active` 非空时记 condition，`active` 为 `None`（clear / achieved / failed）
  时置 `None`。**不要拿它当 goal 状态的读源。**

### 8.2 本期新增的只有四条缝

| 位置 | 内容 |
| --- | --- |
| `set_execution_mode("goal", c)` | 转发**既有** `set_goal(condition, total_tokens)`；`GoalError` 原样上抛（空值 / 超 4000 字校验都在里面）；追加一条 `[Goal set]` 消息；`gate.set_mode("goal")` |
| `_restore_execution_state()` | 从 meta 的 `goal_condition` 重建控制器（`GoalController.restore()`，本期**首次**接入，见 §8.3） |
| Stop 边界 `achieved` / `failed` | 各追加一行调用 `_on_goal_terminated()`（`mode=normal` + 落盘 + 推信封），共 4 行 |
| `rt.busy` 守卫 | 在 `ws_bridge`（goal 的进入/退出不在 busy 时进行） |

**`goal.py` 一行不改**；`set_goal` / `clear_goal` / `goal_status` 的签名与实现不变（CLI 的
`/goal` 路径零改动，有回归断言守护）。

`limit` / `error` / `defer` / `block` 四个分支**一行不动** —— 目标仍激活 → mode 保持 goal →
tag 不撤（与既有语义完全一致）。

### 8.3 `restore()` 是本期新建的链路

`GoalController.restore(evaluator, events, block_cap)` 是既有 `@classmethod`（返回**新控制器**），
但**全仓此前零调用** —— 本期首次接上，因此必须自己补齐三处防御 + 一层字段映射：

| 问题 | 处理 |
| --- | --- |
| `restore` **不做非空校验** | 空 / 空白 condition **不得构造事件**（否则会复活一个 `condition=""` 的空目标） |
| `restore` **不恢复 `consecutive_blocks`** | 恢复后显式归 0 |
| `restore` **不重绑 LLM** | 替换后重新 `set_llm(llm_client, evaluator_model)`（热切换接缝） |
| 字段名不一致 | 真实事件字段是 `{type, condition, active, met, failed, reason, iterations, duration}` —— **没有 `goal_condition` 这个键**。meta 名 `goal_condition` → 事件名 `condition`，需**显式一层映射** |
| 会话切换时的陈旧目标（**实施期新增的第 4 处防御**） | `switch_session` **不重建**控制器，于是 A 会话设的目标会被 B 会话继承、B 的胶囊 tag 会莫名亮起。`_restore_execution_state` 里补：meta 无目标而内存里还挂着 `active` → 重建一个空控制器 |

替换策略：用返回值**整体替换** `self.goal_controller`，最后**用 `active` 校准 mode**。

### 8.4 刻意不做的事

- 不给 `GoalController` 加锁（属改引擎层；改用"busy 时拒绝切换"）；
- 不重写评估器、不新增 goal 判定分支、不新增 goal 状态机；
- 不为 goal 加 system-reminder（§5.3）；
- goal 模式下 `plan_write` 仍被拒绝（goal 不是 plan），写操作走正常权限链。

## 十、取舍理由

### 10.1 为什么不做 Spec 模式

第二个"更重的计划模式"需要有独立语义（多轮迭代 / 评审 / 版本），而当前只有"先出方案再执行"
这一个真需求。多一档就要多一套状态机、多一个 UI 入口、多一处互斥矩阵，且与 plan 的差别说不
清楚 —— 明确列为**非目标**。

### 10.2 为什么不与权限合并判定链

两者回答的是**不同问题**（允不允许 vs 以什么方式干），合并会得到一个"说不清优先级"的链：
`full_access + plan` 到底听谁的？现在的答案是**两条独立轴 + 各判一次**，`full_access` 免审批
但**不免模式墙**。而且 plan 的 bash 只读判定**必须**比权限链更严，合并就等于把语义不同的两份
白名单混在一起（§3.1 的三个理由）。

### 10.3 为什么 goal 不重写

既有 `GoalController` / `PromptGoalEvaluator` / Stop 边界七分支是**已经跑通**的成熟链路
（block 回环、limit 上限、后台 defer、`[Goal still active]` 回注）。重写一遍只会引入新 bug，
且会造出**第二出处**。本期只做薄委托 + meta 喂料 + Stop 边界两行回落广播 —— 新增代码合计
不到 20 行，收益却是完整的目标模式 UI。

### 10.4 为什么卡片挂消息流末尾

见 §7.3：锚定 assistant 消息的链路**不存在**（事件无 `message_id`、`Message` 无 plan 字段、
store 无映射），而"单份覆盖"的文书语义本来就决定了"消息流里只该有最新一份"。贴末尾是
零新增机制 + 实时/回放天然一致的唯一自洽形态。

### 10.5 为什么 `plan_write` 不设 `path` 参数

见 §4.3。落点由后端强制，模型没有"我能换地方写"的错觉，也不会出现"传了 path 但被忽略"的
混乱契约。

### 10.6 为什么工具常驻而不动态裁剪

见 §4.3。动态裁剪要改 4 处工具传参点，收益不抵风险。

### 10.7 为什么 `plan_read` 而不是给 `file_read` 开个后门

`resolve_within(workdir, …)` 这道墙是**右栏文件读取的根基**（防越界读任意文件），为了读一份
自己写的文书去开洞，收益远小于风险。新增专用命令：路径由 sid 唯一决定、不接用户输入、
复用既有降级形状 —— 攻击面为零。
