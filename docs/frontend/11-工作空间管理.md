> 前置阅读：`05-配置与数据目录管理.md`（`~/.aigent` 目录与分层）、`07-会话管理与回收站.md`（会话元数据与生命周期）。

> **状态：已实施（2026-09-18）**。本文既是设计依据，也是该功能的"为什么这么做"记录 ——
> 每一节里"为什么"和"边界"比"怎么做"更重要。

## 1. 概念：什么是工作空间

**工作空间 = 一个真实目录 + 一份元数据目录**。

| 组成 | 位置 | 作用 |
| --- | --- | --- |
| 真实目录（`path`） | 用户自己选的任意目录 | 该空间内所有会话的**工具沙箱根**：`run_bash` 的 cwd、`run_read/write/edit/glob` 的相对路径基准、系统提示词里的"工作目录"、worktree 仓库根探测 |
| 元数据目录（`id`） | `~/.aigent/projects/<id>/` | 该空间的全部运行时数据：会话历史 / 任务 / 记忆 / 收件箱 / 团队 / 工作流 / 定时任务 |
| 索引条目 | `~/.aigent/projects/projects.json` | 名称、真实路径、元数据目录名、时间戳 |

一个后端进程（`ws_bridge.py`）承载**全部**工作空间：会话 → 空间 → 路径束，运行时按 `session_id` 路由。

### 1.1 两个空间之间隔离什么、共享什么

| 隔离（每空间一份） | 共享（全局一份） |
| --- | --- |
| 会话历史 `.chathistory` | 技能 `~/.aigent/skills` |
| 任务看板 `.tasks` | MCP 配置 `~/.aigent/mcp` |
| 记忆 `.memory`（含 `MEMORY.md` 索引） | 模型配置 `~/.aigent/llmconfig.json` |
| 收件箱 `.inbox` / 团队 `.team` | 日志 `~/.aigent/logs` |
| 工作流 `.workflow` / 定时任务 `.scheduler` | worktree `~/.aigent/worktrees` |
| **沙箱根（工具能碰到的文件范围）** | 桌面端产品配置 `~/.aigent/config.json` |

> ⚠️ **记忆按空间隔离是刻意的，也是用户可感知的**：在 A 空间教给智能体的东西，
> 换到 B 空间它不知道。理由：不同项目本就该分开（否则 A 项目的坑会污染 B 项目的判断）。
> 技能保持全局则相反 —— 技能是"应用能力"，换空间后技能全没了是割裂体验。
> 这个取舍在实现前经过确认（2026-09-18）。

## 2. 数据模型

### 2.1 `~/.aigent/projects/projects.json`

```jsonc
{
  "version": 1,
  "active": "ws7Kd93mQxZ",        // 当前活动工作空间（跨重启保留）
  "updated_at": "2026-09-18T18:06:29",
  "projects": [
    {
      "id": "default",             // 默认空间：恒存在、恒第一、不可删/改名
      "name": "默认",
      "path": null,                // 默认空间**没有真实目录**
      "created_at": null,
      "last_opened_at": null
    },
    {
      "id": "ws7Kd93mQxZ",         // "ws" + 10 位 base62 短码
      "name": "learn-claude-code-main",  // 默认取文件夹名；同名自动加 " (2)"
      "path": "/Users/xxx/Documents/Codes/learn-claude-code-main",
      "created_at": "2026-09-18T17:12:03",
      "last_opened_at": "2026-09-18T17:30:11"
    }
  ]
}
```

**为什么元数据目录名不直接用文件夹名**：选的两个目录可能是同名（两个 `frontend`），
文件夹名做目录名必然撞车。所以目录名用不重复短码，展示名才用文件夹名 ——
"名字给人看、短码给机器用"，两者解耦。短码格式与 session id 同款（同字母表、同长度），
`ws` 前缀用于一眼区分。

### 2.2 元数据目录布局（与 `default` 完全同构）

```
~/.aigent/projects/
├── projects.json
├── default/                ← 存量目录，**保持原名不迁移**
│   ├── .chathistory/       ← 会话 jsonl + meta + subagents 旁路
│   ├── .tasks/             ← 任务看板（一会话一 JSON）
│   ├── .memory/            ← 记忆 md + MEMORY.md 索引
│   ├── .inbox/  .team/     ← 队友收件箱 / 团队配置
│   ├── .workflow/  .scheduler/
│   └── .todo/              ← 已下线（2026-09-16），仅存量保留
└── ws7Kd93mQxZ/            ← 自定义空间，结构同上（不建 .todo）
```

`.transcripts` / `.task_outputs` 由 `ContextCompact` 运行期按需创建，不预先建。

### 2.3 默认空间的特殊语义

| 项 | 默认空间 | 自定义空间 |
| --- | --- | --- |
| `path` | `null`（没有真实目录） | 用户选定目录（`Path.resolve()` 后的绝对路径） |
| 沙箱根 | 遗留 `paths.WORKDIR`（`<repo>/WorkSpace/task1`） | 选定目录 |
| `run_bash` 的 cwd | **进程 cwd**（历史行为，刻意不改） | 选定目录 |
| 名称 / 删除 | 不可改名、不可删除 | 可改名、可删除（**只删元数据**） |
| 右键菜单 | 不弹（没有任何可管理的项） | 重命名 / 删除 / 在 Finder 中打开 |
| 失效判定 | 恒"可用"（没有目录可失效） | 目录不存在 → `exists: false` |

> **为什么默认空间的 `run_bash` 不跟着 `workdir` 走**（`ToolRegistry.bash_cwd = None`）：
> 改造前 bash 跑在进程 cwd（Electron 拉起后端时 = 应用/仓库目录），文件工具跑在
> `WORKDIR`，两者本就不同。把默认空间一并挪到 `WORKDIR` 会改变既有会话里所有
> 相对路径命令的落点，收益却为零 —— 所以**只有自定义空间**把 bash 与文件工具
> 统一到选定目录（见 `agents/tools.py` 的 `bash_cwd` 注释）。

## 3. 路径解析：为什么必须"按空间"取

改造前 `agents/paths.py` 的 `DATA_ROOT / TASKS_DIR / MEMORY_DIR / CHAT_HISTORY_DIR / TEAM_DIR /
INBOX_DIR / WORKFLOW_DIR` 都是**模块级常量**，全进程唯一（恒指 default）。多工作空间下
它们回答不了"这个会话属于哪个空间"。

解决办法：把"某空间的全部目录"收成一个不可变路径束，按会话注入。

```python
@dataclass(frozen=True)
class WorkspacePaths:
    id: str
    data_root: Path   # ~/.aigent/projects/<id>
    workdir: Path     # 工具沙箱根
    # 派生：chat_history_dir / tasks_dir / memory_dir / inbox_dir / team_dir /
    #       workflow_dir / scheduler_dir / durable_path / transcript_dir / tool_results_dir
```

解析链路（`ws_bridge.py`）：

```
前端 chat{ text, session_id?, project_id? }
        ↓
ws_bridge：session_id / project_id → 工作空间路径束
        ↓
Agent(workspace=WorkspacePaths)  ├─ ToolRegistry(workdir=…, bash_cwd=…, memory=…, task_manager=…, bus=…)
                                 ├─ SystemPromptBuilder(workdir=…)
                                 ├─ HookSystem(workdir=…)        ← 越界判定基准
                                 ├─ TeammateManager(team_dir) / WorkflowManager(workflow_dir)
                                 └─ SessionManager(chat_history_dir, project_id, tasks_dir)
```

### 3.1 铁律：不传 workspace = default = 改造前行为

`Agent(workspace=None)` 走 `paths.workspace_paths("default")`，默认值一字未改。
这条保证了两件事：CLI（`agent_cli.py`）与既有 190 例回归零改动；
`projects.json` 损坏/丢失也不会让老会话变孤儿。

### 3.2 唯一性：会话 id 必须跨空间查重

`new_session_id()` 只在**单目录**查重是不够的：两个空间可能各自生成同一个 `session_x`。
而 `session_id` 是全链路路由键（前端按它分发事件与消息缓冲、桥层按它解析归属），
一旦重号就是"事件进了别的会话 / 切会话切到别的空间"，且**没有任何自愈路径**。

因此 `session_manage.set_session_id_guard(fn)` 由桥层注入一个跨空间占用查询
（逐空间 stat `session_<id>.jsonl` / `.meta.json`），新建会话时循环重掷。
代价是每次新建多 N 次 stat，换掉一条无法自愈的错位风险。

### 3.3 会话归属缓存

桥层维护两个进程内缓存（只增不删，量级 = 空间数 / 会话数）：

- `_MANAGER_CACHE: project_id → SessionManager`（每空间一份会话管理器）
- `_SID_PROJECT: session_id → project_id`

命中即 O(1)；未命中（重启后首次操作 / 老数据）按各空间的元数据目录**磁盘探测**，
命中即缓存，都不命中回落 `default`（与改造前一致）。

> 所有按 `session_id` 操作的命令（重命名 / 回收站 / 还原 / 删除 / 清空 / 模型绑定）
> **必须**经 `_manager_for_session(sid)` 取管理器。直接取 default 的那份会
> "查无此会话"或误改另一个空间里的同名文件。

## 4. 控制命令（协议补丁，详见 `03-前后端通信协议.md` §2.7）

| 命令 | 载荷 | 回包 / 广播 |
| --- | --- | --- |
| `projects_list` | — | 广播 `projects` |
| `project_add` | `{ path }` | 成功：广播 `projects` + `sessions`；失败：`error{msg}` |
| `project_open` | `{ project_id }` | 广播 `projects`（`active` 更新） |
| `project_rename` | `{ project_id, name }` | 成功：广播 `projects`；失败：`error` |
| `project_remove` | `{ project_id }` | 成功：广播 `projects` + `sessions`；失败：`error` |
| `chat` | 新增可选 `project_id` | — |

`projects` 信封载荷：

```ts
{
  projects: [ { id, name, path, system, exists, created_at, last_opened_at } ],
  active: string   // 当前活动工作空间 id
}
```

连接建立时按 `projects` → `session_status` 的顺序重放；渲染进程刷新（HMR/Cmd+R）
不重建 WS 连接，由前端主动 `refreshProjects()` 补拉（同 `refreshSessions` 的补偿逻辑）。

### 4.1 目录选择与"在 Finder 中打开"为什么走 Electron

这两件事是**宿主能力**（原生对话框 / 系统文件管理器），后端 Python 无法提供同等体验：

- `agent:pickFolder` → 主进程 `dialog.showOpenDialog({ properties: ['openDirectory','createDirectory'] })`，
  渲染层拿到绝对路径后再发 `project_add` 给后端登记；
- `agent:openInFinder` → 主进程 `shell.openPath(path)`。

浏览器回退桥（`lib/browserAgent.ts`）里 `pickFolder` 降级为输入路径、`openInFinder` 仅告警 ——
保持"事件式 UI 在浏览器预览下也能跑通"的既有约定。

## 5. 界面与交互

### 5.1 侧边栏：工作空间树

```
任务列表                    ⚙ +
├─ 📁 默认                 ← 固定第一，不可重命名/删除；无真实目录 → 不弹右键菜单
│   ├─ ● 会话 A（按最后修改时间倒序）
│   └─ 展开全部 32 条       ← 超过 15 条时默认只显示最新 15 条
└─ 📁 learn-claude-code-main   ← 文件夹图标 + 折叠箭头 + 行内「+」
    └─ ● 会话 B
```

| 交互 | 行为 |
| --- | --- |
| 点空间行 | 展开 / 折叠（**不切换会话**，避免误触把正在跑的会话切走） |
| 行内「+」 | 在**该空间**新建任务：`newSession(projectId)` → 首条消息带 `project_id` |
| 会话行 | 点击切换会话，右键/三点 = 重命名 / 删除（回收站） |
| 右键空间行 | 重命名 / 删除工作空间 / 在 Finder 中打开 |
| 折叠态 | 持久化在 `localStorage`（缺省展开） |
| 空间徽标 | 子会话的运行状态上浮为脉冲点；未读条数上浮为橙色徽标（折叠时也可见） |
| 目录失效 | 行变淡 + `!` 徽标 + 禁用「+」（无法在空气目录里干活） |

**会话 15 条折叠**：`SESSION_PREVIEW_LIMIT = 15`，超出时列表末尾出现
「展开全部 N 条」/「收起」——没有这个入口的话旧会话永远看不到。

**路径失效（`exists: false`）**：真实目录被删/改名/移动硬盘未挂载。此时禁止新建任务，
右键仍可"删除工作空间"（只清元数据）—— 否则条目会永久卡在列表里。

### 5.2 输入框 chip：工作空间选择器

底部 chip 显示**当前工作空间**（有会话 = 该会话所属空间；空态 = 待建任务的目标空间），
点开是两段式下拉：

```
┌─────────────────────────┐
│ 已打开的工作空间         │
│ 📁 默认            ✓    │
│ 📁 learn-claude-code-main│
│ ─────────────────────── │
│ ＋ 选择文件夹…            │
└─────────────────────────┘
```

- 选一个空间 = 切到它并回到"新建任务"态（该空间没有会话时不会凭空造会话 —— 会话仍由首条消息惰性创建）；
- 「选择文件夹…」= 原生选择框 → 登记 → 打开 → 新任务态；
- 选中后前端同步调用 `project_open`，让后端"活动空间"跟上（否则下一次 `projects`
  广播会把 chip 拉回去）。

### 5.3 删除工作空间：必须二次确认

删除**没有回收站**（同步 `rmtree` 元数据目录），所以：

1. 右键菜单里点「删除工作空间」→ 按钮变红变「确认删除？」，3 秒内再点一次才真删
   （与「设置 → 回收站」的 arm-confirm 同款交互）；
2. 菜单同时说明删的是什么：**仅元数据（含 N 条会话）**，真实目录 `<path>` **保留**；
3. 后端还有一道守卫：该空间仍有会话在跑（含后台任务）→ 拒绝并回
   `error{msg: "该工作空间还有 N 个会话正在执行…"}`。删掉正在写的会话文件是不可逆事故。
4. 删掉的是"当前活动空间"时，后端把 `active` 回落 `default`；该空间的会话运行时
   一并从注册表移除，前端本地列表同步剔除。

### 5.4 新增工作空间的校验（后端拒绝，前端显式报错）

| 情况 | 结果 |
| --- | --- |
| 目录不存在 / 不是目录 | 拒绝：`目录不存在或不是目录：<path>` |
| 目录不可写（`os.access(W_OK)`） | 拒绝：`目录不可写，请换一个目录：<path>` |
| 选了 `~/.aigent` 内部目录 | 拒绝：`不能把 ~/.aigent 内部目录选为工作空间`（否则用户可见目录里会被塞进 `.chathistory` 之类） |
| 同一真实路径再次选择 | **复用**已有条目（按 realpath 比较，软链/相对路径同样识别） |
| 与已有空间同名（不同目录） | 展示名自动加后缀：`frontend` → `frontend (2)` |
| 重命名成已有名字 | 拒绝：`已存在同名工作空间：<name>`（显式输入不静默加后缀 —— 用户会以为自己改成了想要的名字） |

## 6. 失败态与恢复

| 场景 | 表现与处理 |
| --- | --- |
| `projects.json` 丢失 | 启动 `ensure()` 重建为只含 default 的索引（老用户升级路径） |
| `projects.json` 损坏 | 备份为 `projects.json.bak` 后重建（保留现场供排查），default 条目从索引手改删除也会被归一化补回 |
| 索引被并发修改 | 读-改-写整段持 `RLock` + 临时文件 `os.replace` 原子写（与 `.tasks` 同款教训：半截文件会让整个空间列表消失） |
| 建空间时索引写失败 | 回滚刚建的元数据目录，不留"无主目录" |
| 元数据目录被手工删掉 | 条目仍在但目录不存在 → 删除条目时跳过目录清理（不报错） |
| 自定义空间真实目录消失 | 条目置失效（`exists: false`）；在该空间发消息被拒绝，提示重新选目录 |
| 单个空间列会话出错 | 只跳过该空间并记 error，不拖垮整个 `sessions` 列表 |
