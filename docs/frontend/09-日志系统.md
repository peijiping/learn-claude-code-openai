# 09 - 日志系统

> 状态：已实施（2026-09-11）。本文档描述桌面端前后端的统一日志方案，
> 作为后续垂直类智能体客户端的开发依据。

## 概念

桌面端由两个长驻进程组成：Electron 主进程（前端壳）与 `ws_bridge.py`（Python 后端）。
此前排障完全依赖 `print` 到 stdout，存在三个问题：

1. **无落盘**：Electron 生产模式拉起的子进程 stdout 无人消费，历史输出丢失；
2. **无结构**：没有时间戳 / 级别 / 来源，事后无法回溯"几点几分发生了什么"；
3. **无兜底**：未捕获异常（尤其线程内异常）直接蒸发，进程崩溃无从查起。

日志系统的目标是：**任何一次运行的关键节点（启动、会话生命周期、模型切换、
turn 执行、工具调用、异常崩溃）都能在文件里按时间线回放**。

## 设计

### 目录与文件

- 目录：`~/.aigent/logs/`（常量 `LOG_DIR` 定义在 `agents/paths.py`，随 `ensure_dirs()` 创建）。
- 文件按**日期**命名，跨天（本地时区）自动切换新文件，无需重启进程：
  - 后端（Python）：`agent_YYYY-MM-DD.log`
  - 前端（Electron 主进程）：`frontend_YYYY-MM-DD.log`

### 行格式

```
2026-09-11 15:30:01 [INFO] [ws_bridge] WS 连接建立: ('127.0.0.1', 52318) (active=1)
2026-09-11 15:30:05 [INFO] [agent] 工具执行完成: session_12 read_file (0.03s, 输出 1024 字符)
```

`时间 [级别] [来源] 消息`。来源（logger name）区分模块：`ws_bridge` / `runtime` /
`agent` / `cli` / `crash`（前端用 tag：`app` / `python` / `ws`）。

### 关键取舍

- **只写文件，不写 stdout**：stdout 是 CLI 交互 / Electron 日志面板的通道，
  `print` 继续承担控制台职责；日志走文件，互不干扰、不产生双份噪音。
- **logging 标准库自实现按日切换**：`DailyFileHandler` 在每次 emit 时比对当前
  日期，跨天即换新文件（append 模式）；不引入额外依赖。logging 框架对 handler
  加锁，多线程（turn 工作线程 / 后台子智能体）并发写安全。
- **级别可调**：`LOG_LEVEL`（默认 `INFO`）走既有配置链
  （`~/.aigent/config.json` > 环境变量 > 默认值，见 `05-配置与数据目录管理.md`）。
- **日志失败绝不打断业务**：写文件异常由 `handleError` 吞掉；前端 `appendFile`
  失败静默。
- **每条写完即 flush**：后端长驻进程随时可能被 SIGTERM/SIGKILL（Electron
  退出、孤儿看护自杀），不 flush 的话 Python 文件缓冲里的日志会随进程一起
  丢失。曾因此踩坑：`emit` 里误调基类 `Handler.flush()`（访问不存在的
  `self.stream` 属性抛 `AttributeError` 被吞），表现为"前台测试正常、
  服务进程日志随机丢失"——正常退出的进程会自动刷缓冲，掩盖了 bug。
- **崩溃兜底**：后端入口调用 `install_excepthooks()`，把主线程与子线程的
  未捕获异常（含完整 traceback）写入 `[crash]` 来源，进程被强杀前的最后
  一线证据不再丢失。

from logger import get_logger
log = get_logger("agent")   # 任意模块名
log.info("会话切换: session_%d", num)

### 排障口径：会话"结束"了，但最终总结没出来（2026-09-18 事故）

后台任务全部完成后，`_watch_background` 会自动续一轮（`bg followup`）让主智能体
产出总结。若这一轮**在执行期抛异常**，日志尾部会呈现这样一组三行：

```
16:29:29 [ERROR] [runtime] session_oqlA8pXPQT bg followup 异常: UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe7 in position 4199: unexpected end of data
16:29:29 [INFO]  [runtime] session_oqlA8pXPQT bg watch done (47.6s total)
16:29:29 [INFO]  [runtime] session_oqlA8pXPQT status -> done
```

判读顺序：

1. **`bg followup 异常` = 续轮死了 → 最终总结必然缺失**（前端表现：运行指示正常复位，
   但"最后结果的消息"永远不来，任务面板停在半路）。异常类型直接指向失败层：
   `UnicodeDecodeError` → 工具输出解码；`APIError` / `Timeout` → LLM 层。
2. 看异常**之后**是否有 `bg followup 失败，回滚 M/N 条后台结果待重试（第 K 次失败，上限 1）`
   —— 这是 2026-09-18 新增的回滚重试：`M>0` 表示本批结果被退回、会给一次重试机会，
   随后应再看到一次 `bg followup turn #N`；`M=0` 表示没有可回滚项（如异常发生在消费之前），
   直接收尾属正确行为。
3. **异常已被兜住**的标志：工具路径上还会出现 `[agent] 工具执行异常: …` 或
   `[tools] run_bash 异常: …`（均带堆栈）。只要出现，说明异常已降级为工具结果，
   本轮会继续跑完，不会再"整轮被打死"。

**会话文件侧的对照判据**：被打断的那一轮，`session_*.jsonl` 末条 assistant 会
**有 `tool_calls` 却没有对应的 `tool_result`**。下次加载时自愈逻辑会为每个未闭合的
tool_call 补一条 `Error: missing tool result (recovered)` 占位，历史完整、无需人工修数据。

### LLM 响应画像（2026-09-14 追加）

`session_runtime` 在事件流过 WSSink 时顺手累计"本次 LLM 响应"的形状，并在
`turn_end` 事件（每次 LLM 调用结束都会发）打一行：

```
2026-09-14 10:17:55 [INFO] [runtime] session_1 LLM 响应: finish=tool_calls 工具调用=['sub_agent'] content=65字 thinking=1797字 usage={'prompt_tokens': 11785, ...}
2026-09-14 10:18:11 [INFO] [runtime] session_1 LLM 响应: finish=stop 工具调用=无 content=2457字 thinking=724字 usage={...}
```

**为什么需要**：模型偶尔会产出「正文承诺要干活、却一个 `tool_call` 都没有」的
**正常 `stop`** 响应（实测事故：回了"我派一个子智能体后台去读"然后本轮直接结束，
用户侧看到"直接中断、不往下执行"）。而在此之前，日志里只有 `turn 结束`，
**无法区分「模型没发工具调用」还是「工具调用发了却丢了」** —— 事故复盘只能靠
反推 token 数（6319 + 6840 + 276 ≈ 13435）才能确认到底发生了几次 LLM 调用。

- `finish=tool_calls 工具调用=无` → 会额外打一条 `ERROR`：这是**协议自相矛盾**
  （声明有工具调用却一个都没聚合出来），属真 bug，必须查；
- `finish=stop 工具调用=无` → 模型自己收尾。若正文里"承诺了动作"，说明工具调用
  被模型放弃/被服务端丢弃，问题在**提示词与工具 schema**（措辞、必填项、
  示例工具名是否与真实契约一致），而不在流式聚合。

### 验证方式

```bash
# 启动桌面端后查看当日日志
ls ~/.aigent/logs/
tail -f ~/.aigent/logs/agent_$(date +%F).log
tail -f ~/.aigent/logs/frontend_$(date +%F).log
```

一次完整的"启动 → 新会话 → 对话一轮"在后端日志里应能看到：
`后端启动 → WS 连接建立 → 新会话创建 → chat 派发 → agent 构建完成 →
turn 开始 → 工具执行开始/完成… → turn 结束 → turn 结束(session)`。
