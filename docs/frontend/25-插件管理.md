# 25 - 插件管理

> 在设置弹窗里新增独立的「插件」菜单：**市场浏览与一键安装**、**组件清单确认**、**启停 / 查看详情 / 删除**。
> 核心结论：插件市场**不需要自己造** —— Claude Code 的插件规范是**既定事实标准**，「任何 git 仓库 + 根目录一份 `.claude-plugin/marketplace.json`」就是一个市场（实测官方市场 **314 个插件**）。于是「兼容即市场」，我们只做客户端。
> 本篇的另一半是**能力边界的诚实表述**：插件能贡献 6 类组件，**本期只有「技能」接入运行时**（§2.4）。
>
> 姊妹篇：`23-MCP服务管理.md`（面板语言与协议约定的出处）、`24-技能管理.md`（面板与协议的**逐条复用**，本篇不重复）。

## 一、概念

### 1.1 插件市场：有事实标准，而且可以直接用

2026-09-30 实测：

| 市场 | 形态 | 实测 |
| --- | --- | --- |
| `anthropics/claude-plugins-official` | 仓库根目录 `.claude-plugin/marketplace.json` | ✅ **200，314 个插件** |
| `anthropics/claude-plugins-community` | 同上（第三方经自动校验收录，每条 pin 到 commit） | 内置 |
| `anthropics/claude-code` | 同上（官方示例） | 内置 |
| `anthropics/skills` | 同一个仓库既是技能仓库、也带 `.claude-plugin` 清单 | 内置 |
| `claudemarketplaces.com` / `aitmpl.com` / `claudepluginhub.com` | HTML 目录 | ❌ 无稳定 API |

关键点：**这不是一个中心化 API，而是"任何 git 仓库都是市场"**。所以我们的"市场 API"退化成一件很便宜的事 —— 用户填一个仓库地址，我们读它根目录那份 `marketplace.json`。读用 **raw CDN**（`raw.githubusercontent.com`），**不计入 GitHub API 的 60 次/时限额**。

### 1.2 条目 `source` 的四种形态（实测覆盖官方市场全部 314 条）

| 形态 | 官方市场计数 | 例子 | 翻译成 |
| --- | --- | --- | --- |
| 相对路径 | 52 | `"./plugins/agent-sdk-dev"` | 就在**市场仓库自己**里面 |
| 完整 git url | 164 | `{source:"url", url:"…/x.git", sha}` | 独立仓库 |
| git 子目录 | 98 | `{source:"git-subdir", url, path:"plugins/x", ref, sha}` | 仓库的某个子目录 |
| GitHub 简写 | 0（兼容写法） | `{source:"github", repo:"o/r"}` | GitHub 仓库 |

**绝对路径 / `../` 形态（本地市场专用）明确拒绝并给原因** —— 静默忽略会让用户以为"这个插件消失了"。

⚠️ 优先用 `sha`（Claude Code 会把社区插件 pin 到具体 commit），没有才退到 `ref`、最后才用市场声明的分支。这样"市场更新了但插件没变"不会造成意外升级。

### 1.3 插件是什么

一个目录 + `.claude-plugin/plugin.json` 清单。清单本身可以很短：

```json
{ "name": "code-review", "description": "Automated code review…", "version": "1.0.0" }
```

组件按**约定目录**摆放（不是清单里逐条声明）：

| 组件 | 位置 | 本期是否接入运行时 |
| --- | --- | --- |
| 技能 | `skills/<name>/SKILL.md` | ✅ **是** |
| 命令 | `commands/*.md` | ❌ 只入库 |
| 子智能体 | `agents/*.md` | ❌ 只入库 |
| 钩子 | `hooks/hooks.json` | ❌ 只入库（**不会执行**） |
| MCP 服务器 | `.mcp.json` 的 `mcpServers` | ❌ 不会自动连接（可在「MCP」页手工添加） |
| 语言服务器 | `lspServers`（清单声明） | ❌ 只入库 |

### 1.4 元数据同样走旁路文件

`~/.aigent/plugins_sources.json`，理由与 24 篇 §1.3 **逐条相同**（保持插件目录可移植 / 启停不该改写清单 / 来源信息与内容无关）。UI 数据源同样是**磁盘扫描**而不是过滤后的视图 —— 否则被禁用的插件永远看不见。

## 二、设计

### 2.1 数据布局

| 路径 | 常量 | 作用 |
| --- | --- | --- |
| `~/.aigent/plugins/<name>/.claude-plugin/plugin.json` | `paths.PLUGINS_DIR` | 插件本体（+ 全部组件） |
| `~/.aigent/plugins_sources.json` | `paths.PLUGIN_SOURCES` | 旁路元数据（启停 + 来源） |
| `~/.aigent/plugin_markets.json` | `paths.PLUGIN_MARKETS` | 已注册的市场（内置 + 自定义） |

安装体量闸门：**单文件 2 MiB / 总计 20 MiB / 最多 300 个文件**（与技能侧同级，但插件通常更大）。

### 2.2 组件清单：磁盘发现 ∪ 清单声明

`plugin_store.inventory_of_files()` 按**相对路径**推导组件清单。这条路径既服务本地目录扫描（`_inventory` 把目录读成同一张映射再转调），也服务市场侧的远程抓取 —— **只有一份规则**。

**为什么取并集而不是只信清单**：实测插件清单经常只写一半（有的只声明 `skills` 不写 `commands`，有的这几个字段根本不写）。只信清单会让安装确认页显示的"将要生效的东西"**比实际少** —— 那恰恰是安全闸门最不能出错的地方。

`hooks` 的计数按事件聚合（`PreToolUse（2 条）`），`mcpServers` 列键名。

### 2.3 技能命名空间：`<插件>:<技能>`

插件贡献的技能进入技能表时带前缀（与 Claude Code 的 `plugin:skill` 规则一致）。理由很实际：**插件之间技能重名是常态**（各家都爱叫 `code-review`），不加前缀必然互相覆盖（`SKILL_REGISTRY` 是 dict，后来的静默赢）。

前缀里的 `:` 不可能出现在技能名里（技能名白名单不含 `:`），所以不会歧义。

启停的连带效果：插件禁用 → 它贡献的技能**立即**退出技能表（`iter_skill_manifests()` 只遍历启用且清单有效的插件），并触发一次 system prompt 重建（24 篇 §2.2）。

### 2.4 能力边界必须在界面上说清楚（本篇最重要的决定）

插件的六类组件里，**本期只有「技能」真正接入运行时**。这件事必须在**两个地方**都讲：

1. **列表页常驻横幅**：说明"只有技能接入运行时，其余只落盘不执行"。
2. **安装确认页**：逐个组件列出，并用徽标标注 `本期生效` / `本期未接入`（`plan.wired` 由后端下发，前端零硬编码）。

不这么做的后果很具体：
- 只说"装了能用" → 用户看到一个插件带 3 个 hook、2 个 MCP 服务器，会以为**那些代码开始跑了**；
- 只说"未接入" → 用户又会以为整个插件都没用。

**两侧都要说。** 徽标刻意都用中性色（生效用 accent、未接入用灰）—— 用绿色会让"未接入"显得像错误，而它只是能力边界，不是故障。

### 2.5 安装确认页

`install` 视图是全流程唯一的安全闸门，展示四样东西：

| 区块 | 内容 | 为什么必须有 |
| --- | --- | --- |
| **组件清单** | 6 类逐项，含数量与生效标记 | "这个插件会往你机器上放什么"的完整凭据 |
| **贡献技能首行说明** | `<插件>:<技能>` + 描述 | 让用户看出"这些技能会教模型做什么" |
| **`plugin.json` 原文** | 整份 | "它自称是什么"的一手材料 |
| **文件清单** | 全部文件 + 体积 | 插件可以带脚本；只看清单会漏掉它们 |

不提供"记住我的选择"之类的便捷开关（同 23 / 24 篇的结论）。

### 2.6 界面结构（3 个子视图）

| 视图 | 组件 | 职责 |
| --- | --- | --- |
| `list` | `PluginSettings` 内联 | 插件列表：详情 / 启停 / 删除 |
| `market` | `PluginMarketView` | **选市场 + 搜索 + 分页**，并内联「管理市场」 |
| `install` | `PluginInstallView` | **安装确认**（组件清单 + 清单原文 + 文件清单） |

比技能页少一个 `form`：插件是**能力包**，没有一个"手写一份"的合理形态（手写 = 直接在 `~/.aigent/plugins/` 建目录）。

列表页状态文案：`清单缺失`（红）/ `已禁用`（灰）/ `已启用 · 贡献 N 个技能`（绿）/ `已启用 · 无技能贡献`（灰）。展开区里把组件列成 chip，生效的那类带 `✓`。

## 三、协议

### 3.1 命令与信封（9 条命令 / 4 个信封）

与技能侧**一一对应**（`plugin_*` ↔ `skill_*`），全部点对点、不广播、不进 `isKnownAgentEvent` 白名单。

| 命令 | 载荷 | 回执信封 |
| --- | --- | --- |
| `plugin_config_get` | — | `plugin_config` |
| `plugin_set_enabled` | `{name, enabled}` | `plugin_config` |
| `plugin_remove` | `{name}` | `plugin_config` |
| `plugin_install` | `{name, item}` | `plugin_config` |
| `plugin_read` | `{name}` | `plugin_content` |
| `plugin_market_search` | `{market_id, query?, cursor?, limit?}` | `plugin_market` |
| `plugin_market_resolve` | `{market_id?, item}` | `plugin_market_plan` |
| `plugin_market_upsert` | `{entry}` | `plugin_config` |
| `plugin_market_remove` | `{market_id}` | `plugin_config` |

两点与技能侧的差别：

- **多一个 `plugin_read`**：读 `plugin.json` 原文 + 文件清单。技能的正文已经由 `market_plan` 带回（12 个文件以内），插件的文件清单则可能大得多，单独取更划算。
- **`plugin_market_resolve` 的载荷明显更重**：`components` / `component_counts` / `wired` / `skill_previews` / `plugin_json` / `files`。确认页要展示的全在这里。

### 3.2 `plugin_config` 载荷

```jsonc
{

  "sources_path": "/Users/me/.aigent/plugins_sources.json",
  "markets_path": "/Users/me/.aigent/plugin_markets.json",
  "exists": true,
  "plugins": [{
    "name": "frontend-design",
    "display_name": "frontend-design",
    "description": "Guidance for distinctive, intentional visual design…",

    "author": "Anthropic",
    "homepage": "",
    "has_manifest": true,
    "enabled": true,
    "path": "/Users/me/.aigent/plugins/frontend-design",
    "manifest_path": "/Users/me/.aigent/plugins/frontend-design/.claude-plugin/plugin.json",
    "components": {                       // 6 类，磁盘发现 ∪ 清单声明
      "skills": ["frontend-design"], "commands": [], "agents": [],
      "hooks": [], "mcp_servers": [], "lsp_servers": []
    },
    "component_counts": { "skills": 1, "commands": 0, "agents": 0,
                          "hooks": 0, "mcp_servers": 0, "lsp_servers": 0 },

                "is_default": true }],

  "wired_components": ["skills"],         // 后端声明的能力边界（单一出处）
  "contributed_skill_count": 1,           // 当前实际进入技能表的插件技能数

```

`plugin_content` 载荷：`{name, plugin_json, path, manifest_path, components, files[{path,size}], error}`。
`plugin_market` 载荷：`{items[], next_cursor, market_id, market_name, catalog_name, catalog_owner, query, total, error, elapsed_ms}`（后两者是 `marketplace.json` 里声明的市场名与维护者 —— 展示"这是谁的市场"）。
`plugin_market_plan` 载荷：`{ok, name, plugin_name, display_name, description, version, author, homepage, plugin_json, components, component_counts, wired, skill_previews[{name,description}], files, file_count, total_bytes, source_kind, repo, warnings, unsupported, error, meta}`。

### 3.3 超时

| 命令 | IPC 超时 | 依据 |
| --- | --- | --- |
| `plugin_market_search` | **30s** | 读一次 `marketplace.json`（官方市场 314 条 ≈ 184 KB）实测 1~3s；留足余量 |
| `plugin_market_resolve` / `plugin_install` | **60s** | 要拉下整个插件目录（最多 300 个文件），后端单请求 20s × 并行抓取 |
| 其余 | 默认 5s | 纯本地读写 |

`marketplace.json` 的上限**单独放宽到 8 MiB**（`MARKET_FILE_MAX_BYTES`）—— 通用 raw 抓取的默认上限是 512 KiB，用它会把这份目录截断，而**截断后的 JSON 解析必然失败**（症状是"市场打不开"但看不出原因）。

### 4.2 一个容易混淆的地方：`wired` 从哪来

`wired` **由后端下发**（`plugin_store.WIRED_COMPONENTS`，经 `plugin_config.wired_components` 与 `plugin_market_plan.wired` 两个字段），前端**零硬编码**。理由：能力边界是后端实现决定的，前端写死一份必然在接入新组件时忘记同步 —— 而那种不同步的后果正是 §2.4 要防的"用户以为某类组件生效了"。

## 六、关键取舍与踩坑

| # | 事项 | 结论 |
| --- | --- | --- |
| 1 | 插件市场要不要自建 | **不要**。Claude Code 的 `marketplace.json` 是事实标准，兼容即市场 |
| 2 | 读市场走哪条通道 | **raw CDN**（不计 API 限额）。走 Contents API 会在 314 条目录上直接打爆限额 |
| 3 | `marketplace.json` 的体积上限 | **单独放宽到 8 MiB**。用通用 512 KiB 上限会截断 → JSON 解析失败 → 症状是"市场打不开"但看不出原因 |
| 4 | source 的 `sha` 优先 | pin 到 commit 才是可复现的；"市场更新了但插件没变"不该造成意外升级 |
| 5 | 本地路径形态 | **明确拒绝并给原因**，不能静默忽略（否则用户以为"插件消失了"） |
| 6 | 组件清单 | 磁盘发现 ∪ 清单声明。只信清单会让确认页显示的比实际少 |
| 7 | 能力边界 | 列表页横幅 **与** 确认页徽标**都**要讲；`wired` 由后端下发，前端零硬编码 |
| 8 | 徽标配色 | 中性色。绿色会让"未接入"显得像错误，而它只是能力边界 |
| 9 | 技能命名空间 | `<插件>:<技能>`。不加前缀必然互相覆盖（`SKILL_REGISTRY` 是 dict） |
| 10 | 目录遍历顺序 | `os.walk` 不稳定 → **必须排序**，否则组件清单顺序会飘、界面像"配置变了" |
| 11 | 二进制资产 | 按扩展名判断，非文本原样存 `bytes`。把 PNG 当字符串写出去**不会报错**，只会在用的时候发现图挂了 |
| 12 | 安装协议面 | 只回传「哪一条 + 叫什么名」，后端重新解析 + 重新抓取（同 24 篇 §3.1） |
| 13 | 钩子 / MCP 为什么本期不接 | 两者都是"在本机跑代码/建连接"，接入面远大于"多扫一个目录"：需要在 `mcp_manager` / 生命周期里做增量 reconcile，且要处理"禁用插件时要断开哪些连接"。这是独立的一件事，不该混在管理面里做（§7.1） |
| 14 | raw 抓取通道（2026-09-30 修复） | 插件的 `marketplace.json` 与全部组件文件都走 `skill_market._raw_bytes` —— 该函数已改为**多通道依次回退**（直连 raw.githubusercontent.com → jsDelivr 镜像），修复记录见 24 篇 #17。症状同源：raw 被墙时「插件市场打不开 / 点安装没反应」而搜索（Tree API）正常 |
| 15 | 点「安装」的响应（2026-09-30 修复） | `onPick` **立即切到 install 视图**（resolve 要拉整个插件目录，可能十几秒），不要 `resolve().then(() => setView(...))` —— 抓取期留在市场页无任何指示 = 用户以为「点了没反应」（同 24 篇 #18） |
| 16 | resolve 超时的出路（2026-09-30 修复） | `resolvePluginInstall` 收到 `null`（IPC 超时）必须**合成失败计划**（与 catch 分支同形），不能 `if (res)` 跳过 —— 那会让确认页掉进"安装信息已失效"死端。根因与修法详见 24 篇 §六 #19（后端 `_fetch_git_files` 并行化 + `SKILL_MARKET_RAW_TIMEOUT` 收紧 + 前端 null 合成失败计划，三处同修） |

## 七、后续增量

按优先级排：

1. **钩子与 MCP 组件真正接入运行时** —— 本期只入库不执行。落地要点：插件贡献的 MCP 服务器要像 `mcp_servers.json` 的条目一样进 `MCPManager` 的 reconcile（含禁用插件时的断开），钩子要接进 `hooks.py` 的既有链路并套上审批门控。接入后 `WIRED_COMPONENTS` 加一项、界面上那两处文案自动跟随（因为都读后端下发的 `wired`）。
2. **`commands/` 接入斜杠命令** —— 目前前端没有"从插件加载命令"的通道。这是插件价值最直接的另一半。
3. **插件更新 / 版本对比** —— 现在只能删了重装。需要按 `sha` 判断上游是否变过。
4. **子智能体（`agents/*.md`）接入** —— 与 24 篇的插件技能注入是同一类问题（多一个扫描来源），但子智能体定义有自己的 schema 与校验要求。
5. **市场搜索的服务端聚合** —— 目前一个市场一次搜索（选源 + 搜），跨市场搜索需要先把各市场的 `marketplace.json` 拉下来做本地合并。收益是"一次搜到所有市场的东西"，成本是首屏要拉 N 份目录。
