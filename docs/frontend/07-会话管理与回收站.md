# 会话管理与回收站

> 本文档描述桌面智能体客户端的**会话元数据、标题生成、会话重命名/归档与归档页**机制。核心结论：会话不再只有 `session_N.jsonl` 过程记录，新增同目录的 **`index.jsonl`** **元数据索引**（标题/创建时间/状态/项目归属，以文件名为键与会话文件关联）；运行时数据从项目内 `WorkSpace/task1/` 迁移到用户级 **`~/.aigent/projects/<slug>/.chathistory/`**（分项目隔离，对齐 Claude Code `~/.claude/projects/` 模型）；删除走**软删除两段式**（先归档，归档页内永久删除）；标题采用**简单两段式**：新建会话时先以首条消息前 30 字为默认标题，**第一轮对话结束后**再调用一次大模型总结生成 ≤20 字的精炼标题。按「概念 → 设计 → 落地」组织。
>
> **2026-09-20 术语更名**：界面层的「删除（会话）」更名「**归档**」、「回收站」更名「**归档**」（设置页入口）——软删除机制（`trashed` 状态 / `trash` / `restore`）与协议命令名（`session_trash` / `trash_list` / `sessions_trashed`）**不变**，改的只是用户可见文案。归档页新增工作空间筛选（默认「默认工作空间」），见 §2.6。

***

## 一、概念

### 1.1 为什么需要会话元数据

改造前，会话只有过程数据 `session_N.jsonl`（每行一条消息），没有会话自身的属性：

- **列表无标题**：任务树只能显示 `session_3` 这类编号，用户无法辨识会话内容。

- **无生命周期状态**：没有"已删除"概念，要么保留要么物理删文件，误删无法挽回。

- **无时间与归属**：创建/更新时间只能靠文件 mtime 猜；未来多项目阶段无法区分会话属于哪个项目。

元数据与过程数据**分文件存放**（`index.jsonl` + `session_N.jsonl`），而不是往消息行里塞元数据：消息行是数组语义（append-only），元数据是字典语义（频繁就地更新），混放会让读写双方都别扭。

### 1.2 软删除与归档（桌面产品惯例；UI 名「归档」，机制名 trash）

会话「删除」分两段（2026-09-20 起 UI 统一叫**归档**）：

1. **归档（软删除）**：会话菜单点「归档」→ 元数据 `status: active → trashed`，会话文件原样保留。会话列表不再显示，归档页可见（默认按「默认工作空间」筛选）。
2. **永久删除（硬删除）**：在归档页操作，物理删除 `session_N.jsonl` + 绑定的 `session_N.subagents.jsonl`（子智能体旁路记录）+ 任务板文件 + 元数据条目。

好处：误操作可还原（`restore`）；「归档」按钮永远不造成不可逆后果，破坏性操作集中到归档页并配二次确认。**归档页只有会话级操作，不能删除工作空间**（空间删除在侧边栏空间菜单，且只删元数据目录）。

### 1.3 标题生成：简单两段式（默认截断 + 首轮后一次 LLM 总结）

三种候选方案：

| 方案        | 做法                                                                                                | 问题                                                              |
| --------- | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| A. 解析主对话 | 首轮回复中让模型顺带输出标题（约定格式），前端解析截取                                                                     | 污染主对话历史与 system prompt；格式解析脆弱；流式渲染时标题混入正文；重试/压缩时易丢失 |
| B. 首轮并行小请求 | 首条消息到达时即发独立小请求生成标题，与首轮 `run_turn` 并行（早期实现，已弃用）                                                  | 多一次 LLM 调用且与首轮**抢跑**；并发时序（daemon 线程）复杂，收益仅"标题早出现几秒"    |
| C. 简单两段式   | 新建会话时直接以**首条消息前 30 字**为默认标题（零延迟、零成本）；**第一轮对话结束后**再调用一次大模型总结生成 ≤20 字精炼标题并覆盖 | 标题在首轮进行中仍是截断态（对用户无感，与 TraeWork / WorkBuddy 等主流做法一致）       |

**采用方案 C**（对齐主流智能体行为）：标题不抢跑、不与主对话并发，没有 daemon 线程、没有"先到先得"的时序博弈。默认标题让会话列表**创建即可读**；首轮结束后的一次 LLM 总结把标题精炼到 20 字内，写回后经 `sessions` 全量回发即时刷新。LLM 请求失败/不合法时**保留默认标题**，任何异常都不影响主流程。

## 二、设计

### 2.1 元数据模型（独立 meta 文件 + index.jsonl 兜底轨道）

> **2026-09-14 会话标识与排序改造**：
> 1. **文件命名**：新会话文件为 `session_<id>.jsonl`——`id` 为 10 字符 base62 随机短 id
>    （`secrets` 生成，59.5 bit 熵；创建时查重、撞名重掷，工程上不可能重复；全数字则重掷，
>    保证"全数字 stem = 存量编号、混合 = 新 id"的解析无歧义）。**存量 `session_N.jsonl` 不迁移
>    （新旧共存）**，其 id 即原编号的字符串形式（`"6"`），全链路以 `str` 类型 `session_id` 寻址。
> 2. **元数据双轨**：新会话写独立 `session_<id>.meta.json`（O(1) 读写，字段同下表，主键 `id`）；
>    存量会话继续走 `index.jsonl`（键=文件名）。两轨读取统一封装在 `_meta_entry_for()`。
> 3. **`updated_at` 刷新时机（本改造新增）**：`append_message_to_session` /
>    `append_subagent_to_session`（旁路模式）/ `save_session_history`（压缩、自愈重写）/
>    会话清空后同步刷新 meta `updated_at`——这是"按最后修改时间排序"的数据源；
>    index 轨不单独刷新（避免全量重写），排序时由文件 mtime（亚秒精度）兜底，
>    排序键取 `max(updated_at, mtime)` 的 epoch 数值。
> 4. **排序**：会话列表与 `get_latest_session()`（恢复最近会话）均按「最后修改时间」
>    **最近使用优先**降序，不再按编号排序。
>
> **2026-09-18 多工作空间补充**：短 id 的查重范围从"单个空间目录"扩到**全部工作空间**
> （`session_manage.set_session_id_guard`，由桥层注入跨空间占用查询）。理由：`session_id`
> 是全链路路由键（前端按它分发事件与消息缓冲、桥层按它解析所属工作空间），一旦两个空间
> 各自生成同一个 id，就是"事件进了别的会话 / 切会话切到别的空间"，且**没有任何自愈路径**。
> 概率极低（59.5 bit 熵），但代价是数据错位级别的，所以宁可每次新建多 N 次 stat。
> 详见 `11-工作空间管理.md` §3.2。
>
> 同时：`SessionManager` 新增 `project_id`（写进新会话元数据）与 `tasks_dir`（级联清理用），
> 两者都由所属工作空间注入；`tasks_dir` **不从 `chat_history_dir.parent` 反推**（该约定在 CLI /
> 测试夹具下不成立，会算到隔壁目录去）。

新方案会话元数据与 `session_<id>.jsonl` 同目录独立存放，**以会话 id 关联**：

```json
{"id": "Kx7mQ2vT8p", "file": "session_Kx7mQ2vT8p.jsonl", "title": "分析 goal.py 存储机制", "title_source": "auto", "created_at": "2026-09-08T10:30:00", "updated_at": "2026-09-08T10:35:12", "status": "active", "trashed_at": null, "project": "default",
 "usage_totals": {"prompt_tokens": 25204, "completion_tokens": 1188, "cached_tokens": 19456, "total_tokens": 26392, "turns": 3}}
```

存量 `index.jsonl` 条目结构相同（`num` 字段为历史遗留，读取时兼容，新条目一律写 `id`）：

| 字段                          | 类型           | 说明                                                                           |
| --------------------------- | ------------ | ---------------------------------------------------------------------------- |
| `id`                        | string       | 会话 id（协议寻址用）：短随机串（新会话）/ 存量编号字符串；条目键为文件名，meta 轨以 `id` 定位文件            |
| `file`                      | string       | 关联的会话文件名（index 轨**主键**，`session_` / `cron_` 前缀共用目录时避免冲突）                     |
| `title`                     | string\|null | 会话标题；null 时前端回退显示 `session_<id>`                                            |
| `title_source`              | string       | 标题来源：`user`（手动重命名）> `auto`（首轮后 LLM 总结，≤20 字）> `trunc`（首条消息前 30 字默认标题）> `none`（无标题）。低优先级不覆盖高优先级 |
| `created_at` / `updated_at` | string       | 本地时间秒级 ISO（单机桌面产品，无时区转换）；`updated_at` 在消息追加/重写时同步刷新（见上方变更说明 3）                |
| `status`                    | string       | `active`（任务树） / `trashed`（回收站）                                               |
| `trashed_at`                | string\|null | 移入回收站的时间（回收站列表展示"删除于"）                                                       |
| `project`                   | string       | **所属工作空间 id**（2026-09-18 起为真实 id）：默认空间 `"default"`，自定义空间 `"ws"` + 10 位短码。由 `SessionManager(project_id=…)` 写入；存量会话缺该字段时按**目录归属**兜底（= 该管理器的空间 id），绝不会被错认成 default 空间。**会话建成即锁**（2026-09-20）：归属不可变，后端对已有会话的改归属请求一律拒绝 |
| `work_root`                 | string\|null | **会话级沙箱根快照**（2026-09-20 新增）：新建会话时解析一次写定，之后不可变 —— default 新会话 = `~/.aigent/projects/default/scratch`，自定义空间 = 选定目录；`null` = 存量会话/CLI（读侧回退遗留 `WORKDIR`，零迁移）。读侧 `ws_bridge._workspace_for_session()`：有快照以快照为准（bash 与文件工具同根），无快照按空间现值。详见 `11-工作空间管理.md` §3.4 |
| `usage_totals`              | object       | 会话级 token 消耗累计（可选，2026-09-16 新增）：`{prompt_tokens, completion_tokens, cached_tokens, total_tokens, turns}`。每轮 turn 收尾由 `add_usage_totals()` 增量累加（O(1) 原子写）；主 + 子智能体（含后台迟到，`count_turn=False` 只补数值不加轮数）全部计入；`clear_session` 时清除。切会话经 `session_history.usage_totals` 回放给前端圆圈 tooltip |
| `unread`                   | boolean\|默认false | 未读标记（2026-09-18 新增）：会话完整结束（`done`/`stopped`）且用户当前不在查看它 → `true`；用户进入/点击查看该会话 → `false`。由前端判定后经 `session_set_unread` 写入元数据持久化，跨窗口/重启随 `sessions` 事件同步；侧边栏据此渲染橙色实心点（未读）或空心圆（已读） |

写入策略：

- **原子重写**：`save_index()` 用 tmp + replace 模式（与 `save_session_history` 一致），避免半写损坏。

- **对账补录（backfill）**：`backfill_index()` 在每次 `list_sessions()` 前执行——目录里有 jsonl 但索引缺条目的补录（`title=null`、`created_at` 取文件 mtime）；索引里有但文件已不存在的剔除。老会话零成本接入，索引可随时删除重建。

- **新建即登记**：`create_new_session()` 创建会话文件的同时 `ensure_index_entry()` 写入初始条目。

### 2.2 存储位置：分项目目录（决策记录)

会话数据放哪？两个候选：

| 候选      | 路径                                        | 评估                                                                                                  |
| ------- | ----------------------------------------- | --------------------------------------------------------------------------------------------------- |
| A. 分项目  | `~/.aigent/projects/<slug>/.chathistory/` | 对齐 Claude Code `~/.claude/projects/` 模型；多项目天然隔离；项目选择阶段只需换 slug，代码零改动；会话与该项目绑定的 todo/记忆/任务等运行时数据同居一处 |
| B. 统一目录 | `~/.aigent/chathistory/`                  | 实现最简单；但会话归属关系要靠元数据 `project` 字段维护，跨项目查询/清理都是全量扫描；未来多项目时要做一次大迁移                                      |

**采用方案 A**。运行时数据（`.chathistory/.todo/.tasks/.team/.inbox/.transcripts/.task_outputs/.memory/.workflow/.scheduler`）整体从项目内 `WorkSpace/task1/` 迁到 `~/.aigent/projects/default/`，由 `paths.py` 的 `migrate_workspace_data()` 一次性完成（幂等，源不存在或目标已存在则跳过）。

> **2026-09-18 落地**：方案 A 已扩展到多工作空间 —— `~/.aigent/projects/<id>/` 每个空间一份，
> `id` 为 `default`（目录名不变、存量零迁移）或 `ws` + 10 位短码。
> 当初设想"按工作目录派生 slug"被否掉了：路径派生 slug 会因目录改名/移动反复漂移，
> 而 `id` 必须稳定（它是会话、任务、记忆的目录归属）。改为"短码做身份、真实路径记在
> `projects.json`"，代价是索引文件，收益是改名不动身份。详见 `11-工作空间管理.md`。

### 2.3 会话生命周期（状态机）

```
        新建（惰性：首条 chat 触发）
          │
          ▼
      ┌────────┐  trash（软删除）   ┌─────────┐
      │ active │ ────────────────► │ trashed │
      └────────┘                   └─────────┘
       ▲    ▲                          │    │
       │    └────── restore（还原）──────┘    │
       │                                     │ delete（永久）
       │  新首条消息 → 惰性新建新会话            ▼
       └────────────────────────────    物理删除
```

关键语义：

- **归档当前激活会话**：后端收到 `session_trash` 且目标恰是激活会话时，置空 agent 会话态（`session_num=None` 等），惰性会话机制下下条 chat 自动新建，前端也同步切到空态（`newSession()`）。UI 文案为「归档」（2026-09-20），机制/协议名 `trash` 不变。

- **永久删除连带清理**：`delete_session_permanent()` 删除 `session_N.jsonl` + `session_N.subagents.jsonl`（子智能体旁路记录，与主文件同生共死）+ 任务板文件（`.tasks/session_N.json`，2026-09-16 起 todo 已下线由 task 承接）+ 元数据条目；单个失败不影响批量中其他项。

- **清空连带的旁路文件清理**：`clear_session()` 重写主 jsonl（只留系统提示词）的同时删除 `session_N.subagents.jsonl`（缓存同步失效），并清除元数据 `usage_totals`（token 累计归零），保证「清空会话」后不留旧子智能体记录、圆圈 tooltip 不残留旧统计。

- **批量删除**：`session_delete` 命令携带 `ids[]`（会话 id 字符串数组），逐个执行，回发 `session_delete_result`（`deleted[]` / `failed[]`），前端据此 toast。**删除成功后不再全量回刷列表**：后端 `session_delete` 分支删除完成即回发 `session_delete_result`（不再调用 `_reply_sessions` 全量广播 sessions）；前端 `deleteSessions` 拿到 `deleted[]` 后，在本地 store 从 `sessions` 与 `trashSessions` 中增量移除被删会话。此举避免删除后立即「重建整张列表（每个会话逐个打开文件重数 message\_count）+ 全量广播 + React 整树重渲染」的连带开销，删除刷新即时；回收站页切换仍在挂载/ `refreshTrash` 时全量拉取，语义一致。

### 2.3.1 会话伴生文件：子智能体旁路记录（`session_N.subagents.jsonl`）

除元数据 `index.jsonl` 与会话消息 `session_N.jsonl` 之外，每个会话还可能有一个**旁路记录文件**
`session_N.subagents.jsonl`：子智能体执行过程（思考 + 工具调用 + 终态/耗时）的记录，
由 `subagent_store.SubagentStore` 维护（格式与读取规则见 03 篇 2.1.1）。

为什么单独成文件而不是塞进主 jsonl：`role=subagent` 行与标准消息混写会让 append 顺序成为隐式契约，
打断加载时的 tool 块连续性判定，进而**静默删除整轮对话并重写文件**（详见 08 篇）。
物理隔离后，压缩 / 自愈重写 / 异常恢复三类机制与子智能体记录互不影响。

生命周期与会话主文件**同生共死**：

| 操作 | 对 `session_N.subagents.jsonl` 的处理 |
| --- | --- |
| 新建会话 | 不创建（首次有子智能体时才出现） |
| 归档 / 还原（原回收站） | **不动**（jsonl 与旁路文件均原样保留，还原后切回即可回放） |
| 清空会话（`session_clear`） | 删除旁路文件（与消息一同清空） |
| 永久删除（`session_delete`） | 删除旁路文件 |
| 上下文压缩 / 自愈重写 | **不动**（`save_session_history` 不读也不回写旁路记录） |
| 旧数据迁移 | 首次加载时把主 jsonl 里遗留的 `role=subagent` 行抽出到旁路文件，主文件净化为纯标准消息，并留 `session_N.jsonl.bak` 快照（幂等） |

> 备份说明：`session_N.jsonl.bak` 是「迁移 / 自愈重写前」的一次性快照（谁先写谁生效，不覆盖更早的副本），
> 用于误判时人工回滚；它不参与会话列表统计（`glob("*.jsonl")` 不匹配 `.jsonl.bak`）。

### 2.3.2 token 消耗统计的持久化（轮级 usage/model_info 字段 + 会话级 usage_totals）

token 统计分两级持久化（2026-09-16 新增，数据源为 LLM 接口返回的 `usage` 节点，见 03 篇 2.5）：

- **轮级（每轮消耗 + 本轮模型快照 + 会话累计快照）→ 主 jsonl 该轮末条 assistant 消息行的
  `usage` / `model_info` / `usage_session` 三字段**。
  turn 收尾时 `session_manage.append_usage_to_last_assistant(session_file, usage, model_info, usage_session)`
  持 `_append_lock` 读文件最后一行（4096 字节反向尾块），解析为 JSON 后仅当 `role == "assistant"`
  时写入/覆盖 `usage` 字段（`{prompt_tokens, completion_tokens, cached_tokens, total_tokens}`）、
  `model_info` 节点（本轮模型快照 `{model_id, model_name, max_context, max_context_label, reasoning_effort}`，
  与 usage 平级——usage 是多处直接消费的纯 token 计数 dict，模型信息独立成节点不破坏其形状）与
  `usage_session` 节点（turn 收尾时的会话级累计快照；回放据此恢复 footer 第二段「本会话累计」，
  否则旧轮回放只剩「本轮」）；
  **若切换过模型且净变化非零，`model_info` 还带可选 `switch` 子节点**（净模型切换
  `{from_id, from_name, to_id, to_name, ts}`，见 03 篇 2.5）——分两种落盘时机：
  - **turn 执行期切换**：`Agent.record_model_switch()` 计入本轮 `_turn_switches`，收尾经
    `_net_turn_switch()` 取净变化注入 `model_info.switch`，随 `append_usage_to_last_assistant`
    一次就地重写末行同时补写（写入前同步内存态 `history_messages[-1]`）。
  - **空闲期切换**（turn 未执行，上一轮答复结束到下一条指令之间）：即时调用新增的
    `session_manage.append_switch_to_last_assistant(session_file, switch)`，把 `switch` 写进
    **切换时末条 assistant 行**的 `model_info.switch`（同样尾块 read→truncate→重写、持
    `_append_lock`），并同步该条消息内存态——因此提示落在「切换时最后一条 assistant 消息」上，
    先于用户下一条指令展示，而非下一轮答复末尾。
  净切回原模型时不注入（前端不显示、jsonl 不记录），回放时据 `model_info.switch` 恢复「模型已切换」提示。
  truncate 行首就地重写该行；末行非 assistant（本轮无 assistant 产出）时跳过，该轮无 footer。
  模型快照的窗口取压缩器当前生效值，即「本轮统计用当时选择的模型和上下文参数」的口径
  （2026-09-16 修复统计误用全局 env 1M 窗口的 bug）。
  **读取/重写侧硬性保留（修复 2026-09-16）**：`load_session_history` 归一化与 `_message_to_json_row`
  序列化必须原样携带 `model_info`（含 `switch`）与 `usage_session`——此前只保留了 `usage`，导致
  切会话回放（session_switch 的磁盘加载）与 compact 重写后，历史轮 footer 的模型、「模型已切换」
  提示、「本会话累计」全部丢失，界面只剩当前轮「本轮」。设计理由：usage/model_info/usage_session
  是「关于某条消息的展示元数据」，与 `reasoning_content` 同类——回放天然恢复、无需锚点关联；作为
  **消息上的字段**不引入新行，不违反 D1 事故教训（该教训针对独立非消息行打断 tool 块结构）。compact
  摘要替换消息时三者随消息消失——上下文已不在，历史轮 token 明细本就无意义（会话级累计在 meta 中不受影响）。

- **消息记录时间 → 主 jsonl 每行 user/assistant 消息的 `created_at` 字段**（2026-09-18 新增）：
  落盘时 `_message_to_json_row` 打点（`message.get("created_at") or _now_iso()`——新消息取当前
  秒级 ISO 本地时间如 `2026-09-18T10:30:00`；compact/自愈重写保留行内已有值，避免老行被误改时间）；
  `load_session_history` 归一化与 `_history_to_ui` 原样携带，前端在消息右下角按 `YYYY-MM-DD HH:mm:ss`
  展示（位于复制按钮左侧）；老行无此字段时缺省不显示。同为 UI 展示元数据，受下方白名单投影约束不进模型上下文。

- **会话级（累计）→ 元数据 `usage_totals`**（见 2.1 字段表）。每 turn 一次
  `add_usage_totals(session_id, delta)` 增量累加（O(1) 原子写，与 `updated_at` 刷新同模式）；
  后台子智能体迟到完成时以 `count_turn=False` 补记（只加数值不计轮数）。
  **已落盘的统计数据不回改**：修复统计口径后仅新轮次按新口径记录。

**配套硬约束（模型上下文白名单投影）**：jsonl 消息行从此可携带 `usage` 等展示元数据，但发给
LLM 的 messages 一律经 `Agent._model_messages()` 白名单投影（`role / content / reasoning_content /
tool_calls / tool_call_id` 五字段）——jsonl 后续存储 message 之外的任何扩展字段都不会漏进模型上下文。
读取侧（`load_session_history` 归一化）保留 `usage` / `model_info` / `usage_session` 供 UI 回放，
发送边界统一过滤。

### 2.3.3 会话伴生文件：任务板（`.tasks/session_<id>.json`）

任务板同样是会话伴生数据，自 2026-09-16 起生命周期与会话文件对齐
（改造前是 todo 文件 `.todo/session_<id>.todo.json`，todo 已下线）。

**布局：一个会话一个 JSON 文件，文件内以「组」为 key**（2026-09-16 第二轮改造，
替代原「每任务一文件 `task_<scope>_<ts>_<rand>.json`」）：

```
~/.aigent/projects/default/.tasks/session_Kx7mQ2vT8p.json
{
  "version": 1,
  "scope": "session_Kx7mQ2vT8p",
  "updated_at": 1758000000.123,
  "groups": {
    "g_1758000000_0001": [ {任务}, {任务} ],   ← 一次"派活"= 一个 key
    "g_1758000123_0002": [ {任务} ]
  }
}
```

- 文件数 = **会话数**（原方案是任务数）；面板/回放一次读盘即可拿到整组，
  多组历史天然共存，不再靠文件名排序去"猜"分组
- `scope = f"{session_prefix}{session_id}"`；`scope` 为空（旧全局看板）落到 `_global.json`
- **`group_id` 不落进任务体**：组归属由文件里的 key 承载，读取时回填
  （单一事实来源，杜绝"体内值 ≠ 组 key"）
- 写盘走「同目录临时文件 + `os.replace`」**原子替换**，且「读整份 → 改一条 → 写整份」
  持**路径级可重入锁** —— 一份文件承载整会话任务，非原子写被读到半截会让面板整块消失
- 路径口径**只有一处**：`paths.task_scope_file(scope, tasks_dir)`，
  `task_manager` 直接 import 它（原先两处各持一份 glob 规则，漂移即"清理静默失效"）

> 第一轮方案的存量文件（`.tasks/task_<scope>_<ts>_<rand>.json`）**已不再被读取**，
> 属可删的历史数据（本期不做迁移脚本）。

| 操作 | 对任务板文件的影响 |
| --- | --- |
| 重命名 / 切换 | 不动 |
| **清空会话**（`session_clear`） | **删除**本会话的任务文件（与 chat 同生共死） |
| 软删除（trash） | 不动 —— 还原后任务还在 |
| 还原（restore） | 不动 |
| **永久删除**（`session_delete`） | **删除**本会话的任务文件 |

**关键实现点**：清理逻辑落在 **`SessionManager`**（`clear_session` /
`delete_session_permanent`），而**不是** `Agent.clear_session` ——
因为 `ws_bridge` 的 `session_clear` 分支是**直接调 `sm.clear_session`** 的，不经过 Agent；
只做在 Agent 那层会漏掉这条路径。单个文件删除失败只记日志、不阻断会话操作
（与子智能体旁路文件同策略）。

**另注**：`_gc_scoped_tasks`（本会话任务全部完成即删文件）已于同日**停用** ——
它与前端渲染终态竞争，且"已结束的组不显示"属于**展示层**问题
（`current_board()` 无未完成组时返回 `None`），不该用删数据来实现。
任务文件一律保留到会话被清空 / 永久删除为止。

### 2.4 标题生成流程

触发时机与判定（`ws_bridge.py` chat 处理中）：

```
首条 chat 到达
  ├─ 无激活会话 → 惰性新建会话
  │    ├─ 用首条消息前 30 字写默认标题（_default_session_title → set_auto_title("trunc")）
  │    └─ await _reply_sessions()          ← 列表立刻可读
  ├─ first_turn = 当前会话历史中无真实 user 消息（排除 <system-reminder> 系统注入）
  ├─ turn_task = run_turn(text)            ← 主对话正常执行
  └─ if first_turn: _finalize_title_after_turn(turn_task, ...)
       └─ await turn_task 完成后 → _generate_session_title（≤20 字）→ set_auto_title("auto") → 回发
```

- **两段式时序（对齐 TraeWork / WorkBuddy 等主流做法）**：标题**不与首轮并行抢跑**。
  新建会话时先落"首条消息前 30 字"的默认标题（`_default_session_title()`，空白归一为单行），
  列表创建即可读、零成本零延迟；**第一轮 `run_turn` 执行完之后**，`_finalize_title_after_turn()`
  再调用一次大模型总结生成精炼标题（≤20 字）并覆盖（`title_source` 从 `trunc` 升为 `auto`）。
  没有 daemon 线程、没有"先到先得"的时序博弈——这正是早期 `_start_title_thread` 方案被
  推翻的原因：并发收益仅"标题早出现几秒"，代价是线程调度、去重、跨线程回发一整串复杂度。

- **旧会话首轮同样生效**：`first_turn` 判定沿用"历史中无真实 user 消息"（排除
  `<system-reminder>` 系统注入），老会话补发首条消息时也会在首轮结束后精炼标题；
  默认标题只写**新建**会话（旧会话标题保留现状，LLM 失败时不降级改写）。

- **独立短超时客户端**：标题总结请求不复用主客户端（timeout=1200s、max\_retries=3），
  而是新建 `OpenAI(timeout=30, max_retries=0)` 独立客户端（`TITLE_TIMEOUT=30`），只复用
  鉴权/地址配置——最多 30 秒后必定放弃并保留默认标题，绝不悬挂。

- **max\_tokens 必须给足（推理模型兼容）**：`TITLE_MAX_TOKENS=1000`。推理模型
  （如 deepseek-v4-flash）的思考过程也计入 completion 预算，早期 `max_tokens=48` 会被
  `reasoning_tokens` 整个吃光，content 为空或只挤出单字（实测出现过标题"写"）。

- **结果合法性校验**：清洗（去引号、空白归一、去尾部标点）后长度 < 2 视为不合法，拒绝采用，保留默认标题。

- **完成即刷新**：标题写回元数据后（事件循环内 `await reply_sessions()`）全量回发会话列表，前端即时刷新。

- **索引并发写保护**：`SessionManager._update_entry`（读-改-写元数据文件）整体置于
  `_index_lock` 互斥锁内——标题写回与用户改名/回收站操作并发时不会交错丢更新。

- **Prompt 约束**：`TITLE_SYSTEM_PROMPT` 要求"不超过 20 字、直接输出标题、无引号句号解释"；
  结果再经清洗（去引号、空白归一）并截断 20 字。

- **降级与保护**：LLM 请求失败/为空/不合法（超时 30s、单字标题等）时**保留默认标题**
  （首条消息前 30 字，无需 `_fallback_title` 兜底——默认标题本身就是可读标题）；
  `set_auto_title()` 检查 `title_source == "user"` 则跳过——即使标题写回与用户的手动
  重命名并发，也永不覆盖用户标题；任何异常只打日志，绝不影响主对话。

- **手动重命名**：`rename_session()` 写入 `title_source=user`，截断 60 字，空标题报错。

### 2.5 协议扩展

在 03 篇双层消息模型上新增（`kind` 均走统一信封）：

| kind                    | 方向    | 载荷                                 | 说明                                                                                                      |

> **多工作空间补充（2026-09-18）**：以上会话类命令在桥层一律经 `_manager_for_session(sid)`
> 取**该会话所属空间**的 `SessionManager` —— 直接取 default 那份会"查无此会话"或误改另一个
> 空间里的同名文件。`sessions` 是**全部空间合并**的列表（每条带真实 `project`），
> `sessions_trashed` 同样跨空间汇总（回收站是全局视图，删除时按每个 sid 各自解析空间）。
> 工作空间的增删改查命令（`projects_list` / `project_add` / `project_open` / `project_rename` /
> `project_remove` 与 `projects` 信封）见 `11-工作空间管理.md` 与 03 篇 §2.7。
> 另：`session` 信封新增可选 `project_id`（新会话的所属空间，前端据此对齐活动空间）。

`sessions` 事件载荷升级为元数据 dict（`num/title/title_source/status/created_at/updated_at/trashed_at/file`；`message_count` 已于 2026-09-18 移除现算），不再是裸编号列表；`sessions_list` 的响应与所有会话变更后的全量回发共用此结构。每会话绑定模型 id 存于 `model_id`，参数存于 `overrides`（**按模型 id 分别保存**的 map，每个模型独立存取、互不串改）；由 `session_model` 写入（新建会话由前端收到 `session` 信封后写入；首条 `chat` 后端只落 `model_id`）。

**每会话独立模型绑定**：`SessionRuntime` 构造该会话 `Agent` 或其模型配置重载时，先 `snapshot_llm_env()` 快照全局 LLM 环境变量，加 `ENV_LLM_LOCK` 后按其元数据 `model_id` 用 `apply_model_to_env()` 换绑 env，再构造 / `reload_llm_bindings()`，随后 `restore_llm_env()` 还原全局 env（详见 `agents/session_runtime.py`）。实现「每个会话真正跑在各自模型上」，切换 / 新建（继承上一会话）互不干扰。

**首建必须在换绑 env 之后、于锁内构造 Agent**（`_bind_agent_env` 的 rebuild=False 分支接收 **Agent 工厂**而非已构造实例）：`Agent.__init__` 一次性捕获模型/base\_url/api\_key，若把 `Agent(silent=True)` 作为参数值传入（参数求值先于函数体换绑 env），首建会捕获**全局默认模型**，`_bound_model` 却记录会话 meta model\_id，此后切换模型若恰好切回原 meta 值，比较失效 → 表现为「切换模型不生效」。修复后首轮即按会话绑定模型运行，后续模型切换经 `_bound_model` 比对正常触发换绑。

### 2.6 前端交互设计

**任务树（TaskTree → WorkspaceTree，2026-09-18）**：

> 多工作空间后任务树改名为 **WorkspaceTree**：`default` 固定第一，其余为已打开的工作空间，
> 会话按 `project` 分组挂在各自空间下。分组、折叠、15 条截断、空间级徽标等交互
> 见 `11-工作空间管理.md` §5.1；本节只描述**会话行自身**的行为（未变）。

- **标题展示**：`sessionDisplayName(s)` = `title ?? "session_<num>"`。不再显示消息计数（2026-09-18 移除 `message_count` 现算与右侧数字 badge）。

- **会话状态点**：每行最左侧状态小圆点（`tree-dot`），一状一色，优先级从前到后：
  - **运行中**（在 `runningSessions` 或 `bgSessions`）：青色脉冲点（保留原运行样式，表示"还有活没干完"）；
  - **未读**（`s.unread === true`）：橙色实心圆点——会话完整结束且用户尚未进入查看；
  - **已读**（其余）：空心小圆圈——普通/已读会话默认展示，表示这是一个会话条目的常规指示（不再像旧版那样只对特定状态显示点）。
  点击会话（`switchSession`）进入即置已读。

- **每空间 15 条折叠（2026-09-18）**：单个空间的会话超过 `SESSION_PREVIEW_LIMIT = 15` 条时
  默认只显示最新 15 条，列表末尾出现「展开全部 N 条」/「收起」（状态按空间持久化在
  `localStorage`）。没有这个入口的话旧会话永远看不到。顺序沿用后端的最后修改时间倒序，前端不二次排序。

- **悬停信息卡（SessionTooltip）**：会话行 `onMouseEnter` 时，在行右缘右侧（`rect.right + 10`，fixed 定位，贴近视口边缘回收）弹出信息卡，展示五项会话基本数据（数据全部来自 `list_sessions` 透传的会话元数据，无额外请求）：
  - **完整标题**：`sessionDisplayName(s)` 全文（不截断、可换行，不受行内省略号限制）；
  - **所属项目**：`projectDisplayName(projects, s.project)` —— 会话元数据里的 `project` 是工作空间 **id**，用 `projects` 信封映射成展示名（查不到时回退 id；2026-09-18 前为固定 `default` 字面量）；
  - **总消耗**：`usage_totals.total_tokens` 千分位显示（如 `26,392 tokens`）；无消耗会话显示 `—`；
  - **缓存命中率**：`cached_tokens / prompt_tokens` 取整百分比（输入侧口径，与消息 footer 的圆圈 tooltip 一致）；provider 未返回缓存信息时显示 `—`；
  - **最后更新**：`updated_at` 格式化为 `YYYY-MM-DD HH:mm:ss`（本地时间；非法/缺省显示 `—`）。
  
  实现要点：卡片**纯展示**（`pointer-events: none`）——不拦截鼠标，避免"移出行 → 卡片消失"的闪烁；`z-index: 900` 低于弹出菜单（950）；打开菜单（`openMenu`）时同步清掉 tip，避免与菜单叠层。`title`、`project`、`usage_totals` 为 `list_sessions` 于 2026-09-18 起透传新增字段（此前会话列表只含标题/计数/模型绑定）。

  **数据新鲜度**：每轮 turn 收尾（`usage_stats` 事件携带 `turn`）时，桥层 `deliver()` 自动触发一次 `reply_sessions()`（`_sessions_refresh_pending` 去重排队，全量重建幂等）——`add_usage_totals` 刚把本轮用量写进元数据，tooltip 的 `usage_totals` 即与刚结束的这轮一致，无需切换会话/重进列表；迟到子智能体补发（仅 `session`、无 `turn`）不触发。

- **弹出菜单（SessionMenu）**：会话行 hover 显示 `⋯` 三点按钮；点击与**右键菜单**（`onContextMenu`）共用同一个 `SessionMenu` 组件（fixed 定位于触发坐标，靠近视口边缘回收；点外部/Esc 关闭）。菜单项：`重命名`（edit 图标）、`归档`（archive 图标，danger 红色；2026-09-20 前为「删除」+ trash 图标）。流式进行中（`isSending`）菜单项禁用。样式：容器背景 `--color-bg-main`（纯白、完全不透明，带边框与阴影，悬浮于内容之上，不透出下层内容）。

- **行内重命名**：菜单点"重命名" → 会话行原位变输入框（`autoFocus`，初值为现有标题），`Enter` 提交、`Esc` 取消、`blur` 提交；空值或与现显示名相同不提交。提交走 `session_rename`，成功后 `sessions` 事件回刷列表。

**归档页（设置弹窗 → 左侧菜单「归档」；原回收站，协议命令名不变）**：

- 入口：设置弹窗左侧菜单 `通用 / 模型 / 归档 / 关于`；切到该页时拉取 `trash_list`。

- **工作空间筛选（2026-09-20 新增）**：位于**全选按钮上方**的下拉框，选项 = `全部工作空间` + 各空间（default 显示为「默认工作空间」），**默认选中「默认工作空间」**；列表/勾选/批量删除都只作用于当前筛选结果。**切换筛选时清空勾选**，避免跨空间批量误删。归档页只有会话级操作，**不能删除工作空间**（空间删除在侧边栏空间菜单）。

- 列表行：复选框 + 标题（`sessionDisplayName` 回退）+ 元信息（`归档于 MM-DD HH:mm`）+ `还原` 按钮 + `删除`（彻底删除）按钮。

- **单选/多选/全选**：行复选框切换；顶部「全选」label 切换全部（当前筛选范围内），选中时显示「已选 N 项」。

- **批量彻底删除**：顶部「彻底删除(N)」按钮，选中为空时禁用。

- **二次确认（arm 模式）**：首次点击进入确认态（按钮文字变「确认删除 N 项？」/单行变「确认」并加红色 `confirm` 类），**3 秒内**再点执行、超时自动恢复——不弹系统对话框，交互更轻。

- **还原**：行内「还原」→ `session_restore` → 刷新归档页与会话树两个列表。

### 3.3 取舍与边界记录

- **为什么用 jsonl 存索引而不是 json**：与会话文件格式统一，追加/重写共用一套 JSONL 读写习惯；坏行跳过的容错策略也一致。

- **为什么以文件名为键而不是 num**：`session_` 与 `cron_` 前缀共用 `.chathistory` 目录时，纯 num 会在索引里撞键；文件名天然唯一。

- **索引为什么全量重写而非就地改行**：jsonl 不支持原地修改，重写用 tmp+replace 原子替换；会话量级（几百）下全量重写开销可忽略。

- **标题长度**：默认标题为首条消息前 30 字（`trunc`）；首轮后 LLM 总结截 20 字（prompt 约束 20 字 + 截断余量）；手动重命名截 60 字。

- **首轮判定排除系统注入**：`<system-reminder>` 开头的 user 消息（todo reminder 等）不算真实用户消息，避免"切到老会话发首条消息"误触发首轮标题精炼，也避免新会话被 reminder 抢了默认标题。

- **回收站不自动清理**：不做"30 天自动清空"，永久删除一律用户手动（单机产品，磁盘压力可控，语义最简）。

- **`_ensure_session_manager()`**：惰性会话下 `agent.session_manager` 可能为 None（尚未 init/switch），列表/重命名等只读操作前先兜底构建，构建后 `init_session` 复用同一实例。

- **并发执行的设计**：每个会话一个独立 `SessionRuntime`（各自 `Agent`/缓冲/停止信号），克服"单会话串行会阻塞切换"的瓶颈；`chat` 只派发不等待，事件循环保持可读。每条流式事件携带 `session_num`，前端按号路由到对应缓冲，后台会话增量各自累积——这正是"切换不断流、多会话同跑可来回查看"的根基。

- **未读/已读语义**：unread 由**前端判定**（因为它才可靠知道当前显示哪个会话）、**后端持久化**到会话元数据（跨窗口/重启随 `sessions` 同步）。触发点：
  - **置未读**：`session_status` 为 `done`/`stopped`（会话**完整结束**）且该会话 ≠ 当前 `activeSession` → `setSessionUnread(sid,true)`；`background`（仍有后台任务在跑）不触发——对应"刚执行完"才提醒；
  - **置已读**：`switchSession`（点击进入）→ `setSessionUnread(sid,false)`；当前正在查看的会话完整结束也保持已读。
  不再维护旧版首页级一次性绿点 `completedBg`。**边界**：正在执行（`running`/`background`）的会话优先显示运行脉冲点，其未读标记保留到结束后由 done/stopped 重新判定；标记 `unread`/读会顺带刷新 `updated_at`（契合"最近使用排序"，点过的会话上浮）。

- **停止语义**：`stop` 只停 `num` 指定会话正在执行的那一轮（会话级事件置位协作式收尾），其它后台会话不受影响；同会话并发 turn 被拒，防止两线程同写一个 jsonl。运行中会话不可 `clear`/`trash`（先停后删）。
