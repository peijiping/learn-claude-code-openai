# 会话管理与回收站

> 本文档描述桌面智能体客户端的**会话元数据、标题生成、会话重命名/删除与回收站**机制。核心结论：会话不再只有 `session_N.jsonl` 过程记录，新增同目录的 **`index.jsonl` 元数据索引**（标题/创建时间/状态/项目归属，以文件名为键与会话文件关联）；运行时数据从项目内 `WorkSpace/task1/` 迁移到用户级 **`~/.aigent/projects/<slug>/.chathistory/`**（分项目隔离，对齐 Claude Code `~/.claude/projects/` 模型）；删除走**软删除两段式**（先入回收站，回收站内永久删除）；标题由**独立的小请求**在首条消息到达时与首轮对话并行生成，失败降级为首条消息截断。按「概念 → 设计 → 落地」组织。

***

## 一、概念

### 1.1 为什么需要会话元数据

改造前，会话只有过程数据 `session_N.jsonl`（每行一条消息），没有会话自身的属性：

- **列表无标题**：任务树只能显示 `session_3` 这类编号，用户无法辨识会话内容。
- **无生命周期状态**：没有"已删除"概念，要么保留要么物理删文件，误删无法挽回。
- **无时间与归属**：创建/更新时间只能靠文件 mtime 猜；未来多项目阶段无法区分会话属于哪个项目。

元数据与过程数据**分文件存放**（`index.jsonl` + `session_N.jsonl`），而不是往消息行里塞元数据：消息行是数组语义（append-only），元数据是字典语义（频繁就地更新），混放会让读写双方都别扭。

### 1.2 软删除与回收站（桌面产品惯例）

删除会话分两段：

1. **移入回收站（软删除）**：`index.jsonl` 中该会话 `status: active → trashed`，会话文件原样保留。任务树不再显示，回收站可见。
2. **永久删除（硬删除）**：在回收站中操作，物理删除 `session_N.jsonl` + 绑定的 todo 文件 + 索引行。

好处：误删可还原（`restore`）；"删除"按钮永远不造成不可逆后果，破坏性操作集中到回收站页并配二次确认。

### 1.3 标题生成：独立小请求，而非解析主对话

两种候选方案：

| 方案 | 做法 | 问题 |
| -- | -- | -- |
| A. 解析主对话 | 首轮回复中让模型顺带输出标题（约定格式），前端解析截取 | 污染主对话历史与 system prompt；格式解析脆弱；流式渲染时标题混入正文；重试/压缩时易丢失 |
| B. 独立小请求 | 首条消息到达时，用主模型发一次**极小的非流式请求**（`max_tokens=1000, temperature=0.3`）专门生成标题，与首轮 `run_turn` 并行 | 多一次 LLM 调用（首条消息截断前 2000 字，成本可忽略） |

**采用方案 B**。标题生成与主对话完全解耦：不进消息历史、不占流式通道、失败可静默降级（截断首条消息前 20 字），任何异常都不影响主流程。

## 二、设计

### 2.1 元数据模型（index.jsonl）

与 `session_N.jsonl` 同目录，每行一条会话元数据 JSON，**以会话文件名（含前缀）为键**关联：

```json
{"num": 3, "file": "session_3.jsonl", "title": "分析 goal.py 存储机制", "title_source": "auto", "created_at": "2026-09-08T10:30:00", "updated_at": "2026-09-08T10:35:12", "status": "active", "trashed_at": null, "project": "default"}
```

| 字段 | 类型 | 说明 |
| -- | -- | -- |
| `num` | int | 会话编号（展示与协议寻址用） |
| `file` | string | 关联的会话文件名（**主键**，`session_` / `cron_` 前缀共用目录时避免编号冲突） |
| `title` | string\|null | 会话标题；null 时前端回退显示 `session_<num>` |
| `title_source` | string | 标题来源：`user`（手动重命名）> `auto`（LLM 生成）> `trunc`（首条消息截断）> `none`（无标题）。低优先级不覆盖高优先级 |
| `created_at` / `updated_at` | string | 本地时间秒级 ISO（单机桌面产品，无时区转换） |
| `status` | string | `active`（任务树） / `trashed`（回收站） |
| `trashed_at` | string\|null | 移入回收站的时间（回收站列表展示"删除于"） |
| `project` | string | 项目归属 slug；单项目阶段固定 `default`，项目选择阶段改为按工作目录派生（预留 `_independent` 表示独立会话） |

写入策略：

- **原子重写**：`save_index()` 用 tmp + replace 模式（与 `save_session_history` 一致），避免半写损坏。
- **对账补录（backfill）**：`backfill_index()` 在每次 `list_sessions()` 前执行——目录里有 jsonl 但索引缺条目的补录（`title=null`、`created_at` 取文件 mtime）；索引里有但文件已不存在的剔除。老会话零成本接入，索引可随时删除重建。
- **新建即登记**：`create_new_session()` 创建会话文件的同时 `ensure_index_entry()` 写入初始条目。

### 2.2 存储位置：分项目目录（决策记录)

会话数据放哪？两个候选：

| 候选 | 路径 | 评估 |
| -- | -- | -- |
| A. 分项目 | `~/.aigent/projects/<slug>/.chathistory/` | 对齐 Claude Code `~/.claude/projects/` 模型；多项目天然隔离；项目选择阶段只需换 slug，代码零改动；会话与该项目绑定的 todo/记忆/任务等运行时数据同居一处 |
| B. 统一目录 | `~/.aigent/chathistory/` | 实现最简单；但会话归属关系要靠元数据 `project` 字段维护，跨项目查询/清理都是全量扫描；未来多项目时要做一次大迁移 |

**采用方案 A**。运行时数据（`.chathistory/.todo/.tasks/.team/.inbox/.transcripts/.task_outputs/.memory/.workflow/.scheduler`）整体从项目内 `WorkSpace/task1/` 迁到 `~/.aigent/projects/default/`，由 `paths.py` 的 `migrate_workspace_data()` 一次性完成（幂等，源不存在或目标已存在则跳过）。单项目阶段 slug 固定 `default`；项目选择阶段按工作目录派生 slug，届时只需改 `DATA_ROOT` 的计算，会话管理代码不动。

### 2.3 会话生命周期（状态机）

```
        新建（惰性：首条 chat 触发）
          │
          ▼
      ┌────────┐  trash（软删除）   ┌─────────┐
      │ active │ ────────────────► │ trashed │
      └────────┘                   └─────────┘
       ▲    ▲                          │    │
       │    └────── restore（还原）──────┘    │
       │                                     │ delete（永久）
       │  新首条消息 → 惰性新建新会话            ▼
       └────────────────────────────    物理删除
```

关键语义：

- **删除当前激活会话**：后端收到 `session_trash` 且目标恰是激活会话时，置空 agent 会话态（`session_num=None` 等），惰性会话机制下下条 chat 自动新建，前端也同步切到空态（`newSession()`）。
- **永久删除连带清理**：`delete_session_permanent()` 删除 `session_N.jsonl` + `.todo/session_N.todo.json`（todo 与会话同生共死）+ 索引行；单个失败不影响批量中其他项。
- **批量删除**：`session_delete` 命令携带 `nums[]`，逐个执行，回发 `session_delete_result`（`deleted[]` / `failed[]`），前端据此 toast。

### 2.4 标题生成流程

触发时机与判定（`ws_bridge.py` chat 处理中）：

```
首条 chat 到达
  ├─ fresh=true 或后端无激活会话 → 惰性新建会话（fresh_created = true）
  ├─ needs_title = fresh_created 或 当前会话历史中无真实 user 消息
  │    （排除 <system-reminder> 系统注入，判定"首轮"）
  ├─ if needs_title: _start_title_thread(...)   ← 独立 daemon 线程，先于 run_turn 提交
  ├─ await run_turn(text)          ← 主对话与标题线程完全解耦，互不等待
  └─ await _reply_sessions()       ← turn 结束统一回发（兜底，保证计数/标题最终一致）
```

- **独立线程而非协程**：标题生成是**首条消息到达即启动**的独立 daemon 线程（`_title_worker`），**先于 run_turn 的线程提交**——标题请求最先到达 LLM 服务端。此前实现用 `asyncio.create_task` + `to_thread`，run_turn 线程先入线程池、标题任务晚几毫秒才启动；若服务端串行排队（本地模型/单并发代理），标题请求会排在主对话流式请求之后，表现为"标题等到首轮结束才出现"。改为独立线程后彻底消除该时序缺陷。
- **独立短超时客户端**：标题请求不复用主客户端（timeout=1200s、max_retries=3，一旦排队会悬挂整个 turn），而是新建 `OpenAI(timeout=30, max_retries=0)` 独立客户端（`TITLE_TIMEOUT=30`），只复用鉴权/地址配置——即使服务端串行，最多 30 秒后必定降级兜底，绝不悬挂。
- **max_tokens 必须给足（推理模型兼容）**：`TITLE_MAX_TOKENS=1000`。推理模型（如 deepseek-v4-flash）的思考过程也计入 completion 预算，早期 `max_tokens=48` 会被 `reasoning_tokens` 整个吃光，content 为空或只挤出单字（实测出现过标题"写"）。
- **结果合法性校验**：清洗（去引号、空白归一、去尾部标点）后长度 < 2 视为不合法，拒绝采用，走降级兜底。
- **完成即刷新**：标题写入索引后，通过 `asyncio.run_coroutine_threadsafe(_reply_sessions(ws), loop)` 从工作线程安全调度回事件循环，立即全量回发会话列表，不等 run_turn。
- **同会话去重**：`_title_inflight` 集合 + 锁防止同一会话并发多个标题线程（clear 后重发首条消息等场景）。
- **索引并发写保护**：`SessionManager._update_entry`（读-改-写 JSONL 索引）整体置于 `_index_lock` 互斥锁内——标题线程与用户改名/回收站操作并发更新索引时不会交错丢更新。
- **Prompt 约束**：`TITLE_SYSTEM_PROMPT` 要求"不超过 16 字、直接输出标题、无引号句号解释"；结果再经清洗（去引号、空白归一）并截断 24 字。
- **降级与保护**：LLM 请求失败/为空/不合法（超时 30s、单字标题等）时降级为 `_fallback_title()`——按标点切分取首个语义片段（≤16 字，如"帮我写一个简单的python程序，越简单越好…"→"帮我写一个简单的python程序"），而非盲目截断；`set_auto_title()` 检查 `title_source == "user"` 则跳过——即使标题线程与用户的手动重命名并发，也永不覆盖用户标题；线程内任何异常静默吞掉，绝不影响主对话。
- **手动重命名**：`rename_session()` 写入 `title_source=user`，截断 60 字，空标题报错。

### 2.5 协议扩展

在 03 篇双层消息模型上新增（`kind` 均走统一信封）：

| kind | 方向 | 载荷 | 说明 |
| -- | -- | -- | -- |
| `session_rename` | 前端→后端 | `num` / `title` | 重命名（title_source=user） |
| `session_trash` | 前端→后端 | `num` | 软删除，移入回收站 |
| `session_restore` | 前端→后端 | `num` | 从回收站还原 |
| `session_delete` | 前端→后端 | `nums[]` | 批量永久删除 |
| `trash_list` | 前端→后端 | — | 拉取回收站列表 |
| `sessions_trashed` | 后端→前端 | `sessions[]` | 回收站列表（trash_list 的响应，字段同 sessions） |
| `session_delete_result` | 后端→前端 | `deleted[]` / `failed[]` | 批量删除结果（前端 toast） |

`sessions` 事件载荷升级为元数据 dict（`num/title/title_source/status/created_at/updated_at/trashed_at/message_count/file`），不再是裸编号列表；`sessions_list` 的响应与所有会话变更后的全量回发共用此结构。

### 2.6 前端交互设计

**任务树（TaskTree）**：

- **标题展示**：`sessionDisplayName(s)` = `title ?? "session_<num>"`；右侧保留消息计数 badge。
- **弹出菜单（SessionMenu）**：会话行 hover 显示 `⋯` 三点按钮；点击与**右键菜单**（`onContextMenu`）共用同一个 `SessionMenu` 组件（fixed 定位于触发坐标，靠近视口边缘回收；点外部/Esc 关闭）。菜单项：`重命名`（edit 图标）、`删除`（trash 图标，danger 红色）。流式进行中（`isSending`）菜单项禁用。
- **行内重命名**：菜单点"重命名" → 会话行原位变输入框（`autoFocus`，初值为现有标题），`Enter` 提交、`Esc` 取消、`blur` 提交；空值或与现显示名相同不提交。提交走 `session_rename`，成功后 `sessions` 事件回刷列表。
- **删除**：菜单点"删除" → `session_trash` 软删除；若删的是当前激活会话，前端同步切到空态；toast「已移入回收站」。

**回收站页（设置弹窗 → 左侧菜单「回收站」）**：

- 入口：设置弹窗左侧菜单 `通用 / 模型 / 回收站 / 关于`；切到该页时拉取 `trash_list`。
- 列表行：复选框 + 标题（`sessionDisplayName` 回退）+ 元信息（`N 条 · 删除于 MM-DD HH:mm`）+ `还原` 按钮 + `删除` 按钮。
- **单选/多选/全选**：行复选框切换；顶部「全选」label 切换全部，选中时显示「已选 N 项」。
- **批量彻底删除**：顶部「彻底删除(N)」按钮，选中为空时禁用。
- **二次确认（arm 模式）**：首次点击进入确认态（按钮文字变「确认删除 N 项？」/单行变「确认」并加红色 `confirm` 类），**3 秒内**再点执行、超时自动恢复——不弹系统对话框，交互更轻。
- **还原**：行内「还原」→ `session_restore` → 刷新回收站与任务树两个列表。

### 3.3 取舍与边界记录

- **为什么用 jsonl 存索引而不是 json**：与会话文件格式统一，追加/重写共用一套 JSONL 读写习惯；坏行跳过的容错策略也一致。
- **为什么以文件名为键而不是 num**：`session_` 与 `cron_` 前缀共用 `.chathistory` 目录时，纯 num 会在索引里撞键；文件名天然唯一。
- **索引为什么全量重写而非就地改行**：jsonl 不支持原地修改，重写用 tmp+replace 原子替换；会话量级（几百）下全量重写开销可忽略。
- **标题长度**：LLM 生成截 24 字（prompt 约束 16 字 + 余量）；手动重命名截 60 字。
- **首轮判定排除系统注入**：`<system-reminder>` 开头的 user 消息（todo reminder 等）不算真实用户消息，避免"切到老会话发首条消息"误触发标题生成，也避免新会话被 reminder 抢了标题。
- **回收站不自动清理**：不做"30 天自动清空"，永久删除一律用户手动（单机产品，磁盘压力可控，语义最简）。
- **`_ensure_session_manager()`**：惰性会话下 `agent.session_manager` 可能为 None（尚未 init/switch），列表/重命名等只读操作前先兜底构建，构建后 `init_session` 复用同一实例。

### 3.4 验证要点

1. **后端**：`SessionManager` 单测思路——`create_new_session` 后 `index.jsonl` 有条目；`trash` 后 `list_sessions("trashed")` 可见、`list_sessions()` 不可见；`restore` 回到 active；`delete_session_permanent` 后 jsonl/todo/索引行三者皆无；`backfill_index` 对老目录（无索引）能补录、对幽灵索引行能剔除；`set_auto_title` 不覆盖 `title_source=user` 的条目。
