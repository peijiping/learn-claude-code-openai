# 24 - 技能管理

> 在设置弹窗里新增独立的「技能」菜单：**多源市场浏览与一键安装**、**手动新建**、**启停 / 查看正文 / 删除**。
> 核心结论：**技能这一侧没有 MCP Registry 那样的单一官方源**（实测见 §1.1），所以本期交付的是「**多源聚合 + 统一形状**」，而不是接一个中心；真正的难点不在市场，而在**启停语义**与**引擎侧怎么让改动立刻生效**（§1.3、§2.2）。
> 引擎层只改了 `skills.py` 一个方法（约 40 行，见 §4.1），这是本期唯一的「改引擎」。
>
> 姊妹篇：`23-MCP服务管理.md`（面板语言与协议约定的**出处**）、`25-插件管理.md`（插件贡献技能的那一半）。

## 一、概念

### 1.1 技能市场：没有官方 registry，但格式早已统一

MCP 有 `registry.modelcontextprotocol.io`（免鉴权 REST）。技能**没有**对应的东西。2026-09-30 实测可用的数据源：

| 数据源 | 接口形态 | 是否选用 | 关键短板 |
| --- | --- | --- | --- |
| **git 仓库（扫 `*/SKILL.md`）** | GitHub Tree API + raw CDN | ✅ **主力** | 每个仓库要一次 tree + N 次 raw；未鉴权 60 次/时 |
| `ruleskill.com/api/v1` | 免鉴权 REST | ✅ 可选补充 | **实测当天就返回 `Registry temporarily unavailable`** |
| `openpaths.io/v1/skills` | 读免鉴权、发布要 key | ✅ 可选补充 | 响应形状未逐一验证，按「尽力而为」处理 |
| `agentskillhub.dev` | `POST /api/v1/repos/analyze` | ❌ | 它本质也是 GitHub 导入；我们的 git 源已经覆盖 |
| `skillsmp.com` | HTML / 403 | ❌ | 实测不稳定 |

**选 git 仓库当主力的决定性理由**：Agent Skills 的格式是**事实标准** —— `SKILL.md`（YAML frontmatter 里 `name` / `description`）+ 同目录附属文件。这份格式与我们既有的 `~/.aigent/skills/<name>/SKILL.md` **完全同构**，`skills.py` 一行不改就能吃。于是「市场」退化成一件很便宜的事：**一个仓库地址 + 扫它的 `*/SKILL.md`**。

⚠️ **安全前提（必须原样告知用户）**：这些源**都没有代码审计**。技能不是可执行文件，但它是**写给模型看的指令** —— 能指挥模型去执行东西。所以安装确认页必须展示 **SKILL.md 全文**（§2.5），那是用户唯一的判断依据。

### 1.2 三种源类型，一套接口

前端零分派 —— `search / resolve / fetch_files` 三个方法对三种源同形：

| type | 判据 | 覆盖对象 | 抓取方式 |
| --- | --- | --- | --- |
| `git` | 一个 git 仓库 | `anthropics/skills`、任何社区技能仓库 | 一次 tree（列全仓路径）+ 并行 raw 抓文件 |
| `api` | 第三方公开 HTTP API | ruleskill / openpaths | 各自的搜索与 payload 端点 |
| `index` | 一份自建 JSON 索引 | 团队自托管（最可控，见 §7） | 索引里带 `files` 就直接用，否则回退到 git 抓取 |

`index` 与 `git` 共用同一条抓取链 —— 换句话说，**"自建索引"只是给了 git 扫描一个更准的清单**（不必拉整个仓库 tree）。

### 1.3 为什么元数据走旁路文件，不写进 SKILL.md

启用/禁用状态存在 `~/.aigent/skills_sources.json`，**不写进 frontmatter**。三条理由，第二条是硬的：

1. **技能目录必须保持可移植**：`SKILL.md + 附属文件` 这份原样，是整个 Agent Skills 生态能互通的前提。往里塞元数据就破坏了它。
2. **启停会改写用户手写的正文**：状态若落进 frontmatter，每次点开关都要重写 `SKILL.md` —— 与上游更新冲突、把用户内容弄脏，而且**每次启停都会让生效版的 SKILL.md 变成"被程序改过的"**。
3. 来源信息（从哪装的）与技能内容无关，混在一起会让「更新技能」变成「合并两份不同来源的数据」。

### 1.4 为什么 UI 数据源是磁盘扫描，而不是 `SKILL_REGISTRY`

与 23 篇 §1.4 同源的坑，这里再踩一次：`skills.SkillLoader._scan_skills()` **只收启用的**技能。若设置页拿它当列表数据源，**被禁用的技能就永远看不见 —— 也就无法被重新启用**。

| 用途 | 数据源 | 代码 |
| --- | --- | --- |
| **UI 列表** | 磁盘扫描（**含被禁用项**）+ 旁路元数据 | `skill_store.SkillStore.scan()` |
| **模型技能表** | 只收启用的 | `skills.SkillLoader._scan_skills()`（本期改造为"整体重建"） |

## 二、设计

### 2.1 数据布局（3 个文件 + 1 个目录）

| 路径 | 常量 | 作用 |
| --- | --- | --- |
| `~/.aigent/skills/<name>/SKILL.md` | `paths.SKILLS_DIR` | 技能本体（+ 附属文件），**保持可移植** |
| `~/.aigent/skills_sources.json` | `paths.SKILL_SOURCES` | 旁路元数据：`{name: {source, market_id, market_name, publisher, market_url, installed_at, enabled}}` |
| `~/.aigent/skill_markets.json` | `paths.SKILL_MARKETS` | 已注册的源（内置源 + 自定义源） |

> ⚠️ 技能 / 插件配置**不在** `~/.aigent/config/` 的收口体系内（`config.py` 的文件清单不含它们）→ **不要**塞进 `config_path()`。它们和 `~/.aigent/mcp/`、`~/.aigent/sandbox/` 一样是顶层兄弟。
>
> 旁路文件与 market 注册表都用 `store_io.write_json_atomic`（tmp + `os.replace` + **0600**）—— 自定义源上可能挂私有仓库的访问令牌。

**元数据路径是"跟着目录走"算出来的**（`SkillStore.__init__`）：给了自定义 `skills_dir`，元数据就写在它的**父目录**旁边。这样"技能读 A 目录、启停写 B 文件"的错位在结构上不可能发生。默认值下它与 `SKILL_SOURCES` 常量**逐字等价**（有测试锁住这条，见 §5.1）。

### 2.2 启停 / 删除怎么「立刻生效」

这是本期最容易漏的一环。链路：

```
skill_set_enabled / skill_remove / skill_install
  → 原子写 skills_sources.json（**不碰 SKILL.md**）
  → _reload_skills_all_runtimes()  ← 关键
  → 回读全量 → skill_config 信封
```

`_reload_skills_all_runtimes()` 遍历**全局 Agent + 每个已构造 runtime**，调用 `Agent._refresh_system_prompt()`。

**为什么必须做这一步**：`_refresh_system_prompt()` **只在会话入口**（init / switch / new）被调用，不是每轮都跑 —— 也就是说"装了新技能，当前会话看不到"是个真实存在过的坑（`agent_full_v2.py:1930` 的注释就是为它写的）。刚在设置页装完技能，用户切回对话就期望它生效。

代价是**整段前缀缓存失效一次**（同该方法的 docstring 所述）。这只在技能列表**真的变过**时才发生，而"改了技能表"本来就必须让模型看到新内容 —— 所以是可接受的必要代价，不是可以省掉的开销。

未构造的会话不用管：首次构造 Agent 时自然读到新状态。

### 2.3 界面结构（4 个子视图）

设置弹窗左侧菜单在「MCP」之后插入「技能」（`SettingsModal.tsx` 的 `NAV`）：

```
通用 / 模型 / 权限 / 沙盒 / MCP / 技能 / 插件 / 归档 / 关于
```

顺序刻意是「MCP → 技能 → 插件」：三者都是"给智能体加外部能力"，且**由同一套面板语言构成**，放一起才读得出它们的关系。

| 视图 | 组件 | 职责 |
| --- | --- | --- |
| `list` | `SkillSettings` 内联 | 技能列表：启停 / 查看正文 / 删除 |
| `form` | `SkillForm` | 手动新建（名称 / 用途说明 / 标签 / 正文） |
| `market` | `SkillMarketView` | **选源 + 搜索 + 分页**，并内联「管理源」 |
| `install` | `SkillInstallView` | **安装确认** —— 全流程唯一的安全闸门 |

列表页布局（`list`）：

```
┌ 技能 ────────────────────────────────────────────────────┐
│ 已安装 5 个 · 已启用 5 个 · 来自市场 2 个 · 另有 1 个来自插件 │
│                              [ 从市场安装 ]  [ + 新建技能 ]  │
│ ⚠ 技能是写给模型看的指令：正文会进入系统提示，附属脚本可能被  │
│   模型通过 run_bash 执行。请只安装你信任来源的技能。          │
├──────────────────────────────────────────────────────────┤
│ ● pdf        pdf   官方   已启用    12 个文件  正文 删除 [开] │
│ ○ code-review      本地   已禁用    3 个文件   正文 删除 [关] │
│ ⚠ broken           本地   缺少 SKILL.md  —      正文 删除 [开] │
└──────────────────────────────────────────────────────────┘
```

行内操作（正文 / 删除 / 开关）与主信息**同一行**、开关在最右 —— 与 MCP 页同一套信息密度（23 篇 §2.2 的行高实测：内联后 38px，分两行 70px）。

### 2.4 技能状态三态

| 状态 | 判据 | 呈现 |
| --- | --- | --- |
| `缺少 SKILL.md` | `has_manifest === false` | 红点 / 「缺少 SKILL.md」+ 展开区内联红字说明 |
| `已禁用` | `enabled === false` | 灰点 / 「已禁用」 |
| `已启用` | 其余 | 绿点 / 「已启用」 |

**刻意不做更细的状态机**：技能没有"连接"这种外部状态，唯一的可变维度就是启停 + 清单是否完整。多造状态只会让前端多一堆推不出来的判断。

`缺少 SKILL.md` 的技能**仍然出现在列表里**（而不是藏起来）：它占着一个目录、用户需要知道为什么它不生效、也需要能删掉它。

### 2.5 安全闸门：安装确认页

`install` 视图是整条链路上**唯一**需要用户点头的地方。三条不可妥协的约束：

1. **必须原样展示 SKILL.md 全文**（可滚动、限高 320px，**不折叠不摘要**）。技能不执行代码，但它是**给模型的指令** —— 决定"模型接下来会照着做什么"。
2. **必须列出将要写入的全部文件**，并指出其中有多少是**附属文件**。技能可以带脚本（`scripts/*.py`），那些会被模型通过 `run_bash` 执行 —— 只看 SKILL.md 会漏掉它们。
3. **不提供"记住我的选择"之类的便捷开关**。这套东西装进去是长期生效的，每次都该看一眼。

### 2.6 手动新建：为什么 SKILL.md 由后端拼

前端只收四个字段（名称 / 用途说明 / 标签 / 正文），**YAML frontmatter 由 `skill_store.build_skill_md` 拼**：

```jsonc
// description 里出现 `:` / 引号 / 换行是常态
"description": "Use this when: the user says \"review\" and\nneeds a checklist"
```

裸拼会产出 YAML 语法错误的 frontmatter。所以 `name` / `description` 用 **JSON 字面量**输出（YAML 的标量是 JSON 的超集），`tags` 输出成 **flow sequence**（`tags: ["a", "b"]`）而不是 `a, b` —— 后者解析回来是一个字符串，任何消费方（含别的 Agent）都得自己再切一次。

`description` 是硬必填（前后端都拦）：技能列表与系统提示里的那一行就是它，缺了就只能退回"正文首行"，模型挑技能的准确率会明显下降。

## 三、协议

### 3.1 命令与信封（9 条命令 / 4 个信封）

全部**点对点**：只回发起窗口、**不广播** —— 与 `permission_config` / `sandbox_config` / `mcp_config` 同一约定（广播会冲掉另一个窗口正在编辑的草稿）。因此都**不进** `isKnownAgentEvent` 白名单。

| 命令 | 载荷 | 回执信封 | 说明 |
| --- | --- | --- | --- |
| `skill_config_get` | — | `skill_config` | 磁盘扫描（**含被禁用项**）+ 源列表 |
| `skill_set_enabled` | `{name, enabled}` | `skill_config` | 启停（**只写旁路元数据**） |
| `skill_remove` | `{name}` | `skill_config` | 删目录 + 元数据 |
| `skill_install` | `{name, item}` | `skill_config` | 从市场安装（**后端重新解析 + 重新抓取**） |
| `skill_create` | `{name, description, tags?, body}` | `skill_config` | 手动新建 |
| `skill_read` | `{name}` | `skill_content` | 读 SKILL.md 全文（**不落盘**） |
| `skill_market_search` | `{market_id, query?, cursor?, limit?}` | `skill_market` | 在指定源里搜索 |
| `skill_market_resolve` | `{market_id?, item}` | `skill_market_plan` | **纯抓取、不落盘** —— 供确认页展示 |
| `skill_market_upsert` | `{entry}` | `skill_config` | 新增/更新源 |
| `skill_market_remove` | `{market_id}` | `skill_config` | 删自定义源（内置源会被拒） |

两个刻意的设计：

- **`skill_install` 只回传「哪一条 + 叫什么名」**，不给 `meta`、不给文件内容。后端自己跑 `resolve` + `fetch_files`（结果在后端有内存 TTL 缓存，确认页刚抓过、这里几乎不额外花网络）。这样协议面小得多，也不可能出现"前端传了别的文件却装成别的东西"。
- **源增删复用 `skill_config` 信封**（而不是单开一个 `skill_markets`）。源列表本来就在那份载荷里，少一个信封就少一处"前端要自己把两份状态拼起来"的机会。

### 3.2 `skill_config` 载荷

```jsonc
{
  "dir": "/Users/me/.aigent/skills",
  "sources_path": "/Users/me/.aigent/skills_sources.json",
  "markets_path": "/Users/me/.aigent/skill_markets.json",
  "exists": true,
  "skills": [{
    "name": "pdf",
    "title": "pdf",                     // frontmatter 的 name
    "description": "Use this skill whenever the user wants to do anything with PDF files…",
    "tags": ["pdf", "document"],
    "enabled": true,
    "has_manifest": true,
    "path": "/Users/me/.aigent/skills/pdf",
    "manifest": "/Users/me/.aigent/skills/pdf/SKILL.md",
    "files": ["SKILL.md", "forms.md", "scripts/check_fillable_fields.py"],  // 含 SKILL.md
    "file_count": 12,
    "size_bytes": 58692,
    "source": "market",                 // local | market
    "market_id": "anthropics-official:skills/pdf",
    "market_name": "Anthropic 官方技能",
    "publisher": "official",
    "market_url": "https://github.com/anthropics/skills/tree/main/skills/pdf",
    "installed_at": "2026-09-30T07:41:12+00:00",
    "warnings": []
  }],
  "markets": [{ "id": "anthropics-official", "name": "Anthropic 官方技能", "type": "git",
                "type_label": "git 仓库", "repo": "anthropics/skills", "ref": "main",
                "publisher": "official", "enabled": true, "builtin": true,
                "is_default": true }],
  "default_market": "anthropics-official",
  "plugin_skill_count": 1,              // 只读统计：这些技能不归本页管理
  "summary": { "total": 5, "enabled": 5, "from_market": 2, "invalid": 0 },
  "applied": true,
  "warnings": [],                       // 非阻断（如"已存在同名技能，建议名改为 pdf-2"）
  "errors": [],                         // 校验/落盘错误 → 页面内联展示，不 toast
  "msg": "已安装技能「pdf」"
}
```

`skill_content` 载荷：`{name, text, path, dir, description, files[], error}`。
`skill_market` 载荷：`{items[], next_cursor, market_id, market_name, query, total, error, cached, elapsed_ms}`。
`skill_market_plan` 载荷：`{ok, name, skill_name, description, skill_md, files[{path,size}], file_count, total_bytes, tags, version, warnings, unsupported, error, meta}`。

### 3.3 四条协议级约束

1. **逐字段兜底、绝不上抛**：`handle()` 的命令分发链**没有兜底 try/except**（见 23 篇 §3.3-1），这里抛出去会直接掀掉整条 WS 连接。任何探测失败都降级成中性值，回执照发 —— 否则前端会永远停在"读取技能配置…"。
2. **校验失败不额外发 `error` 信封**：那一封会被 store 的 `case 'error'` 当全局 toast 弹出来，而设置页的约定是**错误内联展示**（用户要对着文本改）。
3. **`skill_market` / `skill_market_plan` / `skill_content` 刻意没有事件分支**（与 `skill_config` 不同）：市场搜索要**按页累加**，事件分支只会把已累加的多页覆盖成最后一页；后两者是一次性读取，走 promise 路径即可。`skill_config` 保留事件分支是有用的冗余：IPC 超时后回执仍能到达并刷新界面。
4. **`skill_config` 六条命令共用同形回执，每次回读全量** → 前端整份替换，**不做增量拼接**（拼接会留下已删技能的残影）。

### 3.4 超时（**实测数据，别照抄默认值**）

| 命令 | IPC 超时 | 依据 |
| --- | --- | --- |
| `skill_market_search` | **30s** | git 源要扫一次仓库树 + 抓当前页的 SKILL.md；第三方 API 实测最慢十几秒 |
| `skill_market_resolve` / `skill_install` | **60s** | 要抓该技能的**全部文件**（官方 `pdf` 技能实测 12 个文件），后端单请求 20s × 逐个文件 |
| 其余 | 默认 5s | 纯本地读写 |

后端另有一层：`SKILL_MARKET_TIMEOUT`（默认 20s）。两层都要放宽 —— 只放大前端超时，后端会在 20s 处自己断。

**`skills.py` 的改动（约 40 行，是本篇唯一的"改引擎"）**

| 改动 | 为什么必须改 |
| --- | --- |
| `_scan_skills` **整体重建**（先 `SKILL_REGISTRY = {}` 再填） | 历史实现**只增不删** → 被删/被禁用的技能会一直留在系统提示里，等于删除按钮是假的 |

### 4.2 样式复用（一条刻意的决定）

技能页 / 插件页与 MCP 页是**同一套面板语言**，所以结构类 `.mcp-*` 是**有意复用**的（`settings.css` 里有一段说明）。理由：三份几乎相同的 CSS 必然各自漂移，而"改一处三处生效"正是我们要的。本期只新增了 MCP 页没有的四类样式（代码原文块 / 市场源选择与管理 / 组件徽标 / 文件清单）。

### 4.3 前端五条硬约束

1. **回执为权威源，整份替换**（同 §3.3-4）。
2. **错误内联、不 toast**（同 §3.3-2）。
3. **读配置失败 ≠ 没有技能**：`skills: [] + errors` 时绝不能渲染成"还没有安装任何技能" —— 那会诱导用户去市场重装，反而覆盖掉磁盘上还在的技能。
4. **搜索 / 安装进行中必须禁用按钮**：主进程 `pending` 表按 kind FIFO 配对且无 id，同一 kind 并发会串台。
5. **`view === 'install'` 且无在途请求时不能停在加载态**：给一条明确的出路（"安装信息已失效，请重新选择技能"），权限页与沙盒页都踩过"塌成加载态"。但这条死端文案**只能是最后防线**——store 里的 resolve 收到 `null`（IPC 60s 超时）时**必须**合成一条失败计划（与 catch 分支同形，见 §六 #19），让确认页走"无法安装 + 原因"分支，而不是掉进死端让用户以为功能永久坏了。

## 六、关键取舍与踩坑

| # | 事项 | 结论 |
| --- | --- | --- |
| 1 | UI 列表数据源 | **必须**读磁盘扫描（含禁用项）。用 `SKILL_REGISTRY` 会让被禁用技能永远不可见、也就无法重新启用 |
| 2 | 启停落点 | 旁路 `skills_sources.json`。写进 frontmatter 会让每次开关都改写用户手写的正文 |
| 3 | 引擎侧"立刻生效" | 必须主动调 `_refresh_system_prompt()`（它只在会话入口跑），代价是前缀缓存失效一次 |
| 4 | 注册表重建 | `_scan_skills` 必须**先清空**。历史实现只增不删，"删除"是假的 |
| 5 | 内置技能的键 | 仍是 frontmatter 的 `name`（换键会让既有会话里模型记住的技能名失效） |
| 6 | 插件技能命名空间 | `<插件>:<技能>`。各家插件都爱叫 `code-review`，不加前缀必然互相覆盖 |
| 7 | frontmatter 实现 | 必须**唯一**（`skill_store.parse_frontmatter`），两处解析会让"设置页描述 ≠ 模型看到的" |
| 8 | `build_skill_md` | 名字/描述用 JSON 字面量、tags 用 flow sequence —— 裸拼 YAML 遇到 `:` / 换行必坏 |
| 9 | 元数据路径 | 跟着 `skills_dir` 走（写在父目录旁），结构上排除"读 A 写 B"的错位 |
| 10 | 安装协议面 | 只回传「哪一条 + 叫什么名」，后端重新解析 + 重新抓取。前端带 meta / 文件内容都是更大的攻击面 |
| 11 | 删除的链接安全 | 符号链接只 `unlink`；否则一个指向 `~/Documents` 的同名链接就能让"删除技能"变成灾难 |
| 12 | 市场搜索的目录顺序 | `os.walk` 顺序不稳定 → **必须排序**，否则组件/文件清单顺序会飘 |
| 13 | 内置源的 upsert | 只认 `{id, enabled}`，**不要**要求调用方把 name/type/repo 填一遍才让改启停 |
| 14 | 抓取走的通道 | 文件用 **raw CDN**（不计 API 限额）；只有列目录用 Tree API。逐个文件走 Contents API 会瞬间打爆 60 次/时 |
| 15 | 市场不落盘缓存 | 第三方源 schema 今天就在变（ruleskill 实测返回 `temporarily unavailable`），只做内存 TTL |
| 16 | 空仓库 | "没找到任何 SKILL.md"不是错误（仓库可能只放插件清单）→ 给带解释的提示，而不是红字报错 |
| 17 | raw 抓取通道（2026-09-30 修复） | `raw.githubusercontent.com` 会被**间歇性整段墙掉**而 `api.github.com` 可达 → 症状是「市场搜得到条目、点安装没反应」（搜索走 Tree API，抓文件走 raw）。`_raw_bytes` 已改为**多通道依次回退**：直连 → jsDelivr（`cdn.jsdelivr.net/gh/<owner>/<repo>@<ref>/<path>`）。进程内记住最近成功通道、失败通道冷却 5 分钟（否则逐文件抓取乃至每个并行 worker 都重新撞一遍 20s 超时）；**404 是确定结果、不换通道**（否则每次 404 变两倍请求）；带斜杠的分支名在 jsDelivr 形态下无法表达 → 跳过该通道 |
| 18 | 点「安装」的响应（2026-09-30 修复） | `onPick` 必须**立即切到 install 视图**：resolve 可能要十几秒（通道探测 + 逐文件抓取），旧实现 `resolve().then(() => setView('install'))` 把整个抓取期留在市场页、没有任何指示 = 用户以为「点了没反应」。确认页在 resolving 时本来就有「正在抓取…」加载态，失败也有明确出路（插件页同款，见 25 篇） |
| 19 | resolve 超时的出路（2026-09-30 二次修复） | 症状：「安装信息已失效，请重新选择技能」。根因有两层：① **性能**——`_fetch_git_files` 逐文件**串行**抓，挂起的 raw 通道让每个文件独立吃满一次超时（20s × n），多文件技能把 resolve 拖过前端 60s IPC 上限 → 已改**并行抓取**（`ThreadPoolExecutor`，同插件侧），并把 raw 通道超时收紧为独立的 `SKILL_MARKET_RAW_TIMEOUT`（默认 10s，CDN 健康 <3s 回包，挂起多等无益）；② **前端**——IPC 超时主进程回 `null`，旧 store `if (res)` 直接跳过 → plan 为 null → 确认页掉进死端。现在 `resolveSkillInstall` 对 `null` **合成失败计划**（"抓取超时…请返回市场重试"），与 catch 分支同形；**MCP / 插件两侧同款缺口一并修掉**（`resolveMcpInstall` / `resolvePluginInstall`）。死端文案保留为最后防线，正常链路不应再触达 |

## 七、后续增量

按优先级排：

1. **技能更新 / 版本对比** —— 现在只能删了重装。需要存 `market_id` + 源里的 commit/版本，才能判断"这份技能上游更新了"，并给出 diff。
3. **`${VAR}` 与私有源鉴权** —— 自定义 git 源目前只能用公开仓库（或全局 `SKILL_MARKET_GITHUB_TOKEN`）。按源独立配 token 更合适。
4. **市场磁盘快照 + 中文增强** —— 解决国内访问慢与全英文描述。要接受第三方 schema 漂移的维护成本。
5. **`index` 源格式定版** —— 目前是"尽力而为"的宽松读取（`{skills: [{name, description, path, url, files?}]}`）。团队自托管要真用起来，得先把格式固化并写进文档。
6. **技能使用统计** —— `load_skill` 被调用了多少次、哪些技能从来没被用过。这是判断"该删哪个技能"的唯一依据，现在完全是黑盒。
