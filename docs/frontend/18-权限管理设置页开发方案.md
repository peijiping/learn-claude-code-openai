## 2. 后端方案

### 2.1 命令契约

#### 2.1.1 `permission_config_get`

前端 → 后端 payload：**空**（`{}`）。后端 → 前端回 `permission_config` 信封：

```jsonc
{
  "kind": "permission_config",
  "payload": {
    "config": {          // permissions.json 归一化后的完整内容（见 17 篇 §5.4）
      "version": 1,
      "default_mode": "default",
      "approval_timeout_seconds": 300,
      "mcp_destructive": "ask",
      "additional_dirs": [],
      "safe_commands": { "enabled": true, "list": ["ls", "git status"] },
      "deny_patterns": [],
      "dangerous_patterns": [],
      "rules": []
    },
    "builtin": {         // 内置清单（只读展示用），由 permission.py 常量下发
      "safe_commands": ["ls", "pwd", "cat", "..."],
      "dangerous":     ["rm ", "> /etc/", "..."],
      "deny":          ["rm -rf /", "sudo", "..."]
    },
    "deny_paths": [      // 敏感路径黑名单的人类可读描述（展示用）
      "*.pem / *.key（任意目录）",
      ".env（任意目录）",
      "~/.ssh/（整个目录）",
      "~/.aigent/config/credentials.json",
      "~/.aigent/config/llmconfig.json",
      "~/.aigent/config/permissions.json"
      // 注：迁移前的顶层旧路径（~/.aigent/credentials.json 等三份）同样在拦，
      // 但**不下发**给前端展示 —— 它们是过渡期兜底，不是用户需要理解的配置面。
    ],
    "builtin_timeout": { "default": 300, "min": 60, "max": 3600 },
    "path": "/Users/xxx/.aigent/config/permissions.json",   // 展示用（"配置文件位置"）
    "exists": false                                   // 文件是否存在（决定首屏提示文案）
  }
}
```

**为什么要下发 `builtin` / `deny_paths` / `builtin_timeout`**：八分区里 ⑤⑥ 的表单形态是
「内置只读 chip + 自定义追加」。若前端自己写一份内置清单常量，就制造了**第二出处**，
以后改 `BUILTIN_DANGEROUS` 必然漏改前端 —— 这正是 17 篇 §1.1 记录的历史缺陷模式。
`exists=false` 时前端显示一句「尚未保存过自定义配置，当前使用内置默认」。

后端新增一个纯展示函数（`agents/permission.py`，与常量同文件 = 单一出处）：

```python
def builtin_snapshot() -> dict:
    """内置清单快照（设置页展示用）。改动内置常量时此函数自动跟随，无需另改。"""
    return {
        "safe_commands": list(BUILTIN_SAFE_COMMANDS),
        "dangerous": list(BUILTIN_DANGEROUS),
        "deny": list(BUILTIN_DENY),
        "deny_paths": [
            "*.pem / *.key（任意目录）",
            ".env（任意目录）",
            "~/.ssh/（整个目录）",
            _tilde(config_path("credentials.json")),
            _tilde(config_path("llmconfig.json")),
            _tilde(config_path("permissions.json")),
        ],
        "timeout": {"default": DEFAULT_TIMEOUT_SECONDS,
                    "min": MIN_TIMEOUT_SECONDS, "max": MAX_TIMEOUT_SECONDS},
    }
```

> `deny_paths` 的文案要与 `_deny_path_roots()` / `_DENY_FILE_SUFFIXES` / `_DENY_FILE_NAMES`
> 保持一致，且**由 `config.config_path()` / `Path.home()` 派生**（配置文件的唯一落点是
> `~/.aigent/config/`，见 05 篇「路径口径」），不要退回手写 `f"{AIGENT_HOME}/xxx.json"`。
> **注意**：`~/.aigent/logs` 已于 2026-09-22 移出黑名单，别再写回去（17 篇 §3.3）。

#### 2.1.2 `permission_config_save`

前端 → 后端 payload：`{ "config": { ...完整配置对象... } }`（整份覆盖式保存，不做字段级 patch）。
后端 → 前端回 `permission_config`：

```jsonc
{
  "kind": "permission_config",
  "payload": {
    "config": { ...落盘后归一化的权威值... },   // 前端以这份为准回填，不信自己的 draft
    "applied": true,
    "warnings": [                               // 归一化过程中被修正/丢弃的项（无人可省）
      "「chmod 777」已在硬拒绝清单中，追加无效",
      "额外目录「Downloads」不是绝对路径，已忽略",
      "安全命令白名单为空，已回落到内置默认清单"
    ],
    "msg": "权限配置已保存并生效"
  }
}
```

**`applied` 的真实语义**：`permissions.json` 落盘成功 = `true`；`false` 只在写盘失败时出现
（`PermissionStore.save()` 抛 `OSError`），此时前端保持原 draft 并显示 `msg`。

### 2.2 `ws_bridge.py` 落点

在 `handle()` 的 if-elif 链里，紧跟 `session_permission` 之后插入两个分支（体例照抄
`llm_config_get` / `llm_config_save`，见 `ws_bridge.py` L1724-1752）：

```python
elif kind == "permission_config_get":
    store = _permission_store()          # 见下
    cfg = await asyncio.to_thread(store.load_public)
    await safe_send(ws, _envelope("permission_config", {
        "config": cfg,
        "builtin": builtin_snapshot(),
        "path": str(store.path),
        "exists": store.path.exists(),
    }))

elif kind == "permission_config_save":
    raw = payload.get("config")
    if not isinstance(raw, dict):
        await safe_send(ws, _envelope("error", {"msg": "配置格式非法"}))
        continue                          # 或按既有分支体例 return / 跳过
    store = _permission_store()
    try:
        normalized, warnings = await asyncio.to_thread(store.save_reporting, raw)
    except OSError as exc:
        log.error("权限配置落盘失败: %s", exc)
        await safe_send(ws, _envelope("permission_config", {
            "config": store.load(), "applied": False,
            "warnings": [], "msg": f"保存失败：{exc}",
        }))
    else:
        refreshed = _refresh_permission_dirs()      # §2.3，在途会话额外目录
        log.info("权限配置已保存（额外目录刷新 %d 个在途会话）", refreshed)
        await safe_send(ws, _envelope("permission_config", {
            "config": normalized, "applied": True,
            "warnings": warnings, "msg": "权限配置已保存并生效",
        }))
```

**`_permission_store()` 怎么拿 store**：不要复用某个 Agent 的 `self.permission_store`
（那是 per-Agent 实例，agent 可能尚未构造）。新建一个独立实例即可 —— `PermissionStore`
是**无状态门面**，多个实例指向同一文件，靠 mtime 检查保持一致（17 篇 §5.4-E11）：

```python
def _permission_store():
    """设置页专用 store 实例（与各 Agent 的实例共享同一文件，mtime 热加载保证一致）。"""
    from permission import PermissionStore
    return PermissionStore()
```

**回执 vs 广播**：**只回执给发起窗口，不广播** `permission_config`。理由：设置页是
「进页拉取 → 本地 draft → 保存」的低频模型，若广播覆盖，会把另一个窗口正在编辑的
未保存 draft 冲掉（对比 `permission_changed` 必须广播 —— 盾牌 chip 常驻输入区，
多窗口不一致是视觉事故）。多窗口同步靠「各自下次打开设置页时重新 get」。

### 2.3 生效语义矩阵（本节是方案的关键）

| 配置键 | 生效路径 | 需要额外动作？ |
| --- | --- | --- |
| `default_mode` | 新建会话时 `resolve_session_mode` 读取 | 否（**在途会话不受影响**，这是设计语义，前端要写清） |
| `approval_timeout_seconds` | `check_tool_call` 里 `store.approval_timeout_seconds` 实时读 | 否 |
| `mcp_destructive` | `evaluate` 里 `store["mcp_destructive"]` 实时读 | 否 |
| `safe_commands` / `deny_patterns` / `dangerous_patterns` / `rules` | `evaluate` 首行 `store = self.store.load()`，mtime 变了就重读 | 否 |
| **`additional_dirs`** | gate 的 `_extra_dirs` 是**缓存集合**，只在 `restore_from_meta()` / `record_session_allow()` 时重建 | **是 —— 必须补刷新** |

`evaluate()` 每轮都 `store.load()`（mtime 热加载），所以第 1–4 类**天然即时生效**。
只有 `additional_dirs` 例外：它进的是 gate 的 `_extra_dirs` 缓存，在途会话不会自己重读。

补法分两步：

**① `PermissionGate` 新增公开刷新方法**（`agents/permission.py`）：

```python
def refresh_extra_dirs(self) -> None:
    """重读 permissions.json 的 additional_dirs 并重建额外目录集。

    设置页保存 global 额外目录后由桥层对每个在途会话调用（其余配置项
    靠 evaluate 的 mtime 热加载已自动生效，只有这个是缓存）。
    session_allows 的 path 类记忆在 _rebuild_extra_dirs_locked 内一并重建。
    """
    with self._lock:
        self._rebuild_extra_dirs_locked()
```

> **红线**：`_rebuild_extra_dirs_locked()` 内部必须是 `self._extra_dirs.clear()` +
> `self._extra_dirs.update(dirs)`（**原地改，不换对象**）。这个 set 与
> `ToolRegistry.safe_path` 的兜底层是**同一个对象**（`attach_tool_registry` 时共享）。
> 若实现者改成 `self._extra_dirs = {...}`，共享断裂 —— 判定层放行了、工具层仍按旧集
> 拦下，表现为「审批通过但工具报 ValueError」，且极难排查。

**② 桥层遍历在途会话**：

```python
def _refresh_permission_dirs() -> int:
    """设置页保存后：把新的全局额外目录推给所有已构造的在途会话 Agent。"""
    n = 0
    try:
        runtimes = registry.all_runtimes() if registry is not None else []
    except Exception:      # noqa: BLE001 - 刷新失败绝不能影响保存回执
        return 0
    for rt in runtimes:
        agent = getattr(rt, "agent", None)
        if agent is None:
            continue       # 未构造 = 尚未读配置，首次构造时自然是新值
        try:
            agent.permission_gate.refresh_extra_dirs()
            n += 1
        except Exception as exc:   # noqa: BLE001
            log.warning("额外目录刷新失败 session_%s: %s", rt.sid, exc)
    return n
```

**未构造 agent 的会话不必管**：`build_agent()` 里 `switch_session` → `restore_from_meta`
会重新读 store，自然拿到新值。

### 2.4 校验与归一化

**归一化责任在后端**（`PermissionStore._normalize` 已经做了绝大部分，前端只是体验层）：

| 已有归一化 | 行为 |
| --- | --- |
| `default_mode` 非法 | 回落 `default` |
| `approval_timeout_seconds` | 钳到 60–3600，非数字回落 300 |
| `mcp_destructive` | 只认 `ask`/`allow`，并兼容旧 env `MCP_ALLOW_DESTRUCTIVE` |
| `rules[]` | `action ∈ {allow,deny,ask}` 且 `pattern` 非空才保留 |
| `additional_dirs[]` / `*_patterns[]` | 过滤空串与非字符串 |
| `safe_commands.list` 为空 | **回落到内置全量清单**（不是清空） |

**需要新增的三项**（写进 `_normalize` 或 save 前置校验）：

1. **`additional_dirs` 必须是绝对路径** —— 否则 `_rebuild_extra_dirs_locked` 里
   `Path(d).expanduser().resolve()` 会以**后端进程的 cwd** 为基准解析，得到意外目录。
   规则：`expanduser()` 后 `is_absolute()` 为假 → 丢弃 + warning。
   （路径不存在**不拦**，只 warning：用户可能先配后建目录。）
2. **去重**：`additional_dirs` / 各 pattern 列表保序去重（避免同一目录在 UI 上出现两遍）。
3. **交叉冲突提示**（warning，不阻断）：
   - 追加项已在内置硬拒绝清单中 → 「已在硬拒绝清单中，追加无效」；
   - 追加项命中敏感路径（如往 `additional_dirs` 加 `~/.ssh`）→ 「与敏感路径黑名单冲突，该目录内仍会被拒绝」。

**warnings 的产生方式**（二选一，**倾向 A**）：

- **A（推荐）**：新增 `PermissionStore.save_reporting(data) -> tuple[dict, list[str]]`，
  内部 `normalized = self._normalize(data)` 后与原值做**逐键 diff**（超时被钳 / 列表项被丢 /
  列表被去重 / 白名单空回落），生成人话 warning。`save()` 保持原签名（`return self.save_reporting(data)[0]`），
  现有调用方与测试零改动。
- B：把 `_normalize` 改成返回 `(dict, warnings)` —— 会波及 `load()` 与现有测试，**不推荐**。

## 3. 前端方案

### 3.1 四层链路（照抄模型页的既有体例）

```
Settings/PermissionSettings.tsx                    ← 表单（本地 draft）
      ↓ 保存
store/agentStore.ts    savePermissionConfig(cfg)   ← 状态与副作用
      ↓ window.agent.permissionConfigSave(cfg)
preload/index.ts + index.d.ts                      ← IPC 桥
      ↓ ipcRenderer.invoke('agent:permissionConfigSave', {config})
main/index.ts          ipcMain.handle + 白名单校验  ← 宿主校验 + WS 转发
      ↓ request('permission_config_save', 'permission_config', {config})
agents/ws_bridge.py                                ← 落盘 + 回执
```

五处都要改（对照模型页 `llmConfigGet` / `llmConfigSave` 的完整链路）：

| 层 | 文件 | 落点 |
| --- | --- | --- |
| 协议类型 | `renderer/src/protocols/agentProtocol.ts` | `PermissionConfig` / `PermissionRule` / `PermissionConfigResult` / `PermissionBuiltin` 接口；`AgentEvent` 联合类型加 `{ kind: 'permission_config'; payload: PermissionConfigResult }` |
| preload | `preload/index.ts` + `index.d.ts` | `permissionConfigGet(): Promise<unknown>` / `permissionConfigSave(config: unknown): Promise<unknown>` |
| main | `main/index.ts` | 两个 `ipcMain.handle`，`isTrustedSender` 守卫 + `config` 是对象的基本校验（非法直接 `null`，不转发） |
| store | `store/agentStore.ts` | 状态 `permissionConfig: PermissionConfigResult \| null`、`permissionSaving: boolean`（落地时定名，驱动「保存中…」与按钮禁用）；action `loadPermissionConfig()` / `savePermissionConfig(cfg)`；WS 分发里处理 `permission_config` 回包。**三处回包落 store 都必须 merge，见 §3.3 与 §4-11** |
| 组件 | `Settings/PermissionSettings.tsx`（新增）+ `SettingsModal.tsx` | NAV 加「权限」、`switchTab` 里 `if (k === 'permission') void loadPermissionConfig()`；渲染分支加 `{tab === 'permission' && <PermissionSettings />}` |

**`SettingsTab` 顺序**：`'general' | 'model' | 'permission' | 'trash' | 'about'`
（17 篇 §5.3 指定「通用 / 模型 / 权限 / 归档 / 关于」，权限紧跟模型）。

**main 层校验**（对齐 `llmConfigSave` 的克制风格，超时按普通命令）：

```typescript
ipcMain.handle('agent:permissionConfigGet', (e) =>
  isTrustedSender(e) ? request('permission_config_get', 'permission_config') : null
)
ipcMain.handle('agent:permissionConfigSave', (e, payload: { config?: unknown }) => {
  if (!isTrustedSender(e) || typeof payload?.config !== 'object' || payload.config === null) return null
  return request('permission_config_save', 'permission_config', { config: payload.config })
})
```

> **不做深度字段校验**：语义归一化是后端 `_normalize` 的职责（单一出处）。主进程只挡
> 「不是对象」这类明显非法载荷 —— 与 `llm_config_save` 同策略。

### 3.3 草稿与保存语义（对齐模型页）

- 进页：`loadPermissionConfig()` 拉取 → `draft = structuredClone(config)`；`dirty = JSON.stringify(draft) !== JSON.stringify(config)`。
- 改字段只改 `draft`；**不发任何命令**。
- 点保存：`savePermissionConfig(draft)` → 等 `permission_config` 回包 → `config = 回执.config`、`draft = clone(回执.config)`、`dirty = false`，展示 `msg` 与 `warnings`。
- **回包是补丁、不是快照 → store 必须 merge**：`get` 回执带 `builtin`/`path`/`exists`，
  `save` 回执带 `applied`/`warnings`/`msg`（`builtin` 在类型里就是可选的）。三处落 store
  （WS 分发 / `loadPermissionConfig` / `savePermissionConfig`）统一走
  `mergePermissionResult(prev, next)`：`{...prev, ...next}`；且 `next.applied === undefined`
  （get 回执）时显式清空 `applied`/`warnings`/`msg`，否则上一次保存的告警会挂在新加载的
  干净配置上。**整份替换的后果见 §4-11。**
- 切页/关弹窗：`dirty` 时不做拦截（与模型页一致，避免过度设计），但**离开时不重置 draft**？—— **要重置**：`closeSettings` 后 draft 丢弃，重进重新 get（模型页同款行为，避免脏状态跨次打开）。
- 保存中：保存按钮进入 loading 且禁用（防连点产生两次原子写）。

### 3.4 selector 约束（必读，17 篇 §6 事故的正面清单）

`agentStore` 是 zustand v5，`useStore(selector)` 的返回值**就是 React 的 getSnapshot**。
新增 selector 时必须：

```typescript
// ✅ 稳定引用
const permCfg = useAgentStore((s) => s.permissionConfig)
// ❌ 禁止：selector 体内 filter/map/Object.values、对象/数组字面量
//    → 每次返回新引用 → Maximum update depth exceeded（切会话必崩）
const ruleCount = useAgentStore((s) => s.permissionConfig?.config.rules.length ?? 0)  // ✅ 原始类型，安全
```

需要派生数据（如「合并展示内置 + 自定义 chip」）→ 先取稳定入参，再 `useMemo([config, builtin])`。
本页是设置弹窗内的独立页面，**不要**在 `MessageList` / `MessageItem` 那类高频组件里挂
任何与权限配置相关的新 selector。

## 4. 踩坑清单（实施前必读）

1. **`additional_dirs` 不刷新 = 保存了但没用**。其余键都热加载，只有它进缓存集合。见 §2.3。
2. **`_extra_dirs` 是共享对象**，刷新时 `clear()+update()`，**禁止重新赋值**。见 §2.3 红线。
3. **白名单删不空**：`safe_commands.list` 为空会回落到内置全量。想"关掉白名单"用
   `enabled: false`。前端要在删空时明确提示，否则用户会以为没保存成功。
4. **前端别硬编码内置清单**（§2.1.1）—— 否则又造一份会漂移的第二出处。
5. **保存回执要回填 draft**：后端 `_normalize` 会丢非法项，前端若保留原 draft，
   界面显示的与磁盘存的不一致（下次打开才发现变了）。
6. **`deny_paths` 别再把 `~/.aigent/logs` 写回去**（2026-09-22 已移出，17 篇 §3.3）。
7. **CSS 前缀独立**：新增 `.perm-*`，不要复用附件 / 引用 / 审批卡的 chip 类名。
8. **`permission_config` 不回广播**（§2.2）—— 广播会冲掉其他窗口的未保存 draft。
9. **`SettingsModal` 的 `settings-body` 有 `flush` 特例**（`tab === 'model'` 时去 padding）：
   权限页按同样式走普通 padding 即可，别顺手加进 flush 判断。
10. **改配置只影响后续判定**：在途审批不重判、已执行操作不回滚（17 篇 E6/E13 语义）。
    设置页文案不要承诺"立即撤销正在运行的操作"。
11. **`permission_config` 回包禁止整份替换 store —— 否则点一次保存整页消失**（落地时真踩到，
    17 篇 §8.2）。`set({ permissionConfig: res })` 会把上一次 get 带回的 `builtin` 抹成
    `undefined`，而组件开头就是 `if (!draft || !builtin) return <div className="perm-loading">`，
    于是八分区连同 footer 一起塌成「读取权限配置…」。**规则**：同一 kind 若存在两种回执形状，
    消费端一律 merge；想整份替换，后端就必须每次下发完整快照 —— 二选一，不能混。
