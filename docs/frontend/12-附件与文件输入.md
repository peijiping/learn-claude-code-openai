## 一、概念

### 1.1 要解决的问题

用户在会话里需要**把文件交给模型**：截图、PDF、Word、Excel、代码片段。模型只能读文本（图片需要 vision 能力），所以"把文件交给模型"实际是两件事：

1. **取得内容**：图片 → 字节（走 vision）；文档 → 抽取出的文本；文本/代码 → 原文；
2. **取得上下文**：文件叫什么、多大、在哪里 —— 用户回看历史时要能认出"我当时发的是哪个文件"。

### 1.2 两类表示（本设计的核心）

同一条带附件的用户消息，在系统里有**两种完全不同的形态**：

| | 账本形态（磁盘 / jsonl） | 请求体形态（发给模型） |
|---|---|---|
| 图片 | `{"type":"attachment","attachment":{id,kind,name,…}}`，**无字节** | `{"type":"image_url","image_url":{"url":"data:image/png;base64,…"}}` |
| 文档 | 同上 | **多个块**：`{"type":"text","text":"[附件: 报告.pdf]（共 12 页，含 5 张图片，已随附）\n…正文…"}` + 按 `<!--img:pN-->` 锚点在正文中**交错**插入的页图 `image_url` 块 |
| 谁生成 | 桥层组装后落盘，**一次写成** | `Agent._model_messages()` 每次请求**现算** |
| 模型可见 | **不可见**（展开后账本块已不存在） | 可见 |
| 是否回写历史 | — | **不回写**：内存与 jsonl 恒为账本形态 |

**一个附件块展开成几个块是不定的**：文档可能产出"头部说明 + 正文 + N 张页图"多个块（顺序仍是"该附件产出的块"聚集在一起）。所以展开侧统一用 `extend` 而不是 `append`。

**账本里永远不出现 base64，也不出现厂商线格式**（`image_url` / `image` / `input_image`）。这条是设计地基，四条理由：

1. 线格式的图片只能装 base64 或 http(s) URL → 存它等于**把文件字节写进 jsonl**。而 jsonl 会被**整文件原子重写**（压缩、自愈、`save_session_history`），一张 3MB 图 base64 后 4MB、八张就是 32MB 每轮复制一次；
2. L4 上下文摘要把消息拼进摘要 prompt（预算 4000 token）—— base64 一进去摘要直接报废，且**原图信息永久丢失**（摘要结果回写后原消息被替换掉）；`estimate_tokens` 按字符启发式估也会被撑爆 → 上下文圆圈提前触顶 → 反复触发压缩；
3. 线格式**不含** `name/size/source_path` → 历史回放显示不出"报告.pdf · 2.1MB"；
4. 线格式**被厂商绑定**（Anthropic 是 `{"type":"image","source":{"type":"base64"}}`）→ 换 provider 要全量迁移历史；也无法按模型能力裁剪（text-only 模型应把图片降级为占位，而不是原样发出去让 API 报错）。

### 1.3 三类附件

| kind | 扩展名 | 处理方式 |
|---|---|---|
| `image` | png / jpg / jpeg / webp / gif / bmp | 走 vision；登记时可用 Pillow 生成缩放副本（省请求体体积） |
| `document` | pdf / docx / xlsx / pptx | **统一转换层**（§2.5.3）：PDF 产出「文本层 + 该渲染的页图」，docx/xlsx/pptx 产出正文文本；正文落 `<att_id>.txt`，页图落 `<att_id>.pages/pN.jpg` |
| `text` | txt / md / csv / json / 各种代码… | 直接按文本读（编码探测），不额外落副本 |

**明确不支持**（后端给可读原因）：`.doc/.xls/.ppt` 老格式（二进制复合文档，纯 Python 无可靠解析方案，提示"另存为 .docx"）、文件夹、无扩展名、0 字节、超限体积、其它未知扩展名。

### 1.4 三条入口

| 入口 | 实现 | 特点 |
|---|---|---|
| `+` 菜单「添加文件或图片」 | 主进程 `dialog.showOpenDialog({properties:['openFile','multiSelections']})` | 有 `filters` 白名单（**只是建议**，见 §4.3） |
| 拖拽到输入框 | `webUtils.getPathForFile(file)` + `dragenter/over/drop` | 拖到 `.composer` 上，遮罩提示投放区 |
| 粘贴（Cmd+V） | `onPaste` 取 `clipboardData.files` | 截图无磁盘路径 → 字节交主进程落临时文件；纯文本粘贴**不拦截** |

三条入口最终都收敛成**本地绝对路径列表**（`InputBox.pathsFromFiles`），交给后端读盘。

## 二、设计

### 2.1 数据流

```
① 入口（+ 菜单 / 拖拽 / 粘贴）→ 收敛为绝对路径列表
② ipc: stageAttachments → WS `attachment_stage {paths, project_id}`
③ 后端 stage()：校验 → 复制到 .attachments/_draft/<att_id>/ → 抽取文本/缩放图片
             → 回 `attachments_staged {items, failed}`
④ 前端按 source_path 与本地占位项配对：就绪项可发送，失败项标红并显示原因
⑤ 发送 chat { text, attachments:[{att_id,kind,name,ext,…}] }（允许 text 为空）
⑥ 后端 migrate_to_session()：草稿 → .attachments/<session_id>/（原子迁移）
⑦ 桥层组装 content = [文本块 + 附件引用块…] → start_turn → 落盘 jsonl
⑧ 发送边界 _model_messages() 展开引用块 → 模型线格式（图片 data URL / 文档文本）
⑨ 历史回放 _history_to_ui() 从 content 块 harvest 出 attachments → 前端渲染
```

### 2.2 存储布局

```
~/.aigent/projects/<id>/.attachments/          # 运行期按需创建，不进 WORKSPACE_SUBDIRS
├── _draft/<att_id>/                           # 尚未发送（新会话此刻还没有 session_id）
│   ├── meta.json                              # 元数据：重启后按 att_id 找回的唯一事实源
│   ├── <att_id>.<ext>                         # 用户文件的副本（原文件不动）
│   ├── <att_id>.txt                           # document 类的抽取结果
│   └── <att_id>.send.jpg                      # 可选：超大图缩放后的发送用图
└── <session_id>/                              # 已发送（发送时原子迁移过来）
    ├── <att_id>.<ext> / <att_id>.txt / <att_id>.send.jpg
    └── <att_id>.meta.json                     # meta.json 迁移时改名，避免同目录多附件撞名
```

**为什么复制而不是引用原路径**：只引用的话，原文件被移动/改名/删除后该条历史消息**永久失效且无法自愈**。代价是磁盘，用下面的清理策略回收。

### 2.3 生命周期与清理

| 事件 | 行为 |
|---|---|
| 登记 | 复制进 `_draft/<att_id>/`（`copy2` 保留 mtime；**不用 move** —— 原文件必须原地留下） |
| 发送 | `os.replace` 原子迁到 `<session_id>/`；跨分区 `OSError` → 降级 `shutil.move`；**迁移失败不阻断对话**，发送边界按缺失降级 |
| 幂等 | 重发同一批 att_id：草稿区找不到就去会话目录找，找到即复用 |
| 跨空间 | `meta.json.project_id` 记来源空间，发送时去该空间草稿区找回 |
| 草稿 GC | 启动时 + 登记时节流（10 分钟一次）：`meta.json` mtime 早于 TTL（默认 72h）→ 删 |
| 孤儿目录 GC | 启动时：`.attachments/<sid>/` 无对应 `*<sid>.jsonl` **且**无 `*<sid>.meta.json`，且目录 mtime > 24h → 删 |
| 归档 / 还原 | **不动附件**（软删除语义：还原后消息里的图片必须还在） |
| 清空会话 / 永久删除会话 | 桥层顺手 `rmtree` 附件目录（**不改引擎**：`delete_session_permanent` 里加不了，桥层有调用点） |
| 删除工作空间 | 整个元数据目录被删，附件随之消失，无需额外代码 |
| 并发 | `att_id = att_ + 12 位 base62 随机`，全局唯一 → 草稿目录天然隔离，无需加锁 |

> 24h 孤儿门限存在的理由：会话刚建、jsonl 还没落盘的瞬间不能误杀。归档只改 meta 状态、jsonl 原样保留，因此永远不会被这条 GC 命中。

### 2.4 数据结构

**jsonl user 行**（`content` 是数组）：

```json
{
  "role": "user",
  "created_at": "2026-09-20T14:30:05",
  "content": [
    { "type": "text", "text": "帮我对比这两个文件" },
    { "type": "attachment", "attachment": {
        "id": "att_7f3k9q2m1x", "kind": "document", "name": "季度报告.pdf",
        "mime": "application/pdf", "ext": ".pdf", "size": 182736,
        "source_path": "/Users/pei/Downloads/季度报告.pdf",
        "stored_path": "~/.aigent/projects/default/.attachments/Kx7mQ2vT8p/att_7f3k9q2m1x.pdf",
        "text_chars": 18422, "text_truncated": false, "pages": 12, "missing": false } }
  ]
}
```

无附件时 `content` 仍是**纯字符串**（与改造前逐字节一致），这条是零行为变化的硬保证。

**`content` 块为什么能穿过读写**：`session_manage._message_to_json_row` 对 user 行的 `content` **原样透传**，`load_session_history` 也是；但它**会丢弃未知的兄弟字段**（只保留 `role/content/created_at`）。所以附件元数据**只能放 content 块内**，不能放消息的兄弟字段 —— 放了会在重新加载时静默消失。

**协议字段**：

```ts
// 前端 → 后端
{ kind: 'attachment_stage', payload: { paths: string[], project_id?: string } }
// 后端 → 前端（点对点应答请求连接）
{ kind: 'attachments_staged', payload: {
    items:  [{ att_id, kind, name, mime, ext, size, source_path, project_id,
               text_chars, text_truncated, pages,
               images, tables, converter, warnings }],
    failed: [{ path, reason }],        // 逐条失败原因，单条失败不影响整批
    project_id: string } }
// chat 扩展
ChatPayload.attachments?: ChatAttachmentInput[]   // {att_id,kind,name,mime?,ext,size?,project_id?}
// session_history 扩展
HistoryMessage.attachments?: AttachmentRef[]      // {id,kind,name,mime,ext,size,source_path,stored_path,missing?}
```

**`images` / `tables` / `converter` / `warnings`（2026-09-20 新增）**：字段先立起来，当前
恒为 `0` / `0` / `"text_layer"` / `[]`（或 `["未提取到文本"]`）—— 本轮只抽文本层，图片与
表格尚未随附。旧附件记录的 `meta.json` 没有这四个字段，`public_item` 一律取默认值，
**存量附件零迁移**。`warnings` 是"诚实失败"通道，UI 据此显示"已降级"，详见 §2.5。

`isKnownAgentEvent` 白名单**不加**（附件不走流式事件线，避免污染前后端版本兼容白名单）。

### 2.5 发送边界的展开与降级矩阵

`Agent._model_messages()` 是账本 → 线格式的**唯一转换点**（也是本次对引擎层的两处授权改动之一）。

| 情况 | 输出 |
|---|---|
| 图片 + 文件在 | `image_url` + `data:` URL（有 `<att_id>.send.jpg` 时优先用它 —— 缩放副本更省请求体） |
| 图片 + **模型不支持图片** | 文本块 `[图片: x.png]（未发送：当前模型不支持图片输入，请切换到带「图片」能力的模型）` |
| 图片 + 文件缺失 | 文本块 `[图片缺失: x.png]（原文件已被移动或删除）` + 告警日志 |
| 图片超过内联上限（默认 15MB） | 文本块 `[图片过大未能发送: x.png]（xxx MB）` |
| 文档 + 正文在 | **首个文本块**：`[附件: x.pdf]（共 12 页，含 5 张图片，已随附）\n<正文>` |
| 文档 + `.txt` 缺但原件在 | 现场重抽取一次 |
| 文档 + 有页图 | 正文里 `<!--img:pN-->` 锚点处**插入图片块**（带 `detail`），位置就是它该在的位置 |
| 页图 + 模型不支持图片 | 该锚点位置降级为占位文本块（**位置保留**，模型知道自己漏看了哪张） |
| 页图资产文件缺失 | 占位文本块 `[图片 pN 缺失：资产文件未找到]` |
| 文档正文为空 | 占位串 `（未提取到文本：…）`（pdf/docx/xlsx/pptx **一律有**）+ `warnings` |
| 附件块格式异常 | **原样透传，不抛** |
| 文本超长 | 截断到 `ATTACHMENT_TEXT_MAX_CHARS`（30000，与 `run_read_pdf` 同口径）+ 末尾给出完整文件路径供模型用工具续读 |

> **绝不抛异常**是硬契约：异常穿透到 `agent_loop` 会让本轮剩余 tool_calls 的 tool_result 全部缺失、整轮被打死。

#### 2.5.1 图片能力门控落在发送边界（2026-09-20）

改前**唯一**的校验是 `ws_bridge._model_supports_image`，它在 chat 命令分发前跑一次，且只扫
**当轮新上传**的 `kind == "image"` 附件。于是三条路径完全裸奔：**会话中途换模型**、
**历史回放**、以及任何把图带进新一轮的场景 —— 图片会被原样发给不支持图片的模型，
provider 报错，或内容被静默忽略。

现在门控是**两层，职责不同，不可互相替代**：

| 层 | 位置 | 职责 |
|---|---|---|
| 预检 | `ws_bridge`，chat 分发前 | 迁移之前就报错 —— 否则草稿已搬到会话目录却没人引用，只能等 GC，白占磁盘 |
| 兜底 | `Agent._model_messages()` | 覆盖全部路径（换模型 / 回放 / 未来新入口），保证"模型看不到的图"一定变成占位 |

判据是三态，且**引擎与桥层共用同一个纯函数** `llm_config.caps_allow_image`（各自保留自己的
`get_model_by_id` 调用点，因为 ws_bridge 的测试在该名字上打桩）：

- 明确声明 `input` 含 `image` → 发图；
- 明确声明了 `input` 列表但不含 `image` → 降级为占位，**绝不静默丢弃**；
- 元数据缺失 / 形状不认识 → **按支持处理**。本地目录可能没收录用户新加的模型，不能因为
  "我们不知道"就本地误拦 —— 宁可让 provider 回一个真实错误，也不要静默吞掉图片。

**无附件时短路**：`_model_messages` 先用 `history_has_attachments()` 扫一遍，没有附件块
就根本不查能力。所以"无附件请求体逐字节等价"由**结构**保证，而不是靠"新增代码恰好没副作用"。

#### 2.5.2 抽空必须留痕（2026-09-20）

事故现场是"前端显示解析成功（`text_chars=23`）"—— 23 恰好是占位串
`（未提取到文本，可能是扫描件或纯图片 PDF）` 的字符数。**`text_chars > 0` 从来不是
"解析成功"的证据。**

改前只有 PDF 有占位串，docx/xlsx/pptx 抽空返回空串，前端照样显示"已提取 0 字"，
用户与模型都不知道内容丢了。现在四种格式抽空时一律写入占位串（公共前缀
`EMPTY_NOTE_PREFIX`，由 `attachments.text_is_empty_note()` 判定），并同时落
`warnings: ["未提取到文本"]`。

两个附带修正：**工作表标题 / 幻灯片页码不算内容** —— 否则一个只有空表的工作簿会抽出
`--- 工作表: Sheet1 ---`，看着"有内容"实则什么都没读到。

#### 2.5.3 统一转换层（`agents/doc_convert.py`，2026-09-20）

为每种格式各写一套"正则式"文本抽取，注定追不上版式复杂度：表格被打散成单词、图表整块
丢失、扫描件抽到空。**根因不是某个 bug，是架构选型。**

查过两家官方文档，做法出奇一致，而且**都不是"逐格式写抽取器"**：

| | 处理方式 |
|---|---|
| **Anthropic** | PDF 走 `document` 内容块直传。官方描述：**每页转成图像，同时抽该页文本，两者一起进模型上下文**。上限 32MB / 600 页；非 PDF 格式 `document` 块不支持 |
| **OpenAI** | `input_file` 项按类型分派：PDF **同时提取文本与页面图像**；非 PDF 文档**仅提取文本**；表格类走专用增强流程。官方明确建议：**要保住非 PDF 的图表精度，请先把文件转成 PDF** |

两家的公共前置都是**"每页渲染成图"**，而不是"想办法把图表转成文字"。方向已经验证过，
不需要重新发明 —— 本层的做法与之一致：**每页渲染成位图，与文本层一起交给模型**：

```
PDF（或后续的 Office 格式）
     │
     ▼
doc_convert.convert_pdf()        ← 叶子模块：标准库 + 懒加载 pymupdf
     │  每页: "--- 第 N 页 ---" + 文本层 + 渲染页图(按需) + <!--img:pN-->
     ▼
<att_id>.pages/p1.jpg …          ← 页图资产（锚点 id 就是文件名去后缀）
<att_id>.txt                     ← 正文（含锚点）
     │
     ▼
_expand_one()                    ← 按锚点把正文切成交错的文本块/图片块
```

**哪些页才渲染**（`_needs_page_image`）—— 判据是"文本层是否足以代表这一页"：

| 信号 | 渲染？ | 理由 |
|---|---|---|
| 页面完全没有文本，但有位图 / 表格 / **矢量绘制** | ✅ | 扫描件、图片页、纯矢量示意图 |
| 页面完全没有文本，且三者都没有 | ❌ | 真空白页，不浪费一张图的额度 |
| 文本层短于 `ATTACHMENT_DOC_PAGE_IMAGE_MIN_TEXT`(200) | ✅ | 大概率是扫描件或图为主的一页 |
| 文本层够密，但有内嵌位图 | ✅ | 有图表/照片 |
| 文本层够密，但 `find_tables` 命中 | ✅ | 表格的行列关系正是文本层会丢掉的 |
| 文本层够密，无图无表 | ❌ | 页图提供不了额外信息 |

> 给纯文本 PDF 的每一页都渲染图是浪费：20 张图 ≈ 19 MiB 请求体（实测），而文本层已经完整。
> 所以**默认不渲染**，只在文本层不足时才渲染。`ATTACHMENT_DOC_PAGE_IMAGE_MIN_TEXT` 调大
> 更保守（更贵、覆盖更全）。

**成本口径**（DeepSeek，2026-09 实测）：服务端会把每张图自动缩到约 1300×1300 像素量级，
**单图 token 封顶 1024** —— 所以图像 token 不是风险，真正的约束是**请求体**（内联图
48 MiB）。本层的 `max_edge` 缩放不省 token（服务端已封顶），意义是省请求体与上传耗时。

实测数字（本次改造）：

| 样本 | 解析耗时 | 页图数 | 请求体 |
|---|---|---|---|
| 事故 PDF（5625×3754pt 单页扫描，662KB） | 0.33s | 1 | 171 KB |
| 24 页扫描件（6.2MB，噪点页） | 1.70s | 20（`max_images` 生效） | 19.25 MiB（余量 60%） |
| 自造 4 页混合（密集文本/位图交替） | — | 2（只渲位图页） | — |

**已知缺口**（明确记录，未做）：

- **office 格式的整页视觉版式**不还原 —— docx/pptx 只抽"保序文本 + 内嵌图 + 表格"，
  没有栏位/排版/图文相对位置。渲染它们需要 LibreOffice（约 800MB 外部二进制），
  与本项目 §四 的既有决策冲突，**已明确不做**；
- **大画布 PDF 的细节**：服务端无论如何会把图缩到约 1300×1300 像素量级，本地缩边救不回
  细节。唯一机制是区域切片（每块独立成图、各自拿到封顶预算），**待实测后再判断是否值得做**；
- **无框线表格**：`find_tables` 对靠位置对齐的表格命中 0（实测）。表格的视觉真相在页图里，
  `meta.tables` 只是下界，**不写进给模型的头部说明**（说一个偏小的数字会让模型以为表格已尽收眼底）。



渲染层拿不到 `file://`（contextIsolation + CSP），因此主进程注册 `aigent-att://` 协议：

```
<img src="aigent-att://local/?pid=<工作空间>&id=<att_id>">
```

**按 (空间, att_id) 寻址，而不是按文件路径** —— 附件在发送时会从 `_draft/` 迁到 `<session_id>/`，路径会变；按 id 检索由主进程负责，缩略图因此跨越迁移稳定（否则"刚发出去的图片缩略图瞬间 404"）。

主进程侧三层安全校验（缺一不可）：
1. **形状白名单**：`pid` 匹配 `^(default|ws[0-9A-Za-z]{10})$`、`att_id` 匹配 `^att_[0-9A-Za-z]{6,32}$` —— 只接受固定形状，根本不存在 `..` 或分隔符注入的空间（不是"过滤 `..`"）；
2. `readdirSync` 只在我们自己拼出的目录里找 `<att_id>.*`（跳过 `.meta.json` / `.send.jpg`）；
3. **符号链接解引后复检**路径仍含 `.attachments` 段 —— `.attachments` 是用户可直接写的目录，放一个指向 `/etc/passwd` 的软链就能让第 1、2 层形同虚设。

CSP 相应放行：`img-src 'self' data: aigent-att:`（`renderer/index.html`）。

### 2.7 撤回与边界（明确的已知约束）

- `.attachments` 目录下的文件**用户可以直接删**：删了以后追问不崩、日志告警、模型收到占位文本、UI 显示「文件已缺失」；
- 缩略图**不落前端缓存**：每次渲染都经协议读取（本地文件，成本可忽略）；
- **切会话清空附件草稿**（文本草稿沿用既有行为不清）—— 草稿属于"正在编辑的这条消息"，跨会话漂移更糟；
- **未做**：`@` 引用文件/文件夹、`#` 引用历史会话、附件拖入消息区（只支持拖到输入框）、压缩包解压、音视频、`.doc/.xls/.ppt`。
  —— 注：**扫描件 OCR 已不在"未做"之列**：无文本层的页改为渲染成页图交给视觉模型（§2.5.3），
  不需要本地 OCR。本地 OCR 反而会丢掉版式与图表。

### 2.8 chip 显示规则（发送前知情，2026-09-20）

**核心原则**：**在发送之前**让用户知道将要付出什么、以及会丢失什么。本次事故里前端显示的
「已提取 23 字」是误导性反馈 —— 23 恰好是占位串本身的长度，而用户以为解析成功了。

四态（`DraftAttachment.status` / `AttachmentView.status`，两处联合类型必须同步改）：

| 状态 | 触发 | 外观 | 副标题 |
|---|---|---|---|
| `staging` | 已提交等后端回包 | 虚线灰、时钟图标 | `读取中…` |
| `ready` | 解析完成、无 warning | 常态 | `2.1MB · 12 页 · 5 图 · 3 表` |
| `degraded` | 后端给了任何 `warnings` | **琥珀**边框 + 名字/副标题琥珀（`--color-warn`） | 有交付 → 照常显示统计；没交付 → `未能完整解析` |
| `failed` | 文件被拒 | **红色**边框（`--color-danger`） | 拒绝原因（自由文本） |

副标题口径（`AttachmentBar.attachmentMeta`，草稿与消息**共用同一函数** —— 这是"发送前看到的"
与"回放看到的"一致的保证）：

```
图片        → 482.4KB · 图片
文档         → 2.1MB · 12 页 · 5 图 · 3 表        （有 pages 用页数，否则用"已提取 N 字"）
什么都没交付  → 2.1MB · 未能完整解析                （唯一会顶掉统计的文案）
staging     → 读取中…
```

**降级 ≠ 什么都没交付**，两者必须分开：

- 「第 N 页无文本层，**已按图像发送**」—— 内容通过页图**交付了**，副标题照常显示 `12 页 · 12 图`；
- 「**未提取到文本**」且没有图片随附 —— 真的什么都没给到模型 → 副标题换成 `未能完整解析`。

判据是 `nothingDelivered()`：`warnings` 里含后端字面量 `未提取到文本` **且** `images === 0`。用
**精确相等**而不是子串匹配 —— 子串会把"某些页无文本层，已按图像发送"误判成未交付。这个字面量
与 `attachments.py` 里那一处逐字对应，改后端文案必须同步改前端常量（见 §3.2 第 16 条）。

**完整原因放 tooltip**：warning 可能很长（`第 1、2、3、4、5 页无文本层 等 24 页，已按图像发送`），
塞进单行副标题只会被省略号吃掉。副标题只放一句短提示，tooltip 里给出全部 warning + 解析方式 +
原始路径。

**可发送性**：`degraded` 与 `ready` 同等可发送 —— 解析不完整不等于不能用。只有 `failed`
与仍在 `staging` 的才拦住发送。

**这个判据只允许有一处**：`agentStore.isSendableAttachment()`。曾因 InputBox（按钮可用性）
与 ChatPanel（**真正构造 payload**）各写了一遍 `a.status === 'ready'`，加 `degraded` 之后
只改了前者 —— 于是附件被**静默**从 payload 里丢掉，后端日志只留下一行
`chat 派发 … attachments=0`，前后端都不报错。这正是本项目要消灭的
"附件没到模型手里、却没有任何提示"。

### 3.2 关键实现要点（勿回退）

1. **`main/index.ts` 的 `!payload.text` 守卫必须保持放宽**（`(!payload?.text && !payload?.attachments?.length)`）—— 历史 bug 就是它把"只发了图片没打字"的消息静默丢掉。
2. **`chat.payload.text` 永远是字符串**。多模态数组只在 `ws_bridge` 内部组装 —— 标题生成（`re.sub`）、首轮判定、日志切片全都依赖这个前提。
3. **拖拽必须用 `webUtils.getPathForFile`**（Electron 32+ 已移除 `File.path`），且**只能在 preload 内调用**（DOM `File` 无法过 IPC）。
4. **拖拽遮罩必须 `pointer-events: none`**：遮罩覆盖整个输入框，若参与命中测试会盖住输入框与发送按钮（实测见 §3.4）。
5. **`ChatPanel` 的全局 `dragover`/`drop` preventDefault 不能删**：否则拖到输入框以外的区域会让 Electron 把窗口导航成 `file://` 页面（白屏事故）。
6. **粘贴只在确实取到文件时才 `preventDefault`**：否则会把纯文本粘贴吃掉。
7. **缩略图 URL 必须按 `(pid, att_id)` 寻址**，不能存路径（迁移后失效）。
8. **图片的能力校验是两层，缺一不可**：`ws_bridge` 的预检**必须留在迁移之前**（否则草稿已搬到会话目录却没人引用，只能等 GC 白占磁盘）；`Agent._model_messages()` 的兜底**也必须有**（预检只扫当轮新附件，换模型 / 回放 / 新入口全绕过）。判据共用 `llm_config.caps_allow_image`，不要在两处各写一份三态。
9. **`capability_source == "auto"` 的模型能力必须每次从预置目录重新推导**（`_normalize_model`）。若改成"存了就优先用存的"，`providers.json`「可随官方整体更新」的设计立刻失效 —— 官方改能力声明，既有安装永远收不到。
10. **修正既有模型的内置声明时必须提升 `CATALOG_VERSION`**：`_merge_provider` 是「文件为准」，不加版本闸门的话旧 `providers.json` 会把内置修正永久压住，而且自愈回写也会失效（merge 结果恒等于文件，被判成"一致"）。
11. **Electron 44 的主进程 `Clipboard` 已改为 W3C 风格异步 API**（不再有 `readImage`）→ 剪贴板图片由渲染层把**字节**（`File.arrayBuffer()`）交给主进程落临时文件。ArrayBuffer/Uint8Array 是 IPC 可结构化克隆的类型，不受"File 不能过 IPC"限制。
12. **页图资产必须跟着附件一起迁移**：`_move_dir_contents` **不能跳过目录**（曾写死 `if item.is_dir(): continue`，导致 `<att_id>.pages/` 留在草稿区、展开发不出图）。同名覆盖时目录要 `rmtree` 而不是 `unlink`（后者对目录抛 `IsADirectoryError`）。
13. **锚点 id 必须等于资产文件名去后缀**（`<!--img:p1-->` ↔ `p1.jpg`）。这条约定让展开侧**不依赖 meta** —— meta 丢了、附件从别处拷来，只要目录在就能按位置恢复。
14. **只有我们自己生成的页图带 `detail`**，用户上传的图片一概不带（`prepare_image` 已定过尺寸；多一个字段只会给不认识它的兼容端点制造 400 风险）。
15. **L1 裁剪必须保住带附件的消息**（`context_compact._has_attachment_block`）：图片在 token 估算里只折算成 `[图片: name]` 约 5 个字符，**看起来是最廉价的裁剪对象，实际是最贵的东西** —— 裁掉它模型就再也看不到那份附件，而图片无法靠"用工具再读一次"补回来。附件消息被摘出放在占位之后、尾部之前，占位里的条数只统计真正被裁掉的。
16. **`WARN_NO_TEXT` 是跨语言的字面量耦合**：`AttachmentBar.tsx` 的前端常量 `未提取到文本` 与 `agents/attachments.py` 里写入 `warnings` 的那一处**逐字对应**，用来区分"什么都没交付"与"已按图像发送"。改后端文案必须同步改前端常量（用**精确相等**匹配，子串匹配会误判扫描件）。
17. **附件的可发送判据只能有一处**（`agentStore.isSendableAttachment`）。不要在组件里再写 `a.status === 'ready'` —— 加 `degraded` 时漏改 ChatPanel 那处，附件就被**静默**从 payload 丢掉（后端日志只有 `attachments=0`，前后端都不报错）。InputBox 的按钮可用性与 ChatPanel 的 payload 构造必须调同一个函数。

## 四、取舍与备选

| 决策 | 选了 | 否掉 | 理由 |
|---|---|---|---|
| 存储 | 复制进会话目录 | 只引用原路径 | 原文件一动历史就永久失效、无法自愈 |
| 传输 | 只传路径（后端同机读盘） | WS/IPC 传文件字节 | `websockets` 默认帧上限 1 MiB，base64 图片必然超限；同机进程没有传字节的必要 |
| 磁盘表示 | 中性引用块 | 直接存 `image_url` + base64 | 见 §1.2 四条理由 |
| 展开时机 | 发送边界现算 | 落盘时展开 | 一次落盘多次请求，展开结果不该污染历史 |
| 缩略图寻址 | `(pid, att_id)` 检索 | 存绝对路径进 URL | 草稿 → 会话目录迁移会换路径 |
| 图片发送 | 优先用缩放副本 | 一律发原图 | 省 vision token；原图仍保留供查看 |
| text-only 模型发图 | 拦住并提示切换 | 后端静默丢弃图片 | 静默丢内容比报错更糟；未知模型一律放过（本地目录可能没收录） |
| 老格式 Office | 拒绝 + 提示另存 | 依赖 LibreOffice 转换 | 引入外部二进制依赖，跨平台失败态复杂 |
