## 一、概念

### 1.1 要解决的问题

用户在会话里需要**把文件交给模型**：截图、PDF、Word、Excel、代码片段。模型只能读文本（图片需要 vision 能力），所以"把文件交给模型"实际是两件事：

1. **取得内容**：图片 → 字节（走 vision）；文档 → 抽取出的文本 + 页面图；文本/代码 → 原文；
2. **取得上下文**：文件叫什么、多大、在哪里 —— 用户回看历史时要能认出"我当时发的是哪个文件"。

### 1.2 两类表示（本设计的核心）

同一条带附件的用户消息，在系统里有**两种完全不同的形态**：

| | 账本形态（磁盘 / jsonl） | 请求体形态（发给模型） |
|---|---|---|
| 图片 | `{"type":"attachment","attachment":{id,kind,name,…}}`，**无字节** | `{"type":"image_url","image_url":{"url":"data:image/png;base64,…"}}` |
| 文档 | 同上 | **多个块**：`{"type":"text","text":"[附件: 报告.pdf]（共 12 页，含 5 张图片，已随附）\n…正文…"}` + 按 `<!--img:pN-->` 锚点在正文中**交错**插入的页图 `image_url` 块 |
| 谁生成 | 桥层组装后落盘，**一次写成** | `Agent._model_messages()` 每次请求**现算** |
| 模型可见 | **不可见**（展开后账本块已不存在） | 可见 |
| 是否回写历史 | — | **不回写**：内存与 jsonl 恒为账本形态 |

**一个附件块展开成几个块是不定的**：文档可能产出"头部说明 + 正文 + N 张页图"多个块（顺序仍是"该附件产出的块"聚集在一起）。所以展开侧统一用 `extend` 而不是 `append`。

**账本里永远不出现 base64，也不出现厂商线格式**（`image_url` / `image` / `input_image`）。这条是设计地基，四条理由：

1. 线格式的图片只能装 base64 或 http(s) URL → 存它等于**把文件字节写进 jsonl**。而 jsonl 会被**整文件原子重写**（压缩、自愈、`save_session_history`），一张 3MB 图 base64 后 4MB、八张就是 32MB 每轮复制一次；
2. L4 上下文摘要把消息拼进摘要 prompt（预算 4000 token）—— base64 一进去摘要直接报废，且**原图信息永久丢失**（摘要结果回写后原消息被替换掉）；`estimate_tokens` 按字符启发式估也会被撑爆 → 上下文圆圈提前触顶 → 反复触发压缩；
3. 线格式**不含** `name/size/source_path` → 历史回放显示不出"报告.pdf · 2.1MB"；
4. 线格式**被厂商绑定**（Anthropic 是 `{"type":"image","source":{"type":"base64"}}`）→ 换 provider 要全量迁移历史；也无法按模型能力裁剪（text-only 模型应把图片降级为占位，而不是原样发出去让 API 报错）。

### 1.3 三类附件

| kind | 扩展名 | 处理方式 |
|---|---|---|
| `image` | png / jpg / jpeg / webp / gif / bmp | 走 vision；登记时用 Pillow 生成缩放副本（省请求体体积） |
| `document` | pdf / docx / xlsx / pptx | **统一转换层**（§2.7）：PDF 产出「文本层 + 该渲染的页图」，页图落 `<att_id>.pages/pN.jpg`；docx/xlsx/pptx 产出正文文本。正文落 `<att_id>.txt` |
| `text` | txt / md / csv / json / 各种代码…（约 60 种扩展名，见 `attachments.TEXT_EXTS`） | 直接按文本读（编码探测），不额外落副本 |

**明确不支持**（后端给可读原因）：`.doc/.xls/.ppt` 老格式（二进制复合文档，纯 Python 无可靠解析方案，提示"另存为 .docx/.xlsx/.pptx"）、文件夹、无扩展名、0 字节、超限体积、其它未知扩展名。

### 1.4 三条入口

| 入口 | 实现 | 特点 |
|---|---|---|
| `+` 菜单「添加文件或图片」 | 主进程 `dialog.showOpenDialog({properties:['openFile','multiSelections']})` | 有 `filters` 白名单（**只是建议**，拖拽可绕过，真守卫在后端） |
| 拖拽到输入框 | `webUtils.getPathForFile(file)` + `dragenter/over/drop` | 拖到 `.composer` 上，遮罩提示投放区；用**深度计数**避免进入子元素时遮罩闪断 |
| 粘贴（Cmd+V） | `onPaste` 取 `clipboardData.files` | 截图无磁盘路径 → 字节交主进程落临时文件；纯文本粘贴**不拦截** |

三条入口最终都收敛成**本地绝对路径列表**（`InputBox.pathsFromFiles`），交给后端读盘。

## 二、设计

### 2.1 数据流

```
① 入口（+ 菜单 / 拖拽 / 粘贴）→ 收敛为绝对路径列表
② ipc: stageAttachments → WS `attachment_stage {paths, project_id}`
③ 后端 stage()：校验 → 复制到 .attachments/_draft/<att_id>/ → 抽取正文 / 渲染页图 / 缩放图片
             → 回 `attachments_staged {items, failed}`
④ 前端按 source_path 与本地占位项配对：就绪项可发送，失败项标红并显示原因
⑤ 发送 chat { text, attachments:[{att_id,kind,name,ext,…}] }（允许 text 为空）
⑥ 后端 migrate_to_session()：草稿 → .attachments/<session_id>/（原子迁移）
⑦ 桥层组装 content = [文本块 + 附件引用块…] → start_turn → 落盘 jsonl
⑧ 发送边界 _model_messages() 展开引用块 → 模型线格式（图片 data URL / 文档文本+页图）
⑨ 历史回放 _history_to_ui() 从 content 块 harvest 出 attachments → 前端渲染
```

### 2.2 存储布局

```
~/.aigent/projects/<id>/.attachments/          # 运行期按需创建，不进 WORKSPACE_SUBDIRS
├── _draft/<att_id>/                           # 尚未发送（新会话此刻还没有 session_id）
│   ├── meta.json                              # 元数据：重启后按 att_id 找回的唯一事实源
│   ├── <att_id>.<ext>                         # 用户文件的副本（原文件不动）
│   ├── <att_id>.txt                           # document 的抽取正文
│   ├── <att_id>.send.jpg                      # 可选：超大图缩放后的发送用图
│   └── <att_id>.pages/p1.jpg …                # 可选：转换层产出的页图资产（PDF）
└── <session_id>/                              # 已发送（发送时原子迁移过来）
    ├── <att_id>.<ext> / <att_id>.txt / <att_id>.send.jpg
    ├── <att_id>.pages/p1.jpg …
    └── <att_id>.meta.json                     # meta.json 迁移时改名，避免同目录多附件撞名
```

**为什么复制而不是引用原路径**：只引用的话，原文件被移动/改名/删除后该条历史消息**永久失效且无法自愈**。代价是磁盘，用 §2.3 的清理策略回收。

页图资产用**目录 + 命名约定**承载（`<att_id>.pages/pN.jpg`），明细不进 `meta.json` —— 省 jsonl 体积，且 meta 丢了也能按目录恢复。

### 2.3 生命周期与清理

| 事件 | 行为 |
|---|---|
| 登记 | 复制进 `_draft/<att_id>/`（`copy2` 保留 mtime；**不用 move** —— 原文件必须原地留下） |
| 发送 | `os.replace` 原子迁到 `<session_id>/`；跨分区 `OSError` → 降级 `shutil.move`；**迁移失败不阻断对话**，发送边界按缺失降级 |
| 幂等 | 重发同一批 att_id：草稿区找不到就去会话目录找，找到即复用 |
| 跨空间 | `meta.json.project_id` 记来源空间，发送时去该空间草稿区找回 |
| 草稿 GC | 启动时 + 登记时节流（10 分钟一次）：`meta.json` 所属目录 mtime 早于 TTL（默认 72h）→ 删 |
| 孤儿目录 GC | 启动时：`.attachments/<sid>/` 无对应 `*<sid>.jsonl` **且**无 `*<sid>.meta.json`，且目录 mtime > 24h → 删 |
| 归档 / 还原 | **不动附件**（软删除语义：还原后消息里的图片必须还在） |
| 清空会话 / 永久删除会话 | 桥层 `_drop_session_attachments` 顺手 `rmtree` 附件目录（**不改引擎**：桥层有调用点） |
| 删除工作空间 | 整个元数据目录被删，附件随之消失，无需额外代码 |
| 并发 | `att_id = att_ + 12 位 base62 随机`，全局唯一 → 草稿目录天然隔离，无需加锁 |

> 24h 孤儿门限存在的理由：会话刚建、jsonl 还没落盘的瞬间不能误杀。归档只改 meta 状态、jsonl 原样保留，因此永远不会被这条 GC 命中。

### 2.4 数据结构

**jsonl user 行**（`content` 是数组）：

```json
{
  "role": "user",
  "created_at": "2026-09-21T09:12:33",
  "content": [
    { "type": "text", "text": "帮我对比这两个文件" },
    { "type": "attachment", "attachment": {
        "id": "att_7f3k9q2m1x", "kind": "document", "name": "季度报告.pdf",
        "mime": "application/pdf", "ext": ".pdf", "size": 182736,
        "source_path": "/Users/pei/Downloads/季度报告.pdf",
        "stored_path": "~/.aigent/projects/default/.attachments/Kx7mQ2vT8p/att_7f3k9q2m1x.pdf",
        "text_chars": 18422, "text_truncated": false, "pages": 12,
        "images": 5, "tables": 3, "converter": "pymupdf",
        "warnings": ["第 3、7 页无文本层，已按图像发送"], "missing": false } }
  ]
}
```

无附件时 `content` 仍是**纯字符串**（与改造前逐字节一致），这条是零行为变化的硬保证。**纯附件消息**（正文为空）不产生 `text` 块，`content` 只有附件块。

**`content` 块为什么能穿过读写**：`session_manage._message_to_json_row` 对 user 行的 `content` **原样透传**，`load_session_history` 也是；但它**会丢弃未知的兄弟字段**（只保留 `role/content/created_at`）。所以附件元数据**只能放 content 块内**，不能放消息的兄弟字段 —— 放了会在重新加载时静默消失。

**协议字段**：

```ts
// 前端 → 后端
{ kind: 'attachment_stage', payload: { paths: string[], project_id?: string } }
// 后端 → 前端（点对点应答请求连接）
{ kind: 'attachments_staged', payload: {
    items:  [{ att_id, kind, name, mime, ext, size, source_path, project_id,
               text_chars, text_truncated, pages,
               images, tables, converter, warnings }],
    failed: [{ path, reason }],        // 逐条失败原因，单条失败不影响整批
    project_id: string } }
// chat 扩展
ChatPayload.attachments?: ChatAttachmentInput[]   // {att_id,kind,name,mime?,ext,size?,project_id?}
// session_history 扩展
HistoryMessage.attachments?: AttachmentRef[]      // {id,kind,name,mime,ext,size,source_path,stored_path,missing?}
```

`images` / `tables` / `converter` / `warnings` 是**解析统计与"诚实失败"通道**：`images` = 随附的页图资产个数、`tables` = `find_tables` 命中数（无框线表格会漏，故只作下界）、`converter` 记录走的哪条转换路径（`pymupdf` / `fallback_text`）。旧附件记录的 `meta.json` 没有这些字段，`public_item` 一律取默认值，**存量附件零迁移**。

`isKnownAgentEvent` 白名单**不加**（附件不走流式事件线，避免污染前后端版本兼容白名单）。

### 2.5 发送边界的展开与降级矩阵

`Agent._model_messages()` 是账本 → 线格式的**唯一转换点**（也是本次对引擎层的两处授权改动之一）。

| 情况 | 输出 |
|---|---|
| 图片 + 文件在 | `image_url` + `data:` URL（有 `<att_id>.send.jpg` 时优先用它 —— 缩放副本更省请求体） |
| 图片 + **模型不支持图片** | 文本块 `[图片: x.png]（未发送：当前模型不支持图片输入，请切换到带「图片」能力的模型）` |
| 图片 + 文件缺失 | 文本块 `[图片缺失: x.png]（原文件已被移动或删除）` + 告警日志 |
| 图片超过内联上限（默认 15MB） | 文本块 `[图片: x.png]（图片过大未能发送：xxx MB）` |
| 文档 + 正文在（**未截断**） | **首个文本块**：`[附件: x.pdf]（共 12 页，含 5 张图片，已随附）\n（以下就是该文件的完整正文，已随消息一并给出；无需再在磁盘或工作空间中查找、读取这个文件）\n<正文>` |
| 文档 + `.txt` 缺但原件在 | 现场重抽取一次 |
| 文档 + 有页图 | 正文里 `<!--img:pN-->` 锚点处**插入图片块**（带 `detail`），位置就是它该在的位置 |
| 页图 + 模型不支持图片 | 该锚点位置降级为占位文本块（**位置保留**，模型知道自己漏看了哪张） |
| 页图资产文件缺失 | 占位文本块 `[图片 pN 缺失：资产文件未找到]` |
| 页图超过内联上限 | 占位文本块 `[图片 pN 未能发送：{size}，超过内联上限]` |
| 文档正文为空 | 占位串 `（未提取到文本：…）`（pdf/docx/xlsx/pptx **一律有**）+ `warnings` |
| 文档 + 内容被截断 | 头部追加 `（下方仅为节选，完整原件路径见本条附件文本末尾）`；末尾追加**如实说明**（见下） |
| 附件块格式异常 | **原样透传，不抛** |
| 单个附件展开抛异常 | 收束为 `[附件读取失败: name]`，**绝不向上抛** |

> **绝不抛异常**是硬契约：异常穿透到 `agent_loop` 会让本轮剩余 tool_calls 的 tool_result 全部缺失、整轮被打死。

**截断时的末尾说明（不得写成"可用工具继续读取"）**：附件目录**恒**在 `~/.aigent/projects/<id>/.attachments/` 下 —— **工作空间之外**，`safe_path()` 的 `is_relative_to(base)` 一律拒绝，`run_read` / `run_read_pdf` 必然失败。所以尾部写的是事实：

```
…（以上为节选，完整原件位于 {原文件绝对路径}。该路径在本会话工作空间之外，
run_read / run_read_pdf 会被沙箱拒绝；需要完整内容时，可先用 bash 把它复制到工作空间内再读）
```

**未截断时不给路径**：给一个读不到的路径只会把模型引向一次必然失败的尝试，再产出一句"读不到"，对用户是纯粹的噪声。未截断的头部声明"正文已完整给出、无需再找磁盘"，才是让模型别再 `glob`/`find` 的正确做法。

**文本上限**：单文档截断到 `ATTACHMENT_TEXT_MAX_CHARS`（30000，与 `run_read_pdf` 同口径）；一条消息内所有附件正文合计不超过 `ATTACHMENT_TEXT_TOTAL_MAX_CHARS`（60000），超了按 `_fit_total` 收紧并置 `total_truncated`。

**展开结果缓存**：`_EXPAND_CACHE`（LRU 24 项）按 `(路径, mtime_ns, size, mime)` 键控。一轮对话里 `_model_messages()` 会被调用多次（每次 LLM 往返一次），没有缓存就会反复读盘 + base64 同一张图；文件被替换即键变、自动失效。

### 2.6 图片能力门控（两层，职责不同，不可互相替代）

| 层 | 位置 | 职责 |
|---|---|---|
| 预检 | `ws_bridge`，chat 分发前 | **迁移之前**就报错 —— 否则草稿已搬到会话目录却没人引用，只能等 GC，白占磁盘 |
| 兜底 | `Agent._model_messages()` | 覆盖全部路径（会话中途换模型 / 历史回放 / 未来新入口），保证"模型看不到的图"一定变成占位 |

判据是三态，且**引擎与桥层共用同一个纯函数** `llm_config.caps_allow_image`（各自保留自己的 `get_model_by_id` 调用点，因为 ws_bridge 的测试在该名字上打桩）；前端 `llmShared.hasImageInput` 同口径：

- 明确声明 `input` 含 `image` → 发图；
- 明确声明了 `input` 列表但不含 `image` → 降级为占位，**绝不静默丢弃**；
- 元数据缺失 / 形状不认识 → **按支持处理**。本地目录可能没收录用户新加的模型，不能因为"我们不知道"就本地误拦 —— 宁可让 provider 回一个真实错误，也不要静默吞掉图片。

**无附件时短路**：`_model_messages` 先用 `history_has_attachments()` 扫一遍，没有附件块就根本不查能力。所以"无附件请求体逐字节等价"由**结构**保证，而不是靠"新增代码恰好没副作用"。

**能力目录的新鲜度**：`capability_source == "auto"` 的模型能力**每次从预置目录重新推导**（若改成"存了就优先用存的"，`providers.json`「可随官方整体更新」的设计立刻失效）；修正既有模型的**内置声明时必须提升 `CATALOG_VERSION`**（`_merge_provider` 是「文件为准」，不加版本闸门，旧 `providers.json` 会把内置修正永久压住，且自愈回写也会失效）。

### 2.7 文档解析：统一转换层与降级链

为每种格式各写一套"正则式"文本抽取，注定追不上版式复杂度：表格被打散成单词、图表整块丢失、扫描件抽到空。**这不是实现缺陷，是架构选型问题。**

两家官方对 PDF 的做法一致，且**都不是"逐格式写抽取器"**：

| | 处理方式 |
|---|---|
| **Anthropic** | PDF 走 `document` 内容块直传。官方描述：**每页转成图像，同时抽该页文本，两者一起进模型上下文**。上限 32MB / 600 页；非 PDF 格式 `document` 块不支持 |
| **OpenAI** | `input_file` 按类型分派：PDF **同时提取文本与页面图像**；非 PDF 文档**仅提取文本**；表格类走专用增强流程。官方明确建议：**要保住非 PDF 的图表精度，请先把文件转成 PDF** |

两家的公共前置都是**"每页渲染成图"**，本层的做法与之一致：

```
PDF
     │
     ▼
doc_convert.convert_pdf()        ← 叶子模块：标准库 + 懒加载 pymupdf
     │  每页: "--- 第 N 页 ---" + 文本层 + 渲染页图(按需) + <!--img:pN-->
     ▼
<att_id>.pages/p1.jpg …          ← 页图资产（锚点 id 就是文件名去后缀）
<att_id>.txt                     ← 正文（含锚点）
     │
     ▼
_document_blocks()               ← 按锚点把正文切成交错的文本块/图片块
```

契约（`convert_pdf(src, out_dir, att_id, *, max_edge, max_pages, max_images, min_text)`）：

```python
{ "markdown": str,   # 每页 `--- 第 N 页 ---` + 文本层 + `<!--img:pN-->` 锚点
  "pages": int,      # 原文档总页数
  "images": [{"id","page","path","width","height"}],
  "tables": int,     # find_tables 命中数（无框线表格会漏）
  "converter": "pymupdf",
  "warnings": [str] }
```

**哪些页才渲染**（`_needs_page_image`）—— 判据是"文本层是否足以代表这一页"：

| 信号 | 渲染？ | 理由 |
|---|---|---|
| 页面完全没有文本，但有位图 / 表格 / **矢量绘制** | ✅ | 扫描件、图片页、纯矢量示意图 |
| 页面完全没有文本，且三者都没有 | ❌ | 真空白页，不浪费一张图的额度 |
| 文本层短于 `ATTACHMENT_DOC_PAGE_IMAGE_MIN_TEXT`(200) | ✅ | 大概率是扫描件或图为主的一页 |
| 文本层够密，但有内嵌位图 | ✅ | 有图表/照片 |
| 文本层够密，但 `find_tables` 命中 | ✅ | 表格的行列关系正是文本层会丢掉的 |
| 文本层够密，无图无表 | ❌ | 页图提供不了额外信息 |

> 给纯文本 PDF 的每一页都渲染图是浪费：20 张图 ≈ 19 MiB 请求体（实测），而文本层已经完整。所以**默认不渲染**，只在文本层不足时才渲染。`max_pages` 只约束**页图数量**，**文本层永远是全量** —— 文本是检索与无视觉模型兜底的主通道，不该被图像预算砍掉。

**成本口径**（DeepSeek，2026-09 实测）：服务端会把每张图自动缩到约 1300×1300 像素量级，**单图 token 封顶 1024** —— 所以图像 token 不是风险，真正的约束是**请求体**（内联图 48 MiB）。本层的 `max_edge` 缩放不省 token（服务端已封顶），意义是省请求体与上传耗时。

实测数字：

| 样本 | 解析耗时 | 页图数 | 请求体 |
|---|---|---|---|
| 单页扫描件（5625×3754pt，662KB） | 0.33s | 1 | 171 KB |
| 24 页扫描件（6.2MB，噪点页） | 1.70s | 20（`max_pages` 生效） | 19.25 MiB（内联上限 48 MiB，余量 60%） |
| 自造 4 页混合（密集文本/位图交替） | — | 2（只渲位图页） | — |

**降级链**（`attachments._convert_document` 编排，**最差情况等于只有文本抽取，零回归**）：

```
document 登记
   ├─ .pdf  → doc_convert.convert_pdf()          converter = "pymupdf"
   │            └─ 库缺失 / 文件损坏 → 抛异常 → 回落 ↓
   └─ .docx / .xlsx / .pptx  → extract_text()    converter = "fallback_text"
```

> 注意：**docx/xlsx/pptx 目前只走文本抽取**，`converter` 记为 `fallback_text`（Office 的整页视觉版式需要 LibreOffice 渲染，见 §四）。

**已知缺口**（明确记录，未做）：

- **office 格式的整页视觉版式**不还原 —— docx/pptx 只抽"保序文本 + 表格"，没有栏位/排版/图文相对位置。渲染它们需要 LibreOffice（约 800MB 外部二进制），与本项目 §四 的既有决策冲突，**已明确不做**；
- **大画布 PDF 的细节**：服务端无论如何会把图缩到约 1300×1300 像素量级，本地缩边救不回细节。唯一机制是区域切片（每块独立成图、各自拿到封顶预算），**待实测后再判断是否值得做**；
- **无框线表格**：`find_tables` 对靠位置对齐的表格命中 0（实测）。表格的视觉真相在页图里，`meta.tables` 只是下界，**不写进给模型的头部说明**（说一个偏小的数字会让模型以为表格已尽收眼底）。

### 2.8 缩略图：`aigent-att://` 自定义协议

渲染层拿不到 `file://`（contextIsolation + CSP），因此主进程注册 `aigent-att://` 协议：

```
<img src="aigent-att://local/?pid=<工作空间>&id=<att_id>">
```

**按 (空间, att_id) 寻址，而不是按文件路径** —— 附件在发送时会从 `_draft/` 迁到 `<session_id>/`，路径会变；按 id 检索由主进程负责，缩略图因此跨越迁移稳定（否则"刚发出去的图片缩略图瞬间 404"）。

主进程侧三层安全校验（缺一不可）：
1. **形状白名单**：`pid` 匹配 `^(default|ws[0-9A-Za-z]{10})$`、`att_id` 匹配 `^att_[0-9A-Za-z]{6,32}$` —— 只接受固定形状，根本不存在 `..` 或分隔符注入的空间（不是"过滤 `..`"）；
2. `readdirSync` 只在我们自己拼出的目录里找 `<att_id>.*`（跳过 `.meta.json` / `.send.jpg`）；
3. **符号链接解引后复检**路径仍含 `.attachments` 段 —— `.attachments` 是用户可直接写的目录，放一个指向 `/etc/passwd` 的软链就能让第 1、2 层形同虚设。

`registerSchemesAsPrivileged`（`standard: true, secure: true, supportFetchAPI: true, stream: true`）必须在 **app ready 之前**调用；CSP 相应放行：`img-src 'self' data: aigent-att:`（`renderer/index.html`）。非法路径一律 404，前端 `AttachmentBar` 的 `onError` 就地降级为图标占位（不留破图）。

### 2.9 chip 四态与显示规则

**核心原则**：在**发送之前**让用户知道将要付出什么、以及会丢失什么。解析统计（`pages` / `images` / `tables` / `warnings`）经 `build_user_content` → jsonl → `harvest_attachments` 一路带到回放，所以**发送前的 chip 与历史气泡显示同一套文案**。

四态（`DraftAttachment.status` / `AttachmentView.status`，两处联合类型必须同步改）：

| 状态 | 触发 | 外观 | 副标题 |
|---|---|---|---|
| `staging` | 已提交等后端回包 | 虚线灰、时钟图标 | `读取中…` |
| `ready` | 解析完成、无 warning | 常态 | `2.1MB · 12 页 · 5 图 · 3 表` |
| `degraded` | 后端给了任何 `warnings` | **琥珀**边框（`--color-warn: #c8860d`）+ 名字/副标题琥珀 | 有交付 → 照常显示统计；没交付 → `未能完整解析` |
| `failed` | 文件被拒 / 归位时发现文件已不在 | **红色**边框（`--color-danger`） | 拒绝原因（自由文本）/ `文件已缺失` |

副标题口径（`AttachmentBar.attachmentMeta`，草稿与消息**共用同一函数** —— 这是"发送前看到的"与"回放看到的"一致的保证）：

```
图片        → 482.4KB · 图片
文档         → 2.1MB · 12 页 · 5 图 · 3 表        （有 pages 用页数，否则用"已提取 N 字"）
什么都没交付  → 2.1MB · 未能完整解析                （唯一会顶掉统计的文案）
staging     → 读取中…
```

**降级 ≠ 什么都没交付**，两者必须分开：

- 「第 N 页无文本层，**已按图像发送**」—— 内容通过页图**交付了**，副标题照常显示 `12 页 · 12 图`；
- 「**未提取到文本**」且没有图片随附 —— 真的什么都没给到模型 → 副标题换成 `未能完整解析`。

判据是 `nothingDelivered()`：`warnings` 里含后端字面量 `未提取到文本` **且** `images === 0`。用**精确相等**而不是子串匹配 —— 子串会把"某些页无文本层，已按图像发送"误判成未交付。这个字面量与 `agents/attachments.py` 里那一处**逐字对应**，改后端文案必须同步改前端常量（见 §3.2）。

**完整原因放 tooltip**：warning 可能很长（`第 1、2、3、4、5 页无文本层 等 24 页，已按图像发送`），塞进单行副标题只会被省略号吃掉。副标题只放一句短提示（`.att-meta` 单行省略），tooltip 里给出全部 warning + 解析方式（`converter`）+ 原始路径。

**可发送性**：`degraded` 与 `ready` 同等可发送 —— 解析不完整不等于不能用。只有 `failed` 与仍在 `staging` 的才拦住发送（`canSend` 还要求 `stagingCount === 0`，避免半成品发出去）。

**这个判据只允许有一处**：`agentStore.isSendableAttachment()`。InputBox（按钮可用性）与 ChatPanel（**真正构造 payload**）必须调同一个函数 —— 各写一遍就会在加 `degraded` 之后只改一处，于是附件被**静默**从 payload 里丢掉（后端日志只留一行 `chat 派发 … attachments=0`，前后端都不报错）。这正是本项目要消灭的"附件没到模型手里、却没有任何提示"。

### 2.10 与其他机制的接缝

| 机制 | 处理 |
|---|---|
| L1 裁剪（`snip_compact`） | **保住全部带附件的消息**（`context_compact._has_attachment_block`）。图片在 token 估算里只折算成 `[图片: name]` 约 5 个字符，**看起来是最廉价的裁剪对象，实际是最贵的东西** —— 裁掉它模型就再也看不到那份附件，而图片无法靠"用工具再读一次"补回来。附件消息被摘出放在占位之后、尾部之前，占位里的条数只统计真正被裁掉的 |
| L4 摘要 / token 估算 | `content_to_str` 把附件块 → `[图片: x.png]` / `[附件: x.pdf]`，线格式图片块 → `[图片]`。**绝不把块序列化进结果**（base64 会污染摘要与估算） |
| 钩子与日志 | `run_turn` 形参放宽为 `str \| list`；钩子契约是"用户原始输入字符串"，带附件时改取 `attachments.text_view()`（`[图片: x]` + 正文） |
| 首轮标题 | 纯附件消息（正文为空）用 `_attachment_title_hint` 兜底 `[附件] 文件名`，否则首轮无标题 |
| 发送守卫 | `main/index.ts` 的 `agent:send` 必须放行为 `(!payload?.text && !payload?.attachments?.length)` —— 只有附件不打字是合法发送 |
| `chat.payload.text` | **恒为字符串**。多模态数组只在 `ws_bridge` 内部组装（标题生成 `re.sub`、首轮判定、日志切片全依赖这个前提） |

### 3.2 关键实现要点（勿回退）

1. **`main/index.ts` 的发送守卫必须保持放宽**（`(!payload?.text && !payload?.attachments?.length)`）—— 只判 `text` 会把"只发了图片没打字"的消息**静默丢掉**。
2. **`chat.payload.text` 永远是字符串**。多模态数组只在 `ws_bridge` 内部组装。
3. **拖拽必须用 `webUtils.getPathForFile`**（Electron 32+ 已移除 `File.path`），且**只能在 preload 内调用**（DOM `File` 无法过 IPC）。取不到路径的图片走 `saveClipboardImage` 的**字节**通路：ArrayBuffer/Uint8Array 是 IPC 可结构化克隆的类型。
4. **拖拽遮罩必须 `pointer-events: none`**：遮罩覆盖整个输入框，若参与命中测试会盖住输入框与发送按钮（实测命中元素会从 `TEXTAREA.composer-input` 变成遮罩内部的 `SPAN`）。
5. **`ChatPanel` 的全局 `dragover`/`drop` preventDefault 不能删**：否则拖到输入框以外的区域会让 Electron 把窗口导航成 `file://` 页面（白屏事故）。
6. **粘贴只在确实取到文件时才 `preventDefault`**：否则会把纯文本粘贴吃掉。
7. **缩略图 URL 必须按 `(pid, att_id)` 寻址**，不能存路径（迁移后失效）。
8. **图片的能力校验是两层，缺一不可**：`ws_bridge` 的预检必须留在**迁移之前**（否则草稿已搬到会话目录却没人引用，只能等 GC 白占磁盘）；`Agent._model_messages()` 的兜底也必须有（预检只扫当轮新附件，换模型 / 回放 / 新入口全绕过）。判据共用 `llm_config.caps_allow_image`，不要在两处各写一份三态。
9. **`capability_source == "auto"` 的模型能力必须每次从预置目录重新推导**；**修正既有模型的内置声明时必须提升 `CATALOG_VERSION`** —— 否则官方改能力声明，既有安装永远收不到。
10. **页图资产必须跟着附件一起迁移**：`_move_dir_contents` **不能跳过目录**（跳过会让 `<att_id>.pages/` 留在草稿区、展开发不出图）。同名覆盖时目录要 `rmtree` 而不是 `unlink`（后者对目录抛 `IsADirectoryError`）。
11. **锚点 id 必须等于资产文件名去后缀**（`<!--img:p1-->` ↔ `p1.jpg`）。这条约定让展开侧**不依赖 meta** —— meta 丢了、附件从别处拷来，只要目录在就能按位置恢复。
12. **只有我们自己生成的页图带 `detail`**，用户上传的图片一概不带（`prepare_image` 已定过尺寸；多一个字段只会给不认识它的兼容端点制造 400 风险）。
13. **发送的图片 MIME 以磁盘上那个文件为准**（`_image_mime`）：有 `<att_id>.send.jpg` 时发的是 JPEG，而元数据里的 mime 仍是原图的 —— 先取原 mime 会把 JPEG 字节标成 PNG。
14. **抽空必须留痕**：`text_chars > 0` **从来不是"解析成功"的证据**。四种文档格式抽空时一律写入占位串（公共前缀 `EMPTY_NOTE_PREFIX`，由 `attachments.text_is_empty_note()` 判定）并落 `warnings: ["未提取到文本"]`。附带口径：**工作表标题 / 幻灯片页码不算内容**（否则一个只有空表的工作簿会抽出 `--- 工作表: Sheet1 ---`，看着"有内容"实则什么都没读到）。
15. **L1 裁剪必须保住带附件的消息**（`context_compact._has_attachment_block`），理由见 §2.10。
16. **`WARN_NO_TEXT` 是跨语言的字面量耦合**：`AttachmentBar.tsx` 的前端常量 `未提取到文本` 与 `agents/attachments.py` 里写入 `warnings` 的那一处**逐字对应**，用来区分"什么都没交付"与"已按图像发送"。改后端文案必须同步改前端常量（用**精确相等**匹配，子串匹配会误判扫描件）。
17. **附件的可发送判据只能有一处**（`agentStore.isSendableAttachment`）。InputBox 的按钮可用性与 ChatPanel 的 payload 构造必须调同一个函数。
18. **截断提示不得写成"可用工具继续读取"**：附件目录在沙箱之外，`run_read` / `run_read_pdf` 必然被拒。未截断时**不给路径**（给了等于引模型去撞一次必然失败的尝试）。

### 3.3 可调参数（`~/.aigent/config.json` / 环境变量）

## 四、取舍与备选

| 决策 | 选了 | 否掉 | 理由 |
|---|---|---|---|
| 存储 | 复制进会话目录 | 只引用原路径 | 原文件一动历史就永久失效、无法自愈 |
| 传输 | 只传路径（后端同机读盘） | WS/IPC 传文件字节 | `websockets` 默认帧上限 1 MiB，base64 图片必然超限；同机进程没有传字节的必要 |
| 磁盘表示 | 中性引用块 | 直接存 `image_url` + base64 | 见 §1.2 四条理由 |
| 展开时机 | 发送边界现算 | 落盘时展开 | 一次落盘多次请求，展开结果不该污染历史 |
| 缩略图寻址 | `(pid, att_id)` 检索 | 存绝对路径进 URL | 草稿 → 会话目录迁移会换路径 |
| 图片发送 | 优先用缩放副本 | 一律发原图 | 省请求体；原图仍保留供查看 |
| 文档转图 | 只渲染"文本层不足以代表"的页 | 每页都渲染 | 纯文本 PDF 20 张图 ≈ 19 MiB 请求体，而文本层已完整 |
| office 整页版式 | 不做（只抽保序文本 + 表格） | 引 LibreOffice 渲染 | 约 800MB 外部二进制，跨平台失败态复杂 |
| text-only 模型发图 | 拦住并提示切换 | 后端静默丢弃图片 | 静默丢内容比报错更糟；未知模型一律放过（本地目录可能没收录） |
| 老格式 Office | 拒绝 + 提示另存 | 依赖 LibreOffice 转换 | 同上 |
| 扫描件 OCR | 渲染成页图交给视觉模型 | 本地 OCR | 本地 OCR 反而丢掉版式与图表；页图路线不需要新依赖 |
| 工作空间外的附件原件读取 | **不放开沙箱**，靠内容注入 | 给附件路径开只读旁路 | 附件 = **存储方式**；上传的语义是把**内容（正文 / 像素）交给会话**，会话引用的是**已注入的内容**而非磁盘路径。为"再读一遍读过的内容"去动引擎层 `tools.py` 不划算（唯一真需要原件的场景是超长截断，尾部提示已写清绕法） |
