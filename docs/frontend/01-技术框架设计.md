# 01 - 整体技术框架设计

本仓库后端是 **Python 实现的 Agent**（OpenAI SDK 流式改造版），只提供命令行交互。本设计要把它的能力包装成 **桌面应用 UI 壳**。前端遵循一个铁律：

> **前端只负责"渲染 + 交互 + 转发"，所有智能体逻辑 / 工具执行 / 流式生成都在 Python 后端。后端为零改动原则（只新增一个挂载** **`WSSink`** **的 WS 桥）。**

后端私有的业务（会话、目标、待办、技能、工具、token 统计）全部通过协议暴露给前端，前端绝不重复实现。

***

## 1. 前置概念：你必须先搞懂的三个词

对完全不熟悉 TS / Electron 的读者，先建立心智模型，细节后续章节展开。

### 1.1 Electron = 浏览器 + Node 的桌面外壳

Electron 把"一个网页"打包进一个桌面窗口。一次运行包含两类进程：

```
┌─────────────────────────────────────────────────────────────┐
│ 主进程 (Main Process, Node 环境)                              │
│   - 创建窗口、管理应用生命周期、访问操作系统能力                 │
│   - 拉起/管理 Python 子进程、维护 WebSocket 服务               │
├─────────────────────────────────────────────────────────────┤
│   │ 通过 IPC（进程间通信）通信                                 │
│   ▼                                                          │
│ 渲染进程 (Renderer, 浏览器环境 — 就是我们的 React UI)          │
│   - 真正的界面：侧边栏、聊天面板、输入框                        │
│   - 不能直接访问 Node API（出于安全），只能经 preload 桥梁       │
└─────────────────────────────────────────────────────────────┘
```

- **渲染进程** = 我们平时写的前端页面（HTML/CSS/React）。

- **主进程** = 一个能跑 Node 的后台，负责"和孩子（Python）说话"、支持系统能力。

- **preload 脚本** = 渲染进程与主进程之间唯一的"合规通道"（通过 `contextBridge` 暴露白名单 API）。

### 1.2 TypeScript = 给 JavaScript 加类型

JS 里的 bug 大多来自"猜变量是什么"，TS 在编译期就帮你把类型定死。例如：

```ts
// TS 能立刻报错：名字参数必须是 string
function send(userQuery: string): void { ... }
send(123);  // 编译报错
```

编码时你写的是 TS，构建时它被编译成普通 JS 交给 Electron。

### 1.3 React = 用组件拼界面，数据驱动视图

React 的核心是**声明式**：你描述"界面在某种状态下长什么样"，数据一变，界面自动对应更新。

```tsx
// 一个组件：接收 props，返回界面
function Message({ text }: { text: string }) {
  return <div className="message">{text}</div>;
}
```

流式消息正好适合 React——后端每来一个 `content_delta`，我们把它追加进状态，界面自动逐字刷新。

## 2. 技术选型

| 层面           | 选择                                           | 理由                                  |
| ------------ | -------------------------------------------- | ----------------------------------- |
| 桌面壳          | **Electron**                                 | 指定框架，生态成熟                           |
| 语言           | **TypeScript**                               | 指定；类型安全，利于大型界面                      |
| UI 库         | **React** (函数组件 + Hooks)                     | 组件化、数据驱动，最贴合流式渲染                    |
| 构建/打包        | **Vite + electron-vite**                     | 热更新快（边改边看），简化 Electron 主/预加载/渲染三端构建 |
| 样式           | **CSS Modules** 或原生 CSS 变量                   | 轻量、无需引入重型 UI 框架（Tailwind 可选，但本项目求轻） |
| 状态管理         | **Zustand**（或 React Context）                 | 少量全局状态：当前会话、连接状态、消息列表；用轻量方案         |
| 通信(渲染↔主)     | **contextBridge + ipcRenderer**（Electron 原生） | 主进程与渲染进程安全交互                        |
| 通信(主↔Python) | **WebSocket**（python 侧 `websockets` 库）       | 复用后端已就绪的 `WSSink`；天然支持后端流式推送        |
| 前端 WS 客户端    | **原生 WebSocket**（浏览器内置）                      | 无需额外依赖                              |

> **为什么让 Electron 主进程去连 Python 的 WebSocket，而不是渲染进程直接连？**
> 因为 WebSocket 是"Node 层"的事，且未来可能要处理鉴权、重连、把 Python 跑在哪儿（本机/远程）。
> 渲染进程保持纯净，只经 `ipcRenderer` 与主进程通信。

## 5. 前后端边界（谁做什么）

| 职责                         | 归属      | 说明                               |
| -------------------------- | ------- | -------------------------------- |
| 界面渲染、交互、快捷键                | 前端      | 侧边栏/聊天/输入框                       |
| 拉起并管理 Python 进程            | 前端(主进程) | spawn、崩溃重启、退出清理                  |
| 发起一次对话                     | 前端→后端   | 前端把用户输入通过 WS 发`chat`指令           |
| 流式文本生成                     | 后端      | 产出 thinking/content 增量，经 WS 推给前端 |
| 工具执行 / 子智能体 / 会话 / 目标 / 待办 | 后端      | 前端只接收事件，不做任何推理                   |
| 事件→视图映射                    | 前端      | 把 `content_delta` 拼成完整消息流展示      |

### 启动顺序与启动画面（方案B：先建窗 + 遮罩）

启动时序遵循「**先建窗显示界面 + 启动画面遮罩**」，后端冷启动期间由遮罩覆盖主界面，
避免直接暴露"连接中"状态条：

```
app.whenReady() → createWindow() → python.start() → ws.connect()
```

- 顺序与最初一致（窗口立即出现）；窗口加载后渲染进程的 `StartupOverlay`（`frontend/src/renderer/src/components/common/StartupOverlay.tsx`）
  以全屏遮罩覆盖主界面，显示品牌字 + 旋转指示器 + "正在启动后端…"。

- 遮罩依据 `agentStore.connection` 控制：`connected`（或 python `crashed`，避免永久遮挡）后淡出
  并卸载，露出主界面与底部状态栏。此时状态栏直接"已连接"，不再出现"连接中"闪烁。

- 交互/连接状态事件见 `02-界面功能设计.md` / `03-前后端通信协议.md`。

- 演进备注：曾尝试方案A（后端就绪再建窗 `await python.whenReady()`），实测窗口延迟 \~3s 出现、
  体验不佳，已回退；最终采用方案B。`PythonManager` 的 stdout 就绪探测仍保留（驱动 python 状态）。

### 5.1 后端 Agent 的定位与 system prompt 分层

**定位：通用型 AI 助手，不是编程专用**。大模型本身是通用的，助手也应该通用 —— 给定一个
**工作空间**（`WORKDIR`），写作 / 科研 / 编码 / 数据分析 / 资料整理都要能做。因此 identity 段
**不预设任务类型**，只给「先判断任务性质，再决定方法」的元规则与操作边界：

- 工作空间是文件操作边界（读写 / 检索 / 执行命令都在其中）；

- 内部动作（读文件、检索、整理、分析）放手做，外部动作（发邮件、发布内容、推送代码）先确认；

- 关键信息不足时先问清楚，不要凭猜测长时间执行；

- 如实汇报（没做成的、跳过的、有风险的都要说）。

子智能体同样是通用定位（`agents/subagent.py` 的 `DEFAULT_SYSTEM_PROMPT`）。

**system prompt 按「变化频率」分层**（不是按重要性）。原因：本链路是 OpenAI SDK +
OpenAI 兼容端点，走**自动前缀缓存**（按最长公共前缀**逐字节**命中，**没有** `cache_control`
参数），未命中代价 ≈ 前缀长度 × 变化频率：

| 层         | 位置                          | 内容                                                                                                  | 变化来源                               |
| --------- | --------------------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------- |
| **L0 冻结** | system prompt 前部            | 身份与工作方式、回复输出格式、上下文保护规则；工具**使用策略**（**不枚举工具名**）；技能列表（名 + 一行描述）；记忆**机制说明**                             | 改代码 / 装删技能                         |
| **L1 冷**  | system prompt 末尾            | workspace 指令文件（`AGENTS.md` → `CLAUDE.md` → `AGENT.md`，**目录 =** **`WORKDIR`（用户的工作空间）**；多个并存则**都加载**） | 改指令文件                              |
| **L2 热**  | **不进 system prompt**，消息尾部追加 | 记忆索引（`<memory_index>`）；环境与上下文（`<env>`：日期 / 星期 / 平台）；工作区指令更新（`<project_rules>`，仅会话期间被改时）             | 记忆增删；跨天；换机器 resume；`AGENTS.md` 被编辑 |

L2 的触发规则与前端可见性见 `03-前后端通信协议.md` §2.1.2。核心收益：把易变内容移出消息
数组的 `[0]` 之后，L0/L1 在**同一工作空间**的所有会话间**逐字节相同**，可跨会话共享前缀缓存；
而尾部追加不改变前面任何字节，只有新增那一条未缓存（而它本来就是本轮的新内容）。

**L0 是「按工作空间恒定」而非「全局恒定」**：`## Worktree` 子段**仅在 workspace 是 git 仓库
（存在** **`.git`）时注入** —— worktree 是 git 专属能力，对写作 / 科研类工作空间纯属噪音；且它的
默认结论本就是「不用」，不注入也不损失能力（模型仍能从每轮下发的工具 schema 看到
`create_worktree`）。实测：本工作空间 prompt **3896 字符 / ≈2502 token**（设计部分约 2859 字符 +
workspace 指令约 1000 字符，取自 `WorkSpace/task1/` 下的 `CLAUDE.md` + `AGENT.md`）。

**⚠️ 指令文件来源是「工作空间」，不是「本仓库根」**：本仓库根的 `AGENTS.md` 是给**开发本项目的
编码助手**看的（改代码的约定），不属于终端用户的助手上下文 —— 曾误把仓库根 `AGENTS.md` 注入
（一度占 prompt 的 60%，8891 字符），已修正。两个判据支持这一结论：① 身份段明确"文件操作仅限
工作空间内"，仓库根的代码规范模型根本读不到；② `WorkSpace/task1/AGENT.md` 明确写着"应参考本文件
和 `CLAUDE.md` 中的 workspace 规则"，说明 workspace 里多文件并存是设计内行为。

**规则的「新鲜度」分两级处理**（详见 `03-前后端通信协议.md` §2.1.2）：

- **进会话时（方案 B）**：`init_session` / `switch_session` / `new_session` 都会用最新构建结果
  **替换** **`messages[0]`**。此前 resume 时 `load_session_history()` 读回的旧 system message 会覆盖掉
  重算结果（等于白算），所以"改了 `AGENTS.md` 当前会话看不到"——根因是**重算了但没替换**。
  只改内存、不写回会话文件，因此不触碰会话文件的原子重写（无需 `.bak`）。

- **会话期间（方案 C）**：检测到工作区指令文件变更 → 尾部追加 `<project_rules>` 全文，
  块内声明"以本条为准"。为什么不直接重建 system prompt —— 那会让**整段前缀（含全部历史）**
  失效重算，长会话下代价高得多；尾部追加只让新块未缓存，其余前缀照旧命中。

**L2 每次判定都现场取值**（不是会话创建时固化），所以跨天日期会自动更新、换机器 resume 时
平台会自动纠正；而当天内指纹不变 → 不重复注入、零开销。

**为什么 git 状态不进环境上下文**：它随每次 commit / 切分支就变，是缓存杀手（会频繁打断尾部
前缀）；真需要时让模型跑一条 `git status` 更划算。

## 6. 数据流：一次对话的完整流程

以用户在输入框敲一句话为例：

```
1. 用户在 InputBox 输入 → 点击发送
2. 渲染进程: store.dispatch('agent/send', text)
3. preload:   window.agent.send(text)   // contextBridge
4. 主进程:    ipc 'agent:send' → agentWS.send({type:'chat', text})
5. Python:    ws_bridge 收到 → agent.run_turn(text)
6. Python:    stream_sink(WS) 逐条 emit:
             thinking_delta / content_delta / tool_call_start / ... / turn_end
7. 主进程:    agentWS 收到事件 → 转发到渲染进程 (ipc 'agent:event')
8. 渲染进程:  useAgentStream 钩子把事件写进 agentStore
9. React:     MessageList 因状态更新自动重渲染，界面逐字刷新
```

> **浏览器预览回退**：dev 模式下渲染页可在普通浏览器直接打开（无 Electron preload）。
> 此时渲染层入口安装回退桥 `renderer/src/lib/browserAgent.ts`：实现与 preload 相同的
> `AgentApi`，但把命令按同一信封协议直连 `ws://127.0.0.1:8765` 发往后端 ws\_bridge
> （指数退避重连 + 断线排队补发）。Electron 内该桥自动跳过，走上图正常链路。
> 细节见 [03-前后端通信协议.md](03-前后端通信协议.md) §6.1。

## 7. 安全与合规（Electron 最佳实践）

- **渲染进程** **`contextIsolation: true`、`nodeIntegration: false`** —— 渲染层不接入 Node，防止注入。

- 只在 **preload** 用 `contextBridge` 暴露白名单方法（`send` / `onEvent` / `getState`）。

- 主进程对 IPC 通道做校验（来源必须是本窗口）。

- Python 进程端口绑定 `127.0.0.1`，不上公网。

***

## 8. 异常与状态

| 场景              | 处理                                     |
| --------------- | -------------------------------------- |
| Python 进程崩溃     | 主进程监听到退出 → 提示用户 → 可一键重启                |
| WS 断开           | 前端显示 `重新连接` 状态，自动重连，指数退避               |
| 发送中禁用重复发送       | InputBox 在响应期间禁用发送按钮，显示停止按钮            |
| 消息超长 / token 耗尽 | 后端已处理（finish\_reason）；前端展示 usage 与收尾状态 |
