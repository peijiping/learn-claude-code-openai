# 03 - 前后端通信协议（对接 WSSink）

本设计复用后端 `agents/streaming_client.py` 已就绪的 **JSON 行协议（`StreamEvent.to_json()`）**，
并在 Python 侧新增一个**薄桥层** **`ws_bridge.py`**（属"新增"，不改业务代码），把 WebSocket 客户端
（Electron 主进程）的命令翻译成 `Agent` 方法调用，再把流式事件经 `WSSink` 推回前端。

> 后端铁律：只新增 `ws_bridge.py` 这一个薄层，`agent_full_v2.py` 及以下**零改动**。
> 唯一替换点是 `Agent.stream_sink = WSSink(send_func=ws.send)`。

## 1. 双层消息模型

在同一 WebSocket 上，用 `kind` 区分两类消息：

| kind                    | 方向    | 说明                                            | 载荷字段                                                                                                             |
| ----------------------- | ----- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `event`                 | 后端→前端 | 流式事件（透传 `StreamEvent.to_dict()`，含所属会话号）       | `session_num` / `type/text/tool_*/finish_reason/usage`                                                           |
| `chat`                  | 前端→后端 | 向目标会话发起一轮对话                                   | `text` / `num?`（缺省=新建任务，后端惰性领号）/ `model_id?` / `overrides?`                                                      |
| `stop`                  | 前端→后端 | 停止指定会话正在执行的那一轮                                | `num`                                                                                                            |
| `session_status`        | 后端→前端 | 会话执行状态变更（运行/后台/完成/停止）                         | `num` / `status`（`running`/`background`/`done`/`stopped`）                                                        |
| `status_query`          | 前端→后端 | 拉取仍在运行会话的执行状态（重放 `session_status`，见 5.2）      | `—`                                                                                                              |
| `session`               | 后端→前端 | 激活会话变更通知（惰性新建/清空后）                            | `num` / `message_count`                                                                                          |
| `session_history`       | 后端→前端 | 会话历史回放（切换会话后）                                 | `num` / `messages[]`                                                                                             |
| `session_switch`        | 前端→后端 | 切换会话                                          | `num`                                                                                                            |
| `session_model`         | 前端→后端 | 持久化会话绑定模型与参数到会话元数据                            | `num` / `model_id?` / `overrides?`（按模型 id 的 UI 档位 map `{[model_id]: {thinking_strength?, max_context_option?}}`） |
| `session_clear`         | 前端→后端 | 清空会话                                          | `—`                                                                                                              |
| `sessions_list`         | 前端→后端 | 拉取会话列表                                        | `—`                                                                                                              |
| `sessions`              | 后端→前端 | 会话列表（列表拉取/会话变更后下发，含元数据）                       | `sessions[]`                                                                                                     |
| `session_rename`        | 前端→后端 | 重命名会话                                         | `num` / `title`                                                                                                  |
| `session_trash`         | 前端→后端 | 软删除会话（移入回收站）                                  | `num`                                                                                                            |
| `session_restore`       | 前端→后端 | 从回收站还原会话                                      | `num`                                                                                                            |
| `session_delete`        | 前端→后端 | 批量永久删除会话                                      | `nums[]`                                                                                                         |
| `trash_list`            | 前端→后端 | 拉取回收站列表                                       | `—`                                                                                                              |
| `sessions_trashed`      | 后端→前端 | 回收站列表（trash\_list 的响应）                        | `sessions[]`                                                                                                     |
| `session_delete_result` | 后端→前端 | 批量永久删除结果                                      | `deleted[]` / `failed[]`                                                                                         |
| `context_stats`         | 后端→前端 | 上下文使用量统计（每轮结束 / 切会话后推送）                       | `num` / `used_tokens` / `max_tokens` / `used_percent` / `max_label`                                              |
| `goal_status`           | 前端→后端 | 查询目标状态                                        | `—`                                                                                                              |
| `tasks`                 | 前端→后端 | 拉取待办看板文本                                      | `—`                                                                                                              |
| `skills`                | 前端→后端 | 拉取技能列表                                        | `—`                                                                                                              |
| `llm_config_get`        | 前端→后端 | 读取大模型配置（连接 + 扁平模型视图 + 预置厂商目录）                 | `—`                                                                                                              |
| `llm_config`            | 后端→前端 | 大模型配置响应（读 / 存通用）                              | `config`（v2：`{version, active_model_id, connections[], models[], providers, api_formats}`）/ `applied?` / `msg?`  |
| `llm_config_save`       | 前端→后端 | 保存大模型配置（落盘 → 重映射 env → 就地热切换）                 | `config`：`{active_model_id, connections[]}`（兼容 v1 扁平 `models[]`）                                                 |
| `llm_models_fetch`      | 前端→后端 | 「刷新」：调远端 `GET {base_url}{models_path}` 拉取模型列表 | `base_url?` / `api_key?`（留空回退已存连接密钥）/ `connection_id?` / `api_format?` / `models_path?`（默认 `/models`）            |
| `llm_models`            | 后端→前端 | 模型列表刷新结果                                      | `ok` / `models[{id}]` / `base_url?` / `error?`                                                                   |
| `pong` / `error`        | 双向    | 心跳 / 错误                                       | `msg`                                                                                                            |

> **惰性会话（重要语义变更）**：`session_new` 命令已移除。"新建任务"是**纯前端行为**
> （清空消息流、`activeSession=null`）；后端会话 `session_N.jsonl` 只在两种时机产生/加载：
>
> 1. 首条 `chat` 消息不带 `num`（新建任务/后端无激活会话）→ 事件循环内确定性领号，惰性新建；
> 2. 用户点击会话列表 → `session_switch` 加载既有会话。
>    后端启动（ws\_bridge 进程拉起）**不再**创建会话，避免"每次打开窗口都多一个空 jsonl"。

> 统一信封格式（JSON）：

```json
{ "kind": "chat",   "payload": { "text": "帮我分析 goal.py", "num": 3 } }
{ "kind": "stop",   "payload": { "num": 3 } }
{ "kind": "event",  "payload": { "session_num": 3, "type": "content_delta", "text": "…" } }
```

## 1.1 多会话并发与会话级事件路由（核心语义变更）

**目标**：所有会话可任意来回切换，正在执行/输出的会话继续输出不受影响；多个会话可同时执行，各自独立。

- **并发执行**：桥层维护 `SessionRuntimeRegistry`，**每个会话一个独立** **`SessionRuntime`**（持有独立 `Agent` 实例 + 各会话消息缓冲 + 独立停止信号）。`chat` 命令只派发不等待——后台线程跑该会话的 `run_turn`，事件循环立即继续处理其它命令（切换 / 其它会话 / stop），故切换不断流。

- **运行时 Agent 惰性构建**：`SessionRuntime.build_agent()` 对全新 `Agent` 实例直接调 `switch_session(num)` 加载历史，`Agent.switch_session` 内部对 `session_manager is None` 惰性构建（同 `init_session`），保证首轮 turn 不会因会话管理器未初始化而异常收尾（曾因缺失该兜底导致 turn 秒挂、前端假 `done`、绿点消失、无任何流式输出——切换会话后表现尤甚）。

- **事件路由**：每条流式 `event` 携带 `session_num`，前端据此把增量合并进**对应会话的消息缓冲**（`messagesBySession[num]`）。当前显示会话 = 缓冲 `messagesBySession[activeSession]` 的投影；后台会话增量各自累积，切过去即可看到最新输出。**子智能体（含后台子任务）的思考与工具事件也走该路由**（事件带 `subagent_id` 标识来源）：桥层为会话绑定 WSSink 时同步重绑 `subagent_runner.sinks`（否则子智能体沿用 Agent 构造期捕获的 PrintSink，事件只打印到后端 stdout，UI 无输出）。

- **会话状态事件**：每个会话的 `start_turn` 开始时桥层下发 `session_status: running`；结束时按终态**只发一条**：`stopped`（用户停止）/ `background`（turn 结束但该会话仍有后台任务（如后台子智能体）在执行）/ `done`（全部结束）。历史缺陷：结束路径曾先发 `done` 再发 `background`（两条之间隔着 `reply_sessions` 的磁盘 IO），前端运行指示会"消失又出现"闪烁，已改为单条终态。进入 `background` 后由桥层守望后台任务、全部完成后补发 `done`（期间新 turn 开始会取消守望，状态交回 `running`）。前端据此驱动：①侧边栏运行中青色脉冲点（`running` 与 `background` 都亮，后者 title 为"后台任务执行中"）；②会话彻底完成后当前显示的不是它 → 亮**绿色未读点**，切到该会话即清除；③**停止按钮仅在** **`running`** **时显示**（`stop` 只能停 turn，停不了后台任务）。

- **后台完成自动续轮（v2 语义增强）**：`background` 守望的后台任务全部完成后，若仍有**未消费的后台执行结果**（如后台子智能体刚跑完、`<task_notification>` 尚未注入主智能体上下文），桥层会自动发起一轮新的 turn（`Agent.run_background_followup()`，不伪造用户消息，由 `agent_loop` 起点预热注入通知），让主智能体拿到结果并给出最终总结——避免"子智能体跑完了、主智能体却停在『已派发后台任务，稍等片刻』的占位回复上，用户永远等不到最后总结"。状态序列表现为：`running`（原 turn）→ `background`（守望中）→ `running`（自动续轮的 turn）→ `done`。自动续轮设上限 `MAX_BG_FOLLOWUPS=10` 防"续轮又派后台 → 再续轮"的极端连环派发；用户中途点 `stop` 会终止后续自动续轮并回 `done`。

- **独立停止**：`stop` 只停 `num` 指定的会话正在执行的那一轮（通过该会话的事件置位，协作式收尾），其它会话不受影响。同会话并发 turn 会被拒绝（返回 `error`，避免两线程同写一个 jsonl）。

### 并发下的事件线

```json
{ "kind": "session_status", "payload": { "num": 3, "status": "running" } }
{ "kind": "event", "payload": { "session_num": 3, "type": "content_delta", "text": "后台会话 3 的输出" } }
{ "kind": "session_status", "payload": { "num": 3, "status": "done" } }
```

> 新建任务（`chat` 不带 `num`）时，后端在单线程事件循环内确定性领号，先回发 `session` 信封（`num`），前端据此把临时草稿缓冲迁移到正式会话缓冲；随后的流式事件即按该 `num` 路由。

## 2. 事件线协议（后端 → 前端）

前端按 WS 收到的每一行 JSON 解析，`kind == "event"` 时还原为 UI 动作。
事件类型与后端 `StreamEvent` 一一对应，**这是打字机回显的唯一数据来源**。

| type              | 含义          | 前端渲染                                   |
| ----------------- | ----------- | -------------------------------------- |
| `thinking_delta`  | 思考增量        | 追加到当前 assistant 消息的 thinking 区（灰）      |
| `content_delta`   | 正文增量        | 追加到 assistant 正文（打字机）                  |
| `tool_call_start` | 工具名出现，预测式展示 | 新建工具折叠条：`⚙ 名称(`                        |
| `tool_call_delta` | 参数增量        | 续写参数文本                                 |
| `tool_call`       | 工具调用聚合完成    | 闭合折叠条，标注状态                             |
| `turn_end`        | 回合结束        | 停止光标、显示 usage、解锁输入                     |
| `sub_agent_start` | 子智能体任务开始    | 新建子智能体折叠块（机器人头图标，`text` 为任务 prompt 预览）；`tool_id` = **发起该子任务的主工具调用 id**（唯一锚点，见下） |
| `sub_agent_end`   | 子智能体任务结束    | 收起块流式状态（停转圈 / 打完成勾）；`tool_id` 同上（锚点兜底）       |

**子智能体来源标识** **`subagent_id`**：所有 `StreamEvent` 序列化都携带该字段（空串 = 主智能体事件）。
子智能体把其思考与工具事件上行时，由 `subagent.py` 的 `FilterSink` 给事件打上本次子任务 id
（`sub_` 前缀），前端据此把事件折叠进对应子智能体块下，与主消息互不干扰。
**不转发** `content_delta`（子智能体的答复是给主智能体的结果，不进用户视野、也不进卡片，避免与主正文重复）与子智能体内部各轮的
`turn_end`（整个任务以 `sub_agent_end` 作为统一结束标志）。

**唯一锚点规则（实时与回放一致）**：子智能体卡片永远挂在**发起它的那条 assistant 消息**下。
`sub_agent_start` / `sub_agent_end` 的 `tool_id` 承载**发起该子任务的主智能体 tool_call_id**
（注意：这里不是子智能体内部工具的 id），前端据此定位宿主消息：
①该 `subagent_id` 的块已存在 → 沿用其所属消息（同一子智能体的后续 `thinking`/`tool_*` 事件不带该 id，只能靠这一步保证不被挂到别的消息上）；
②首次创建时按 `tool_id` 匹配宿主 assistant；③回退末尾 assistant；④兜底新建。
回放侧（2.1.1）按同一条规则从旁路记录挂载 → 切换会话前后卡片位置不跳变。

一个完整事件 JSON 示例（来自 `StreamEvent.to_dict`）：

```json
{
  "type": "content_delta",
  "text": "经分析，goal.py 的存储机制是…",
  "tool_id": "",
  "tool_name": "",
  "args": "",
  "finish_reason": "",
  "usage": {},
  "subagent_id": ""
}
```

子智能体工具事件示例（含来源标识与锚点 id）：

```json
{ "type": "sub_agent_start", "text": "请分析 ws_bridge.py 的依赖…", "tool_id": "call_7", "subagent_id": "sub_ab12cd34" }
{ "type": "thinking_delta", "text": "我先读取该文件…", "subagent_id": "sub_ab12cd34" }
{ "type": "tool_call_start", "tool_id": "call_1", "tool_name": "read_file", "args": "", "subagent_id": "sub_ab12cd34" }
{ "type": "tool_call_delta", "tool_id": "call_1", "args": "{\"path\":\"ws_", "subagent_id": "sub_ab12cd34" }
{ "type": "tool_call", "tool_id": "call_1", "tool_name": "read_file", "args": "{\"path\":\"ws_bridge.py\"}", "subagent_id": "sub_ab12cd34" }
{ "type": "sub_agent_end", "tool_id": "call_7", "subagent_id": "sub_ab12cd34" }
```

> 子智能体块内的 `tool_call_start` / `tool_call_delta` / `tool_call` 的 `tool_id` 是**子智能体内部工具**的 id，
> 前端按该 id 归位工具行（并行多个工具调用各自成行，不串台）。这与上面 `sub_agent_start` 的
> `tool_id`（发起方主工具调用 id）语义不同，按事件类型区分。

### 2.1 会话历史回放（`session_history`）

`session_switch` 成功后由桥层下发，前端整体替换消息流渲染。`messages[]` 为后端
session jsonl 历史经 `_history_to_ui()` 转换后的产物：

- **busy/后台会话跳过磁盘回放**：切换到正在执行的会话（turn `running` 或后台任务 `background`）时，桥层回放 `messages: []`（空），前端以实时缓冲为准（`session_history` 处理里的 `hasLive` 守卫：会话在 `runningSessions`/`bgSessions` 且缓冲非空则不覆盖）。原因：turn 在途时 jsonl 可能处于 "assistant(tool\_calls) 已落盘、tool 响应未落盘" 的中间态，此时读盘会触发孤儿清理并重写文件，截断在途消息（读-改-写竞争），故一律不读盘；后台任务产出的增量同理只存在于实时缓冲；

- 跳过 `system` / `tool` 消息（前者无展示价值，后者聚合进 assistant 工具条）；

- 跳过系统注入的 user 消息（`<system-reminder>` 开头的 todo reminder 等）。**判定条件就是
  `content.startswith("<system-reminder>")`** —— 新增同类注入时**必须**用
  `<system-reminder>…</system-reminder>` 包裹，否则会作为用户气泡漏到聊天界面。当前各注入的归属：

  | 注入 | 产生位置 | 包裹 | 前端可见性 |
  | --- | --- | --- | --- |
  | todo reminder | `agent_full_v2._inject_todo_reminder` | `<system-reminder>` | 不可见 |
  | 记忆索引 `<memory_index>` | `agent_full_v2._sync_memory_index` | `<system-reminder>` | 不可见 |
  | 环境上下文 `<env>` | `agent_full_v2._sync_environment` | `<system-reminder>` | 不可见 |
  | 工作区指令更新 `<project_rules>` | `agent_full_v2._sync_project_rules` | `<system-reminder>` | 不可见 |
  | 后台任务 `<task_notification>` | `background_manager.collect_background_results` | `<system-reminder>` | 不可见（2026-09-11 补齐包裹） |

- assistant 保留 `reasoning_content` → `thinking`、`tool_calls` → `toolCalls`（已完成态）；

- 子智能体执行记录（来自**旁路文件**，见 2.1.1）挂到**发起调用的 assistant 消息**的
  `subagents` 数组下：记录内带触发它的 `tool_call_id`（主消息 `tool_calls`
  中 `sub_agent` 调用的 id），后端据此精准挂载；找不到记录（compaction 后原归属
  被摘要替代 / 老数据无 `tool_call_id`）时回退到最近一条 assistant 消息，属可接受行为。
  另兼容 messages 中残留的旧 `role=subagent` 行（按 `subagent_id` 去重，旁路记录优先）。

- `content` 兼容 str 与多模态 blocks（list 时拼接 text 块）。

```json
{
  "kind": "session_history",
  "payload": {
    "num": 3,
    "model_id": "deepseek-v4",
    "overrides": {
      "deepseek-v4": { "thinking_strength": "very_high", "max_context_option": "extended" },
      "claude-sonnet": { "max_context_option": "extended" }
    },
    "messages": [
      { "role": "user", "content": "帮我分析 goal.py" },
      { "role": "assistant", "content": "…", "thinking": "…",
        "toolCalls": [{ "name": "run_bash", "args": "{\"cmd\":\"ls\"}" }] },
      { "role": "assistant", "content": "…", "thinking": "…",
        "toolCalls": [{ "name": "sub_agent", "args": "{}" }],
        "subagents": [
          { "id": "sub_ab12cd34", "name": "请分析 ws_bridge.py 的依赖…",
            "thinking": "我先读取该文件…",
            "status": "done", "durationMs": 159000, "error": "",
            "toolCalls": [{ "name": "read_file", "args": "{\"path\":\"ws_bridge.py\"}", "status": "done" }] }
        ] }
    ]
  }
}
```

> `model_id` 为该会话绑定的模型（来自元数据，可为 `null`/空）。`overrides` 为**按模型 id 分别保存**的参数覆盖 map（`{ [model_id]: {thinking_strength?, max_context_option?} }`）——每个模型独立存取，改动一个模型不串改其它模型。切换到该会话时前端据此恢复输入区的模型高亮，并按各模型恢复悬浮配置面板（`sessionModelId` / `overridesByModel`），同时记入 `lastSessionModelId` / `lastOverridesByModel` 供「新建会话继承」。

### 2.1.1 子智能体执行记录（旁路文件格式与持久化边界）

**为什么是独立文件**：子智能体执行过程**不再与标准消息共用 `session_N.jsonl`**，而是写到同目录的
旁路文件 **`session_N.subagents.jsonl`**（append-only，每行一条 JSON 记录）。原因：`role=subagent` 行混在主
jsonl 里时，`assistant(tool_calls) → subagent → tool` 这种 append 顺序会打断加载时的 tool 块连续性判定，
导致**整轮对话被自愈逻辑删除并重写文件（不可逆）**；且该行与上下文压缩、拼行修复、异常恢复互相耦合
（现状证据见 08 篇）。

**记录格式**（`v:1`）：

```json
{ "v": 1, "subagent_id": "sub_ab12cd34", "tool_call_id": "call_7", "session_num": 6,
  "name": "请分析 ws_bridge.py 的依赖…", "status": "running|done|error|aborted",
  "source": "sync|background|migrated", "prompt": "……",
  "started_at": "2026-09-11T09:31:02", "ended_at": "2026-09-11T09:33:41", "duration_ms": 159000,
  "thinking": "子智能体全部 thinking_delta 的拼接", "text": "子智能体返回给主智能体的摘要",
  "toolCalls": [ { "tool_id": "call_1", "name": "read_file", "args": "{\"path\":\"ws_bridge.py\"}", "status": "done" } ],
  "error": "" }
```

**读取规则**：按 `subagent_id` 分组**取每组最后一条**（后写覆盖先写）——「启动占位行 + 结束完整行」
天然合并为最终态；进程被强杀（只留下占位行）时状态为 `running`，卡片显示「执行中／已中断」。

- **写入（两段式）**：①子智能体启动 → 桥层在 `sub_agent_start` 事件处写 `status=running` 占位行
  （崩溃留痕 + 实时卡片立即可见）；②子智能体结束 → 写完整终态行
  （`session_manage.append_subagent_to_session` → `SubagentStore.append`）。
  `text` 字段记录子智能体返回给主智能体的摘要（**不在 UI 展示**，仅作记录完整性与排障用）。

- `tool_call_id`：触发该子智能体的主消息 `sub_agent` 工具调用 id，由
  `SubAgent.spawn_subagent(..., tool_call_id=…)` 记入 transcript 并随行落盘，供回放按唯一锚点规则挂载。

- `toolCalls` 由 `tool_call_start(tool_id)` 建条目、`tool_call_delta(tool_id)` 续 `args`、
  `tool_call(tool_id)` **按 `tool_id`** 闭合为 `done`。旧实现按 `tool_calls[-1]`（最后一条）闭合，
  一次响应里并行 N 个工具调用时前 N-1 条会永久 `running`（实测 session_6 为 6/7，卡片一直转圈）——已修。

- **落盘时机**：transcript 在子智能体任务完成时立即落盘（同步路径在主线程、后台路径由 worker
  线程执行，`_append_lock` 与 agent_loop 的写入不交错）；进程被强杀时至少留有启动占位行。

**旧数据迁移（幂等）**：首次加载某会话时，主 jsonl 里遗留的 `role=subagent` 行会被一次性抽到旁路文件、
主文件重写为纯标准消息，并留 `session_N.jsonl.bak` 快照。旧行中残留的 `running` 工具状态属旧配对 bug
产物，迁移时归一化为 `done`（避免卡片永久转圈）。

**持久化边界（硬约束）**：子智能体记录**只进旁路文件与前端回放展示，绝不进入 LLM 上下文**。三道防线：

1. **边通道**：`_run_subagent` 只把子智能体返回的**摘要**作为 `sub_agent` 工具结果
   回传主上下文；transcript（思考 + 工具过程）按 `tool_call_id` 暂存于
   `_subagent_transcripts`，不 append 进 `history_messages`。
2. **加载过滤**：Agent 初始化 / 切换 / 清空会话时统一 `_strip_subagent_rows()` 剔除可能残留的
   `role=subagent` 行；主会话文件本身已不再产生该行（新数据）。
3. **物理隔离**：`save_session_history`（compact / 自愈重写）**不读也不回写**子智能体记录
   ——旁路文件与之互不影响，消除「重写丢记录 / 重复行」的整类问题。

**生命周期**：`clear` → 删除旁路文件；`delete_session_permanent` → 删除旁路文件；
`trash` / `restore` 只改元数据状态，主 jsonl 与旁路文件均原样保留（还原后切回即可回放）。

### 2.1.2 L2 尾部按需注入（记忆索引 / 环境上下文，前端不可见）

有两块**每轮都可能变**的内容不进 system prompt，而是由 `agent_full_v2` 在变化时往
`history_messages` **尾部追加**一条 user 消息（同一套机制，各块独立判指纹）：

```text
<system-reminder>
<memory_index revision="ab12cd34ef56">
- [name](name.md) — 一行摘要
</memory_index>
</system-reminder>

<system-reminder>
<env revision="57f05c25a829">
当前日期：2026-09-11
星期：周五
运行平台：darwin
</env>
</system-reminder>

（以下块仅在"工作区指令文件于本次会话期间被改动"时出现）
<system-reminder>
<project_rules revision="9f3c1a0b7e42">
工作区指令文件已在本次会话期间变更，以下为**最新版本**；与之冲突时以本条为准。

以下是工作区根目录下的 AGENTS.md 文件内容：
…全文…
</project_rules>
</system-reminder>
```

| 块 | 产生者 | 内容来源 | 变化来源 |
| --- | --- | --- | --- |
| `<memory_index>` | `_sync_memory_index()` | `MemoryStore.read_index()` | `write_memory` / `forget_memory` |
| `<env>` | `_sync_environment()` | `_environment_snapshot()`（**每次现场取值**，不固化） | 跨天；换机器 resume |
| `<project_rules>` | `_sync_project_rules()` | `SystemPromptBuilder.get_workspace_instructions()` | 会话期间 `AGENTS.md` 被编辑（用户手改，或智能体自己写项目记忆） |

**为什么放尾部**：本链路（OpenAI SDK + OpenAI 兼容端点）用**自动前缀缓存**，按最长公共前缀
逐字节命中。改 system message（消息数组的 `[0]`）会让整段前缀失效；在**末尾追加**则只有新增
那一条未缓存 —— 而它本来就是本轮的新内容。把易变内容移出 `[0]` 后，静态段在所有会话间逐字节
相同，可跨会话共享缓存。

**触发规则**：各块以 `sha1(内容)[:12]` 作为指纹写进自己的 `revision` 属性，**按 tag 独立判定**
（`_last_injection_revision(tag)` / `_append_injection(tag, ...)`）。

| 场景 | 行为 |
| --- | --- |
| 会话初始化 / 新建 / 切换 | 扫不到指纹 → 各块注入一次（首轮在用户提问之前） |
| 内容未变 | 指纹相同 → **不注入**（零开销、历史零膨胀） |
| `write_memory` / `forget_memory` 之后 | 下一轮 turn 起点检测到指纹变化 → 追加 `<memory_index>` |
| 跨天 / 换机器 resume | `<env>` 指纹变化 → 追加 `<env>`（通常一天一次） |
| resume 旧会话 | 指纹从**本会话历史**恢复（不存外部状态）→ 不重复、不漏 |
| 会话期间 `AGENTS.md` 被改动 | 指纹 ≠ system prompt 里那份 → 追加 `<project_rules>`（全文，声明以本条为准） |
| 标记被上下文压缩裁掉（snip 只保头 3 + 尾 N） | 扫不到 → 视为未注入 → 自动补注 |

**为什么不把 git 状态放进 `<env>`**：它随每次 commit / 切分支就变，会频繁打断尾部前缀
（缓存杀手）；真需要时让模型跑一条 `git status` 更划算。

**「进会话」与「会话期间」用两套机制**（方案 B / 方案 C），别混：

| | 方案 B · 进会话刷新 | 方案 C · 会话期间尾部注入 |
| --- | --- | --- |
| 触发点 | `init_session` / `switch_session` / `new_session` | 每轮 turn 起点检测到指令文件变更 |
| 手段 | **替换 `messages[0]`**（`_refresh_system_prompt`） | 尾部追加 `<project_rules>`（`_sync_project_rules`） |
| 缓存代价 | 整段前缀（含全部历史）失效一次 | 只有新块未缓存，其余前缀照旧命中 |
| 为何这样选 | 进会话时历史还短，且替换是"纠正错误状态"——文件里那份本就该被换掉 | 会话中途历史已很长，重建 system prompt 太贵 |

> 背景：resume / 切会话时 `load_session_history()` 读回来的 `messages[0]` 是**该会话创建时**那份，
> 会覆盖掉 `build_system_prompt()` 重算的结果 —— 所以在方案 B 之前，"改了 AGENTS.md / 装了新技能
> 当前会话看不到"的根因是**重算了但没替换**，不是没重算。
>
> 方案 B 只改内存、**不写回会话文件**：文件里那份旧的根本不会被使用（每次进会话都重建替换），
> 下次 `save_session_history` 重写时会自然带上新内容 —— 从而避开会话文件的原子重写（无需 `.bak`）。

**前端可见性**：以 `<system-reminder>` 开头 → 被 `_history_to_ui` 过滤，不出现在
`session_history.messages` 里。它**存在于会话 jsonl**（可调试时从
`~/.aigent/projects/<slug>/.chathistory/session_N.jsonl` 直接查看），只是不下发前端。

**退化行为**：若某个端点不做前缀缓存，本机制无收益也无损失（只在内容变化时注入，
不增加总 token 量）。

### 2.2 会话元数据与管理命令

`sessions` / `sessions_trashed` 载荷中的每个条目为**会话元数据 dict**（后端 `index.jsonl` 直出，详见 07 篇）：

```json
{
  "num": 3,
  "title": "分析 goal.py 存储机制",
  "title_source": "auto",
  "status": "active",
  "created_at": "2026-09-08T10:30:00",
  "updated_at": "2026-09-08T10:35:12",
  "trashed_at": null,
  "message_count": 24,
  "file": "session_3.jsonl",
  "model_id": "deepseek-v4",
  "overrides": {
    "deepseek-v4": { "thinking_strength": "very_high", "max_context_option": "extended" }
  }
}
```

- `model_id` / `overrides`：该会话绑定的模型，以及**按模型 id 分别保存**的参数覆盖 map。用户在输入区选模型 / 悬浮配置面板改动时经 `session_model` 写入（每个模型独立，互不串改）；新建会话时由前端在收到 `session` 信封后经 `session_model` 写入。后端 `SessionRuntime` 构造/重载该会话 Agent 时按其 `model_id` 应用模型（env 快照恢复见 07 篇 2.5），每个会话独立绑定。

- `sessions` 只含 `status=active` 的会话（任务树），`sessions_trashed` 只含 `status=trashed`（回收站）。

- 标题自动生成：后端在**首条消息到达时**即并行启动独立小请求生成标题（`title_source=auto`，与 `run_turn` 并发，不等首轮结束），失败降级为首条消息截断（`trunc`）；`title_source=user`（手动重命名）不会被自动标题覆盖。写入后立即通过全量 `sessions` 回发让前端即时刷新（详见 07 篇 2.4）。

- `session_trash` 若删除的是当前激活会话，后端置空会话态（惰性机制下下条 chat 自动新建），前端也应同步切到空态。

- `session_delete` 为批量语义：逐个执行、单条失败不断整批，结果经 `session_delete_result` 回发（前端据此 toast）。**删除成功后后端不再广播全量** **`sessions`**——前端拿到 `deleted[]` 在本地从 `sessions` / `trashSessions` 增量移除被删会话（`session_delete_result` 之后不再有 `_reply_sessions`）。这样删除操作避免「删除 + 重建整张列表（逐个重数 message\_count）」两段全量开销，刷新即时。`trash`（软删除）与 `restore`（还原）仍走全量 `sessions` 回刷，语义不变。

### 2.3 会话级请求覆盖（`chat.overrides`）

`chat` 载荷可带可选 `overrides`，用于**当前会话新一轮请求生效**的思考强度 / 更大上下文。除内存态覆盖（不写 `llmconfig.json`、不影响其它会话）外，会经 `session_model` **持久化进该会话元数据**（按模型 id 分别保存）：每会话独立，切换时按各自元数据恢复，直到再次修改。后端每轮据此 `set_request_overrides()` 设入 Agent 并同步压缩阈值。

> **新建会话继承**（主流智能体行为）：前端把上一会话最后选定的模型（`lastSessionModelId`）与按模型参数覆盖（`lastOverridesByModel`）带入新会话；收到 `session` 信封后经 `session_model` 写入新会话元数据，使新会话默认按「当前会话最后选择的模型与对应参数」执行。

```json
{
  "kind": "chat",
  "payload": {
    "text": "再来一轮",
    "num": 3,
    "model_id": "deepseek-v4",
    "overrides": {
      "thinking_strength": "very_high",
      "max_context": "1M"
    }
  }
}
```

模型绑定字段：

- `model_id`：本次请求绑定并写入新会话元数据的模型 id（`chat` 携带，缺省即不动）；已有会话改模型走 `session_model`。

`overrides` 字段说明：

- `thinking_strength`：思考强度档位，取值来自公共模型元数据 `thinking_strengths`（`low`/`high`/`very_high`）；缺省用全局配置。

- `max_context`：上下文窗口字符串（如 `1M` / `128k`），由前端按「标准/扩展」叠加态换算成具体窗口值随请求带上来；取扩展窗口值（`max_context_extended`），标准则不加该字段（回落全局/默认）。持久化时以 `max_context_option`（`standard`/`extended`）存于元数据。

后端 `ws_bridge` 收到后：`set_request_overrides(reasoning_effort, max_context)` 设入 Agent（思考强度映射为 OpenAI `reasoning_effort`，`low→low / high→high / very_high→max`），并 `session_manager.set_max_context()` 同步 **ContextCompact 压缩阈值**，使压缩触发点与窗口大小一致。元数据写入：新建会话首条 `chat` 只落 `model_id`；参数覆盖（按模型 map）由前端收到 `session` 信封后经 `session_model` 写入——`chat` 的 `overrides` 是已换算的单轮 resolved 形状（`thinking_strength` + 具体窗口串），不直接落元数据；已建会话的参数由 `session_model` 写。

### 2.4 上下文使用量统计（`context_stats`）

后端在**每轮 turn 结束**和**切换会话后**各推送一次，供输入区圆圈指示器按会话展示。它与模型元数据里的窗口上限共同决定「已用/总计」。

```json
{
  "kind": "context_stats",
  "payload": {
    "num": 3,
    "used_tokens": 8450,
    "max_tokens": 128000,
    "used_percent": 6.6,
    "max_label": "128k"
  }
}
```

字段说明：

- `used_tokens` / `max_tokens`：已用与上限（token 数）；`max_tokens` 跟随会话级覆盖（若开启更大上下文，则取模型扩展窗口）；`used_percent` 为百分比。

- `max_label`：展示用标签（如 `128k` / `1M`），直接来自模型元数据 `max_context`（或 `max_context_extended`）。

- 前端 `agentStore` 收到时校验 `num === activeSession`，只更新当前显示会话的指示器；切换会话后按新会话的统计数据刷新。

## 3. 前端协议实现要点

### 3.1 定义一个类型安全的协议文件（`protocols/agentProtocol.ts`）

```ts
export type AgentEvent =
  | { type: 'thinking_delta'; text: string }
  | { type: 'content_delta'; text: string }
  | { type: 'tool_call_start'; tool_id: string; tool_name: string; args: string }
  | { type: 'tool_call_delta'; tool_id: string; tool_name: string; args: string }
  | { type: 'tool_call'; tool_id: string; tool_name: string; args: string }
  | { type: 'turn_end'; finish_reason: string; usage: Record<string, number> };

export interface WsEnvelope { kind: 'event' | 'chat' | ...; payload: unknown; }

export function parseWsLine(raw: string): WsEnvelope {
  return JSON.parse(raw);
}
```

### 3.2 状态聚合逻辑（`useAgentStream.ts`）

收到 `content_delta` 等，往 store 的"当前消息"追加文本。典型 reducer：

```ts
function reduceEvent(state: AgentStore, ev: AgentEvent): AgentStore {
  if (ev.type === 'content_delta') {
    return { ...state, messages: appendToLast(state.messages, ev.text) };
  }
  if (ev.type === 'thinking_delta') {
    return { ...state, messages: appendThinking(state.messages, ev.text) };
  }
  // tool_call_*：展开工具条；turn_end：标记结束
}
```

> 要点：增量事件**不覆盖**，只 append，因此 React 每次仅追加一小段文本，形成打字机效果。

## 4. 主进程 WS 客户端（`agentWS.ts` 职责）

1. 连接 `ws://127.0.0.1:${PORT}`（端口由 Python 写入，或用约定端口并支持 `--port`）。
2. 收到渲染进程 `ipc('agent:send', payload)` → 组 `{kind:'chat',...}` 发给 Python。
3. 收到 Python 事件 → `webContents.send('agent:event', envelope)` 转发给渲染进程。
4. 断线重连（指数退避：1s→2s→4s…封顶 30s），并把连接状态同步给渲染进程。`connect()`
   带重入守卫（已有 socket 不重复建连）；`onclose`/`onerror` 记录 code/reason 诊断日志，
   迟到的旧 socket 关闭事件直接忽略。多连接广播与状态重放语义见 5.2。

## 5. Python 薄桥层设计（`ws_bridge.py`，新增，后端零改动）

```python
"""
ws_bridge.py - 桌面端桥层（新增，不修改 agent_full_v2.py）
把 Agent 变成 WS service：命令进、事件出（走 WSSink 的行协议）。
"""
import asyncio, json
import websockets
from agent_full_v2 import Agent
from streaming_client import WSSink

agent = Agent(silent=True)      # 静音，避免打印干扰
# 惰性会话：启动不 init_session，见下方 chat 分支

async def handler(ws):
    # 把 agent.stream_sink 换成 WSSink，把事件推给当前连接的 ws
    agent.stream_sink = WSSink(send_func=lambda line: ... )  # 发到 ws
    async for raw in ws:
        msg = json.loads(raw)
        kind = msg.get("kind")
        if kind == "chat":
            # 惰性会话：fresh=true（前端新建任务后的首条消息）或后端尚无激活会话时，
            # 先 init_session 新建并回发 session 信封，再跑 run_turn
            if msg["payload"].get("fresh") or agent.session_num is None:
                await asyncio.to_thread(agent.init_session, resume=False)
                await ws.send(...)  # {kind:'session', payload:{num: agent.session_num}}
            await asyncio.to_thread(agent.run_turn, msg["payload"]["text"])
        elif kind == "session_switch":
            await asyncio.to_thread(agent.switch_session, msg["payload"]["num"])
            await ws.send(...)  # {kind:'session_history', payload:{num, messages: _history_to_ui(...)}}
        elif kind == "session_clear":
            await asyncio.to_thread(agent.clear_session)
        elif kind == "goal_status":
            await ws.send(json.dumps({"kind":"event","payload":{"type":"goal_status_data","data":agent.goal_status()},ensure_ascii=False))

async def main():
    async with websockets.serve(handler, "127.0.0.1", 8765):
        await asyncio.Future()

if __name__ == "__main__":
    asyncio.run(main())
```

> 说明：`WSSink` 的 `send_func` 拿到的是序列化好的 JSON 串；桥层负责把它包进 `{kind:'event', payload:...}` 信封发到前端（或在 send\_func 内完成包装）。
> 惰性会话下 `agent.session_manager` 可能为 None：`sessions_list` 等只读操作前由桥层 `_ensure_session_manager()` 兜底构建；`tasks` / `session_clear` 在无激活会话时回占位文本 / error，不触碰 Agent 状态。

### 5.1 事件转发的线程模型（流式实时性的关键）

`run_turn` 经 `asyncio.to_thread` 跑在工作线程，事件从工作线程逐条产出；桥层用
「`asyncio.Queue` + writer 协程」把同步回调转成异步发送：

```python
async def handler(ws):
    loop = asyncio.get_running_loop()
    line_q: asyncio.Queue = asyncio.Queue()

    def send_func(line: str):          # WSSink 在 run_turn 工作线程里调用
        payload = json.loads(line)
        loop.call_soon_threadsafe(line_q.put_nowait, _envelope("event", payload))

    agent.stream_sink = WSSink(send_func=send_func)

    async def writer():                # 事件循环协程：逐条 flush 给前端
        while True:
            line = await line_q.get()
            await ws.send(line)
```

> **铁律：跨线程投递必须走** **`loop.call_soon_threadsafe`。** `asyncio.Queue` 不是线程安全的，
> 从工作线程直接 `put_nowait` 只会 `call_soon` 唤醒 waiter（不写 self-pipe，事件循环不会
> 被唤醒），所有增量事件会积压在队列里，直到 `run_turn` 结束、事件循环因其他原因被唤醒
> 才**一次性刷出**——前端表现即"整段回复（含思考过程）瞬间全部出现，无流式效果"。
> 这是流式链路最容易踩的坑，且各层（WSSink/主进程转发/store）代码看起来都正确。

### 5.2 多连接广播与状态重放（ConnectionHub）

**背景坑**：早期版本 registry 与 deliver 绑死在单个连接上——前端断线重连后，仍在执行的
后台子智能体事件持续流向已被弃用的旧连接 → 前端永久停滞（"连接活着但事件断流"）。

现状为**连接无关的广播层** `ConnectionHub`：

- `register(ws)` 在连接建立时返回该连接专属的 `asyncio.Queue`；`unregister(ws)` 在退出时注销；

- `broadcast(kind, payload)` 把信封放入**所有**活跃连接的队列——会话事件与会话列表广播到
  所有连接，连接断开/重连不影响运行中的会话；

- 每个连接各自的 writer 协程负责 flush，单个连接发送异常只注销自己，不影响其它连接；

- 工作线程（run\_turn / 后台子智能体 / 标题线程）经 `deliver()` →
  `loop.call_soon_threadsafe(hub.broadcast, ...)` 调度回事件循环。

**状态重放**：新连接建立（含断线重连）时，`handle()` 遍历 registry 里所有 `SessionRuntime`，
按 `current_status()` 立即补发 `session_status` 信封，前端据此恢复运行指示（转圈/后台脉冲点）：

| `current_status()` 返回 | 含义                    | 是否补发 |
| --------------------- | --------------------- | ---- |
| `"running"`           | turn 执行中（`busy=True`） | 是    |
| `"background"`        | turn 已结束但后台任务仍在跑      | 是    |
| `None`                | 空闲                    | 不发   |

**`status_query`** **命令（渲染进程刷新补偿）**：连接级重放只覆盖"主进程 WS 重连"场景；
**渲染进程刷新（Vite HMR / Cmd+R）不重建主进程 WS 连接**，后端无从得知前端丢了内存态
（`runningSessions` / `bgSessions` / `connection` 全部清零）。历史 bug：刷新后子智能体仍在
后台执行、事件流仍在到达（消息内容继续更新），但运行指示与停止按钮永久消失，且用户再次发消息
会被后端以"会话正在执行"拒绝——即"执行状态断了"。补偿链路：

1. 渲染进程挂载时 `getConnectionStatus()`（IPC）恢复连接态（`agent:status` 是变化驱动，
   不补发当前值）；
2. `connection === 'connected'` 时（首次/每次重连）调 `window.agent.queryStatus()` →
   主进程发 `{"kind": "status_query"}` → 后端把 `_status_snapshot_lines()`（与连接级重放
   共用同一快照函数）经该连接的 writer 队列回发 → 前端重新点亮运行指示。幂等：重放与
   query 的信封形状一致，前端 `addUnique`/filter 合并，重复无害。

> 历史坑：重放循环上线时漏写了 `SessionRuntime.current_status()` 方法——任何会话开启过
> 对话（registry 非空）后，**每个新 WS 连接都会在握手阶段 AttributeError 直接断开**，前端
> 表现为"对话开始后就一直后端未连接"。同理，`_start_title_thread` 改为广播制后调用点仍按
> 旧签名传 `ws`，chat 命令一进入就 TypeError 断连。两处均已修复；新增调用点时务必与
> 当前签名对齐，并让 `handle()` 内的异常尽早暴露。

### 5.3 后端关键节点日志（排查"执行状态断了"的对照手册）

后端所有关键节点直接打在 stdout（Electron 终端可见，`python -u` 无缓冲）。排查前端状态
异常时按时间序对照以下日志即可定位断点在哪一层：

| 日志                                                       | 打点位置                          | 含义                                                |
| -------------------------------------------------------- | ----------------------------- | ------------------------------------------------- |
| `[ws_bridge] WS server listening on 127.0.0.1:8765`      | `main()`                      | 后端就绪（该行**只出现一次**；重复出现 = pythonManager 双打印 bug，已修） |
| `[ws] connection opened/closed: addr (active=N)`         | `handle()`                    | 连接生命周期，`active` 为当前活跃连接数                          |
| `[ws] replay N running session status(es)`               | `handle()`                    | 新连接建立时的状态重放                                       |
| `[ws] status_query -> N running session(s)`              | `handle()`                    | 前端主动拉取运行状态（渲染进程刷新补偿）                              |
| `[ws_bridge] new session -> session_N`                   | chat 分支                       | 惰性领号新建会话                                          |
| `[ws_bridge] chat -> session_N: 'text…'`                 | chat 分支                       | 对话命令派发                                            |
| `[ws_bridge] stop -> session_N`                          | stop 分支                       | 停止命令                                              |
| `[session N] status -> running/background/done/stopped`  | `SessionRuntime._push_status` | **会话状态机的每一次翻转（前端指示的唯一驱动源）**                       |
| `[session N] agent built (model=M)` / `rebinding model…` | `build_agent()`               | 会话 Agent 首建 / 模型换绑                                |
| `[session N] turn end (Xs, done, bg_running=True/False)` | `start_turn` finally          | turn 收尾（耗时 + 是否有后台任务残留）                           |
| `[session N] bg watch start/done/cancelled`              | `_watch_background`           | 后台任务守望生命周期（done 后补发 `done` 状态）                    |
| `[session N] turn worker crashed: …`                     | `start_turn` except           | run\_turn 线程未捕获异常（状态按 done 回）                     |
| `[background] dispatched bg_XXXX: cmd`                   | `start_background_task`       | 后台任务派发                                            |
| `[background] completed bg_XXXX (X.Xs): cmd`             | worker 完成时                    | 后台任务**真正执行完**（区别于"结果注入主循环"）                       |
| `[background done] bg_XXXX: …`                           | `collect_background_results`  | 结果注入主循环通知                                         |
| `[subagent] 开始执行任务 / 结束 (X.Xs)`                          | `spawn_subagent`              | 子智能体生命周期（前台后台都走这里）                                |
| `[ws] writer died (addr): …`                             | writer 协程                     | 该连接发送管道异常（只注销自己，不影响其它连接）                          |

**前端（Electron 主进程）日志**同样打在终端：`[agentWS] connected`（连上）、
`[agentWS] onclose: code=… (python bridge not ready yet, will retry)`（首连失败是启动期
正常现象——Python 还在 import、端口未 listen，Connection refused 必然出现一次，已标注
避免误读为断连故障）、`[python] 退出 code=…`（后端进程退出）。

> pythonManager 历史坑：stdout 曾挂两个监听器（统一打印 + readyProbe 内又打一次），
> 导致 "WS server listening" 每次出现**两行**，排查时误判为拉起了两个后端进程。readyProbe
> 已改为只探测不打印。

### 6.1 纯浏览器预览回退（`renderer/src/lib/browserAgent.ts`）

dev 模式下渲染页可脱离 Electron 在普通浏览器直接打开（vite dev server，如 IDE 预览窗格），
此时 **preload 不存在、`window.agent`** **为 undefined**：发消息会抛
`TypeError: Cannot read properties of undefined (reading 'send')`，且连接状态永远"未连接"
（`useAgentStream` 的订阅被 preload 缺失守卫静默跳过）。

为此渲染层入口（`main.tsx`，React 挂载之前）调用 `installBrowserAgent()` 安装**回退桥**：

- 仅当 `window.agent` 不存在时安装；Electron 内 preload 先于渲染层脚本运行，自动跳过，行为不变；

- `BrowserAgentBridge` 实现与 preload 完全相同的 `AgentApi`（类型直接取
  `typeof window.agent`，防止两处形状漂移），但把命令按同一 WS 信封协议**直连**
  `ws://127.0.0.1:${VITE_AGENT_WS_PORT || 8765}` 发往后端 `ws_bridge`；

- 连接管理复刻主进程 `agentWS.ts`：指数退避重连（1s→30s 封顶）、断线命令排队补发、
  重入守卫防僵尸连接；`onopen` 即视为 Python 后端存活（上报 `python: running`）；

- 请求-响应型命令（sessions\_list / trash\_list / goal\_status / tasks / skills /
  llm\_config\_get / llm\_config\_save / llm\_models\_fetch / session\_rename / trash / restore / delete）按
  **应答信封 kind** 匹配 resolve（默认 5s 超时回 null；`llm_models_fetch` 单独放宽到 30s，
  与主进程 `agent:llmModelsFetch` 一致）；chat / stop / session\_model /
  session\_switch 等命令类 fire-and-forget（结果由流式/广播事件驱动）；

- 所有收到的信封（含应答类）都上行给 `onEvent` 订阅者，与主进程转发行为一致，store 的
  事件处理无需区分两种模式。

> 注意：浏览器直连意味着后端 `ws_bridge`（`websockets.serve` 默认不校验 Origin）接受任意
> 本机浏览器页面的连接——仅限本地开发使用，生产构建不存在该路径。
