# 03 - 前后端通信协议（对接 WSSink）

本设计复用后端 `agents/streaming_client.py` 已就绪的 **JSON 行协议（`StreamEvent.to_json()`）**，
并在 Python 侧新增一个**薄桥层** **`ws_bridge.py`**（属"新增"，不改业务代码），把 WebSocket 客户端
（Electron 主进程）的命令翻译成 `Agent` 方法调用，再把流式事件经 `WSSink` 推回前端。

> 后端铁律：只新增 `ws_bridge.py` 这一个薄层，`agent_full_v2.py` 及以下**零改动**。
> 唯一替换点是 `Agent.stream_sink = WSSink(send_func=ws.send)`。

***

## 1. 双层消息模型

在同一 WebSocket 上，用 `kind` 区分两类消息：

| kind                    | 方向    | 说明                               | 载荷字段                                           |
| ----------------------- | ----- | -------------------------------- | ---------------------------------------------- |
| `event`                 | 后端→前端 | 流式事件（透传 `StreamEvent.to_dict()`） | `type/text/tool_*/finish_reason/usage`         |
| `chat`                  | 前端→后端 | 发起一次对话                           | `text` / `fresh?`（`fresh=true` 表示无激活会话，后端惰性新建） |
| `session`               | 后端→前端 | 激活会话变更通知（惰性新建/清空后）               | `num` / `message_count`                        |
| `session_history`       | 后端→前端 | 会话历史回放（切换会话后）                    | `num` / `messages[]`                           |
| `session_switch`        | 前端→后端 | 切换会话                             | `num`                                          |
| `session_clear`         | 前端→后端 | 清空会话                             | `—`                                            |
| `sessions_list`         | 前端→后端 | 拉取会话列表                           | `—`                                            |
| `sessions`              | 后端→前端 | 会话列表（列表拉取/会话变更后下发，含元数据）          | `sessions[]`                                   |
| `session_rename`        | 前端→后端 | 重命名会话                            | `num` / `title`                                |
| `session_trash`         | 前端→后端 | 软删除会话（移入回收站）                     | `num`                                          |
| `session_restore`       | 前端→后端 | 从回收站还原会话                         | `num`                                          |
| `session_delete`        | 前端→后端 | 批量永久删除会话                         | `nums[]`                                       |
| `trash_list`            | 前端→后端 | 拉取回收站列表                          | `—`                                            |
| `sessions_trashed`      | 后端→前端 | 回收站列表（trash\_list 的响应）           | `sessions[]`                                   |
| `session_delete_result` | 后端→前端 | 批量永久删除结果                         | `deleted[]` / `failed[]`                       |
| `goal_status`           | 前端→后端 | 查询目标状态                           | `—`                                            |
| `tasks`                 | 前端→后端 | 拉取待办看板文本                         | `—`                                            |
| `skills`                | 前端→后端 | 拉取技能列表                           | `—`                                            |
| `pong` / `error`        | 双向    | 心跳 / 错误                          | `msg`                                          |

> **惰性会话（重要语义变更）**：`session_new` 命令已移除。"新建任务"是**纯前端行为**
> （清空消息流、`activeSession=null`）；后端会话 `session_N.jsonl` 只在两种时机产生/加载：
>
> 1. 首条 `chat` 消息（`fresh=true` 或后端无激活会话）→ 惰性 `init_session` 新建；
> 2. 用户点击会话列表 → `session_switch` 加载既有会话。
>    后端启动（ws\_bridge 进程拉起）**不再**创建会话，避免"每次打开窗口都多一个空 jsonl"。

统一信封格式（JSON）：

```json
{ "kind": "chat",    "payload": { "text": "帮我分析 goal.py" } }
{ "kind": "event",   "payload": { ...StreamEvent.to_dict()... } }
```

## 2. 事件线协议（后端 → 前端）

前端按 WS 收到的每一行 JSON 解析，`kind == "event"` 时还原为 UI 动作。
事件类型与后端 `StreamEvent` 一一对应，**这是打字机回显的唯一数据来源**。

| type              | 含义          | 前端渲染                              |
| ----------------- | ----------- | --------------------------------- |
| `thinking_delta`  | 思考增量        | 追加到当前 assistant 消息的 thinking 区（灰） |
| `content_delta`   | 正文增量        | 追加到 assistant 正文（打字机）             |
| `tool_call_start` | 工具名出现，预测式展示 | 新建工具折叠条：`⚙ 名称(`                   |
| `tool_call_delta` | 参数增量        | 续写参数文本                            |
| `tool_call`       | 工具调用聚合完成    | 闭合折叠条，标注状态                        |
| `turn_end`        | 回合结束        | 停止光标、显示 usage、解锁输入                |

一个完整事件 JSON 示例（来自 `StreamEvent.to_dict`）：

```json
{
  "type": "content_delta",
  "text": "经分析，goal.py 的存储机制是…",
  "tool_id": "",
  "tool_name": "",
  "args": "",
  "finish_reason": "",
  "usage": {}
}
```

### 2.1 会话历史回放（`session_history`）

`session_switch` 成功后由桥层下发，前端整体替换消息流渲染。`messages[]` 为后端
session jsonl 历史经 `_history_to_ui()` 转换后的产物：

- 跳过 `system` / `tool` 消息（前者无展示价值，后者聚合进 assistant 工具条）；

- 跳过系统注入的 user 消息（`<system-reminder>` 开头的 todo reminder 等）；

- assistant 保留 `reasoning_content` → `thinking`、`tool_calls` → `toolCalls`（已完成态）；

- `content` 兼容 str 与多模态 blocks（list 时拼接 text 块）。

```json
{
  "kind": "session_history",
  "payload": {
    "num": 3,
    "messages": [
      { "role": "user", "content": "帮我分析 goal.py" },
      { "role": "assistant", "content": "…", "thinking": "…",
        "toolCalls": [{ "name": "run_bash", "args": "{\"cmd\":\"ls\"}" }] }
    ]
  }
}
```

### 2.2 会话元数据与管理命令

`sessions` / `sessions_trashed` 载荷中的每个条目为**会话元数据 dict**（后端 `index.jsonl` 直出，详见 07 篇）：

```json
{
  "num": 3,
  "title": "分析 goal.py 存储机制",
  "title_source": "auto",
  "status": "active",
  "created_at": "2026-09-08T10:30:00",
  "updated_at": "2026-09-08T10:35:12",
  "trashed_at": null,
  "message_count": 24,
  "file": "session_3.jsonl"
}
```

- `sessions` 只含 `status=active` 的会话（任务树），`sessions_trashed` 只含 `status=trashed`（回收站）。

- 标题自动生成：后端在**首条消息到达时**即并行启动独立小请求生成标题（`title_source=auto`，与 `run_turn` 并发，不等首轮结束），失败降级为首条消息截断（`trunc`）；`title_source=user`（手动重命名）不会被自动标题覆盖。写入后立即通过全量 `sessions` 回发让前端即时刷新（详见 07 篇 2.4）。

- `session_trash` 若删除的是当前激活会话，后端置空会话态（惰性机制下下条 chat 自动新建），前端也应同步切到空态。

- `session_delete` 为批量语义：逐个执行、单条失败不断整批，结果经 `session_delete_result` 回发（前端据此 toast）。

## 3. 前端协议实现要点

### 3.1 定义一个类型安全的协议文件（`protocols/agentProtocol.ts`）

```ts
export type AgentEvent =
  | { type: 'thinking_delta'; text: string }
  | { type: 'content_delta'; text: string }
  | { type: 'tool_call_start'; tool_id: string; tool_name: string; args: string }
  | { type: 'tool_call_delta'; tool_id: string; tool_name: string; args: string }
  | { type: 'tool_call'; tool_id: string; tool_name: string; args: string }
  | { type: 'turn_end'; finish_reason: string; usage: Record<string, number> };

export interface WsEnvelope { kind: 'event' | 'chat' | ...; payload: unknown; }

export function parseWsLine(raw: string): WsEnvelope {
  return JSON.parse(raw);
}
```

### 3.2 状态聚合逻辑（`useAgentStream.ts`）

收到 `content_delta` 等，往 store 的"当前消息"追加文本。典型 reducer：

```ts
function reduceEvent(state: AgentStore, ev: AgentEvent): AgentStore {
  if (ev.type === 'content_delta') {
    return { ...state, messages: appendToLast(state.messages, ev.text) };
  }
  if (ev.type === 'thinking_delta') {
    return { ...state, messages: appendThinking(state.messages, ev.text) };
  }
  // tool_call_*：展开工具条；turn_end：标记结束
}
```

> 要点：增量事件**不覆盖**，只 append，因此 React 每次仅追加一小段文本，形成打字机效果。

## 4. 主进程 WS 客户端（`agentWS.ts` 职责）

1. 连接 `ws://127.0.0.1:${PORT}`（端口由 Python 写入，或用约定端口并支持 `--port`）。
2. 收到渲染进程 `ipc('agent:send', payload)` → 组 `{kind:'chat',...}` 发给 Python。
3. 收到 Python 事件 → `webContents.send('agent:event', envelope)` 转发给渲染进程。
4. 断线重连（指数退避：1s→2s→4s…封顶 30s），并把连接状态同步给渲染进程。

***

## 5. Python 薄桥层设计（`ws_bridge.py`，新增，后端零改动）

```python
"""
ws_bridge.py - 桌面端桥层（新增，不修改 agent_full_v2.py）
把 Agent 变成 WS service：命令进、事件出（走 WSSink 的行协议）。
"""
import asyncio, json
import websockets
from agent_full_v2 import Agent
from streaming_client import WSSink

agent = Agent(silent=True)      # 静音，避免打印干扰
# 惰性会话：启动不 init_session，见下方 chat 分支

async def handler(ws):
    # 把 agent.stream_sink 换成 WSSink，把事件推给当前连接的 ws
    agent.stream_sink = WSSink(send_func=lambda line: ... )  # 发到 ws
    async for raw in ws:
        msg = json.loads(raw)
        kind = msg.get("kind")
        if kind == "chat":
            # 惰性会话：fresh=true（前端新建任务后的首条消息）或后端尚无激活会话时，
            # 先 init_session 新建并回发 session 信封，再跑 run_turn
            if msg["payload"].get("fresh") or agent.session_num is None:
                await asyncio.to_thread(agent.init_session, resume=False)
                await ws.send(...)  # {kind:'session', payload:{num: agent.session_num}}
            await asyncio.to_thread(agent.run_turn, msg["payload"]["text"])
        elif kind == "session_switch":
            await asyncio.to_thread(agent.switch_session, msg["payload"]["num"])
            await ws.send(...)  # {kind:'session_history', payload:{num, messages: _history_to_ui(...)}}
        elif kind == "session_clear":
            await asyncio.to_thread(agent.clear_session)
        elif kind == "goal_status":
            await ws.send(json.dumps({"kind":"event","payload":{"type":"goal_status_data","data":agent.goal_status()},ensure_ascii=False))

async def main():
    async with websockets.serve(handler, "127.0.0.1", 8765):
        await asyncio.Future()

if __name__ == "__main__":
    asyncio.run(main())
```

> 说明：`WSSink` 的 `send_func` 拿到的是序列化好的 JSON 串；桥层负责把它包进 `{kind:'event', payload:...}` 信封发到前端（或在 send\_func 内完成包装）。
> 惰性会话下 `agent.session_manager` 可能为 None：`sessions_list` 等只读操作前由桥层 `_ensure_session_manager()` 兜底构建；`tasks` / `session_clear` 在无激活会话时回占位文本 / error，不触碰 Agent 状态。

## 6. IPC 通道清单（渲染进程 ⇄ 主进程）

| 通道                                                | 方向   | payload          | 用途                           |
| ------------------------------------------------- | ---- | ---------------- | ---------------------------- |
| `ipcRenderer.invoke('agent:send')`                | 渲染→主 | `{text, fresh?}` | 发送对话（`fresh=true` 触发后端惰性建会话） |
| `renderer.on('agent:event')`                      | 主→渲染 | `WsEnvelope`     | 收到后端事件                       |
| `invoke('agent:switchSession')` / `clearSession`  | 渲染→主 | `{num}?`         | 会话操作（新建任务不走 IPC，纯前端态）        |
| `invoke('agent:listSessions')`                    | 渲染→主 | —                | 拉任务列表                        |
| `invoke('agent:goalStatus')` / `tasks` / `skills` | 渲染→主 | —                | 状态类查询                        |
| `invoke('agent:connectionStatus')`                | 渲染→主 | —                | 查询连接状态                       |

渲染层通过 preload 暴露的安全封装使用（不透出原始 ipc）。

## 7. 协议版本与演进

- 事件类型以后端 `StreamEvent.type` 为准；前端解析未知 type 时**忽略并告警**，保证前后端版本兼容。

- 新增命令（模型、历史等）走增量式扩展：WS 加一个 `kind`，前端加一个分支即可，不断裂已有流程。
